# Spec:DTS 列表逐单分支匹配——分支列、未配置禁发起、退役产品版本选择框

> to-spec 草稿,待发布到 GitHub issues(发布时加 `ready-for-agent` 标签)。
> 设计出处:grill-with-docs 会话(2026-09-17),决策记录见 ADR-0038 与 CONTEXT.md 词条「分支匹配」。

## Problem Statement

开发责任人在 DTS 列表发起问题会话时,决定"按哪个分支拉代码"的是列表上方一个全局的「产品版本」选择框:批量发起前先选一个版本,这批单就统一按它带出的分支走。但每张 DTS 单据的版本号本就各自携带版本事实,同一批单据版本常常并不相同——全局选择在混合版本的批次里既冗余又可能选错;而配置中心里的版本→分支映射早已存在,却没有在列表上逐单呈现,发起者看不到每个单子会落在哪个分支。另外两处静默兜底(单据版本没匹配到配置就沿用原基线;配置的分支在仓里不存在就退回默认分支继续干)会让修复在无人察觉的情况下跑在错误的分支上。

## Solution

DTS 列表每个单子的分支由它自己的版本号推导:单据版本字符串**包含**配置中心配置的某个产品版本即命中(多命中取最长),列表新增「分支」列逐单显示;未命中显示「未配置分支,前往配置」,点击直达配置中心的「版本与分支」页签,并且该行禁止发起(前端禁勾选、后端硬拒绝)。列表上方的全局产品版本选择框退役。配置的分支在远端仓里不存在时,拉仓直接失败并如实报告,不再悄悄换默认分支。手工登记与需求侧发起的选择框不在此列。

## User Stories

1. 作为开发责任人,我想在 DTS 列表直接看到每张单对应的分支,以便发起前就知道修复会落在哪条版本线上。
2. 作为开发责任人,当单据版本没有配置对应分支时,我想在分支列看到「未配置分支,前往配置」并能一键跳到配置中心的版本与分支页签,以便立刻补配置而不用自己找入口。
3. 作为开发责任人,我想让未配置分支的单子无法勾选发起,以便不会无意中把修复跑在未知的分支上。
4. 作为开发责任人,我想让批量全选自动跳过未配置分支的单子,以便不用手工逐一剔除。
5. 作为开发责任人,当后端拒绝发起时,我想看到明确的「未配置分支」错误而不是静默换轨,以便知道该去补哪条配置。
6. 作为开发责任人,我想让发起后的会话固定使用发起时刻解析出的分支,以便配置后续变更不影响已在进行中的修复。
7. 作为开发责任人,当配置的分支在远端仓里已被删除时,我想让拉仓直接失败并明确报告「基线分支不存在」,以便不悄悄在默认分支上改代码。
8. 作为开发责任人,我想让 AI 在拉仓失败时把分支缺失如实报出来并停在该阶段,以便我修好配置或分支后重试。
9. 作为配置中心维护者,我想继续在唯一的「版本与分支」页签维护版本→分支映射,以便一处配置同时服务问题侧与需求侧。
10. 作为配置中心维护者,我想让配置项只需维护版本组形态(如 V100R025C10SPC010)而不必逐 B 版构建号枚举,以便配置量最小。
11. 作为团队管理者,我想让分支推导只有一个后端实现口径,以便列表显示与实际拉取永不漂移。
12. 作为开发责任人,我想移除 DTS 列表上方的产品版本选择框,以便少一个可能与逐单分支冲突的全局选项。
13. 作为测试(登记人),我在手工登记时仍可选产品版本带出分支,以便无单登记不受本次改动影响。
14. 作为需求交付用户,需求侧发起的产品版本选择保持原样,以便另一条流程零感知。
15. 作为 AI 修复 Agent,我拉仓时拿到确定的基线分支,以便工作分支与 MR 都落在正确的版本线上。
16. 作为 AI 修复 Agent,当基线分支缺失时我收到失败事实而不是被平台悄悄换轨,以便如实上报而不是在错误分支上产出。
17. 作为开发责任人,已发起的单子仍按「已发起」禁发起并默认滤出列表,以便分支列不与发起状态语义混淆。
18. 作为开发责任人,配置修改后刷新列表即可看到分支列更新,以便所见即所配。
19. 作为开发责任人,当单据版本同时包含多个配置版本时,我想按最长命中取分支,以便更具体的配置赢。
20. 作为开发责任人,我想让配置中心对非法分支名的拒绝照旧生效,以便坏配置进不了匹配。

## Implementation Decisions

- **匹配口径(ADR-0038)**:单据版本字符串大小写敏感地**包含**配置中心某个产品版本即命中;多命中取配置版本字符串最长者。配置中心配版本组形态(剥掉 B 版构建号)即可命中带 B 段的单据版本。
- **真相源单点**:匹配只在后端实现。DTS 列表 API 逐单带出解析后的分支(未命中缺省);发起时后端按同一口径再解析一次,解析结果快照为会话基线(既有快照机制不变)。前端分支列纯展示:命中显示分支名,未命中渲染「未配置分支,前往配置」深链到 `/configuration?tab=versions`。
- **禁发起双闸**:前端未命中行禁勾选(与「已发起」同款先例,全选只作用于可勾行);后端对 dts 来源、版本未命中的 create 请求硬拒绝并报「未配置分支」,废除"未匹配沿用原基线"的兜底,DTS 列表上方选择框及其说明文案一并移除。
- **拉仓硬失败**:基线分支在远端仓不存在时,pull_repo 返回失败事实(与普通克隆失败同型),不再退回默认分支继续;AI 把「基线分支不存在」报出来,会话停在拉仓阶段。原 baselineMiss 的降级语义反转。不做发起时的远端分支预检(不为它新增 ls-remote 机制)。
- **显示与执行的时点纪律**:分支列按当前配置现算;会话执行用发起时刻的快照——发起后改配置不追溯进行中会话,与环境快照同一纪律。
- **移除范围**:仅 DTS 列表页签上方的产品版本选择框。手工登记表单与需求侧发起页的同款选择框保留——它们没有单据版本号可推导,全局选择仍是唯一入口;无单(自研)会话不在本需求管辖内。
- **文档**:决策与理由记 ADR-0038,术语记 CONTEXT.md 词条「分支匹配」(与「版本组」互为邻接)。

## Testing Decisions

- 好测试只断言外部行为:HTTP 请求/响应、工具回执事实、用户可见的界面契约;不测内部函数拆分。
- 三个既有测试缝,不开新缝:
  1. **HTTP API 缝(最高缝)**:服务级起服打路由——配置两个互为包含的版本验证最长命中;未配置版本验证列表分支缺省与 create 硬拒绝;显式携带产品版本的 create(手工登记路径)不受影响。先例:`tests/issueFlowContract.test.ts`、`tests/configurationCenter.test.ts` 的服务级 HTTP 测试。
  2. **拉仓行为缝**:临时 bare 仓造"配置的分支不存在"场景,断言失败事实、无默认分支降级。先例:`tests/issueFlowFixed.part2.test.ts` 的 git 行为测试。
  3. **UI 源码契约缝**:断言分支列表头、「未配置分支,前往配置」深链、未命中行禁勾选、产品版本选择框在 DTS 列表退役;同步改写既有两例受影响断言(版本列漏斗契约、发起状态列契约)。先例:`tests/issueUiContracts.test.ts`。
- 按仓库测试纪律点名跑受影响套件,不做全量回归。

## Out of Scope

- 手工登记表单与需求侧发起页的产品版本选择框(原样保留)。
- 发起时的远端分支预检(不加 ls-remote)。
- 分支列的过滤与排序。
- 配置中心「版本与分支」维护页的结构改动(映射维护已存在,原样复用)。
- 已发起会话的分支展示改用会话快照(维持现算口径)。
- 无单/自研会话的基线处理(现状不动)。

## Further Notes

- 调试形态的罐头单据版本形如 V100R025C10SPC010B009,本机验收前需在配置中心种一条对应版本组的映射,分支列才有命中可看。
- 拉仓降级的原有注释语义("缺失不炸——如实报后退回默认分支")随硬失败一并改写,避免注释与行为相反。
- 历史已发起会话不受影响:基线快照存于会话,配置与列表怎么改都不追溯。
