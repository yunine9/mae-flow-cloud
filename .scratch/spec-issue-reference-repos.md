# Spec:问题会话参考仓——模块订阅公共组件仓、按需拉取只读参考件、取消仓数量上限

> to-spec 草稿,已发布:[yunine9/mae-flow-cloud#420](https://github.com/yunine9/mae-flow-cloud/issues/420)(`ready-for-agent`)。
> 设计出处:grill-with-docs 会话(2026-09-23),决策记录见 ADR-0054 与 CONTEXT.md 词条「参考仓」「公共组件仓目录」(均已落盘)。

## Problem Statement

定位问题深入后,经常发现要参考公共组件/公共库的源码才能改对问题——比如业务仓里 import 了公司公共组件库,不看它的源码就不知道接口契约和坑。但问题会话现在只有模块预绑的那几个仓:AI 不知道公共仓的地址,只能每次口头问用户要,闭环卡在人身上。就算有了地址,拉进来也算「关联仓」——彼此平等、可改可交付,而公共组件是跨模块共享资产,不该被一纸问题单顺手改掉。另外,会话里拉过哪些仓、知识仓装没装,人只有翻过程记录才能看到。最后,仓数量上限 8 是个无论证的防御性数字,绑定仓多的模块再补仓就会被它卡住。

## Solution

组件仓库表(组件知识研究线既有的公共构建块清单)成为公共仓的唯一维护处。业务模块新增「参考组件仓」配置:从登记表条目中多选订阅,存引用不抄地址。问题会话开场只把**本模块订阅条目**的名称、地址、「何时需要读取」描述注入上下文(skill 描述同款机制);不依赖公共组件的模块零注入、零污染。AI 按描述自行决定,照抄地址调拉仓工具;宿主发现地址命中登记表,就把它记入参考仓台账而不是登记清单——目录照常落地可随便读,但推送、MR 等交付工具只认登记清单,参考仓在结构上够不着(与知识仓同一套已验证机制)。界面仓卡片出四类身份徽标(模块绑定/用户指派/参考仓·只读/知识仓·只读),拉过什么一目了然。仓数量上限整体取消。

## User Stories

1. 作为 AI 修复 Agent,我想在会话上下文里永久看到本模块订阅的公共组件目录(名称、地址、何时需要读取的描述),以便定位到公共组件相关问题时自主决定拉哪个仓,不用等用户喂地址。
2. 作为 AI 修复 Agent,我想让拉取公共仓的动作与拉业务仓是同一个工具(照抄地址调用),以便不学新机制。
3. 作为 AI 修复 Agent,当拉仓回执标明「参考仓·只读」时,我想立刻知道这个仓可研读不可交付,以便把功夫花在读源码上而不是改它。
4. 作为 AI 修复 Agent,当我判断某个参考仓其实无关时,我想用摘仓工具把它移出台账,以便会话账面干净。
5. 作为 AI 修复 Agent,我想让参考仓目录照常落在会话工作区里可自由研读,以便正常 grep、看历史、追调用链。
6. 作为模块责任人,我想在编辑模块时从已维护的组件仓清单里多选「参考组件仓」,以便声明本模块依赖哪些公共组件,而不必自己抄写仓地址。
7. 作为模块责任人,当登记表里的条目地址变更时,我想让我的模块订阅自动跟着走(存引用不抄地址),以便地址维护只发生在一处。
8. 作为模块责任人,当我的模块不依赖任何公共组件时,我想让会话上下文里完全不出现组件目录,以便不被无关内容污染。
9. 作为模块责任人,当我在模块里引用了已被删除或停用的登记表条目时,我想在模块配置页看到「已失效」标注,以便知道该清理订阅了。
10. 作为配置中心维护者,我只想在组件仓库表一处维护名称、地址与「何时需要读取」描述,以便一张表同时服务组件知识研究与问题流两条线。
11. 作为配置中心维护者,我想让描述字段的填写指引说明「写何时需要读取,问题会话的 AI 据此决定是否拉取」,以便描述写出来对 AI 真的有用。
12. 作为开发责任人(会话发起人),我想让开场只注入本模块订阅的组件描述,以便上下文里没有用不上的东西。
13. 作为开发责任人,手工登记未选模块时,我想让会话不注入任何组件目录,以便无单会话保持干净。
14. 作为开发责任人,我想在会话详情的仓卡片上看到四类身份徽标(模块绑定/用户指派/参考仓·只读/知识仓·只读),以便一眼看清这个会话拉过哪些仓、各自是什么身份。
15. 作为开发责任人,我想让知识仓也以卡片形式陈列(而不是只躺在过程记录里),以便确认它装没装、装的是哪个仓。
16. 作为开发责任人,当 AI 误拉了参考仓时,我想让事件流记录这次拉取与摘除,以便审计会话里发生过什么。
17. 作为开发责任人,我想让仓数量上限彻底取消,以便绑定仓多或参考仓多的会话不被一个无论证的数字卡住。
18. 作为开发责任人,当用户在元信息页签指派一个公共仓地址时,我想让它按用户意志成为平等关联仓(可改可交付),以便「改共享资产」的决定保留人的记录。
19. 作为开发责任人,当 AI 拉取的地址命中登记表但模块没订阅它时,我想让它仍判为参考仓,以便仓的身份不随模块视野漂移。
20. 作为评审人,我想让参考仓在结构上不可能被推送或提 MR(而不是靠提示词自觉),以便公共组件不被问题单顺手改掉。
21. 作为团队管理者,我想让参考仓身份在会话全生命周期不变(无原地升级按钮),以便要改公共组件永远走用户指派这道人工。
22. 作为测试/维护者,我想在调试形态就能自测参考仓全链路(镜像播种、本地地址注入、拉取、徽标),以便不依赖内网环境验证。
23. 作为 AI 修复 Agent,我想让拉仓阶段的验收口径维持「绑定仓拉齐」不变,以便参考仓按需拉取不干扰既有阶段节奏。
24. 作为开发责任人,我想让参考仓与知识仓随工作区终态一起回收,以便会话现场不残留只读件的磁盘占用。

## Implementation Decisions

- **目录与订阅(ADR-0054)**:组件仓库表是公共仓唯一维护处(名称、地址、描述)。业务模块新增「参考组件仓」字段:从登记表条目多选,存条目引用(不抄地址),模块保存时拒绝引用不存在的条目;条目事后被删/停用时模块配置页标「已失效」、注入时跳过。模块编辑对话框的参考组件仓为多选选择器,选项来自登记表启用行。
- **订阅管注入,目录管身份**:会话开场组装只注入本模块订阅条目的名称、地址、描述(无订阅或无模块则整节省略);拉取时的身份判定只看地址是否命中登记表启用行——命中即参考仓,与是否订阅无关,身份不随模块视野漂移。订阅解析在开场组装时刻快照,会话进行中改模块订阅不追溯。
- **身份判定优先级**:拉取时——地址在模块绑定仓或已在登记清单 → 平等关联仓(现状不变);否则命中登记表启用行 → 参考仓台账;都未命中 → 平等关联仓(现状:用户口头给的地址就是平等仓)。用户意志(绑定/指派)永远压过登记表。
- **台账隔离的结构只读**:参考仓记入独立台账、不进登记清单;目录照常平铺落地可研读,但交付工具只认登记清单,参考仓推不了、交不了(与知识仓同款机制,零新增门禁)。不做文件系统只读锁(shell 可绕,假保证);不设原地改身份通道(真要改公共仓,用户按普通地址重新指派一次,指派后重新拉取即转为平等关联仓);摘仓工具移除参考仓台账行并物理删工作区目录(与登记仓同款账实一致)。
- **可见性**:会话详情仓卡片按身份出四类徽标——模块绑定/用户指派/参考仓(只读)/知识仓(只读);知识仓从只出现在过程记录升为独立卡片;元信息页签同口径分组。
- **取消数量上限**:仓数量常量及其三处同尺校验(工具门禁、指派仓端点、元信息页签前端预判)一并删除,修订 ADR-0023 的对应条款;端点保留 https 限定、归一去重、模块绑定仓拒删、终态守卫。不设替代护栏。
- **目录名占用**:参考仓与登记仓、知识仓共用同一套仓名派生,目录名占用集合三者合并,防止同仓名互相覆盖。
- **调试形态**:启动播种顺带为登记表启用行建 bare 镜像(超集),示例模块订阅其中若干;注入目录时地址替换为本地镜像路径。
- **提示词**:开场契约改为「绑定仓逐个拉;订阅的公共组件按描述按需拉,参考仓只读不可交付」;拉仓阶段「把绑定仓拉齐」的口径不变;拉仓回执对参考仓注明只读身份。
- **Agent 主理**:拉取与摘除本就由 AI 经工具执行,平台只归类、落账、回事实,不代拉不代删;模块订阅是登记态配置(人配),不涉及运行时代执。
- **文档**:决策与理由记 ADR-0054(已落盘,含同日二稿修订记录:注入范围由全量启用行收窄为模块订阅);术语记 CONTEXT.md「参考仓」「公共组件仓目录」,并已补「关联仓」边界与「业务模块」订阅说明。

## Testing Decisions

- 好测试只断言外部行为:工具回执事实、HTTP 请求/响应、用户可见的界面契约;不测内部函数拆分。
- 三条既有缝,零新缝:
  1. **拉仓行为缝**:临时 bare 仓 + 登记表 fixture,直接驱动拉仓/摘仓/推送工具执行——命中登记表的地址落参考仓台账且回执带「参考仓·只读」;未命中照旧入登记清单;对参考仓推送报「未登记」;未订阅条目的地址拉取仍入参考仓台账;摘除参考仓只删台账行;登记仓与参考仓同仓名时目录互不覆盖。先例:问题流 git 行为测试。
  2. **HTTP 契约缝**:服务级起服打路由——会话详情带出参考仓台账;指派仓端点超过 8 个也放行且 https 限定、绑定仓拒删、终态守卫仍在;模块保存拒绝引用不存在的登记表条目;开场组装注入订阅条目描述、不含未订阅条目、无订阅整节省略。先例:问题流契约测试。
  3. **UI 源码契约缝**:仓卡片四类徽标(含知识仓入卡)、元信息页签分组陈列、「最多 8 个」预判与文案退役、模块编辑对话框参考组件仓多选选择器。先例:问题流 UI 契约测试。
- 按仓库测试纪律:grep 枚举受影响调用方,定向跑绿 + typecheck,不做全量回归。

## Out of Scope

- 原地改身份通道(参考仓身份全生命周期不变;改公共仓走既有用户指派通道)。
- 目录检索工具(订阅节直接注入,不做按需查询)。
- 文件系统只读锁与容器级写隔离。
- 登记表(组件仓库表)自身维护功能的改动——沿用现状,只补描述字段的填写指引文案。
- 组件知识研究线对登记表的既有用法(零感知)。
- 需求交付流程(需求侧任务流)的同类机制——本 spec 只管问题会话。
- 无单会话的模块绑定机制变化(无模块即无注入,其余照旧)。

## Further Notes

- ADR-0054 与 CONTEXT.md 词条已随设计会话落盘,实现时以它们为决策依据;本 spec 与其不一致处以 ADR 为准。
- 参考仓与知识仓是同档不同源:知识仓全局唯一、开工即装;参考仓按模块订阅、按需拉取。两者都不可交付。
- 数量上限的取消是显式拍板(「无意义的限制」),不在代码里留可复活的开关。
