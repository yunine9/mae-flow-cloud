# Mae-Flow

Mae-Flow 是一套给 CodeAgent 使用的代码交付流程。

近期变化见 [更新记录](CHANGELOG.md)。

你给出单号和需求，它会先把需求问清楚，再做设计、编码、编译、CodeCheck、单元测试和推送。中间需要你
决定的地方会停下来问，不该由 AI 自己决定的事，它不能悄悄替你做。

它解决的不是“让 AI 多写几份文档”，而是三个很实际的问题：

- 需求没说清楚就开始写，越到后面返工越多；
- 流程很长，AI 容易忘步骤、忘约束，甚至做完了才发现没编译；
- 会话中断、上下文变长或者换了模型以后，前面的进度和判断容易丢。

Mae-Flow 把流程进度、允许做的事和检查结果都记在项目里。AI 每次只处理眼前这一步，不靠它从头记到尾。

> 只安装插件不会接管项目。没有主动发起 Mae-Flow 时，改代码、执行命令和使用子 Agent 都照常进行。

## 它能做什么

| 你现在要做的事 | 入口 | 实际会发生什么 |
|---|---|---|
| 开发一个新需求或修复一个缺陷 | `/mae-flow:mae-flow` + 单号 + 需求 | 从需求澄清一直做到分支推送 |
| 处理已经交付过的评审、走读或流水线意见 | `/mae-flow:mae-flow review-fix` | 先逐条查证意见，再做增量修改、编译、检查和测试 |
| 晚上交给 AI 连续开发，早上看结果 | `/mae-flow:mae-flow moonlight` + 需求 | 不再中途提问，尽力做到推送；做不完的如实写进晨间报告 |
| 只补并运行单元测试 | `/mae-flow:mae-flow ut` + 目标功能或文件 | 不启动完整流程，只生成和执行 UT，默认不提交 |
| 只做 CodeCheck | `/mae-flow:mae-flow codecheck` + 范围 | 先检查，0 告警直接结束；有告警才修，默认不提交 |
| 只把一段需求问清楚 | `/mae-flow:mae-flow grill` + 需求 | 一次问一个问题，最后留下澄清结果，不设计、不写代码 |
| 一个需求涉及多个代码仓 | `/mae-flow:mae-flow chain` + 单号 | 查清各仓触点、接口和先后顺序，生成各仓都能直接使用的启动说明 |
| 只补一份 STORY | `/mae-flow:mae-flow story` + 单号 | 根据已有需求产物补 STORY，不启动代码开发 |
| 不想继续走流程，直接改代码 | `/mae-flow:mae-flow exit` | 保存现场并立即退出，不回滚代码，不再受流程门禁限制 |
| 忘了怎么用 | `/mae-flow:mae-flow help` | 根据本说明给出入口和下一步 |

独立 UT、CodeCheck 和需求质询可以直接处理未提交代码，不要求单号和分支。它们不会创建完整交付状态，
也不会顺手替你提交或推送。

完整交付里还会自动处理这些容易漏掉的事情：

- 按团队规则创建分支、组织提交并推送；
- 根据需求说明生成给测试使用的本地 STORY，始终保留在过程区、不进入交付提交；
- 精简 AI 写出的重复和膨胀代码；
- 在状态栏持续显示单号、步骤和分支；
- 会话中断后从原步骤恢复，不用让新会话重新理解全量历史；
- 结束时整理本仓真正值得复用的构建、测试和排障经验。

## 30 秒开始

在项目仓库中打开 CodeAgent，发一句：

```text
/mae-flow:mae-flow
交付 REQ2026071801，需求文档在 docs/se/xxx.md
```

没有文档也没关系，一句话需求也可以：

```text
/mae-flow:mae-flow
交付 DTS2026071902。删除好友时没有清理会话缓存，偶尔会崩溃。
```

后面你只需要做三件事：

1. 回答它确实拿不准的需求问题；
2. 在需求说明、实现范围和遗留问题这些确认点上做决定；
3. 分支推送后去代码平台创建 MR，跟进流水线和合入。

流程运行中不用反复敲 `/mae-flow:mae-flow`。直接回答、说“继续”、问进度都可以。会话崩了、清空上下文或电脑重启
也没关系，新会话里说“继续之前的交付”，它会从磁盘上的断点接着走。

## 一次完整开发会经过什么

```text
确认项目和运行方式
        ↓
把需求问清楚
        ↓
确认需求说明
        ↓
设计实现方案
        ↓
确认 Story
        ↓
自由实现与定稿(编码、编译自查、测试、需求对照一步完成)
        ↓
归档领域知识
        ↓
确认结果并推送(推送前真实编译+UT 验证,流水线绑提交复核)
```

### 1. 确认项目和运行方式

插件会直接准备它自己需要的规格与流程目录，然后确认单号、基线分支、需求材料、源码范围，以及项目究竟
怎么编译、怎么生成和运行 UT。这些内容后面统一复用，编译 Agent 和 UT Agent 不能到现场再猜另一套命令。

这里不再有“先跑 setup、迁移 Skill、初始化一堆平台、再 reload”的安装阶段。插件自带的方法和专项 Skill
安装插件后就可用；项目只需要提供它本来就必须具备的编译和测试条件。

### 2. 把需求问清楚

AI 会先读需求和相关代码，然后一次问一个问题。它不会只问完预先准备的清单就结束：你的回答如果带出
新的名词、边界、异常场景或前后矛盾，它会顺着继续追问。

这一阶段要说清楚的是：做什么、不做什么、输入输出、异常情况、兼容要求和验收标准。

### 3. 确认需求说明

讨论结果会整理成正式的需求说明，并把三类内容分开：

- 已经由你确认的事实；
- AI 根据代码做出的推断；
- 仍然需要你决定的地方。

这里需要认真看一遍。后面的设计、编码和测试都以这份说明为准。需求说明错了，后面跑得再顺也只是把
错误实现得更完整。

### 4. 用 Story 设计实现方案

AI 会查清要修改的模块、现有调用关系、数据如何流转、异常怎么处理，以及会不会影响已有行为。方案确认后，
形成可以直接落地的完整实现方案。

小而明确的修改会减少前期工作；跨模块或行为变化较大的需求会做完整分析。AI 会说明建议和理由，由你确认，
不会自己偷偷选一条省事的路。

业务方案写入 `.mae-flow-work/<单号>/story.md`，严格保持原有 Story 模板结构；性能规格只指可量化性能指标，
接口设计只指对外或跨组件接口。Grill 实现影响、关键函数修改、整体实现约束和领域归档影响单独写入本地
`implementation.md`。不再额外生成 UT 蓝图、Roadmap 或逐行 Build Plan。两个文件可以反复修改，但只做
一次联合设计检视和一次用户确认，不因文件摘要变化自动重审。

### 5. 整体编码、专项编译和人工检视

主 Agent 直接读取已确认的本地 Spec 与 Story，从第一行代码到定稿一次完成需求涉及的全部生产代码：
实现、编译、精简、规范、测试、需求对照，顺序自定，中间没有强制关卡，也不生成编码前计划过程件。
（2026-08-25 编排瘦身：原先的专项编译任务卡、中途人工检视、CodeCheck/UT/需求对照四步验证和
质量小循环已整体退役——模型能力上台阶后，逐步编排从扶手变成了栅栏。）

自由的对价是出口从严，交付前有三道真验收：推送前在真实构建环境完成编译与 UT（本机没有构建链时
由权威流水线代跑）；流水线结果绑定当次提交 SHA 逐项核销，旧绿灯不背书新代码；MR 上检视人的意见
是最高裁决。定稿前 Agent 要过一份出门清单（编译过、精简过、规范与测试、对照需求核过、改动已提交），
每一项凭真证据作答——验收环节会逐一实测这些证据，不接受口头“完成了”。

单测写法按开局确认的「UT生成方式」执行（AutoUT / java-autout skill 或仓内既有写法）。
UT 暴露出被测代码可能有问题时，AI 先自行调查，再把证据和倾向判断交给你，由你决定是修源码、
修测试，还是另开问题处理。交付定稿之后的任何代码改动（含用户直接介入修改）都会把流程拉回
自由实现步重新定稿，绑定旧代码的验证结果同时失效——旧结果不背书新代码。

### 6. 确认结果并推送

最后会展示改了什么、检查结果、遗留问题、提交列表和准备推送的分支。没有遗留决策时直接推送，
不再为“检查已经完成”额外要求一句确认。

质量验证后会执行一次领域知识归档：Spec、Grill、Story、实施附录、评审和验证记录仍留在
`.mae-flow-work/<单号>/`，只有实际新增或变化的 `docs/specs/<domain>.md`（以及新领域所需的
`docs/specs/index.md`）可以进入交付清单。没有新增长期知识时以 `unchanged` 正常完成，不制造文档。
归档候选先本地生成并展示 diff，用户确认一次后才应用；候选过期只重新准备归档，不把编码和质量阶段打回。

## 不想跑完整流程时

### 只补 UT

```text
/mae-flow:mae-flow ut
给 src/probe/GeoInfoManager.cpp 当前改动补边界测试
```

启动前必须定位至少一个被测业务文件，不能拿空范围或只有测试文件的范围开工。脚本会列出完整文件清单，
你需要再确认一次。确认之前不会生成测试，也不会派 UT Agent。

确认后才会按项目已经配置好的生成方式和运行命令工作。任务通过代表测试真实执行并全绿，不只是生成了文件。

### 只做 CodeCheck

```text
/mae-flow:mae-flow codecheck
检查 GeoInfoManager 这次修改
```

没有点名文件时，默认从当前工作区改动中找业务代码；测试文件自动排除。实际清单同样会展示给你二次确认，
确认前不会运行 CodeCheck。

0 告警直接结束。有告警才派专门的修复 Agent；认为某条不该改时只能报告原因，不能自动写豁免。

### 只把需求问清楚

```text
/mae-flow:mae-flow grill
支持按名称查询基站，具体边界还没想清楚
```

这个入口只做需求澄清。主 Agent 负责和你对话，另一个只读 Agent 会在开始和结束时各检查一次有没有漏问。
最终只留下澄清结果，不进入设计和编码。

### 调整或取消独立任务

UT 和 CodeCheck 的范围确认页有两个选择：

- **确认以上范围**：冻结该清单并开始执行；
- **需要调整范围**：取消当前任务，按新范围重新发起。

Agent 不能在你确认后静默扩大文件范围。任何独立任务都可以用 `/mae-flow:mae-flow cancel` 取消；已经产生的代码和
报告会保留，普通开发不会被拦。

范围确认不要求你复述固定口令。Agent 展示范围并通过按钮或普通消息取得答复后，只需执行
`action confirm-scope`；Mae-Flow 会校验该答复是否发生在范围展示之后，并绑定当前文件清单与代码基点。
类似“范围没问题，优先覆盖缺失较多的文件”这样的自然答复可以直接形成收据；否定、疑问、要求调整以及
旧范围的答复都不会被当成确认。

## 月光宝盒：晚上跑，早上看

白天限流严重，或者你不想守着每个确认点时，可以在新需求或进行到一半时切换：

```text
/mae-flow:mae-flow moonlight REQ2026071801，需求是……
```

进入后不再向用户提问。它会根据已有需求、代码和项目配置采用保守判断，继续分析、编码、编译、CodeCheck、
UT 和推送。

这里的目标是“尽力做到可以让人早上接手”，不是把失败包装成成功：

- 能修的问题先真实修；
- 有限尝试后仍解决不了，记录现象、尝试和风险，再继续后面的步骤；
- CodeCheck 遗留会如实进入晨间报告，不会为清告警无限返工；不会删掉、禁用或过滤失败测试；
- 会尝试推送，但认证、网络或冲突失败时只保留现场，不会谎报已推送；
- 推送后停在晨间检查，不自动定稿需求。

如果启动时已经位于带有代码的非基线分支，月光宝盒不会退回去追问，也不会为了通过分支检查自动
merge、cherry-pick 或 reset。它按以下优先级处理：

1. 启动原话明确要求“继续/沿用当前（现有）分支”，且该分支包含当前基线 HEAD：自动沿用；
2. 原话没提分支，但 `.mae-flow.json.last` 同时证明同单号、同分支，且上一轮记录的 HEAD 是当前
   HEAD 的祖先，并且当前分支包含当前基线 HEAD：按同一交付续跑；
3. 当前就在基线 HEAD、没有既有工作：仍按约定名称正常创建分支；
4. 其他归属不明、历史分叉或基线不在祖先链上的情况：自动写入晨间报告并停止，等待人工处理。

分支名里碰巧包含单号不算续跑证据。自动沿用会记录请求或上一轮状态摘要、当前分支/HEAD 和基线
HEAD，便于早晨审计；“沿用分支”也只解决代码归属，不代表允许扩大本次需求范围。

早上常用三个入口：

| 入口 | 作用 |
|---|---|
| `/mae-flow:mae-flow moonlight report` | 看完成内容、自动判断和遗留问题 |
| `/mae-flow:mae-flow moonlight repair` | 根据报告继续修，再重新走后续检查和推送 |
| `/mae-flow:mae-flow moonlight finalize` | 结果满意后进入最终确认 |

报告保存在 `.mae-flow-work/moonlight-report.md`，不进入业务提交。

## 评审意见和跨仓需求

### 已经有 MR，又收到评审意见

使用 `/mae-flow:mae-flow review-fix`，把意见原文贴进来。

AI 会先查代码和规格，再逐条给出结论：需要修、可以有依据地回复，或者这条意见其实改变了需求，应该转成
新的开发轮次。确认后只处理本轮增量，再编译、CodeCheck、补测和推送，提交会追加到原 MR。

### 一个需求涉及多个代码仓

先使用 `/mae-flow:mae-flow chain REQxxx`。

它会从关键词、调用链和配置入口几个方向查触点，再和你确认各仓职责、接口字段、错误语义和交付顺序，
最后生成一份链路说明和每个仓的启动卡。之后每个仓各自运行完整流程，使用同一份链路说明作为需求输入。

如果任一仓开发过程中发现链路说明有遗漏，应先修订说明并同步其他仓，不能让这个仓自己悄悄绕开约定。

## 中断、退出和重新启用

### 会话断了

说“继续之前的交付”。状态保存在项目里，不需要依赖旧对话。

### 不想再走流程

直接发送：

```text
/mae-flow:mae-flow exit
```

这条消息本身就是授权，不会再问你一次。退出会保留全部代码、提交和文档，并把流程现场放到
`.mae-flow-work/exited/`。退出后可以直接让 AI 改代码或补 UT，原流程不再强制编译、检查和提交。

如果上一单已经交付完成，门禁其实已经解除。此时再次发送 exit 会直接提示“无需再次退出”，并保留终态
供 `current/status/report` 查询和下一单自动归档；这不是失败，也不需要再去真实终端执行任何命令。

如果 Hook 本身损坏，命令会给出一个需要你在真实终端输入 `EXIT` 的紧急出口。不要手删
`.mae-flow.json`：手删既没有留档，也不能保证所有控制状态一起退出。

### 想重新接回原流程

明确说“重新接回 Mae-Flow”。恢复时会检查退出期间代码有没有变化；变过就回到相应的编译和检查入口，
退出前的旧结果不会复用。普通的“帮我改一下代码”不会被解释成重新启用流程。

如果你明确执行 `/mae-flow:mae-flow review-fix`，这条命令本身已经是开启评审修复轮的授权，不会再让你确认一次。
系统会用 Hook 捕获的真实消息 ID 恢复或换单，避免长需求原文在 shell 中转述失败。退出前的流程已经结束时，
会自动备份为 `.mae-flow.json.last` 并开启下一轮；退出前的流程尚未结束而你明确要开另一轮时，旧现场仍保留在
`.mae-flow-work/exited/`。

`.mae-flow.json.exited` 只是指向退出快照的控制记录，不是流程主状态。不要把它移动或改名为
`.mae-flow.json`；恢复和换单都应由 `init` 完成。

## 它是怎么保证 AI 不乱跑的

提示词只负责告诉 AI 应该怎么做，真正的约束由程序完成：

- 当前走到哪一步、下一步是什么，由状态文件记录；
- 不该改源码的阶段，编辑操作会在真正发生前被拦下；
- 分支名、提交信息、需求文档结构和检查结果都会实测，不接受 AI 口头说“完成了”；
- Agent 实际写过的文件只进入“可能提交”的候选范围，仍须逐个审阅 diff；编译或生成命令顺带
  出现的文件会提示确认，明显的新增临时编译产物会在提交前拦下；
- 流程启动前已存在、且本单 Agent 没有实际改写的文件会被识别为上一单/用户现场，不能随本单提交；
  当前交付清单拒绝整个 OpenSpec 和所有需求过程件；领域文档只允许本次归档实际变化的精确路径；
- 真正需要用户决定的事项来自真实按钮或用户消息，Agent 不能替用户选择；
- 所有按钮选择都绑定当次 AskUserQuestion 的选项收据，以用户实际点中的选项映射机器选择，
  不把中文文案当协议；旧宿主缺少选项元数据时，`继续/修改` 型检视仍接受“确认，进入编码”等
  自然答复，明确提出遗漏、问题或修改时只能进入返工，含糊答复不会推进；
- 配置阶段会先生成一份绑定全部配置和需求文档内容的确认单，用户只做一次最终确认；局部回答、旧确认或
  “确认 A 后提交 B”都不能推进；
- 推送与流水线核销属于机器事实：推送以远端真实状态为准（不信任务自述），流水线结果绑定当次
  提交 SHA 逐项核销；定稿后的任何代码改动都会把流程拉回自由实现步重新定稿再走一遍验收；
- 检查结果绑定当时的代码，代码一变，旧结果自动失效；
- 每一步都能从磁盘恢复，不依赖主会话长期记忆。

这些门禁是为了阻止未经确认的动作，不是为了把流程卡死。独立 UT/CodeCheck 任务的专项 Agent 收尾
因宿主兼容问题无法识别时，会展示真实风险，让你选择重试或承担风险继续；
确认消息没被宿主回传时，让用户发送页面要求的普通确认消息即可恢复，不需要退出重开。任何阶段仍保留
`/mae-flow:mae-flow exit`。

## 安装以后还需要准备什么

正常情况下，安装 Mae-Flow 插件就代表插件功能已经可用：

- 需求与规格管理、设计方法、编码纪律、代码精简和流程脚本都随插件固定版本提供；
- build-fix、AutoUT 和 java-autout 是内网插件自带 Skill，安装后直接调用；
- 不要求在每个项目运行 setup；
- 不创建 `.cac/skills` 或 `.claude/skills`，不迁移个人目录；
- 不要求执行 reload，也不调用全局 `comet init`；
- 不改用户的 npm registry、Git 代理或 SSL 配置。

想排除机器上旧版 OpenSpec、Comet 和其他插件的影响，可以按
[Mae-Flow 干净环境验证](CLEAN-ROOM-TEST.md) 卸载外部组件后做一次最小实跑。

Mae-Flow 真正依赖的宿主基础环境只有 Python 3.8+、Git 和 Windows 下随 Git for Windows 提供的
Git Bash（v4 起规格引擎纯 Python 内化，Node.js 降为可选件，仅开发期差分对拍用，缺失不影响交付）。
`python ".mae-flow-work/bin/mae-flow.py" envcheck` 会实际执行版本命令，并显示各项的版本和真实路径；首次开启完整流程时也会复用同一套
检查。缺少必需依赖会在创建流程状态前明确报错，因此不会激活 Hook 把普通开发锁住。Git worktree 的
`.git` 文件形式也支持。

项目编译工具、测试框架和访问依赖仓库的权限仍由具体项目提供。这些不是 Mae-Flow 重复安装的东西：即使不用
AI，开发者本来也需要它们；它们会在真正编译和测试时按项目已确认的配置验证，不会重新引入耗时的 setup。

CodeCheck 是唯一例外。它来自公司内网 npm 仓库，第一次真正执行规范检查时，Mae-Flow 会先查找
`codecheck`/`codecheck.cmd`；找不到才尝试一次：

```text
npm install -g @baize/codecheckcli --registry=https://cmc.centralrepo.rnd.huawei.com/artifactory/api/npm/product_npm/
```

这条命令只给本次安装指定仓库，不会永久修改 npm 配置。安装失败会保存诊断，不会反复安装、误派修复 Agent
或把流程锁死：普通模式直接把它作为建议项留痕继续；月光宝盒会记录到晨间报告。
每轮 `codecheck-scan` 会打印 `.mae-flow-work/` 下的人类可读 Markdown 详细日志路径，按时间记录实际检查命令、退出码、
原始输出、用户范围确认，以及修复 Agent 的命令结果、报告和 Git diff。它专用于定位工具问题和误拦，
不会进入业务提交；日志自身写入失败也不会卡住流程。

为减少问题积攒到正式 CodeCheck，编码阶段还带一个内置轻量预检：提交 Hook 只看本次真实提交快照，
手动执行只看本轮当前代码差异，并排除未变化的启动前脏文件。它会提前提示“参数超过 5、函数有效代码行
超过 50、控制结构最大嵌套深度超过 5、修改行超过 120 字符”。
提交前由 Hook 静默运行，编译任务生成时再兜底一次；C/C++（含模板实现文件）、Java、
JavaScript/TypeScript（含现代模块扩展名）和 Python
使用插件内固定版本的语法分析器，不要求项目安装依赖。它不会新增流程节点或门禁：解析不确定、超时、
工具异常、生成代码以及基线已经存在的问题只在 `.mae-flow-work/lightcheck/latest.md`
留痕并继续，Agent 无需主动执行预检命令，最终仍以公司 CodeCheck 为准。

需要检查插件自身是否完整时，可以让 AI 执行 `python ".mae-flow-work/bin/mae-flow.py" envcheck`。它会检查上述四个基础运行时和插件内嵌
能力，但不安装项目编译环境。CodeCheck 缺失会提示，但不会把插件判为不可用。

团队可以把稳定的项目配置写进 `.mae-flow-defaults.json` 并提交：

```json
{
  "编译方式": "项目真实编译命令或 Mae-Flow 自带 build-fix skill",
  "UT生成方式": "Mae-Flow 自带 AutoUT / java-autout",
  "UT运行命令": "项目真实 UT 命令",
  "执行补充": "本仓长期采用的关注点、先后偏好或协作要求（可选，最多 2000 字）",
  "测试路径": ["测试目录正则"],
  "源码路径": ["源码目录正则"]
}
```

后续开发者只需在完整配置确认单上检查一次，不用逐项确认，也不用每次重新猜。
其中「执行补充」会由 Cloud 在下单时固定为文字建议层（任务/仓库/团队各一层），随定格
方案一起写进 `.mae-flow-work/workflow-profile.json` 的 `supplements` 字段，显示在任务的
执行方案中，并随每个阶段的 `current` 交给 Agent；它不能关闭阶段、真实证据、人工决定或
Git/交付权限。想调整阶段的**结构**（增删改排执行项）请使用工作流资产库的结构化定制。
（勘误 2026-08-29：v1 `execution-profile.json` 与"按阶段勾选可选动作/优先能力"的有界
定制已整体退役并入上述单一文件——两套定制并存造成过门禁只保一半的真实事故，趁无存量
窗口统一。）

## 常见问题

### 为什么 AI 停下来了？

先看它最后展示的是“需要你决定的问题”还是机器证据错误。真实选择直接点按钮；编译、检查、测试等阶段
不应等待人工确认。如果仍要求你手动输入“确认××”，执行 `python ".mae-flow-work/bin/mae-flow.py" doctor` 查看按钮结果是否被宿主回传。

### 为什么提示“证据不足，拒绝推进”？

说明它声称完成的事没有对应到真实文件、命令结果或专项 Agent 报告。让它按报错补证据。相同问题重试代价
很高时，系统会给出用户承担风险继续的出口，不需要无限循环。

### 中文需求文件乱码，怎么确认都过不去？

不要继续说“我确认”，确认不能修复坏文件。让 AI 执行 `python ".mae-flow-work/bin/mae-flow.py" doctor`。口述需求会通过确定性命令写成
UTF-8；已有 GBK/UTF-16 文本也可以规范化后再进入完整配置确认。连续失败会停止重复命令，但流程不会锁死。

### AI 在不该改代码的阶段被拦了

这是正常的阶段保护。如果你就是不想走流程，发送 `/mae-flow:mae-flow exit`；如果只是想并行处理另一件事，建议用
`git worktree` 新开一个工作目录，避免把无关代码混进当前 MR。

### 一个目录能同时跑两单吗？

不能。一个工作目录只有一个有效流程。并行开发请使用不同的 `git worktree`。

### 专项 Agent 跑了很久，最后因为格式问题不让继续

先让 AI 展示拒绝原因。可以低成本重答就重答；宿主没有提供完整收尾记录或重跑成本很高时，让 AI 给出
“重试 / 承担风险继续”选项。风险确认只放行当前任务卡和当前代码，不会把其他检查一并关掉。

### 怎么看现在走到哪了？

状态栏会显示单号、当前步骤和分支。也可以直接对 AI 说：

| 你说的话 | 用途 |
|---|---|
| `执行 python ".mae-flow-work/bin/mae-flow.py" current` | 看当前步骤该做什么 |
| `执行 python ".mae-flow-work/bin/mae-flow.py" status` | 看原始状态 |
| `执行 python ".mae-flow-work/bin/mae-flow.py" doctor` | 做完整体检，排障首选 |
| `执行 python ".mae-flow-work/bin/mae-flow.py" report` | 看本单各阶段耗时和流程摩擦 |
| `执行 python ".mae-flow-work/bin/mae-flow.py" report --all` | 看本仓历史交付统计 |
| `执行 python ".mae-flow-work/bin/mae-flow.py" envcheck` | 检查插件内嵌运行时是否完整 |

Hook 通用日志位于 `%TEMP%\mae-flow-hook.log`。CodeCheck 问题优先提供扫描输出中打印的专项详细日志；
其他无法解释的拦截，把 `doctor` 输出和 Hook 日志最后几十行一起交给维护者。

宿主可能把正常的门禁拒绝也显示为 `PreToolUse:<工具> hook error`。此时查看同一时刻的
`decision event=pretooluse ... result=blocked source=mae-flow rule=<规则>`：存在该行表示
Mae-Flow 按规则主动拦截，不是 Hook 崩溃；`command_sha256` 只用于判断多次拦截是否来自同一条
Bash 命令，日志不会保存命令原文。`EXC`、`WATCHDOG` 或“非门禁语义退出码”才表示 Hook/运行环境异常。

如果界面显示失败的 Bash 恰好是 `python ... mae-flow.py <子命令>`，还要看命令自身的中文错误：
这通常是 Mae-Flow 的业务校验拒绝，不是 Bash 解释器或 Hook 崩溃。普通确认命令自动消费结构化回答；
高风险授权先执行 `messages`，再把左侧 ID 传给 `--message-id`，不要复制、概括或重新发明用户原话。
报错提示消息属于旧步骤、旧范围或旧检视版本时，应重新展示当前内容并取得新回答，不能重放旧 ID。

## 哪些内容会留下

根据任务类型，项目中可能产生：

- 业务代码、单元测试和必要的构建配置或资源；
- 本次确认、实现并验证后实际新增或更新的 `docs/specs/<domain>.md`；
- 新领域确实需要时同步更新的 `docs/specs/index.md`。

Spec、Grill、Story、实施附录、决策、评审、验证、CodeCheck 豁免、任务卡和月光宝盒报告全部留在
`.mae-flow-work/<单号>/`。它们不会因为取消或退出被删除，也不会进入交付清单；最终文档归档只保存
当前有效的领域真相，不保存按单号排列的开发流水。
