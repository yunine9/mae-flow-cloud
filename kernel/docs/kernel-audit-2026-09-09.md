## 第二轮：旧状态、重启、重复操作

用真实临时 Git 仓验证同内容重复应用、代码/文档混合提交、构建产物存在、候选再编辑、JSON 状态重载、旧审批卡和缺失候选。

- 归档指纹仅包含候选、目标与索引；其他源码、编译产物、暂存/提交、过程记录不使它过期。
- apply 根据当前候选重新计算，不盲目返回旧 applied 状态；同字节不重新写盘。
- result / changed_paths 表示本次实际内容变化；applied_paths 仅保存认领凭证，非空不等于还要新提交。
- prepare --unchanged 表示不再执行新的归档修改，保留现有文档和既有凭证，不由历史提交增量否决。
- 没有实施基线的旧任务首次检视时绑定实际 SHA，避免移动 HEAD 作废同内容确认。旧卡路径与逐文件指纹完全一致时保留原 ID；实际内容改变仍要求重新检视。
- 当前审批对象上的自然语言肯定回复不要求照抄按钮；否定、未知回答、过期对象仍不能被冒充确认。

## 第四轮：新指令不能被旧结果短路

本轮新增四个真实临时 Git 仓回归，修改前均失败，覆盖三个实际遗漏：

- 已应用归档后，prepare 新领域或新关键词被旧文件指纹短路，直接返回旧 applied。本次将命令参数也纳入是否为重复请求的判断，新增领域正常准备，已有领域继续保留。
- 显式 --adopt-existing 复用了旧候选，随后 apply 可能覆盖人工更新的正式文档。本次明确以当前正式文档为认领来源，刷新候选；普通 prepare 仍保留候选编辑。
- 重复 apply 在核对显式 message-id 前返回成功。本次先核对真实答复并尊重拒绝，再复用旧结果；不增加本地编辑索取确认的要求。

同时复核 Edit/Bash 的配置前边界，未改变流程图或恢复步骤级编辑限制，并清理仍声称存在“精确提交闸”的旧注释。
