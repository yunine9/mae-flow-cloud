## 2026-08-14（四）：确认卡整卡极性——"需要修改"不再被邻座答案背书

云端打回路径演练逮住的真缺口:配置确认卡答"需要修改"+"交付方式: 完整开发",
`done` 照样推进。根因是两条确认判定(`_config_ack_verified` 与
`_implicit_ack_verified`)都对卡上每个答案**独立**判极性——"完整开发"
不是拒绝词,就替确认题签了字。纯文本通道的极性判定
(`_is_positive_confirmation` 的否定词表里明明有"需要修改")在按钮
通道丢失了。

修法(两处同款):同一张卡的整卡候选里有任何拒绝形回答=整卡打回,
卡上其他问题的回答不得代为背书;遍历从新到旧,最新的打回封路,更旧的
确认不能越过它复活;打回场景的报错说人话("按用户意见修订后重新出卡
确认"),不再误导成"未匹配标准按钮"。回归钉在
test_choice_receipts.ConfigCardPolarityTests:打回拦住 → 重审确认放行;
最新打回压过更早确认。老宿主(CodeAgent)同样中招此缺口——answers
形状两边一致,修复对插件世界同样生效。

附带:ack.py 触到 500 行模块上限,把 `_is_positive_confirmation`/
`_button_confirmation_alias` 移入 ack_confirmation.py 并注册进 CLI
门面(api 属性名不变,standalone_core 的调用不受影响)。


## 2026-08-14（三）：云端代码移出内核仓——边界与语言双拍板

用户两次拍板落地:**云端服务新开仓**(`mae-flow-cloud`),**语言按亲和选**
(Pi 是 TypeScript,SDK 支持进程内嵌入,服务层用 TS)。本仓移除上一条落地的
`adapters/cloud/`、`cloud-probe` 命令与 pi 桥扩展,回归纯内核+插件;
架构测试的"入口可达"约束随之自然恢复,不留豁免。

为什么这不是白干:Python 版把整条链在真 pi 进程上验证过
(RPC 子进程 + HTTP 环回桥,五问全部实证),TS 版是**同一份灵魂的
进程内形态**——tool_call 钩子即同步拦截,未 resolve 的 Promise 即
人工节点挂起,平行 AgentSession 即子 Agent,桥和 RPC 解析两层直接消失。
mae-flow-cloud 首提交九项事实全绿,裁判是本仓的契约函数
(harness/verify_transcript.py import mae_flow_core)——
**内核唯一权威**在跨语言边界上的落法:TS 写现场,Python 裁决,
transcript JSONL 是中立契约。

跨语言迁移三条实战教训(两边都踩过、都堵上了):
环回流量必须直连(内网 Clash 把 127.0.0.1 的模型请求劫走回 502,
模型侧零请求,报错却指向"网络");pi 只认 throw 作为工具失败信号
(返回对象里的 isError 被 agent-loop 忽略);被打回的调用也必须登记
tool_use 行,否则 tool_result 按 id join 不上,"打回"在审计中不可见。

## 2026-08-14：云端宿主适配层落地——Pi 事件流进内核的第一段真实管道

云端 MVP 详设(docs/superpowers/specs/2026-08-14-cloud-host-adapter-design.md)
的第一个可运行增量:`mae_flow_core/adapters/cloud/` 七个文件 + 22 个新测试 +
`cloud-probe` 演练命令。总纲一句话:**冻结内核面向的接口,翻译只发生在
pi_event_map.py 一个文件里**。为什么这么切——盘点发现内核消费的五样东西
(Hook payload 字段、transcript JSONL、pretool 纯函数裁决、AskUserQuestion
工具结果、Task 派发+生命周期对账)全是**数据形状**,不是宿主私有 API,
所以正确做法不是让契约学新格式,而是让云端把 Pi 事件流写成契约已认识的格式:

- **semantic_events**:十种语义事件 + 追加式事件日志。幂等锚是任务内单调
  event_id,重放 no-op、倒退拒收、畸形抛错(静默丢事件=投影缺页还查不出来);
- **transcript_store**:事件 → transcript 同形 JSONL,quality 四契约零改动
  (测试直接拿 parse_transcript/bash_call/call_failed/select_contract_marker
  验收云端产物);子 Agent 落 `subagents/agent-<call_id>.jsonl`,旧插件的
  确定性绑定(tool_use_id → 文件名)原样命中;
- **gate_service**:tool_requested 的同步裁决点,路由复用
  active_pretool_decision,深层契约留端口注入;fail-open 语义保留
  (门禁自身故障=放行+留痕,与看门狗同一精神);
- **human_gate**:AskUserQuestion 永不真实执行——拦下转结构化待办,
  决定按 call_id 以工具结果回注,**34 处步骤文档零改动**;同 call_id 幂等
  (恢复重放不出第二张待办),先到决定生效、后到抛 StateConflictError;
- **pi_session/agent_bridge**:会话驱动 + 平行会话模拟 Task。登记归属规则
  防双行:谁执行谁登记——Pi 跑的工具由 Pi 事件登记,宿主代演的(人工决定、
  子 Agent 结果)由 driver 登记,Pi 回声丢弃;子 Agent 不设人工节点,
  提问被打回而不是挂起整个任务(旧插件"子 Agent 非交互"契约同款);
- **reference_runtime + cloud-probe**:参考线格式的唯一可执行定义,契约测试
  与演练命令共用,不留两份格式各自漂移。架构测试拦过一次
  "cloud 包不可达"——这正是"预埋≠接线"的机器化身,修法不是白名单豁免,
  而是按 codespec 先例给真实入口:`cloud-probe` 跑通整链(同步拦截、打回、
  子 Agent、人工挂起回注、证据验收)并留档现场;真 Pi 客户端就位后,
  同一剧本换实现对拍,就是阶段 0 的验收动作。

没做的(诚实边界):gate 深层契约(gate-edit/gate-bash 的证据链)尚未接进
GateService 端口;真 Pi 客户端未写(线格式待阶段 0 拿到);云端服务/Web 层
一行没动。这些都在详设里有位置,不影响本段管道的验收。

## 2026-08-14（续）：横向排查——同一个洞还有三个出口,同一个概念还有两份副本

上一条修完立刻横扫了同形状的问题。洞的形状是**"从仓库枚举出来的清单,不设上限
地进了给 Agent 或用户看的文本"**。`_dirty_paths()` 用的是 `--untracked-files=all`,
仓里没忽略 node_modules 时它返回几千条。三处都用 3000 个未跟踪文件实测过:

- **`symbol_refs`(最狠)**——`git grep --untracked` 只排除了 `.mae-flow-work`
  和 `*.min.js`。实测搜一个普通符号命中 **2400 处,排除依赖目录后 0 处**。
  而这份清单的用途是让 Agent"每一处要么适配、要么写明为何不需要",2400 条
  等于当场压死它。现在排除依赖目录,并加 200 条上限——**截断时明说"不能据这份
  清单判定收口"**,因为静默截断在这里等于假收口,比不列更糟。
  搜索的排除刻意只用第一档:漏掉一处真引用的代价是"编译全绿功能坏",
  而 `build/` `vendor/` 里确实可能有仓库自己的代码,方向与"判定源码"相反。
- **退出预览**——把全部脏路径 join 成一行,实测 **105000 字符的一行**。
- **`init`**——给每个脏文件算指纹写进 `.mae-flow.json`,实测单这一项 **422 KB**,
  而状态文件每推进一步都要整份重写。指纹本身只要 0.19s,不是性能问题,是持久化
  垃圾。这里不能只截断:`initial_dirty` 是保护用户现场的依据,截断等于把一部分
  现场丢了保护——所以按口径过滤(工具自管目录不是用户现场,没人手写 node_modules)。

同时清掉两份同义副本(这正是上次漏掉第三个出口的根因):

- `lightcheck._GENERATED_PATH_PARTS` 是依赖目录清单的**第四份手抄**,而且抄漏一档:
  没有 `.venv/` `site-packages/` `__pycache__/`,于是 Python 虚拟环境里的三方代码
  会被当成本单源码去报复杂度告警。现在接到共用判据上,只留它特有的生成代码判据。
- `shared.CODE_EXTS` 与 `lightcheck.SUPPORTED_EXTENSIONS` 是**逐字节相同**的两份
  清单。收进 `source_paths.CODE_EXTENSIONS`,两边转发(`shared` 本来就已经这么
  转发 `SOURCE_EXTS`/`SOURCE_FILENAMES` 了,这份只是漏了)。

新增一条机器约束:任何模块再手抄一份依赖目录清单,`test_dependency_flood` 直接失败。

## 2026-08-14：「什么算我们的源码」收拢成一个口径——依赖洪水的第三个出口

内网卡死的那次(几千个 `node_modules/@fission-ai/openspec/…` 塞满任务卡),
上一版只堵了两个出口:检视卡片内嵌、面板未跟踪清单。**漏了第三个**——独立任务
的范围自动推导(`standalone_core._action_files`:用户没点名文件时,范围取整棵
工作树的脏源码)。用户报的文件名是 `grill-prep-task.md`,那正是独立任务这条路的
卡片命名(`standalone_core.py` 的 `<label>-task.md`),而我按完整交付那条路
(`role-tasks/`)去找,得出"不是我们生成的"这个错判,把人引偏了一轮。

教训不在这三处代码,在于**同一个概念散着实现就一定会漏**:"什么算我们的源码"
原本在三个文件里各有一份目录清单,补两处漏一处是必然。现在口径只有一份,
在 `foundation/source_paths`,并且按"仓库有没有资格说不"分成三档:

- **工具自管目录**(`node_modules/` `.venv/` `site-packages/` `.gradle/` …):
  硬判不是源码,仓库配置也翻不了案——没人往这些目录里放手写代码;
- **产物/外部代码目录**(`build/` `dist/` `target/` `vendor/` `third_party/`):
  判成"未知",交给仓库自己配的 `source_patterns` 定夺。默认不是(挡洪水),
  显式配了就仍然是。这一档是 selftest 逼出来的:我起初把 `vendor/` 归进硬判档,
  当场撞上一个把 `vendor/private/` 配成自己源码路径的仓;
- **编译产物扩展名**(`.pyc` `.class` `.o` `.so` `.jar` …):按扩展名硬判。
  必须硬判是因为目录模式会把它们捞进来——flow 默认源码模式含 `(^|/)lib/`,
  而 pyenv 的 `python3.13/lib/*.pyc` 正好命中,跑全量测试时一个沙箱凭空多出
  68 个"改动源码"。注意不含 `.lock`:`cargo.lock`/`yarn.lock` 是构建描述文件,
  它们的变更恰恰要检视。

面板刻意**不**用扩展名那档:面板回答的是"这次要检视什么",不是"这是不是源码"。
本单新加的 `logo.bin` 不是源码,却实实在在是待检视增量(列出、不出 diff)——
按扩展名排会把它吞掉,那正是面板最不能犯的错:显示与现场不符。

另加一道有界防线:独立任务自动推导范围超过 200 个文件就停下来请用户用
`--files` 点名。上限定在 200 而不是几十——这条线是拦病态(几千个),不是拦
大改动(实测一个测试沙箱就有 68 个正常文件);卡住正常改动等于凭空多一步返工。

## 2026-08-10（下午）：内网首战暴露的授权与引导问题——一次收拢,不再缝补

内网真实环境第一天,撞出的问题与无人值守复现共同定型了三件事:

### 授权收拢为一个模块(workflow/consent.py),规则一句话

**同意看回答,相关性看问题,用户打字最大。**

- 起因:用户点选批准基线提交,被判"原话未覆盖本动作的全部路径"——回答是短
  选项,装不下 12 个路径;Agent 转头拼了不存在的 `--paths` 参数又撞一层错。
  同一概念当时散在四个文件七个判据里,每撞一个症状就地加一个,是教科书式
  霰弹修改,而且其中三个是当天新加的。
- 收拢后只剩结构判据:拒绝词两档(硬拒一票否决;犹豫词遇明确放行不作数——
  「考虑过了,放行」是放行)、放行编号须出现在 Agent 代问的**问题**里(答案里
  出现不算,用户随口一句不是授权)、用户自己打字免编号(没人代问,他的话就是
  授权本身)、exit 这类无编号动作看问题在不在问这件事(答案字面有"退出"不算——
  实测「选择 1（退出 Mae-Flow，直接开发）」曾把整轮流程误退掉)。
- 配置确认同源改造:措辞白名单删除,单项回答不能替整份背书的判据改为收据
  结构(answers 的键是配置项名即单项)。18 条场景矩阵铺满,内网撞过的逐条标注。

### 首次开工的鸡生蛋问题——hook 直接铺桥

全新仓里转发壳不存在,SKILL 却让模型用转发壳跑 init;第一版修法让 hook 打印
插件绝对路径给 Agent 抄,内网实测 Windows 长路径被抄错两处。定稿:用户明确
发起交付的那条消息上,hook 当场把转发壳铺进 .mae-flow-work/bin/,Agent 全程
只知道短路径;无关仓一个文件不写(原铁律保持);铺不动才降级递路径并自我声明
"这不该经常出现"。转发壳自带来源与修复说明,不再只甩 can't open file。

### 用户现场的第三条保护腿

无人值守复现轮:模型处理推送分叉连出七招,门禁拦住六招(含借放行令夹带
git reset --hard),第七招 `git checkout -- <文件>` 单文件丢弃穿透,销毁了用户
流程启动前的未提交改动——而这招还是全树拦截提示自己教的。新增
bash-discard-user-scene:丢弃式 checkout/restore 命中"启动前就存在、指纹未变、
本单未改写"的文件即拦,走 break-glass 由用户裁决。至此用户现场不被卷进提交
(carryover)、不被全树清除(wipe-worktree)、不被单文件抹掉(discard-user-scene)。

### 新增红线

- 教出去的命令必须是真命令:拦截/指引消息里建议的每个参数,ast 提取后逐个
  对照真实 argparse 定义,不存在即红(假出路比死路更费轮次);
- 授权场景矩阵 18 条,含"必能放行"的措辞全集与该拒的问句/犹豫/硬拒全集。

## 2026-08-10：无人值守实战暴露的一批门禁误判与残留污染

用弱模型（Haiku）在隔离沙箱里无人值守跑完整交付，把流程当黑盒撞。两种模式
各两轮，撞出 11 处真问题——**没有一处是靠读代码想出来的**，全部来自真实运行。
1058 单测 + 463 项发版门禁全绿。

### 机器诬告：把老实人判成说谎

- **验证报告里出现 `SendResult.fail(` 就被判 FAIL**。结论判定整篇搜
  `(?i)\bFAIL\b`，而这一单的需求恰恰是"失败要重试"，报告越老实逐条列实现
  位置，`fail` 越多。改成只认独立成行、落在行尾的结论；正文里的
  `test_x_fail`、表格行、代码引用一律不算。**机器只拦谎言，不拦用词。**
- **面板自己写的文件被当成业务源码**。`.mae-flow-work/panel-stamp.js` 以 `.js`
  结尾，源码判定光看后缀就把它算进交付源码，于是"源码变了必须重编译"，把一次
  正常交付拐进 `quality_recompile` 回环。而面板的第一条铁律正是永不影响推进。
  修在唯一判定点（Edit 门禁／Bash 门禁／令牌新鲜度／UT 源码回流四套口径共用）。
- **heredoc 写的多行提交信息被判不合规**。取到的是 `$(cat <<'EOF'\n…` 整串，
  开头当然不是 `[单号][feat]`。取值时先拆 heredoc 再校验。
- **领域归档写的文件每单都报"来路不明"**。它们是 harness 自己写的、不经 Write，
  于是每一单收尾都要人确认同样两个文件——狼来了喊多了就没人听。认账依据改为
  这一单归档时实际落盘的那份清单，不是给 `docs/specs/` 开白名单。

### 授权与残留：上一单的东西不能留给下一单

- **答选择题的那句话被当成退出授权**。流程在问交付方式，用户答
  「选择 1（退出 Mae-Flow，直接开发）」——他要的是选项 1，括号里是自己的注解。
  可 `exit` 的 ack 只做精确匹配，这句话原样对得上，流程当场退出。授权必须绑定
  到"当时在问的是什么"，与实战里"choice 问了两遍"同源。
- **退出与开新单漏收三个旁路状态**：`.quality-executions`（编译/UT 执行台账）、
  `.agent-observations`（Agent 派发返回证据）、`.advisories`。前两个是证据来源，
  留着新一单就可能拿旧记录充数。名单完整性改由不变量兜住：凡代码会写的
  `.mae-flow.json.*` 都必须在白名单里。
- **过程区按步骤命名，换单撞名**：`agent-tasks/build-compile.md`、
  `role-tasks/story-story-review.md` 只带步骤名，而任务卡正是要"原样转交给子
  Agent"的话术。开新一轮时连同 `lightcheck/` 一起清；带单号的目录明确保留。
- **轻检报告不能自证新鲜**：文件叫 `latest.md`，既无生成时间也不绑版本，而面板
  和 `current` 都把它当当前结论。报告头补上生成时间与绑定 HEAD，取不到就写
  "未记录"，不许编。

### 活锁：拦住了却不给出路

- **按配置项分岔的步骤没有默认分支**。月光宝盒写完代码、编译、测试、提交、推送
  全过了，`done` 却说"步骤 build 缺少可解析的下一步"——`build` 按 `code_reviewer`
  分岔而这个键从没写进配置。步骤文档明写着"缺少该字段时按 enabled 兼容"，
  **代码里没兑现**。三个分岔步骤补上明写的默认分支（取门禁最多的那条）。
- **同一步反复登记阻塞，记录上看不出在重复**。每次登记都把上一条标成
  superseded 再追加，模型收不到"别再试了"的信号，一步走成八步。现在同因第二次
  就点破；同一步连登多条且措辞各异时，反过来提醒它"多半是你自己改完又改，
  先看现场"。

  公式与协议是否逐项对得上含下标起点与取整方向）；
- **不命中一个字都不加**，不做固定阶段；spec 轴永远不带这段，避免掺进工程细节；
- 触发词按 camelCase 复合词校准过：`\bslot\b` 匹配不到 `slotIndex`，
  这类最常见的写法本来会整批漏掉，已放宽为 `\bslot\w*` 等；
- 6 个真实命中样例全中、6 个非量纲改动全静默。

### 规格符合性：散文升级为逐条对齐矩阵

`verification.md` 原来要求"至少记录已核对的验收条件、代码证据……"——是散文，
可以一句话糊过去。现在核心是一张矩阵（验收项｜实现位置｜验证方式｜结论），
一条验收项一行，且**指不到实现位置的那条结论只能写"缺失"**，
不许因为"整体看起来实现了"记成满足。

Trail of Bits 那条"不一致要么是代码 Bug 要么是文档错误"我们已经有，而且是三分支
（Spec 需修订 / 代码偏离 / 需求本身不明确）——第三种最常见，二分会逼模型在两个错答案里选。

### 检视分级：只有 BLOCKER 挡住推进

Reviewer 的五条发现此前**看上去无差别地都很急**。现在每条必须带处置标签：
`BLOCKER`（功能错误、崩溃、回归、数据损坏、安全）只有这一级在人工检视前修掉；
`WARNING`（可维护性、复杂度、潜在风险）与 `NOTE`（风格偏好）原样呈报由用户定。
拿不准往低一级标——把 WARNING 说成 BLOCKER 造成的摩擦比漏标更常见。

与两天前落的"硬违规 vs 判断题"**合并而非并行**：那一层管陈述强度，这一层管处置紧迫度，
硬违规通常是 BLOCKER 或 WARNING，判断题最高只到 WARNING，风格偏好一律 NOTE。

### 三条一行补丁

- `build.md`：顺序有余地时**把最不确定、风险最高的那块提前**——先做确定的部分，
  等于在没验证过的假设上盖楼，错了要连带推翻后面的块；
- `build.md`（切斯特顿围栏）：需求确实要求改历史代码时，先查调用方、测试、`git blame`；
  **说不出这段代码当初为什么存在，就还没到能改它的时候**——那个看起来多余的判断
  往往是某次故障的补丁；
- `IMPLEMENTATION-TEMPLATE.md` §3：新增对外接口时站在**困惑的调用方**位置问两句——
  参数调换会不会照样编译通过？默认值会不会静默做错事？（`setFrequency(int, int)`
  两个整数传反，编译器一声不响）正确用法应该是最省力的用法。

### survey.md 补四个字段，而不是新建"上下文包"

`survey.md` 本来就是"记全一次、全程不再重读代码"的共享地图，缺的只是四项写码时
最常缺的事实：**仓内同类实现的位置**（照它写，不另发明）、**本模块的错误处理惯例**、
**必须保持不变的存量行为**、**已知历史坑**。补字段而不新建产物——新建就是又一份过程件。

### 明确没采纳（附原因）

### 小歧义：选一个，并把假设写出来

原来只写了"根本缺口就停下"。但 `implementation.md` 里够不上停下、却有两种讲得通读法的

### 路过的旧死代码：指出来，不要动

它可能有你不知道的调用方（反射、脚本、外部仓），而且会让本单 diff 混进与需求无关的行，
把真正的逻辑改动淹掉。

- `code-taste-v1.md` 第 13 条改为「删除是一等操作，但只删自己弄死的」，补上补集与反例

- `verify_ponytail.md`：明确 `delete` tag 只作用于本次新增或被本次改动弄死的代码，

## 2026-08-07：CODE 预检拆成"需求符合性"和"工程质量"两个互不参考的视角

原来一张卡把 Spec、Story 和代码规范全递给同一个 craft-reviewer-agent。这个安排有个已知的
失效模式：**一个 Agent 同时盯业务正确性和工程质量时，注意力会全部流向业务**，命名、重复实现、
资源收口这类工程问题就漏了；反过来只盯规范的也发现不了需求做错。实际上我们更偏后者——
`craft-reviewer-agent` 的 CODE 检视正文里根本没有一句要求它比对需求覆盖，
需求符合性只在实施附录的定稿自查里查过一次，那是**设计时**，代码写完后再没人比对。

- `role-task code-review` 一次调用生成**两张**卡，两个视角的权威输入刻意不同：
  - **需求符合性(spec)**：拿 Spec、Story、实施附录。三类结论——需求要求了但缺失或只做一半、
    增量里有需求没要求的行为（擅自扩大范围）、看起来实现了但方式与需求不符。
    每条必须引用需求原句，引不出原句的不报；
  - **工程质量(standards)**：**故意不给 Spec 与 Story**。只对着增量和编码基准看代码本身，
    外加两类必查（共享符号全仓引用核对、复制来的副作用在新时序里是否应该再次发生）。
    withhold 需求文档是这个设计的核心，不是省事；
- 两张卡由两个独立子 Agent 各执行一张，上下文互不污染；主 Agent 汇总时两个视角**并列列出，
  不合并、不互相重排优先级**。不额外向用户要确认——人工检视就在下一步；
- 预检仍然只跑一轮：两张卡各派一次，结论是 ISSUE 也不自动重来；
- 卡模板对 code-review **拒绝默认视角**（缺 stage 直接 ValueError）：给了默认值就等于又回到
  一个 Agent 看全部；
- `agent_tasks["REVIEWER"]` 固定指向 standards 那张卡（而不是循环里最后写入的那张——
  那会让指向哪张卡取决于迭代顺序），两张卡的路径一并记进 `axis_cards`。
  证据仍是**一次** REVIEWER 返回：拆两轴不把一个可选顾问步变成两条硬证据，
  否则观察漏报的概率翻倍，而它后面紧跟着的人工检视才是真门禁；
- 三处（卡模板、步骤提示、Agent 定义）由 `CodeReviewTwoAxisTests` 一起锁住，
  防止"卡里拆了、提示没拆"。

### 顺带修掉 grill 提问的一个复发口子

实测中 `AskUserQuestion` 出现 `InputValidationError: 无法解析为 JSON`（972 字节的选项文本）。
这不是流程问题——调用被 harness 在校验阶段退回，不写任何流程状态。但 `grill.md` 原来只说
"工具不可用才结束回复纯文本"，**模型不一定把"调用报错"读成"工具不可用"**，于是倾向于
反复重发同一个坏 payload。

- 明确写成"不可用**或调用报错**时重试一次，仍失败就用纯文本问同一题"，并说明报错不写状态、
  重问不会重复计数；
- 要求选项文本保持短：一个选项一行结论，推荐理由和代码佐证写在卡外正文——
  长文本塞进选项正是超长和未转义字符的来源。

## 2026-08-07：清掉三处"说了不做数"

### 门禁配置空转：两个 flag、11 个字段、一行反着说的提示

- `perms_line` 改为「写入范围」，只陈述真实成立的事：`tests_only` 是门禁真会拦的，

### 交付清单不认更早的提交

`delivery_manifest_committed` 只比对 `本步入口 HEAD..HEAD`。可交付清单是**整单**的产物清单，
其中一部分文件常在更早的步骤就进了 commit（质量检视后的提交、build 之后的提交）。
那些文件不在窗口内，于是报「交付清单仍未形成提交: X」——而 X 早就在 HEAD 里了，
Agent 拿着这句话无从下手。

- 新增 `_branch_committed_paths`：以 `git merge-base <基线分支> HEAD` 为界，把本分支上
  已经提交过的路径一并算作已提交。放宽的只是"在哪一段提交的"，没放宽"必须已提交"——
  diff 两端都是 commit，工作区脏改动进不来，后面的 dirty 检查照旧，
  「本步必须真的产生过提交」仍由 `commit_tagged_after_entry` 单独把关；
- 拿不到基线分支时退回原来的窗口，不静默放行。

## 2026-08-07：命令入口明确"第一动作是启动流程"

实战暴露:命令正文原来只说"不要自由发挥,严格按以下步骤执行",但**没说清第一个动作是什么**。
模型据此自行开局——派只读侦察子代理调研架构、先出实现方案——与流程意图完全相反。
在只读/计划模式下更明显:`init` 落不了盘,模型索性用"先给个方案"代替整条流程。

- `commands/mae-flow.md` 第一段即钉死:第一个动作固定是启动流程本身;禁止在启动前派只读侦察、
  禁止先做架构调研、禁止先写方案或计划——读哪些代码、读到什么深度由 grill / open / story
  各步给出确切指令,自行开局的调研既不进产物也不构成证据,纯属重复劳动;
- 若宿主处于只读/计划模式（`init` 无法落盘），要求先告知用户切出再开始，不得用方案代替流程;
- 新增测试锁住这三句，防止空档被重新引入。

## 2026-08-07：基准新增第 2 条——副作用会随复制翻倍（真实事故）

真实案例入库：既有函数 = 先 clear 资源再做业务；模型照抄出第二个函数（也带 clear）跟在
原函数后调用，第二次 clear 把原函数刚建好的资源清掉了——编译全绿，功能直接坏。

- 基准第 2 条「复用靠调用，不靠粘贴」：复制的每一行都会在新位置重新发生，clear/reset/init/
  register/truncate 这类生命周期语句写在原处是因为原处在生命周期的那个位置；复制前逐行问
  "这一行属于业务，还是属于原函数的位置"；
- Craft Reviewer 对应必查项：diff 中出现与既有函数高度相似的新函数时，核对复制进来的副作用
  语句在新调用时序里是否应该再次发生——按正确性问题报告，不占品味名额。

## 2026-08-07：编码基准 v2——补上"漏一处适配"这一类

按实际观察到的缺陷补四条（模型缺陷分类学角度，非工程学正典）：

- **改动收口**（针对"十几处修改漏一处导致基本功能坏"）：动共享符号必先全仓列引用清单再逐项
  适配——含 XML 映射、配置、SQL、反射字符串等**编译器看不见的非编译文件**；"编译通过≠适配完整"。
  三处闭环：build 纪律要求清单收口才算块完成（可派只读侦察生成清单）、基准写成 before/after、
  Craft Reviewer 对每个被动符号**独立 grep 复核**，漏适配按正确性问题报告；
- **资源在每条离开路径收口**（针对"低级错误频发"）：提前 return/异常/break 不许带着锁和连接跑，
  try-with-resources / RAII、申请释放视觉成对；
- **最小改动面**（针对可读性）：diff 里只出现需求要求的行，不顺手重排 import、不重命名路过的变量；
- **依赖方向顺着既有分层**（针对可扩展性）：新增 import 顺着仓内既定方向，拿不准看邻居 import 谁。

另：机械扇出工单从"指针"改为"载荷"——旧检查点模式慢的真正原因是每个子 Agent 重建上下文
（重读 spec/story/领域文档/代码）。铁律"工单携带上下文而不是指向上下文"：样例+文件清单+平移
规则随工单走，并明确禁止子 Agent 重读过程文档；写不成自包含工单说明这活不是机械的，主 Agent 亲写。

## 2026-08-07：实现子 Agent 从全面禁止改为边界管理

"完全不派"损失了两类真实收益，但放开必须避开品味陷阱——两个新上下文会各自发明两套方言
（两套命名、平行 helper），这正是品味问题的主要来源。边界：

- **设计承载的代码不外包**：接口定义、每类模式的第一个实现、跨模块接缝必须主 Agent 亲写；
- **只读侦察随时可派**：梳理既有抽象、调用点、模块惯例并返回精炼结论，把主上下文的注意力
  留给写码——直接服务"顺应优先于自包含"；
- **机械扇出有条件可派**：仅当第一个完整样例已亲写、接口签名已定稿、剩余是照样例平移到多处；
  派发给精确文件清单+样例路径，返回后纳入四项自查与跨块漂移检查——产出不免检；
  少于三个文件不值得派（冷启动比亲写贵）；
- 派发不改变任何门禁与证据：编译仍一次、检视仍一次、子 Agent 禁止 git 操作（现有 gate 照拦）。
  Hook 层本就对通用子 Agent 放行（不要求任务卡），此前的禁令只存在于步骤文档；
  测试改锁边界语义：放宽永远不得放宽到"实现整体外包"。

## 2026-08-07：编码品味——分块纪律与审美基准（不新增停靠、不新增编译）

流程把下限修得很好（编译/CodeCheck/UT/机械 lightcheck），但没有环节在生产上限——
这是"编译通过却难读难改"的结构性原因。两个改动，都不增加任何流程动作：

- **分块纪律**：build 步从"一口气生成全部代码"改为按 `implementation.md` 任务顺序逐块写，
  每块过四项自查（命名承接邻居/无重复 helper/错误路径同惯例/接口签名定稿），
  最后通读整个 diff 处理跨块漂移。全部发生在同一上下文内——块间不编译、不 done、不问用户。
  这是老 CP 模式的品味收益（单元小+回读）剥离掉它的成本（每 CP 三次派发+一次编译+一次人工停靠）；
  测试锁死"不得回退成流程批次"；
- **审美基准** `runtime/standards/code-taste-v1.md`：十条目标状态（顺应优先于自包含、命名承接
  邻居、防御在边界、按概念拆函数、不写投机灵活性、布尔参数是坏味道、对称性、删除是一等操作等），
  每条带 before/after。它是目标不是门禁；主 Agent 写码前读，Craft Reviewer 按单挑刺
  （品味问题与正确性问题同级占名额）。基准描述的是模型的系统性坏习惯，不采仓库历史代码；
- Reviewer 预检推荐口径改为按改动形态（跨文件/跨模块推荐启用）——模型评审能力强于生成能力，
  这一次派发是全流程性价比最高的质量投入；
- 顺带修复：`comment-standard-v1.md` 此前只有测试在锁、生产链路无人引用——现与编码基准一起
  物化到 `.mae-flow-work/plugin-resources/standards/` 并写进 build 步上下文；
  新增测试要求标准文件必须有生产消费者，防止再次出现"有资产无人读"。

## 2026-08-07：多模块 Java 仓不再默认整仓编译（提示，不是门禁）

一次交付通常只碰本服务的 sdk / model / service 几个模块，整仓 `mvn compile` 动辄十几分钟。

- `config-review` 在检测到「根 pom 声明了多个模块」且「编译命令未限定模块」时，直接在确认单的
  「编译方式」那一行下面列出仓内模块和可照抄的写法：`mvn -pl <sdk>,<model>,<service> -am compile -q`，
  并把 sdk / model / service 一类模块排在前面；
- 出现的时机就是**用户拍板编译命令的那一刻**，不用等到编译慢了才发现；
- **只是提示**：用户坚持整仓编译照样接受，不阻断、不记风险、不影响任何证据。确定长期用某条命令后
  可写进 `.mae-flow-defaults.json` 的「编译方式」自动预填；
- 已限定模块（`-pl` / `--projects` / `-f`）、非 Maven 编译方式（如 build-fix）、单模块仓都不提示，
  五种情形逐个实测过。

## 2026-08-07：修正总账里两条规则的出口分类

`bash-build-artifacts` 和 `bash-compile-side-effects` 在 `gate.py` 里被升级为绝对类——不签发放行令、

## 2026-08-07：编译产物不再靠"提示"把关

模糊产物（`.so .dll .exe .a .lib .jar .war` 与 `build/ dist/ out/ target/ bin/ obj/ debug/ release/`
等输出目录）此前只给提示、不阻断。而提示走的是门禁放行时的 stderr——宿主不会把它送进模型上下文，
**Agent 眼里那次提交完全静默**，这就是编译产物混进交付分支的直接成因。

- 位于输出目录或具有产物特征、**且 Agent 从未用 Write/Edit 直接改写过**的候选，升级为裁决类拦截
  `bash-build-output-artifacts`；文案给出 `git restore --staged` 的具体做法，并自动附一次性放行令编号，
  真要交付预编译产物时用户一句授权即可放行；
- **不按路径一刀切**：`bin/` `out/` 在有些项目里放的是正经源码。Agent 亲手写过的文件仍然只提示，
  实测 `bin/deploy.sh` 不受影响；
- 归属明确的编译副作用（`bash-compile-side-effects`）仍然先裁决——它是完整性边界，不是用户可放行项；
- 同一条信息不再既拦又提示：被拦下的路径从"产物提示"里移除。

实测放行链路完整：拦截 → 拿编号 → 捕获用户授权原话 → `allow <编号> --message-id` → 同一命令放行 →
放行令用后即废。

## 2026-08-07：给检视后回流加上界，并补齐它的转移边登记

上一轮新增的「检视之后的改动强制回流」把静默丢弃换成了另一个问题：无人值守夜跑时质量检视会
被自动通过，回流又会重新提交并前进，HEAD 每轮都变，既有的 CodeCheck 两轮上限也拦不住外层——
一个反复「再修一点」的夜跑能整夜打转。

- 回流按整单封顶两次（`LATE_REFLOW_LIMIT`）。超限后停下来并给出两条真实出路：撤销这次改动
  （`git checkout -- <文件>`）后重新 done，或把改动交给用户裁决（无人值守用 `moonlight defer`
  登记遗留、`moonlight blocked` 留痕停止）——不是把活锁换成死锁；
- `late_source_change_next` 补登进 `transition_targets`。漏登记不会在运行期报错（done 直接改
  `current`），但图校验、活性红线和环分析会对那条边全部失明：登记后流程图里立刻多出 20 个经
  该回流的环，此前完全不可见；
- 新增红线：**凡是取值为真实步骤名的键都必须被 `transition_targets` 看见**。它抓的正是这次
  自己犯的错，已用故障注入验证（撤掉登记即失败）。
- 顺带核过的可达环共 29 个，全部有界：人工检视门（交互态）、CodeCheck 两轮上限、UT 改源码需
  用户裁决 `unlock`（无人值守下 AskUserQuestion 被禁即天然封死）、以及本轮的回流上限。

## 2026-08-07：新增流程节点必须接全（两条接线红线）

已有红线管的是「删了没清干净」，管不了「加了没接全」——后者同样出真故障，而且只在夜跑或
异常恢复时才暴露。补两条可从 `flow.json` 推导的红线：

- **有质量证据（COMPILE/CODECHECK/UT/review_codecheck）的可达步骤必须登记进月光宝盒的
  `QUALITY_STEPS`**：没登记的话，无人值守夜跑在那一步撞上失败就没有 `moonlight defer` 出口；
- **不存在「改了源码之后绕过全部机器检查直达 push」的路径**：每个可达步骤要么自己重新编译、
  要么以 `review_snapshot` 拒绝脏源码、要么声明源码变化回流。这是瘦身删掉「本步不许改源码」
  之后的替代保障。

两条都用故障注入验证过真会咬：新增一个未登记的编译节点、以及撤掉本轮刚补的回流声明
（精确复现上一轮那个漏口），都会立刻失败。

## 2026-08-07：质量链只做一次人工检视

原来 Ponytail、CodeCheck、UT 每一步只要改了源码，就各自拉一轮「重新编译 + 人工检视」，
而 Ponytail 的职责本身就是删代码、几乎必然触发。最坏情况用户被叫四次，CodeCheck 还要重跑三次。

- Ponytail 改源码 → 重新编译后**直接继续 CodeCheck**（它的产物本来就要过 CodeCheck）；
- CodeCheck 修告警改源码 → 新增 `verify_codecheck_compile` 重新编译后**直接继续 UT**
  （该步自身的机器复检已经要求告警清零，回头再跑一遍没有新信息）；
- 质量链的全部改动按设计一路保持未提交，因此到 UT 之后工作区里就是本轮完整增量——
  **在这里做唯一一次统一检视**，通过即提交。人工轮次从最多 4 轮降到 1 轮，
  而且一次看合并后的完整 diff 比分三次看增量更容易判断；
- 安全性不变：最终提交的代码仍然 100% 是用户检视过的那一版（`review_snapshot` 照旧校验
  HEAD 未漂移、无新增脏文件），唯一的提交走廊仍然只有「检视通过」这一条；
- **UT 经用户裁决 `unlock source` 改的被测源码仍单独回流并重跑 CodeCheck**：那部分代码
  从未经过 CodeCheck，不能混进批量检视一起放过。

## 2026-08-07：Hook 瘦身，只拦底线（37 → 27 条）

退役 10 条流程督促规则。它们拦的都是**可逆**动作，真正的把关在 `done` 的证据检查和提交那一刻：

- `edit-source` / `bash-source`：本步不许改源码。编码-编译-检视本身就是循环，逐步拦只制造摩擦；
- `edit-specs` / `bash-specs`：写 `docs/specs/` 领域真相源。误写会在提交时被交付清单当"夹带"拦住；
- `edit-docs-req` / `bash-docs-req`：直写需求文档。编码正确性由 `requirement-record` 的回读校验保证；
- `bash-branch-name`：分支命名约定（错了可改名；提交到错分支仍由 `bash-commit-branch` 实时拦）；
- `bash-worktree`、`bash-comet-init`、`bash-mkdir-openspec`：历史包袱，不影响交付正确性。

同时删掉一条依赖"本步禁止改源码"的软提醒（cp/mv/tee 启发式，误报率高且同样到不了 Agent）。

**保留为底线的三条**（原本列在降级名单里，评估后上调）：

- `edit-tests-only` / `bash-tests-only`：UT 步禁止改产品代码。改产品代码让测试变绿属破坏信任，
  不是可逆的流程瑕疵；出口仍是用户裁决后 `unlock source`；
- `bash-compile-task-pending`：编译未完成不许提交。提交后回退要 `reset`/`amend`；它已修复为
  按真实证据放行，不再死锁。

`unlock source` 因此仍是有效逃生口，整条 unlock 机制无需退役——没有产生新的残留。

## 2026-07-25：流程魔改——轻量化与质量的平衡批次

准则:轻量化只删"重复劳动"(同一决定问两遍/同一 agent 白跑),不删决策点与证据;
每项过三问——删的是重复还是必要冗余?错误还有没有另一层接住?用户能否退回重路径?

### 一卡合一(体验)

- 配置确认卡合并收集四个开场决策(配置确认/交付方式/是否质询/是否 STORY,各带推荐):
  完整开发的用户停顿从 5 次降到 2 次(开场一卡 + 定稿确认);
- workflow_select/grill_ask/story_ask 直接消费配置卡捕获的真实答案(`_current_ack_messages`

### grill 与 brainstorming 去重(体验)

用户实感的重复有三处,病根不是"两步该合并"(WHAT 在规格前、HOW 在规格后,时序正确):

- open 决策摘要卡①类(有质询/文档依据的 Scenario)明确**禁止逐条重问**——已拍板的事再确认

- 需求级新缺口回流质询的通道原样保留(去重不去防线)。

### 质量补强(与轻量化对冲)

- `agent-task` 生成任务卡时统一注入 delivery-notes 沉淀经验(≤40 行,冲突时任务卡优先):

## 2026-07-25：误拦治理与月光/comet 集成加固

目标：把硬拦截收敛到"只拦真违规"，误拦弹回是最大的 token 浪费源；同时补上月光宝盒
与 comet 集成审计发现的真实质量洞。done 侧证据体系未做任何放松。

### 误拦六修（流畅性）

- gate 源码判定统一"项目根相对+正斜杠"匹配（原始与 realpath 双口径）：仓库祖先目录名
  含 src/app/lib 时全仓 Edit 被误判源码、defaults 锚定正则(`^ut/`)永不命中，两者同根修复；
- Bash 写盘检测强弱分层：`2>&1` 等裸重定向不再算写盘，改为解析真实落盘目标；
  `git format-patch` 不再命中 `patch`；cp/mv/tee/patch 弱启发降为软提醒（按 3.3 软层定位），
  重定向写源码与 sed -i 等强动词照拦；
- **修复"openspec 路径被判手动创建"黑事件**：`(mkdir|md|new-item)` 左侧未锚定，
  `git add openspec/.../proposal.md` 里 "proposal.md" 命中 "md" 被拦，而 clean_paths 证据
  又要求必须提交——门禁与证据互锁卡死。动词改为命令位锚定且只检查其自身参数；
- 分支 gate 排除 `checkout HEAD -- 文件` / `checkout .` / sha 游离检出等文件恢复形态；
- choice 验真从全文子串搜索改为"全等或标签前缀"（ASCII 代号只认全等）：
  "这次不是 hotfix，走完整开发" 不再被误判为 Agent 替用户改选；
- SubagentStop 多标记打回放宽：同名同值重复标记视为无歧义直接接受，矛盾标记才打回，
  且打回话术如实说明"标记互相矛盾"而非误导性的"第一行必须是标记"。

### break-glass 兜底：一次性放行令 + 三振熔断（gate 误报的优雅出口）

gate 的误报不可能降到零(静态文本判断动态行为)。兜底纪律:

- **规则分两类**:绝对类(密钥/危险命令/状态文件/伪造通道)永远没有放行令,用户手动
  执行就是它们的逃生口;裁决类(源码步骤判定/测试路径/分支与提交约定/openspec 目录等
  全部可能误报的启发式,共 14 条)接入统一 break-glass 出口;
- **三振熔断**:同一规则同一步骤连拦 3 次,拦截消息自动升级,附本次动作的放行令编号
  与签发指引——出口平时不广告,卡死的那一刻自己出现;
- **一次性放行令** `mae-flow allow <编号> --ack "用户原话"`:与 accept-risk 同级强验真;
  只豁免触发的那一条规则、只对这一个动作生效一次,绑定当前代码版本与步骤,
  用后即废、代码变化即废,签发与消费全部进历史账本;
- **月光模式**下没有用户,放行令天然签不出来:三振升级改为指向 moonlight blocked/defer
  留痕停在安全点,早晨由用户裁决——夜间完整性零妥协;
- **兜底同时是误报采集器**:三振记录进 doctor(「疑似误拦」条目),反复出现即修规则的
  工单,残余误报从事故变成带标签的 bug 报告;
- **done 证据连拒 ≥2 次时亮出用户裁决出口**:用户明确说"跳过吧/可以了"时,拒绝消息
  直接给出 `goto <下一步> --force --ack "用户原话"` 的整步跳过命令(留痕审计)——
  该通道一直存在但只写在维护文档里,"用户说跳过、hook 不听"的体验源于不可发现,
  不是不可为。没有用户原话时 Agent 仍不得自行跳过。

### 拦截时机前移（拦截时机 = 错误发生时机）

不在对的时机拦不如不拦：检测点离错误点越远，积累的重做成本越高，late 拒绝只会让
Agent 面对无法归因的证据错误然后罢工。两处重灾区前移：

- **质量 agent 派发前验任务卡**（PreToolUse 新增 Task 匹配）：compile/codecheck/UT
  派发时任务卡缺失或 HEAD 过期立即拦下并给出重签命令——原来要跑完上百轮才在
  SubagentStop/done 被打回整只重来；story 等无任务卡机制的 agent 不受影响；
- **提交时验分支**：`git commit` 的 gate 在提交这一刻校验当前分支==约定分支——
  原来只在 done 时查，站错分支提交一整步才发现，返工要 cherry-pick。

### Hook 自身健壮性

- hooks.json 六命令加文件存在守卫（if/exec 保退出码）：插件根变量缺失/文件被隔离时
  旁路放行，不再以 exit 2 锁死整个会话；dispatch 对 mae-flow.py 缺失同样 fail-open，
  子进程退出码白名单化（非 0/2 按插件故障放行并留日志）；
- stdin 兜底线程超时后改走 os._exit 收尾：消除"Fatal Python error + exit 134"；
  statusline 同样补 stdin 超时守护；
- 状态写盘对杀软短锁做指数退避重试（os.replace/os.remove 全路径）；exit 删除主状态
  失败时如实报"退出未生效"（原实现谎报成功但门禁仍在）；
- hook 日志超 5MB 滚动；DIRECT/CORRUPT 每条消息的横幅改为每会话一次；
  UTRUN 探测收窄到 UT 步骤（FIELD-TEST 0.2 待办）。

### 月光宝盒（按场景化审计修复）

- Stop 反收工护栏从"链级一发"改为无进展计数：状态 revision 有推进就继续拦，
  连续三次零进展才 fail-open——修复"第一次打回后任何收工都放行"的静默白夜；
- `moonlight off` 与 on 对称要求用户原话授权，夜间 Agent 不能自行拆除约束；
  off 后 moonlight_review 的 repair/finalize 不再要求"已开启"（消除互相踢皮球）；
- defer 复用 done 的源码回流纪律：UT 步内改过被测源码后 defer 自动回流重新编译，
  不再出现"改过源码未复验就推送"；
- `moonlight on` 冷启动补 prepare_project 前检（环境问题启动即报，不留到凌晨）；
  在已完成的终态单上开月光会先按 init 规则换单滚动，不再整夜停在"交付完成"；
- `init --ack` 接回流程时清除月光标记，恢复普通交互不再被 Ask 拦截。

### comet 集成收口（按上游 0.3.9 对照审计）

  verify_result/phase/archived/verified_at（transition 专属）；拦 COMET_FORCE_PHASE 与
  直接执行内嵌脚本；run_comet 环境剔除 COMET_FORCE_PHASE；

- 项目 .gitattributes 自动补 `openspec/** text eol=lf`，插件自身 vendor 目录加 `-text`
