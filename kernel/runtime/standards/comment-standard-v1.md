# Comment Standard v1

本规范是 Mae-Flow 新增和修改注释的唯一真相源。

注释是编码与检视的高优先级导向：让接手者理解职责、契约与决策原因。
不按注释行数、比例或模板完整度判定交付，不因注释不足新增 hook、门禁或固定确认步骤。
发现不足时指出具体理解成本和改法，由责任人判断如何收口。

## 语言与格式

- 新增业务注释统一使用简体中文。
- 代码符号、协议名、错误码和命令保留英文原文。
- 公共 API 使用语言原生 Doc 语法，正文使用中文。
- 不强制翻译未修改的历史英文注释。
- 使用完整句子和中文标点，单行不超过 120 列。

## 允许解释的内容

注释只解释：

1. 为什么选择当前实现；
2. 不能破坏的业务不变量或技术约束；
3. 调用者必须知道的错误、副作用、并发和兼容契约；
4. 临时代码存在的原因和删除条件。

禁止逐行翻译代码、保留注释掉的旧代码、记录修改历史、写无依据警告或无问题单 TODO。

## 局部注释

- 注释放在目标代码正上方，不使用行尾注释。
- 优先通过重命名、拆函数和拉平控制流消除注释需求。
- 复杂逻辑需要时写详细说明，不硬限三行；跨模块背景放入 Story，代码保留就地理解所需的约束及引用。
- 修改行为时同步检查相邻注释，更新已经失效的契约，删除误导性的旧解释。

## 公共 API

新增或修改的公共 API 只写实际存在的项目：一句话职责、前置条件、行为约束、参数的非显然语义、
返回值、错误语义、副作用、并发或线程安全。不存在的项目不保留空模板。实现与接口契约完全一致时
继承接口文档，不复制。

## 按需选用的注释模板

模板是思考提示，不是必填表。用语言原生 Doc 或块注释承载，只保留对当前代码有意义的项目。

**模块或组件**：

```text
职责：<提供的业务能力、调用入口>。
边界：<依赖哪些外部能力、由谁负责状态和资源生命周期>。
关键约束：<必须维持的业务不变量、幂等或一致性约定及原因>。
```

**公共接口**：

```text
<一句话说明调用者可以依赖的行为>。
输入约定：<单位、范围、空值、前置条件等非显然语义>。
结果与失败：<返回值含义、失败是否重试、是否可能已产生部分副作用>。
副作用与并发：<写入、事务、线程安全或重复调用约定>。
```

**复杂逻辑或兼容处理**：

```text
这里采用 <处理方式>，因为 <代码本身无法表达的业务或技术原因>。
必须保持 <不变量>；否则 <具体影响>。
```

例如 SQL 构造函数应说明“占位符与参数同步追加，以保持参数顺序；空筛选条件不代表允许全表更新”，
而不是逐行写“创建数组、遍历参数、返回 SQL”。实际数据库事务和失败语义写在执行边界。

## TODO 与 FIXME

只允许以下格式：

```text
TODO(<问题单>): <待完成动作>；删除/完成条件：<明确条件>。
FIXME(<问题单>): <当前已知缺陷>；临时处理：<当前方案>。
```

无问题单、无动作或无结束条件的 TODO/FIXME 不允许新增。

## Task 注释计划

每个实现 Task 必须使用 `ADD`、`UPDATE`、`REMOVE` 描述具体符号和理由；确实不需要时写：

```text
NONE：行为可由类型、命名和控制流完整表达。
```

禁止“适当补充注释”等模糊表述。
