# 编码基准 v1（审美目标）

定位：这是**目标状态**，不是门禁。lightcheck 与 CodeCheck 守下限（能编译、无告警、
不超机械限值）；本文件描述"好"。主 Agent 写每一块前后对照自查，Craft Reviewer 按本单
逐条检查。所有条目服从一条总纲：**代码是写给下一个读它的人的，那个人默认不是你**。

## 1. 顺应优先于自包含

动笔前先找仓内同类实现。已有的抽象能用就用、能扩展就扩展；只有说得出"既有的为什么
不够"时才新建，并把理由写进实施附录。

- 坏：仓里已有 `OrderUtil.parse()`，新代码又写了 `OrderHelper.doParse()`，两套并存
- 好：调用或扩展 `OrderUtil`；确需重写时先删旧的（删除是改动的一部分）

## 2. 复用靠调用，不靠粘贴：副作用会随复制翻倍

需要"同样的事"时调用既有函数；只需要其中一部分时，先把那部分提取出来再调用。
整块复制的每一行都会在新位置**重新发生**——尤其 clear/reset/init/register/truncate
这类生命周期语句：它写在原处是因为原处在生命周期的那个位置，复制到别处就是在
错误的时机多执行一次。复制前逐行问：这一行属于业务，还是属于原函数的位置？

- 坏（真实案例）：既有函数 = 先 clear 资源再做业务。照抄出第二个函数（也带 clear），
  跟在原函数后调用——第二次 clear 把原函数刚建好的资源清掉了。编译全绿，功能直接坏
- 好：直接调用既有函数；或把业务段提取成独立函数复用，clear 留在唯一的生命周期入口

## 3. 改动收口：动了共享符号，必先列全引用清单

修改函数签名、枚举值、常量、配置键、协议/表字段时，先全仓列出**全部**引用再逐项适配——
含 XML 映射、YAML/properties 配置、SQL、反射字符串、定时任务注册等**非编译文件，
编译器看不见它们**。清单没收口，这一块就没写完。**编译通过 ≠ 适配完整**。

- 坏：`queryOrder(id)` 加了租户参数，十三处调用改了十二处，MyBatis XML 里那处没动——
  编译全绿，基本功能挂
- 好：先用 mae-flow 的 `symbol-refs queryOrder` 列全仓清单（自动含资源目录与未跟踪文件），
  逐项对钩后才进入下一块

## 4. 命名从邻居继承，同一概念全程一个名字

新文件的命名风格抄同目录邻居，不自创方言；一个概念在本次改动里只允许一个名字。

- 坏：同一份配置在三处分别叫 `cfg`、`config`、`settings`；仓里都叫 `Repo` 它偏叫 `Dao`

## 5. 错误处理：防御在边界，一次到位，错误带上下文

入口校验一次并给出带上下文的错误；内部代码信任已建立的不变量，不逐层重复判空。
吞掉异常等于把调试成本转嫁给未来的值班人。

- 坏：每层都 `if (x == null) return null;` —— 错误无声传播，最终在离根因十万八千里处爆掉
- 坏：`catch (Exception e) { log.warn("failed"); }` —— 丢上下文、吞栈、继续跑
- 好：边界处 `Objects.requireNonNull(order, "order from mq payload")`；内部直接用

## 6. 资源在每条路径上都要收口

提前 return、抛异常、continue/break——每条离开路径都不许泄漏资源或漏还状态
（流、连接、锁、事务、计数器）。这是"低级错误"的最大来源之一。

- 坏：`lock.lock(); if (invalid) return; ... lock.unlock();` —— 提前返回带锁跑了
- 好：Java 用 try-with-resources / try-finally；C++ 用 RAII；申请与释放视觉上成对

## 7. 最小改动面

diff 里只出现需求要求的行。不顺手重排 import、不重排字段、不改无关空白、
不重命名路过的变量——无关变更污染检视，还掩盖真正的逻辑改动。

## 8. 函数按概念拆，不按行数拆

lightcheck 的 50 行是下限不是刀。每个函数名必须是一个能独立陈述的职责。

- 坏：`doWork1/doWork2/doWork3` 各 49 行，互相传 7 个参数
- 好：`validateQuota() / reserveStock() / emitAuditEvent()`，各自能单独解释

## 9. 不写投机的灵活性

没有第二个调用方之前：不抽接口、不加配置开关、不留"以后可能用"的参数。
可扩展性来自清晰的职责边界，不来自预埋的钩子。

- 坏：单实现的 `XxxStrategy` 接口 + 工厂 + 配置项，全仓只有一个分支
- 好：直接写那一个实现；真出现第二个变体时再抽——那时才知道变化轴在哪

## 10. 依赖方向顺着既有分层

新增 import 必须顺着本仓既定的依赖方向；拿不准就看邻居 import 了谁。
下层引用上层、工具类反依赖业务、跨层直捅，都是把未来的改动成本焊死。

- 坏：`common/util` 里 import 业务 `service` 的类；Mapper 里写业务判断
- 好：依赖只往下（或只往接口）；需要反向信息时用回调/事件，跟仓里既有做法一致

## 11. 布尔参数是坏味道

`send(order, true, false)` 在调用点读不懂。两个以上布尔参数几乎必然是两个函数
被硬挤在一起。

- 坏：`export(data, true /*compress*/, false /*async*/)`
- 好：拆成 `exportCompressed(data)` / 用枚举 `export(data, Mode.COMPRESSED)`

## 12. 对称性：相似的事看起来相似

新增第 N 个 case/分支/处理器时，先读前 N-1 个，让新的长得像旧的——结构、顺序、
错误处理、日志格式全部对齐。读代码的人靠差异发现逻辑，无意义的差异是噪音。

## 13. 删除是一等操作，但只删自己弄死的

改动使旧代码失效时，删掉它：不注释掉、不留 `_old` 后缀、不留"暂时保留"的死分支。
本次改动让某个 import、变量、函数没人用了，它就属于这次改动的收尾。
ponytail 会兜底，但兜底不是授权。

**补集同样是纪律**：不是本次弄死的旧死代码，**指出位置就够，不要删**。
它可能有你不知道的调用方（反射、脚本、外部仓），而且顺手删会让本单 diff 混进
与需求无关的行，把真正的逻辑改动淹掉（第 7 条）。要清理就单独开一单，由用户决定。

- 坏：改 A 函数时顺手删了隔壁看起来没人用的 B——B 被一份 XML 按名字反射调用
- 好：删掉因本次改动而失效的那三个 import；在结论里点一句"B 疑似无引用，未处理"

## 14. 注释解释为什么，不复述代码

按 `comment-standard-v1.md` 执行：新增业务注释用简体中文，写"为什么这样做/为什么
不那样做"；逐行翻译代码的注释一律不写。遗留问题用 `TODO(<问题单>)` 留痕。

## 15. 出错先定位根因，再动手改

铁律：**没做完根因定位，不许提出修复**。症状修复算失败——改一行看看好没好，是把偶发
变成潜伏。编译失败、测试失败、行为不对，全部适用；越急越要走这条，试探性修补比它慢。

1. **逐字读报错**：堆栈读完、行号文件码看清——答案常常就写在里面，不要跳过去看代码；
2. **稳定复现**：确认触发步骤；复现不了就继续收集证据，不许靠猜；
3. **查最近改动**：`git diff` 与本轮已写的块——多数故障来自刚动过的东西；
4. **多层系统先加诊断再改**：跨组件（接口→服务→存储、构建→打包→签名）时，先在每个边界打点
   看数据进出与配置传递，跑一次定位到**是哪一层坏的**，再去查那一层；不许对着整条链猜；
5. **一次只改一个变量**：改完立刻验证这次假设成立与否；两处一起改就分不清哪处起了作用。

- 坏：测试红了 → 直接改被测代码里看起来相关的那行 → 还红 → 再改一处 → 越改越乱
- 好：先看断言实际值与期望值差在哪 → 定位到数据在哪一步被改写 → 只改那一处 → 验证

## 16. 散弹式修改：先做完，再记账，不顺手重构

一个逻辑改动逼你在很多文件里做同一件事（新增一个渠道要动枚举、工厂、三份配置、XML 映射、文档），
说明这个概念没有归拢在一处。本次交付照旧把每一处改完（第 3 条），额外做一件事：
把观察记进实施附录的风险节——**分散在哪几个文件、下次新增同类还要动几处**。

归拢的时机是"同一处分散第二次咬到人"且用户同意；本次交付里第 7 条最小改动面优先。
留下账比悄悄重构有用：下一个人凭这条记录就能判断值不值得动，而不必重新踩一遍。

- 坏：发现分散 → 本单顺手把枚举 + 工厂重构成注册表 → diff 一半改动与需求无关，检视被冲淡
- 坏：发现分散 → 六处改完就走 → 下一个人重新摸索一遍，始终没人知道这里要动六处
- 好：六处全改完并逐项对钩 → 实施附录记"新增渠道需同步 6 处，清单在此" → 何时归拢交给用户定

## 17. 每块写完的四项自查（与 build 步骤一致）

1. 命名与邻居文件一致？
2. 有没有和本次已写、或仓内已有重复的 helper？
3. 错误路径处理与本模块惯例一致？
4. 暴露给后续块的接口，签名此刻定稿？

本块动过共享符号的，额外核对第 3 条"改动收口"的清单是否逐项打钩。
