# 编码执行方式:新上下文(L3)

仓库预设 `.mae-flow-defaults.json` 写 `"编码执行方式": "新上下文"` 时,build 步改按本协议执行。
默认(未设置或 `"主会话"`)不走本文,主 Agent 亲写,一切照旧。

## 为什么存在这个模式

长会话尾部写码,注意力已被四个阶段的对话稀释——被否掉的方案、中途改过的主意
都还躺在上下文里(lost-in-the-middle)。本模式做一次干净的倒置:

- **老上下文不再生成代码**,只干它真正擅长的:拆工单、验收 diff、
  用它记得的用户意图纠偏;
- **新上下文(实现子 Agent)只看工单**,不带包袱地按用户确认过的决策实现。

## 第一原则:喂到嘴边,不给路径

**新鲜上下文是本模式唯一的资产,让子 Agent 自己去读文档就是当场把它挥霍掉。**
读三份文档 40KB、再 grep 几轮代码库,它开写时的注意力和主会话已经没有区别——
换个脑子写码的意义随之归零。所以工单**携带原文摘录,不携带文档路径**
(派发三原则第一条;机械扇出一直是这个纪律,本模式一视同仁)。

工单必须**内嵌**:

1. 该任务对应的**验收项原文**(从 spec/story 摘录的原句,不是"见 spec.md");
2. **接口契约两栏逐字**:消费(前序任务已定稿的精确签名)、产出(后续任务会依赖的签名);
3. **文件清单与单一职责**:每个文件新建还是修改、这次要它承担什么;
4. **必要的既有代码摘录**:要照着写的样例函数、要对齐的邻居命名、要复用的工具函数签名——
   由主 Agent 摘给它,不让它自己找;
5. 编码基准路径(`code-taste-v1.md`,唯一允许给路径的文档,约 9KB,通用且必读)。

**子 Agent 被明令禁止**:读 spec/story/实施附录/grill/决策记录/领域文档;
通读代码库;探索式 grep 找上下文。**唯一允许打开的代码**是工单点名的待改文件
与样例文件——改一个文件当然要先看它,但看的范围由工单钉死。

信息不够时**返回 NEEDS_INPUT 说明缺什么**,由主 Agent 补进工单重派;
子 Agent 自行去仓库里补齐上下文,等于把本模式的收益还回去。

## 协议

1. 主 Agent 读三份文档与编码基准(照常),按 `implementation.md` 的任务边界
   逐任务出**自包含工单**(内容见上),写明"所需信息全在本工单内,不回放聊天记录,
   不要读 spec/story/领域文档,不要通读代码库"。
2. 每个工单派一个实现子 Agent(通用型,可写码,禁 git 操作)。任务间有
   接口依赖时按顺序派,无依赖可并行;**上一任务的产出签名进下一工单**。
3. 子 Agent 返回后,主 Agent 通读其全部改动,执行 build 步的四项自查与
   跨块漂移检查——**产出不免检**,这条与机械扇出同款,不因模式放宽。
4. 全部任务完成后照常:一次 COMPILE 任务卡、一次人工检视。
   门禁与证据一个都不变。

## 边界(与主会话模式共用的铁则)

- 工单写不成自包含 → 该任务回主 Agent 亲写(信号:文档没承载住决策);
- 子 Agent 卡住或返回 NEEDS_INPUT → 修工单重发,不替它补产出;
- 主 Agent 在验收中发现文档有缺口 → 停,走既有的"缺口回实施附录订正"通道,
  不在工单里口头补需求。
