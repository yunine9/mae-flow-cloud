向用户展示当前完整未提交 diff、修改文件和编译结果，请他检视。
**别指定他在哪看**（IDE、编辑器、某个本地路径）——宿主形态不由你决定：
终端用户在 IDE 里看，云端控制台用户在页面上看，说错了就是给一条他做不到的指令。

**小结是写给人看的，不是写给流程看的。** 用户要在这里拍板"放不放行"，
他需要的是"改了什么、为什么这么改、哪里值得你多看一眼"：

- 先一句话说清这一轮解决了什么问题，用需求的说法，别用代码的说法；
- 再逐条说每处改动为什么这么做。有取舍的、你自己没把握的，明确点名
  "**这处请你重点看**"——用户最需要的恰恰是这几处，而只有你知道它们在哪；
- 不列文件清单、不报行数统计、不复述 diff：那些他在改动里看得见，
  重复一遍只会把真正要紧的两三句话淹掉；
- 不用流程黑话。步骤名、门禁名、Agent 名、证据类型对用户都是黑话。

信息密度高不等于说清楚了。用户看不懂的小结，等于没有小结——他只能盲签，
而盲签正是这个人工节点存在要防的事。

用 AskUserQuestion 只询问一次：

- `我已认真检视并完成自验证，继续`
- `需要调整代码`

用户点选后同轮执行 `done --choice continue|revise`。Agent 预检只是可选辅助，不代替本次人工检视。
该规则同样适用于后续质量阶段产生的源码、测试或构建改动；质量阶段通过统一检视节点执行，不在各 Agent 内提交。

本步的取舍依据（检视关注点与返工边界），见 `.mae-flow-work/plugin-resources/guidance/review.md`。
