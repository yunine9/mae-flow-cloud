评审意见处理的裁决步(receiving-code-review 纪律:先查证、再裁决,反驳要依据,禁照单全收)。
把模板 {REVIEW_TEMPLATE_PATH} 复制落盘为 `.mae-flow-work/{单号}/review.md`
(文件已存在 = 前轮记录,本轮**追加新一节**勿覆盖;章节结构由 hook 校验)。
收集意见:用户粘贴的评审/走读/门禁意见**原文照录**进意见清单,禁止改写、归并、漏条;逐条标「待裁决」。
逐条处理,顺序固定:
1. **先亲自查证**(事实自己查):意见指的代码在哪、说得对不对、影响面多大——结论写进"定性"栏,带文件/行出处;
2. **再呈用户裁决**(决策问用户):意见互相独立时按每卡最多 4 条分批放进一次
   AskUserQuestion 调用(每条仍是独立问题,附你的定性与建议);同根因、修法互斥等互相耦合的意见,
   或用户追问某一条时退回逐条裁决。每条都有三个去向:
   - **修复**:纳入本轮修复清单;
   - **反驳**:写明代码/spec 依据,汇总进「反驳汇总」章(用户可直接贴回评审系统);
   - **转规格轮次**:意见涉及行为/规格变更——review 轮次红线是**不碰规格**,该条本轮不修,
     提醒用户之后按 hotfix/full 另开轮次处理;
   禁止不查证就全盘接受("您说得对"式照单全收与伪造同罪),也禁止未经用户同意自行反驳。
全部裁决完(done 硬校验:零「待裁决」残留 + 本步内真实 AskUserQuestion)→ 展示三类汇总 → done。
评审裁决是本地过程件，禁止 git add 或 commit。
批量呈卡只合并往返轮次,不合并意见、定性或决策。每条意见已经由用户逐项裁决，汇总后不再要求用户重复确认。
若裁决原话和文档都已完整落盘,仅因宿主未签发 ASKUSER 令牌被拦,按 done 报错让用户选择
重问或 `accept-risk askuser`;放行不会消掉「待裁决」、未提交文档等其他检查。
中断恢复:读 REVIEW 文档,残留「待裁决」的条目接着查证/裁决,已确认的禁止重问。
