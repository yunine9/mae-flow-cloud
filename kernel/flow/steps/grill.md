五条铁律（与下文冲突时以此为准）：1 不懈追问直至共同理解；2 沿决策树逐支走，**树在对话中生长**；
3 每题附推荐答案（含理由与代码佐证）；4 一次只问一个，等回答再问下一个；5 事实自己查、决策问用户。

本阶段的哲学（用户原话，照此执行）：**不怕问题多，就怕问题遗漏**——很多人自己都不知道需求要达成什么预期，
grill 的目标就是让开发和 AI 共同把边界和细节全部摆上台面。

## 执行顺序

1. **定向读领域文档**：从需求中提取领域关键词，执行
   `python "{MAEFLOW_PATH}" domain-docs context --term "<需求关键词>"`，只读输出列出的相关文档。
   索引报错时先执行 `python "{MAEFLOW_PATH}" domain-docs validate` 修好再继续。
2. **代码勘察**：通读 SE 文档 → 定向探索相关模块，边探边把「代码勘察笔记」写进
   `.mae-flow-work/{单号}/survey.md`（相关模块清单、关键文件 + 职责、现有接口/数据结构、
   调用链要点、与本需求的触点，外加四项写码时最常缺的事实：**仓内同类实现的位置**（照它写，
   不另发明）、**本模块的错误处理惯例**、**必须保持不变的存量行为**、**已知历史坑**）。
   这份笔记是后续 open/design/build 阶段的共享地图：
   **记全一次，全程不再重读代码**。
3. **备课**（先填工作表，再开口提问）：把模板 {GRILL_PREP_TEMPLATE_PATH} 全文复制落盘为
   `.mae-flow-work/{单号}/grill-prep.md`（先保结构后填内容；章节由 hook 校验，缺章打回），
   再逐维把「(待填…)」占位替换为结论。**8 维每维都要落一个实质结论**，二选一：
   - 有缺口 → 写成候选题，四要素齐全：缺口位置 / 代码佐证 / 推荐答案 / 实现影响（写不出实现影响的删掉）；
   - 不适用 → 写出定位到代码或文档的具体依据（"无关""不涉及"不算依据）。

   SE 文档写清了某维也照此办：转成"确认题"（向用户核实我理解得对不对），或"不适用 + 依据"。
   hook 会拦残留的 {{占位}}/待填，逼你真扫过每一维。第 9 章汇总：候选题按阻塞性排序，
   技术分歧记入「留给设计阶段」。
4. **备课 Critic**：执行 `python "{MAEFLOW_PATH}" role-task grill-critic --stage prep --document ".mae-flow-work/{单号}/grill-prep.md"`，
   把输出的唯一启动话术原样交给 grill-critic-agent。它只读找遗漏；把真实缺口补入候选题后再开始提问。
   **它在后台跑、还没回来时：直接结束回复等它。** 不要用占位问题、进度同步之类的提问占着——
   等后台 Agent 不是需要用户决策的事，拿它打扰用户是白打扰一次。
5. **成组质询**：优先 AskUserQuestion（选项 = 推荐答案（标注"(推荐)"）+ 主要备选，用户可 Other 自由输入）。
   **彼此独立的题一次问 3～4 个**——AskUserQuestion 本来就能一次带多题，各题各自作答，不会串。
   实测一次交付的候选题可达 17～23 个，一题一回合就是二十多个来回，光这一段就占掉全程三分之一。
   **必须单独问的两类，不许合并**：① 后一题的问法取决于前一题的答案（先问渠道范围，才知道要不要问重试次数）；
   ② 高影响裁决（豁免、改被测源码、承担风险、缩小范围）——这类要用户看清上下文单独拍板。
   拿不准是否相关就分开问：合并问错的代价，比多问一轮大得多。
   **选项文本保持短**：一个选项一行结论，推荐理由和代码佐证写在卡外的正文里——
   长文本塞进选项会让工具输入超长或带进未转义字符，调用直接被判非法。
   AskUserQuestion 不可用**或调用报错**时，重试一次；仍失败就结束回复、用纯文本问同一题，
   不要反复重发同一个 payload（报错不写任何流程状态，重问不会重复计数）。
   每拿到**一组**答案，先跑下方**衍生检查**（逐条对刚拿到的每个答案跑），再问下一组。
6. **收敛**：题尽（含衍生题）/ 用户说"其余按推荐答案"（落盘标注未经确认）/
   超 15 题 → 告知规模由用户选（用户要继续就继续，不设硬上限）。
7. **收尾 Critic**：先把当前完整树同步到 `.mae-flow-work/{单号}/grill.md`，再执行
   `python "{MAEFLOW_PATH}" role-task grill-critic --stage final --document ".mae-flow-work/{单号}/grill.md"`，
   把输出的唯一启动话术原样交给 grill-critic-agent（同样：它没回来就结束回复等着，不发占位提问）。
   它指出的新缺口回到第 5 步逐题问；
   无缺口、或新增题闭环后才收尾。Critic 只在这一步跑一次。
8. **落盘并 done**：增量写 `.mae-flow-work/{单号}/decisions.md`，把完整问题树、用户答案、推荐依据、
   实现影响、未决项整理进 `.mae-flow-work/{单号}/grill.md`。两者都是本地 Spec 和 Story 的强制输入，
   已拍板答案在下游直接引用、不再重问。展示摘要后直接 done——用户已在逐题过程中完成决策，
   "阶段结束"不额外索要一次确认。Grill 的文件都是本地过程件，留在工作目录里，不进 git。

## 衍生检查（每个答案都逐条机械触发）

- 答案含"一般/通常/大概/看情况/应该/都行" → 追问到具体值或具体条件；
- 答案引入工作表里没出现过的名词/状态/场景 → 追问其定义与边界（新名词 = 新问题源）；
- 答案与工作表已有结论或此前答案矛盾 → 当场对质，以用户裁决为准并更新旧结论；
- 答案推翻某维"已覆盖"的判断 → 该维重开，补出候选题；
- 用户反问"你觉得呢/你定" → 给推荐 + 依据，仍要用户点头确认。

衍生出的新题**追加进工作表**（标注"衍生自答案N"）并入队继续问——问题变多是本阶段在正常工作。
**工作表是起点弹药库，不是问题总量**：真正的 grill 发生在问答里，树随答案生长。

## 提问的高度

本阶段只问**需求/规格层**决策：要什么、边界在哪、什么算对。技术实现方案的分歧（选型、模块划分、算法）
记入「留给设计阶段」清单（工作表第 9 章，收尾时同步到本地 decisions 文档尾部），交给设计阶段展开——
在这里问会和那一步撞车。

凡属**行为规格**的答案，落盘写成 EARS 句式：「WHEN <条件/触发> THE SYSTEM SHALL <可观测行为>」
（一句一测，是后面规格条目 Scenario 和 UT 验收对照的原材料）。写不成 WHEN/SHALL 的答案多半没问透，
回炉再问。

## 八维全部无缺口时

若 8 维全部为「不适用 + 具体依据」且候选题为 0，用一次 AskUserQuestion 展示八维结论摘要，
让用户选择「确认八维均无待决项，直接进入提案 / 指定某一维继续抽查 / 补充遗漏信息」。
拿到这次真实决策后直接收尾，满足 ASKUSER 证据。问题由工作表推导，不凭空发明。

## 中断恢复

先读 `.mae-flow-work/{单号}/grill-prep.md`（备课与衍生题）与 `.mae-flow-work/{单号}/decisions.md`
（已拍板答案），从未问的题继续——已拍板的直接沿用，文档即状态。

本步的取舍依据（追问深度与停止条件），见 `.mae-flow-work/plugin-resources/guidance/grill.md`。
