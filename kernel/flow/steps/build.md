本步从第一行代码到定稿一次完成需求涉及的全部生产代码:实现、编译、精简、规范、测试、
对照需求,顺序你自己定,中间没有任何强制关卡;不要拆开发批次,也不新建编码前计划文档。
出口有三道**真**验收替你把关:推送前宿主会在构建容器里跑仓库真实编译与 UT;权威流水线
绑当次 SHA 复验;检视人提意见，由责任人逐条决定并闭环。所以本文档只给判据与边界,不给编排——
**你的自由越大,出门自查越要当真**。

**注意力锚定**:编码依据**只有**本单 `spec.md`、`story.md`、`implementation.md` 与
`.mae-flow-work/plugin-resources/standards/code-taste-v1.md`(编码基准)、
`.mae-flow-work/plugin-resources/standards/comment-standard-v1.md`(注释标准);
会话早前与文档冲突的记忆(被否掉的方案、中途改过的主意)一律以文档为准——
文档是用户确认过的版本，记忆不是。

## 干活方式

- **核心原则：关键代码可被接手者理解**。按注释标准中的模块、公共接口、复杂逻辑模板按需说明
  职责、错误与副作用契约、业务不变量和选择原因；复杂处可以详细写，避免逐行翻译代码。
  行为变化同步更新旧注释，收口时专门通读本次增量的注释与实现是否一致。
  不为凑模板写空项，不按注释数量阻断交付，不新增 hook、门禁或固定确认。
- **分块纪律**:按 `implementation.md` 的任务顺序逐块写;顺序有取舍余地时,
  **最不确定、风险最高的块提前**。每块收尾过一遍四项自查:命名与邻居一致;
  无重复 helper;错误路径与模块惯例一致;暴露给后续块的接口签名定稿。
  块与块之间不 done、不询问用户;编译时机自定(随块编译或最后统编都行)。
- **编译自检派通用子 Agent**:编译尽量不在自己上下文里跑——完整构建日志会淹掉
  你正在写的代码现场。用 Task 派一个通用子 Agent(subagent_type 如
  `build-verify-agent`,不要用 compile-agent 等保留名,那些卡已退役),工单写清:
  按仓库真实构建入口增量编译(存在 `.mae-flow-work/build-notes.md` 时优先按它,
  没有就自己发现并顺手写入该文件),只回传结论与前几条错误原文,不改任何文件、
  不做 git。失败由你自己修——子 Agent 没有你的实现上下文。
  开始某块执行 `python "{MAEFLOW_PATH}" milestone start --task <编号>`,
  完成用 complete、卡住用 block(带 --reason)——append-only 观察事件,
  只喂云端进度展示,不参与任何门禁。
- **核心原则：可测试性在编码时形成**。函数级 UT 是基础，模块/集成验证与之互补。
  将条件判断、数据转换、SQL 构造和参数绑定等逻辑与数据库执行、远端调用等副作用合理分离，
  让逻辑能通过输入输出直接验证。公共依赖沿用可替换边界，mock/fake 在测试支持代码中按需
  复用、按用例隔离状态；按测试目标隔离外部依赖，被测逻辑使用真实实现，不 mock 核心判断来验证预设答案。
  不为测试方便给每个类加接口，不向生产代码塞测试分支；遗留耦合难以隔离时如实报告验证缺口，
  不用大量内部 mock 冒充覆盖。这是编码导向，不增加机械门禁或固定人工确认。
- **单测写法**:本单配置「UT生成方式: {UT生成方式}」。取值是 skill 名(如 java-autout、
  AutoUT)时,**写第一个测试之前先用 read 工具读取该 skill 的 SKILL.md 全文**
  (路径在系统提示 available_skills 里),之后严格按它的写法展开;把测试外包给
  子 Agent 时,工单里必须原文携带 skill 的关键约定。取值为「仓内既有写法」则
  先读同模块既有测试再动笔。没读 skill 就写测试 = 没按团队规范写,检视会打回。
- **模块级 UT 同样重视**：在函数 UT 基础上，结合本模块已确认的验收场景，从业务入口
  运行内部真实协作，尽力覆盖关键正常、边界和异常行为。复用仓内测试框架与命令，只有必要
  的外部依赖使用替身；没有现成测试入口时，在本次改动范围内合理建立测试装配，不另造测试平台。
  派测试工单时携带入口、场景依据、真实执行范围及替身边界；报告实际运行结果。环境或耦合限制
  无法解决时说明未验证场景、原因和影响，交责任人决策，不凑数量、不把函数 UT 通过当作模块已验证，
  也不新增模块 UT 专门门禁或固定审批步骤。
- **设计用例落实**：测试名称或注释关联设计用例编号，可一对多或多对一。收口时逐条说明
  对应测试位置、实际执行结果及证据，未编写、未执行或覆盖不足的场景如实说明原因和影响。
  核对条件、操作、预期与真实断言，不仅核对编号；不擅自改变已确认预期来迁就实现。
  对应清单仅供现有检视使用，不要求固定格式，不新增 hook、门禁、阻断状态或审批步骤。
- 全部块写完通读整份改动,消掉**跨块漂移**(同一概念两套写法、前紧后松的错误处理)。
- **改动收口**:动过共享符号(签名、枚举、常量、配置键、协议/表字段)就用
  `python "{MAEFLOW_PATH}" symbol-refs <符号>...` 列出每一处引用逐项适配——XML/YAML/SQL/
  反射字符串编译器看不见,编译通过不等于适配完整。
- **卡住就停，不要猜**:缺依赖、指令不清、`implementation.md` 有根本缺口时停下说明,
  不做试探性修改;计划层缺口回实施附录订正(经用户确认后 goto)。
  **小歧义:选一个,把假设写出来**(「按 X 理解,另一种读法 Y,影响 Z」)——检视人看得到
  假设才能纠偏,默默挑一个就是让检视少一次机会。

## 编码执行方式

仓库预设「编码执行方式: 新上下文」时,改按
`.mae-flow-work/plugin-resources/guidance/build-fresh-context.md` 的协议执行:
主会话只拆自包含工单与验收,代码由新鲜上下文按文档实现。未设置即主会话亲写。
两种方式的门禁与证据完全相同。

## 子 Agent 边界

设计承载的代码不外包——接口定义、每类模式的第一个实现、跨模块接缝由主 Agent 亲写。
可派两类,工单一律**自包含**(携带上下文,而不是指向上下文):
**只读侦察**(窄问题+明确入口,返回压缩结论);**机械扇出**(已亲写第一个完整样例、
接口定稿、剩余是照样平移到三个以上文件;工单给样例路径或 diff、目标清单、平移规则,
并写明"不要读 spec/story/领域文档,所需信息全在本工单内")。写不成自包含工单,
说明这活不是机械的,改由主 Agent 亲写。
子 Agent 的产出不免检,一并纳入自查;子 Agent 不做 git 操作。
派出去没收到返回时先查生命周期事实,**禁止自动重派**——上一只可能还在跑,
重派只会两只互踩;确认死透再派新的。

## 出门清单(done 之前逐项自问,凭真证据作答,"应该没问题"不算)

1. **编译过**:{{#LOCAL_COMPILE}}用本单配置的编译方式真实跑过。{{/LOCAL_COMPILE}}{{#PIPELINE_COMPILE}}在容器里按仓库真实构建方式编译过(pom/build 脚本自己找);
   构建链确实起不动就如实说明,留给推送前验证与流水线,不许编造绿灯。{{/PIPELINE_COMPILE}}
2. **精简过**:只审本单 diff(基线..HEAD),该删的删——但 YAGNI 不砍 spec 要求的行为
   (spec 是合同,砍需求先呈报用户);不是本次弄死的旧死代码点个位置就好,diff 里不出现,
   顺手清理会把真正的逻辑改动淹掉。
3. **规范与测试**:规范问题扫过修过;新逻辑有测试盯着,按「UT生成方式」的口径写全
   {{#LOCAL_UT_RUN}}(用本单配置的 UT 命令真实跑过){{/LOCAL_UT_RUN}}{{#PIPELINE_UT_RUN}}(运行与统计在权威流水线,你保证测试能编译、断言真实;
   推送前宿主验证会先跑一遍,写空壳测试当场现形){{/PIPELINE_UT_RUN}}。
4. **对照需求核过**:把 spec 与 Grill 决策拆成逐条验收项,每条指得出实现位置与验证证据;
   指不到位置的只能算"缺失",不能因为"整体看起来实现了"就放过。发现 spec 与实现不一致,
   向用户裁决一次,不擅自选边。
5. **改动已提交**:在本单约定分支上核对实际 diff，提交本次要交付的文件。
   提交信息建议带单号；本地暂存方式和提交批次由你选择，不会因 `-A`、`.`、提交格式
   或代码与文档混合提交而被拦。构建产物可留在工作区支持增量编译，不应仅为消除
   内部记账提示而清缓存、回退提交或修改 `.gitignore`。交付文件以人的选择为准。
   确认应交付内容已进入提交，避免漏交；质量失败和未验证项如实报告，不伪造通过。

清单过完执行 `done`,进入知识归档与交付清单,随后推送。判断口径的完整版见
`.mae-flow-work/plugin-resources/guidance/construction.md`(分块与派发的取舍依据)与
`.mae-flow-work/plugin-resources/guidance/quality.md`(精简与质量链口径)、
`.mae-flow-work/plugin-resources/guidance/review.md`(检视意见的接收纪律:先核实、
可带依据反驳、一次一项、不做表演式回应),需要时自己读,不需要背。
