本步在同一步骤内一次完成需求涉及的全部生产代码：一次构建验证义务、一次人工检视，代码保持未提交。
任务顺序已在 `implementation.md` 里——不要拆开发批次，也不新建编码前计划或实现任务文档。

**注意力锚定**：本步编码依据**只有**下列三份文档与两份基准；会话早前与文档冲突的
记忆（被否掉的方案、中途改过的主意、拷问期的试探性说法）一律以文档为准——
文档是用户确认过的版本，记忆不是。

## 执行顺序

1. 读本单 `spec.md`、`story.md`、`implementation.md`，以及
   `.mae-flow-work/plugin-resources/standards/code-taste-v1.md`（编码基准）与
   `.mae-flow-work/plugin-resources/standards/comment-standard-v1.md`（注释标准）。
2. **分块纪律**：按 `implementation.md` 的任务顺序逐块写，每块收尾过一遍下方**四项自查**
   并给出结论，过了再写下一块。块与块之间不编译、不 done、不询问用户。
   开始/完成某块时可分别执行 `python "{MAEFLOW_PATH}" milestone start --task <编号>` 与
   `milestone complete --task <编号>`；卡住则用 `milestone block --task <编号> --reason "<简短原因>"`。
   这些是 append-only 观察事件，方便云端展示过程进度；**不拆 build 步、不产生人工卡、也绝不参与 done 门禁**。
   顺序上有取舍余地时，**把最不确定、风险最高的那块提前** —— 先做确定的部分，
   等于在没验证过的假设上继续盖楼，错了要连带推翻后面的块。
3. 全部块（含扇出子 Agent 的产出）写完后通读整份改动一遍，消掉**跨块漂移**：
   同一概念两套写法、前紧后松的错误处理、后写的块偏离先定的接口。
{{#LOCAL_COMPILE}}
4. 执行 `python "{MAEFLOW_PATH}" agent-task compile --scope "本需求完整代码增量"`，
   把输出的那一句话交给 compile-agent；编译成功后执行 `done`。
   任务卡已启动却没收到返回时，先查已记录的 Agent 生命周期；禁止自动重派或重复编译。
{{/LOCAL_COMPILE}}
{{#PIPELINE_COMPILE}}
4. 本机没有构建链，不生成 COMPILE 任务卡、不启动 compile-agent。完成全部代码与自查后直接执行
   `done`；内核只登记“待权威流水线编译”，此刻绝不宣称编译成功。
{{/PIPELINE_COMPILE}}

## 判据

**四项自查**（每块收尾逐项作答）：

1. 命名与邻居文件一致；
2. 没有与本次已写、或仓内已有重复的 helper；
3. 错误路径处理与本模块惯例一致；
4. 暴露给后续块的接口签名此刻定稿。

**改动收口**：本块动过共享符号（函数签名、枚举值、常量、配置键、协议/表字段）时，
先全仓列出该符号的**每一处**引用，逐项适配、逐项对钩——**一处未对钩，该块就没写完**。
清单必须覆盖 XML 映射、YAML/properties、SQL、反射字符串等非编译文件：编译器看不见它们，
编译通过不等于适配完整。清单用 `python "{MAEFLOW_PATH}" symbol-refs <符号>...` 一条命令生成
（词边界精确匹配、含未跟踪文件、自动把编译器看不见的文件排在最前），不要手工 grep 拼。

**卡住就停，不要猜**：缺依赖、指令不清、验证反复失败，或 `implementation.md` 有根本缺口时，
停下并说明情况。不做试探性修改。缺口属于计划层面就回实施附录订正（经用户确认后 goto）。

**小歧义：选一个，并把假设写出来**。不够格停下来、但确实有两种以上讲得通的读法时——
先按最合理的那种写，同时把这条假设记进本块结论：「我按 X 理解，另一种读法是 Y，
影响是 Z」。人工检视要看到这些假设才能纠偏；**默默挑一个，就是让人工检视少一次机会**。
写完那一块前不要回头改这条假设的措辞，交给检视裁决。

**路过的旧代码：指出来，不要动**。本次改动使某段旧代码失效，删掉它（编码基准第 13 条）；
但**不是本次弄死的**旧死代码、旧命名、旧格式，在本块结论里点一句位置就够，diff 里不出现。
顺手清理会让本单 diff 混进与需求无关的行，把真正的逻辑改动淹掉。
需求确实要求改动某段历史代码时，先弄清它为什么长这样——查调用方、查测试、查 `git blame`；
**说不出这段代码当初为什么存在，就还没到能改它的时候**（那个看起来多余的判断往往是某次故障的补丁）。

## 编码执行方式

仓库预设「编码执行方式: 新上下文」时，改按
`.mae-flow-work/plugin-resources/guidance/build-fresh-context.md` 的协议执行：
主会话只拆自包含工单与验收，代码由新鲜上下文按文档实现（长会话注意力稀释的解法）。
未设置即主会话亲写，下述边界照旧。两种方式的门禁与证据完全相同。

## 子 Agent 边界

**设计承载的代码不外包**——接口定义、每类模式的第一个实现、跨模块的接缝，由主 Agent 亲写。
其余两类可派，工单一律**自包含**：携带上下文，而不是指向上下文。

- **只读侦察**（随时可派）：窄问题 + 明确入口（目录/文件/符号名），返回压缩结论。
  用于梳理既有抽象、调用点、模块惯例、可复用实现。
- **机械扇出**（三条同时满足才派）：已亲写第一个完整样例、接口签名已定稿、剩余是照样例
  平移到三个以上文件。工单给样例路径或 diff、目标文件清单、平移规则、编码基准路径，
  并写明"不要读 spec/story/领域文档，所需信息全在本工单内"。写不成自包含工单，
  说明这活不是机械的，改由主 Agent 亲写。

子 Agent 返回后，主 Agent 通读其全部改动并纳入四项自查与跨块漂移检查——它的输出不免检。
子 Agent 不做 git 操作。派发不改变门禁与证据：构建验证义务仍然一次、检视仍然一次。

分块与派发这样安排的原因（上下文重建为何是真成本、旧检查点模式为何被退掉），
见 `.mae-flow-work/plugin-resources/guidance/construction.md`。
