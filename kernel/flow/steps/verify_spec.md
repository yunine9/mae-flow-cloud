对照 `.mae-flow-work/{单号}/spec.md`、Grill 决策、Story 和最终代码执行规格符合性检查，不创建或修改 OpenSpec 文件。

按下方内嵌方法生成 `.mae-flow-work/{单号}/verification.md`。

核心是一张**逐条对齐矩阵**——先把 Spec 与 Grill 决策拆成一条条独立的验收项，每条单独找实现证据，
一条一行，不许把多条合并成一句话概述：

| 验收项 | 实现位置 | 验证方式 | 结论 |
|---|---|---|---|
| AC-1 一句话说清要求 | 文件:函数/分支 | UT 用例名 / 编译 / 人工检视 | 满足 / 部分 / 缺失 |

**指不到实现位置的那条，结论只能写"缺失"**，不能因为"整体看起来实现了"就记成满足。
矩阵之外再记：异常与兼容性结论、未解决风险、总体结论。
最后必须用独立一行写 `PASS` 或 `FAIL`；存在任何 `FAIL` 时不得完成本步。报告是本地过程件，禁止提交。

发现 Spec 与代码不一致时只向用户裁决一次：

- 本地 Spec 需要修订且实现正确：修订本地 Spec 后重做本步；
- 代码实现偏离：回到编码入口修复，并重新经过完整编译、CodeCheck、UT 和本检查；
- 需求本身仍不明确：记录问题并等待用户决定，禁止擅自选边。

**证据铁律**：矩阵每行的"验证方式"必须指向本流程真实产生过的证据（UT 用例名、编译记录、
人工检视结论）——没有新鲜证据不得写"满足"，"应该没问题"不是结论。
编译、CodeCheck、UT 已由前序步骤提供真实证据，本步只引用、不重复执行，也不派任何审查子 Agent。

验证通过并展示摘要后 done。

验证纪律的完整口径见 `.mae-flow-work/plugin-resources/guidance/quality.md` 与 `guidance/review.md`。
