**配置确认卡(一卡合一)已收集过交付方式时:直接 done --choice 对应代号,禁止重复提问**;
以下提问流程仅在预答缺失(旧会话/宿主未回传)时执行。
用 AskUserQuestion 单选提问。**这一项不给推荐、不排序、不加"(推荐)"**:
按 flow 定义顺序原样列出四项,把代价摆清楚,让用户自己选。
你在这一刻还没看过代码,信息最少,推荐只会变成被顺手点过去的默认答案;
而代价是不对称的(见下),替用户预设立场就是替他承担那个不对称。
**选项用公司语言展示**,括号内为内部代号(--choice 传代号,不必展示给用户):
- 完整开发(full):新功能、跨模块、需设计分析
- 已定位问题修复(hotfix):问题和修改位置已经明确,跳过重设计
- 局部修改(tweak):文案、配置或范围很小的代码调整
- 处理评审意见(review):**仅限已交付单**处理评审/走读/门禁意见(经 /mae-flow:mae-flow review-fix 或用户明说
  "处理评审意见"发起;全新需求禁止选,它跳过设计与定稿、不碰规格)
**每项的代价要一并说给用户**(步数、要他拍板几次、本道特有哪几步):`steps` 命令按 flow 现算,
照它转述,别手写一份会过期的说明。
**这一轮定了不能中途换道**,必须说清:代价是不对称的——选重了白走几道前期工序、多占用户
几次拍板;选轻了发现不够,这轮先把小的交付掉、大的另开一轮。四条路的编码、检视、提交、
推送都要走,轻的只是前期工序更少、验证形态更小,**不是免检**;别让用户以为选轻的就不验证了。
(工具不可用才展示后结束回复等文本回答。)
拿到按钮选择后直接 done --choice full|hotfix|tweak|review，harness 会核对本步骤真实发生过用户选择；
不要再让用户补输确认句。
禁止自主选择;用户内联贴的需求描述再详细也只是输入,不构成跳过流程的理由。
