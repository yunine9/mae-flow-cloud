## 执行顺序

1. 按下方「当前环境所需配置的取值口径」逐项取值。能自动拿到的直接拿，拿不到的问用户——
   一次问一项事实，不要求用户逐项说"确认"（整份配置只在第 3 步确认一次，单项回答也不能给整份背书）。
2. 值全部明确后执行 current 末尾给出的 `config-review --set ...`。脚本统一校验当前环境的有效配置、派生分支名、
   展示需求内容摘录，并生成绑定配置指纹的确认单；校验失败不写入任何已确认配置，不留半套。
3. **先把 config-review 打印的确认单逐项复制进你的回复正文**——工具输出用户
   看不见，只发一张"是否确认"的卡而不给配置内容，用户无从确认。然后按输出用
   **一次** AskUserQuestion 问完两项开场决策（Q1 整份配置是否正确、Q2 交付方式）。用户答完：Q1 为确认就执行输出里那条 `done`；
   Q2 的答案由随后的 `workflow_select` 直接消费，那一步不再重复提问。
   用户选"需要修改"则改对应值并重新 `config-review`，旧确认自动失效。

完整开发固定执行 Interactive Grill、生成本地 Spec 与本地 Story，不再询问是否跳过或是否入库。

**仓库预设**：current 输出若带「仓库预设(.mae-flow-defaults.json)」块（团队提交进仓的恒定项，
如构建与 UT 约定），直接以其值预填进入确认展示，不再重新推断。
预设只提供候选值，最终仍以完整配置确认单为准。

## 当前环境所需配置的取值口径

- **工号**：`whoami` 或 `git config user.name`。Windows 的 `whoami` 返回「域\用户名」，
  只取反斜杠后的部分——反斜杠进不了分支名。
- **基线分支**：以 `git branch --show-current` 为候选值，连同用途一起进最终确认单；
  用户可在最终确认时改成 master / develop / release。这一项不单独再确认一次。
- **单号**：用户输入，REQ→feat / DTS→fix。出现多个单号时，先问用户拆分还是合并、主单号取哪个。
- **需求文档**：**单号与需求完全解耦**——单号只用于 git 分支与 commit 命名，二者互不推导、各自必填。
  取值分三种情形，见下方「需求文档的三种来源」。
{{#LOCAL_COMPILE}}
- **编译方式**（build-fix skill | mvn 命令 | 其他）：按仓库构建体系推断候选，用户拍板。
  C++/CMake/mcde 仓用 build-fix（随插件提供，无需安装或 reload）；Java/Maven 仓给明确的 mvn 命令；
  其余请用户给一条能跑通的命令。**这是全流程唯一编译路由**：编码期的自行编译验证与推送前
  验证全按它执行，任何 agent 现场另猜编译命令都是违规。多模块 Java 仓另见下方「编译范围」。
{{/LOCAL_COMPILE}}
- **UT 编写方式（内部配置键 `UT生成方式`）**：自动推断后进确认单（C++/mcde→插件自带 AutoUT skill；Java/Maven→插件自带
  java-autout skill；其余→参考仓内写法）。这些能力随插件安装，无需单独安装或 reload。
{{#LOCAL_UT_RUN}}
- **UT运行命令**（随生成方式确定 | mvn test | 其他）：这是运行入口提示，不是逐字字符串门禁，
  最终以真实执行结果为准。
{{/LOCAL_UT_RUN}}
{{#PIPELINE_UT_RUN}}
- **验证环境（只读）**：权威流水线。编译、UT 运行、CodeCheck 均由平台按最终 SHA 执行，
  不向用户询问本机命令；UT 编写仍由 Agent 按上面的 Skill/仓内写法完成。
{{/PIPELINE_UT_RUN}}
- **分支名**：由 `config-review` 从基线分支、工号、单号派生，不用单独取值。

## 需求文档的三种来源

① **用户已给路径** → 先读。可读（md/txt/代码内注释等文本）就把路径 + 标题/首段摘录一起进确认单
（防路径对文件错）。二进制（docx/pdf/图片）或读出乱码时，如实告知该格式无法直接读取，
请用户粘贴关键内容或给文本版；粘贴的按 ② 落盘，文件头标注"提取自 <原路径>"备查。
读不懂就说读不懂——需求文档是需求质询与提案规格步的输入，喂进一份读不了的文件，后面全流程都在编。

② **用户只有一段描述**（对话中粘贴或口述） → 用确定性命令落盘，不用 Bash/echo/重定向自行写文件
（Windows 默认编码曾把中文写成乱码并导致确认死循环）：先 `python "{MAEFLOW_PATH}" messages`
找到承载需求原文的消息 ID，再 `python "{MAEFLOW_PATH}" requirement-record --message-id <ID> --ticket <单号>`。
工具原文照录为 UTF-8、写入正文指纹并回读校验；把生成路径与内容摘录进确认单。
已有 GBK/UTF-16 文本用 `requirement-record --source "<原文件>" --ticket <单号>` 规范化。

③ **用户没有任何需求材料** → 停下并请用户提供路径或口述。需求是交付的前提，由用户给出。

**候选列举纪律**：默认不扫描仓库凑候选清单（选择空间本身就是引导）。用户明说"帮我找找"才定向搜索，
且每个候选必须标注来源并附摘录供核对。

`done` 时状态机硬校验：需求文档真实存在、可严格按 UTF-8 读取、无高置信乱码；
由 `requirement-record` 生成的文件还会核对正文 SHA-256。乱码不是用户确认问题——
出现乱码就按上面的确定性命令重新落盘，不要反复让用户说"我确认"。

## 编译范围（仅多模块 Java 仓需要读）

{{#LOCAL_COMPILE}}
一次交付通常只碰本服务的 sdk / model / service 几个模块，整仓 build 动辄十几分钟。
推荐形如 `mvn -pl <sdk>,<model>,<service> -am compile -q`（`-am` 自动带上被依赖模块）。
`config-review` 检测到"多模块仓 + 未限定模块"时会在确认单里列出仓内模块和可照抄的写法。
这是**建议不是门禁**：用户坚持整仓编译照样接受，只是慢。确定长期用某条命令后，
可写进 `.mae-flow-defaults.json` 的「编译方式」自动预填。
{{/LOCAL_COMPILE}}
{{#PIPELINE_COMPILE}}
本机没有构建链，本节无需取值；模块选择由权威流水线的工程配置决定，不让下单用户填写命令。
{{/PIPELINE_COMPILE}}

## 跨仓交付

需求涉及多个代码仓时，读 `.mae-flow-work/plugin-resources/guidance/cross-repo.md`（链路分解文档、本仓职责取值、回流条款）；不涉及跨仓则跳过本节，也不必向用户提起。

## 确认结果没回传时

让用户发送一条普通消息"确认以上全部配置"，再原样执行 `done` 即可。
确认失败只会停止重复执行同一条错误命令，流程不会锁死，不需要 exit、删状态或重新 init；
执行 `messages` 可直接看到脚本提取到的真实答案。
用户确实不想继续时，仍可发送 `/mae-flow:mae-flow exit`。
