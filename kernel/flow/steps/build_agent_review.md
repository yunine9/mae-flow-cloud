用户已在开场选择：人工检视前先进行一次可选 CODE Agent 预检。

## 执行顺序

1. 执行 `python "{MAEFLOW_PATH}" role-task code-review`。它一次生成**两张**任务卡，
   对应两个互不参考的视角：
   - **需求符合性(spec)**：拿 Spec、Story、实施附录，只判断需求有没有做全做对、有没有擅自扩大范围；
   - **工程质量(standards)**：不给 Spec 与 Story，只对着增量和编码基准看代码本身。
2. 按输出的两句启动话术，**分别派两个 craft-reviewer-agent**，每个只执行自己那张卡。
   两次派发都只传卡路径，不复述聊天记录，不把两张卡合成一次派发。
3. 两轮结论回来后，由主 Agent 汇总：两个视角的问题**并列列出，不合并、不互相重排优先级**，
   每条保留 Reviewer 给的处置标签。**只有 BLOCKER（功能错误、崩溃、回归、数据损坏、安全）
   在进入人工检视前修掉**；WARNING 与 NOTE 原样呈报，由用户决定这一单改还是另开——
   预检的目标是降低风险，不是把代码打磨到完美。修完 BLOCKER 后执行 `done`。
   这一步不向用户额外要确认——人工检视就在下一步。

## 为什么拆两轴

一个 Agent 同时拿着 Spec、Story 和代码规范时，注意力会全部流向业务正确性，命名、重复实现、
资源收口这类工程问题就漏了；反过来只盯规范的也发现不了需求做错。两张卡的权威输入刻意不同，
互不污染，各自只报自己那一类。

## 边界

预检只跑这一轮：两张卡各派一次，无论结论是 CLEAR 还是 ISSUE 都不自动重来，也不形成复检循环。
它不代替用户人工检视，两个 Agent 都是只读，不改任何文件。

任务卡已启动却没收到返回时，先查已记录的 Agent 生命周期；不自动重派。
