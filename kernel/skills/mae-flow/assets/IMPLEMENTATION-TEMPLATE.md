## 1 文件结构与任务边界

先列出本次要新建/修改的每个文件及其单一职责——拆分决策在这里锁定，不留到写码时临场决定。
一起变的东西放在一起，按职责拆而不按技术分层；既有仓库遵循既有形态，不单方面重构。

每个新增的文件或类都过一遍**删除测试**：假设把它删掉，复杂度是消失，还是会在多个调用方那里
重新长出来？消失说明它只是个转手层，把内容并回调用方；重新长出来说明它在挣钱，保留。
接缝同理——**一个实现是假接缝，两个实现才是真接缝**：只有一个实现时就写那一个实现，
不为"以后可能换"先立接口（编码基准第 9 条）。

再据此划任务边界，判据是：**一个新来的检视者能否独立否决其中一个任务而批准它的邻居**。
能，就该拆；不能，就是同一个任务。setup、配置、脚手架、文档折进它服务的那个任务，不单列。
每个任务以一个可独立验证的交付物收尾。任务粒度不必细到逐步操作。

**写法（每个文件一行）**：

- `路径` — 新建/修改。单一职责一句话。任务 N

正例：

- `service/src/demo_service/sms_handler.py` — 新建。短信渠道的校验→截断→发送→记账四段。任务 1
- `service/src/demo_service/notify_service.py` — 修改。仅在 send 入口接入短信分支与失败重试。任务 3

**任务清单（文件行之后必写，一个任务一行）**：标题一句话说清这个任务交付什么。
它会原样出现在云端进度展示上——编码期间用户看到的就是这行字，
「任务 2」这种无标题占位没人知道 Agent 在干什么。

- [ ] 1. <一句话标题，如：TextUtil 新增脱敏方法并接入三渠道拼装>
- [ ] 2. <一句话标题，如：脱敏行为全量用例与渠道断言>

## 2 接口契约两栏（每个任务必写，只写签名不写实现）

- **消费**：本任务用到的、由前序任务产出的精确签名；
- **产出**：后续任务或机械扇出工单会依赖的精确函数名、参数与返回类型。

这两栏是签名定稿的地方——`build` 步允许机械扇出的三条前置里，"接口签名已定稿"指的就是它。
缺了它，同一个概念在第 3 块叫 `clearLayers()`、到第 7 块变成 `clearFullLayers()`，编译能过、行为不对。

新增或修改对外接口时，站在**困惑的调用方**位置问两句：参数调换了会不会照样编译通过？
默认值会不会静默做错事？`setFrequency(int value, int type)` 这种签名两个整数一传反，
编译器一声不响。正确用法应该是最省力的用法——用类型、枚举或拆成两个函数把误用挡在编译期。

契约划得对不对有个现成判据：**接口就是测试面**。后面的 UT 只能从这两栏写出的签名进去；
要想测到接口背后才验得了，说明这一块的边界划错了，回第 1 节重划。

正例（一个任务两行，不带实现）：

- 消费：`truncate(text: str, limit: int) -> str`、`channel_state.session(tenant_id, channel) -> Session | None`
- 产出：`sms_handler.send(notification: Notification) -> SendResult`
