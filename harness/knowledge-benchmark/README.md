# 知识 benchmark

用固定的虚构语料测量当前 Cloud 的检索、范围和版本保护，以及模型是否把知识正确用到代码。直接调用生产使用的 `KnowledgeSearch`、`knowledge` 工具、memsearch sidecar 和 `CloudSession`，不连接生产知识库。

## 运行

```bash
# 默认：真实本地 ONNX 检索 + 范围/版本保护，不调用生成模型
npm run benchmark:knowledge

# 加上真实模型对照：三个任务，各运行有 knowledge / 无 knowledge 两组
npm run benchmark:knowledge -- --agent

# 指定已有环境；模型配置不会复制进报告
npm run benchmark:knowledge -- --agent \
  --python .local/memsearch-venv/bin/python \
  --models .local/models.json --provider glm --model glm-5.3-flash \
  --repeats 3 --timeout-ms 180000

# 对比先前结果；请使用同样的参数和语料版本
npm run benchmark:knowledge -- --baseline .local/knowledge-benchmark/run-OLD/report.json
```

需要已有的 memsearch Python 环境及缓存的 `gpahal/bge-m3-onnx-int8` 模型，运行设置 `HF_HUB_OFFLINE=1`，不自动下载。真实模型评测另外需要模型服务可访问、配置文件有效，以及 C++17 编译器（默认 `c++`，可设 `CXX`）。`--agent` 会调用模型服务；“本地评测”指本机运行评测程序和检索，不表示生成模型也在本机。

默认输出 `.local/knowledge-benchmark/run-随机编号/`。可用 `--output DIR` 指定一个尚不存在的目录，避免覆盖历史结果。每次独立建库；启动和索引耗时单独记录，查询耗时是在索引就绪后测量。sidecar 随运行结束停止，日志最多约 1 MiB。保留语料和模型生成的代码方便复核；确认进程结束后可删除整个输出目录。

## 测量内容

### 检索

26 个固定查询：23 个正例、3 个负例。包含中文改写、精确符号、共仓不同模块、相反产品版本、跨仓隔离、未发布和停用资料、无关问题。

- `hit_at_1/5`：预期文档是否出现在前 1/5 个返回片段中。
- `mrr_at_5`：首个预期文档片段的倒数排名均值；没有命中为 0。
- `evidence.hit_at_1/5`：带明确证据短句的案例，按返回行号实际读取后，是否在前 1/5 个片段中读到所需内容。命中文档标题不会冒充读到规则。
- `negative_rejection_rate`：无相关资料时返回空结果的比例。
- `scope_leaks`：返回明确禁止的模块、仓库、产品版本或发布状态条目的数量。
- `p50_ms/p95_ms`：宿主侧查询及该案例证据读取的耗时，不包含首次索引。

这里的命中率按“至少一个预期条目”计算，不是大规模多相关文档集合的完整召回率。片段排序不会先按文档去重，以保留 Agent 实际看到的顺序。

### 范围和版本保护

检查共仓模块未明确时的歧义提示、已发布 Skill 不进入文档检索、待审/停用资料不可读、跨模块/跨版本不能按 ID 绕过、旧 revision 被拒绝、重新索引后的内容替换、自动经验上下文及撤回后移除、索引后停用、检索服务不可用时原文仍可读。

### 模型应用

三个独立任务，各有一组实际 C++17 编译与运行检查：

1. 创建文件：名称缺失、打开失败、写入失败和成功路径；打开失败也必须 `close` 一次。
2. 借用 writer：写入成功/失败都不能打开或关闭调用方的句柄。
3. 产品版本：2.7B 读取秒配置并转换成毫秒，不能读旧版毫秒键。

两组使用相同需求和 API 声明，只改变是否提供 `knowledge` 工具及其现有指引。测试驱动在模型会话结束后才写入工作区，结果由执行轨迹断言判定，不让模型给自己打分。不开放 Task 工具，测量单会话消费，不包含子 Agent 编排、自动经验上下文或 Skill 触发。

每个任务保留 prompt、工具查询和原文读取结果、会话记录、生成的 `solution.cpp`、编译诊断和逐项运行结果。重复运行时交替两组先后顺序。单轮只有三个模型任务，不能据此宣称显著提升；建议使用 `--repeats 3` 或更多，并逐例看失败原因。

## 报告与退出码

- `report.json`：环境、代码提交及相关源码摘要、语料/评分器摘要、逐例数据、汇总、基线比较。
- `summary.md`：人可读摘要。
- `fixture-manifest.json`：固定语料、查询、预期结果与本次资产 ID 映射。
- `agent/`：真实模型对照的原始产物。

检索、保护检查或有 knowledge 组失败时退出码为 1；无 knowledge 对照组失败只作为对照事实记录，不单独令命令失败。启动失败和中断不会算成功。报告逐例及时写入，异常时保留已完成结果。

基线比较必须使用相同语料、评分器及运行配置，拒绝直接比较不同口径；输出退步、改善、新增、移除的案例及命中率/耗时变化。改生产检索实现或工具提示词后，可以沿用同一基线；改题目、评分逻辑或模型运行参数后，应建立新基线。硬件和服务负载会影响耗时，比较时同时查看环境信息。

## 如何扩展

在 `fixtures.ts` 添加一条语料和对应查询，预期结果用稳定的 key，不写运行时 ID。涉及模块/版本时显式指定范围；增加应拒绝的内容时写 `forbidden`。需要验证命中章节时写原文中的 `evidence` 短句。

修改语料时递增 `SUITE_VERSION`，保留旧报告。不要为了跑绿删掉难例或根据本次排序修改预期答案。真实内网案例应先脱敏，再补入固定集，并明确它与虚构案例的来源区别。当前整套语料为虚构样例，不代表真实内网知识库准确率。

本 benchmark 没有源码符号/语义漂移校验，也不能证明某条经验提升了生产交付质量。它把“找得到”“读到依据”“代码遵守规则”分开测量，给后续迭代提供可复核的基线。

## 生命周期评测（版本 3）

默认运行新增 9 个真实 `TaskService` 装配场景：明确模块、继承父任务、模块列表、共仓歧义、未知模块、单模块与列表冲突、两个明确模块、唯一仓库映射、错误产品版本。分别记录 `expected`、`readable`、`injected`，不能只检查两条路径相等——两条都返回错误内容也必须失败。该组用确定性的 sidecar 替身返回宿主允许的来源，检查宿主范围判断；真实 ONNX 召回仍由独立检索组检查。

### 交付经验生成

```bash
# 开发集：资源归属、版本单位、非幂等重试、无真实缺陷，调用生产复盘 Agent
npm run benchmark:knowledge -- --generation --split development

# 保留集：ETag 条件更新、显式零值；提示词固定后再运行
npm run benchmark:knowledge -- --generation --split holdout

# 全部生成场景，多次运行观察稳定性；可同时加 --agent 做代码应用对照
npm run benchmark:knowledge -- --generation --split all --repeats 3
```

每个场景建立独立 Git 仓库的首次/最终提交，提供意见目录和完整处理结果，直接运行 `runDeliveryExperienceAgent`、`delivery_source`、`experience_evidence` 及原有生产提示词。评分答案不进入模型提示，模型不能访问评分文件。保留 prompt、原始输出、工具记录、固定评分规则、各项检查和模型返回的 Token 用量；凭据配置在结束后删除。

自动检查包括：引用实际缺陷依据、同一根因不拆碎、包含适用条件与例外、没有扩大为跨仓规则、未虚构测试通过、实际成功回读所有被引用意见和版本差异（空结果也要核对完整意见）。引用被否决意见或新增需求的候选进入语义复核清单：同一份否决依据可能被用于学习正确的反证，也可能被错误地当作规范，来源 ID 不能代替这项判断。

**生成组的“通过”仅表示固定证据与概念契约检查通过，不是语义正确率。** 概念词出现仍可能表达错误关系；必须结合 `output.txt` 核对条件、结论和例外是否成立。评分器测试注入删例外、伪造依据、重复根因、扩大范围及虚构验证等错误，防止评分逻辑总是通过。负例要求空数组，不能凭输出数量越多越好打分。

### 防止过拟合

- 先写用户期望行为和反例，再让生产实现接受这些输入。不能从当前函数分支直接抄预期答案。
- 同一能力使用成对条件：拥有/借用、明确/未明确模块、当前/旧版本、真实缺陷/新增需求、有依据/无依据。期望随业务条件变化，不能只换措辞扩充数量。
- `generation-fixtures.ts` 明确区分 development 和 holdout。开发阶段只看开发集；保留集用于调整后的验收。保留集一旦被用来改提示词，就应视为开发集，补充新的保留集，不能继续宣称独立验收。
- 固定用例与评分器摘要随报告保存。修改生产实现后可对比同口径结果；改题、评分或参数必须建立新基线，不能混合不同口径的通过率。
- 失败保留原样，不通过删除难例、放宽答案或只报成功的重复轮次提高分数。必须区分运行失败、契约不满足和需要人工判断的语义问题。
- 样例数量不是覆盖率。当前保留集只有两个合成事件，不足以估计生产准确率；同一事件重复运行也不是新增独立样本。下一批应来自脱敏后的独立历史事件，由熟悉业务的人先给出证据与期望。

当前覆盖：检索、实际任务范围接入、失效保护、交付经验生成契约、代码应用行为、生成经验的自动上下文消费、专题整理的事实保留与冲突呈现。尚未覆盖组件/领域研究的真实生成质量、Skill 触发和来源代码语义漂移；现有单元测试不能冒充这些场景的真实模型评测。

### 评分器本身也需要验证

报告把生成结果分成 `contract_passed`、`contract_failed`、`invalid_output` 和 `execution_errors`，`semantic_accuracy` 保持空值。连接失败和中止不进入“质量不合格”的解释。所有生成结果都需要语义复核，自动检查通过不是免审结论。

有一项反向测试专门给出“借用句柄不得关闭”和“借用句柄必须关闭”，二者引用同一条否决意见。仅靠证据 ID 无法判定谁正确，评分器必须明确留下待复核标记，不能制造自动判断能力。

修订评分器后可以复用已保存的模型输出，不重新调用模型，也不覆盖旧报告：

```bash
npm run benchmark:knowledge -- --generation-replay .local/knowledge-benchmark/run-OLD/report.json
```

回放要求语料摘要一致，重新执行当前范围与检索检查，并用新评分器评估旧输出和工具轨迹。新报告保存来源报告标识、原模型参数和旧结论。回放不是新模型样本，不增加重复次数；旧运行的错误也保留，不借回放隐藏失败。

### 生成经验能否帮助下一次任务

```bash
npm run benchmark:knowledge -- --generation --split development --pipeline --repeats 2

# 已有生成结果时，复用输出，只重新运行后续消费模型
npm run benchmark:knowledge -- --generation-replay PATH/report.json --pipeline --repeats 2
```

`--pipeline` 取本轮生成的资源归属和版本配置经验，通过 `MemoryStore` 模拟审核采纳并等待真实索引就绪，再由真实 `TaskService.taskMemoryContext`、ONNX 检索和 `CloudSession` 提供给新的代码任务。消费者只看到正常需求、API 声明与自动注入的结论，不能读取原始复盘意见或评分文件。代码检查沿用拥有句柄、借用句柄和版本单位的独立 C++ 行为检查：同一份资源经验在拥有与借用条件下应产生相反的清理行为。

每个案例必须同时满足：相关生成经验实际进入上下文、代码编译成功、行为断言通过。记录 `expected_memory_ids`、`observed_memory_ids` 和 `context_injected`，保存模拟采纳记录及真实 `memory-usage.jsonl`。缺少有效生成结果记为 `source_unavailable`，保留为链路失败，不跳过后宣称全通过。回放时 `--repeats` 应与来源中已有的生成轮数一致。

这里的采纳由 benchmark 模拟，不改生产审核规则，也不表示生成结果已经获得人工质量认可。通过检查只证明这三个固定任务中的可执行行为，不能证明所有语义正确。与 `--agent` 的有/无工具对照分开报告。

## 设计依据

- [ACE](https://github.com/kayba-ai/agentic-context-engine)：把执行证据、经验反思、后续整理区分开；本仓沿用现有复盘和审核服务，不引入第二套运行框架。
- [memsearch](https://github.com/zilliztech/memsearch)：保留可读原文，索引可重建；原文 ID、修订号和行号用于复核。
- [Anthropic skill-creator](https://github.com/anthropics/skills/tree/main/skills/skill-creator)：有/无能力对照、预先定义行为断言、保留原始输出，并补充语义复核与独立验收集。
- [Compound Engineering 的知识维护](https://github.com/EveryInc/compound-engineering-plugin/tree/main/skills/ce-compound-refresh)：区分过时、有效规范被实现违反、暂时无法核实；保留人工补充和冲突证据。共享写作指引已进入实际生成提示词，提示词要求本身不是自动质量保证。

## 消费结果反馈到经验维护

```bash
npm run benchmark:knowledge:feedback -- --output .local/knowledge-benchmark/feedback-NEW

# 仅复测明确失败的场景，报告记录本次选择；不算整组重新通过
npm run benchmark:knowledge:feedback -- --case rule-needs-update --output .local/knowledge-benchmark/feedback-recheck-NEW
```

这组直接运行生产 `DeliveryExperiences` 协调器及真实模型，不启动检索侧车。三个固定合成事件分别验证：已有规则有效但实现违反规则、已有规则需要修订、消费时的历史版本缺失。真实创建 Git 首次/最终版本，记录经验消费后再模拟人工维护，通过历史版本读取检验复盘不会拿新正文冒充旧现场。

检查内容包括证据回读、必要条件、需要修订时引用原经验、原条目及人工补充不被覆盖、新草稿仍待审。前两类应产生不同结果：有效且没有新信息的已有规则不重复生成；规则确需变化才提出有依据的建议。没有历史版本时不能仅凭当前内容推断旧知识有害。

`report.json` 保存源码/案例摘要、模型调用和 Token 用量；逐例保留原始输出、意见、使用记录、经验历史和模型工具轨迹。自动检查仍不等于语义正确率，需要复核原始输出。此组是开发回归，不将其称为独立保留集；同文件后来出现意见仅记录相关性，不作为知识排序的自动扣分。

语义复核至少检查两类自动词语检查容易漏掉的问题：是否将“收到过经验”擅自写成“采用经验导致缺陷”；是否只凭修订号变大就认定旧错误已经修正。需要修订的场景应明确写出当前版本的正确做法，仅给“以后注意核实”的建议不算完成。复核记录另存 `semantic-review.json`，注明复核者及是否独立验收，保留自动报告和失败原文。
