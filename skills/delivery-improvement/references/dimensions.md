# 六类分析维度

各维度先核对指标首轮边界和实际修改动机，再查以下问题。独立维度子 Agent 对分配的维度说明查过什么、读了哪些依据、发现及限制；主 Agent 负责六类覆盖完整，并回到原文核实，不按子 Agent 数量或赞同次数证明结论。

覆盖状态四选一：有发现、已检查未发现、不适用、证据不足。没有读到足够材料时用“证据不足”；不适用须说明本次任务为何没有这类场景。缺记录或材料截断不能作为“已检查未发现”的依据。

## 1. 业务规则与需求理解

- 首轮遗漏了哪些业务规则、边界和异常场景？它们是首轮前已明确，还是后来新增或改变？
- 需求、澄清答复、Spec/Story、拆分方案和实现之间在哪一步发生偏差？
- 前期哪些具体问题可由 Agent 根据已有资料自行查证，哪些必须由人决定？
- 对照需求修订及人工决定的时间、当时设计和首次代码；不能用最终文档倒推首次应知。

## 2. 规范与组件用法

- 后续修改涉及哪些明确规范、接口契约、组件版本或生命周期要求？当时适用条件是否满足？
- 规则或示例是否准确、可获得，有没有冲突或版本不匹配？
- 已有规则未生效时，问题是提供、定位、理解还是落实？是否已有可复用的具体检查？
- 对照规则固定正文、依赖版本、返回材料及代码，不因检视意见被采纳就认定它天然正确。

## 3. 知识获取与使用

- 当时已有知识是否覆盖问题？任务是否获得目录，搜索是否命中，返回了什么，是否继续读取必要正文？
- 检索词、模块/仓库范围、适用条件和知识修订是否正确？有没有过时或错误内容？
- 对已提供或读取的内容，代码是否与之相符？存在明确采用记录，还是只能确认内容一致？
- 回查任务正文快照、历史经验、知识工具原返回和 Bash/Read 等执行记录；无足迹不等于没读。

## 4. 实现与测试

- 每次提交改了什么，解决哪个问题？同一问题的多次修改为何未一次解决？
- 是否只修表象、修错方向、引入新缺陷，或者属于合理需求演进和必要重构？
- 前期设计的测试是否覆盖该场景，实际实现和断言是否有效？最终新增测试能否提前暴露问题？
- 串联提交差异、意见版本、修复 SHA 及测试原文；代码行数或多次失败本身不证明实现方法有问题。

## 5. 验证环境与执行

- 失败来自代码、命令、依赖、构建环境还是输入材料不足？失败原文是否真的传给了执行 Agent？
- 验证对应哪个代码版本，有无未提交变化？重复验证是否针对新改动或新增信息？
- 哪些已有检查具备前移条件，哪些环境事实可提前查明，哪些重复工作没有增加质量收益？
- 读取各轮 prepush、流水线历史及工具返回；整体绿灯、基线成功不能替代逐项验证，版本缺失明确未知。

## 6. 平台流程与工作方法

- 首轮应完成的工作是否遗漏，提示词、规则或工具能力是否含糊、冲突或未实际生效？
- 主/子 Agent 分工是否清楚，任务卡是否提供必要输入和验收目标，结果是否传回并被后续工作使用？
- 父子任务拆分、上游交付与下游输入是否脱节，是否重复探索已经查清的问题？
- 是否存在重复确认、无新信息的反复尝试或可以合并、删除的步骤？原有质量边界能否承担它的作用？
- 对照实际任务卡、工具记录、人工决定和对应版本机制；当前源码只能解释当前机制，历史版本或未来规划未知时留给维护者核实。
