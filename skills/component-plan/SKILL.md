# 组件使用计划

这是 issue 446 component-plan 的 Cloud 适配版，替换原组件知识分析方法。使用平台现有 `knowledge` 工具、实施计划和知识使用记录。不要另建组件工具、独立计划文件或审批阶段。

## 何时使用

在制定 implementation 实施计划、拆解编码任务之前使用。关注异步、调度、重试、超时、配置、消息、存储、日志、网络等通用能力。纯文案或不涉及组件选择的局部修复可说明后跳过。

目标不仅是替换某个 API，还要避免重复实现组件已经负责的队列、状态机、资源管理和退出逻辑。代码检查不能代替这项设计判断。

## 输入与权限

任务卡应包含需求、仓库与代码入口、语言、模块、产品版本，以及现有 implementation 文件的准确路径。

你只更新该文件中的组件与规范内容，不写业务代码、不推进阶段、不提交或推送。保留计划的其他内容；与主 Agent 避免同时编辑同一文件。若路径未提供，只返回需要主 Agent 合入的内容，不猜路径或另建平行文档。

## 工作步骤

1. 阅读需求和相关代码，把需要的通用能力列为 C1、C2……。已有封装也要核对其职责，不能因为熟悉原生库就跳过内部组件。
2. 调用 `knowledge(action=component_context, plan_path=实施计划路径)`。它返回表格模板；卡片少时列出当前适用的推荐范式，卡片多时要求逐项查询。卡片只是定位信息。
3. 对能力调用 `knowledge(action=search, scope=components, plan_path=实施计划路径, capability=C1, query=具体需求)`。优先用需求的说法，例如“周期性执行优化任务”；不足时再用原始写法，例如“C++ std::thread sleep while 循环”。memsearch 不可用时宿主自动使用本地卡片检索。结果包含实际使用的检索方式。
4. 用返回的文档 ID、版本和行号调用 `knowledge(action=read, plan_path=实施计划路径, capability=C1, id=文档ID, revision=文档版本, start_line=起始行, end_line=结束行)`。继续读取相关组件契约与例外，不能只信卡片或第一条命中。结合当前仓库的真实依赖和调用代码确认 API。
5. 将决策写进已有实施计划的“组件使用计划”表格，使用 `component_context` 的七列表格和标记：
   - **使用**：范式填完整 `card_id`；来源版本填 `文档ID@文档revision`；理由写为何满足需求。
   - **不使用**：说明候选哪里不满足需求、已有封装或自行实现的依据；不要把一次空结果当作没有组件。
   - **待核实**：明确检索故障、知识冲突、缺少依赖或证据，不伪装成已经确认的选择。
   - **设计约束及应对**：写清回调在哪个线程、能否阻塞、生命周期与退出顺序、容量和失败处理等对本方案的实际影响，以及准备怎样遵守。没有相关限制时也说明核对依据。
6. 调用 `knowledge(action=plan, operation=validate, plan_path=实施计划路径)`。宿主核对当前正式范式、推荐状态、来源版本、决策和约束，并自动把真实检索记录写回同一文件。不要手写或修改“系统生成”的检索记录。
7. 将组件选择与约束对应到已有实施任务，随原方案一起评审。实现时按这份计划落实；完成后调用 `knowledge(action=plan, operation=check_impl, plan_path=实施计划路径)`，核对计划接口是否出现以及是否出现计划外接口。有差异时查明原因，修改实现或解释计划调整。
8. `knowledge(action=plan, operation=gaps)` 汇总本任务记录过的“不使用/待核实”能力与理由，作为组件缺口。不自动发消息、修改组件或启动另一轮研究。

## 判断边界

- 知识只来自已采纳的正式资料。基础组件知识的萃取仍只使用基础仓代码和 everycode；草稿不是规范。
- 范式必须存在、当前有效且为 recommended。legacy、unverified、停用、删除或版本过期的范式不能被称为当前推荐方案。
- 知识与真实 API 冲突时，记录具体冲突并核对源码。知识不覆盖用户明确要求；不允许为满足知识描述而编造接口或改坏业务行为。
- 校验验证的是可程序化核对的事实，不证明设计正确。接口名匹配也不证明调用顺序、参数或生命周期正确；必须结合代码审查和测试。
- 查询和读取记录由宿主自动记录在现有知识使用记录中，只能证明实际访问过哪些资料，不能证明已正确采用。
- 检索失败、知识质量问题或少于两次查询不新增交付门禁，不进入重复审批或等待循环。说明不确定性，继续有独立依据的工作；真正影响需求正确性的未决事项由主 Agent 判断是否需要用户澄清。

完成时只汇报计划路径、已确认的选择、设计约束和待核实项，不声称完成了业务编译或测试。
