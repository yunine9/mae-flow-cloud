# MFC 问题定位

本 Skill 的使用者是能访问内网现场的 Agent。它是一项按需调用的工具能力；以下取证方法和输出约定仅适用于内网 Agent 执行本工具。维护本仓的开发助手读取或分析 GitHub Issue 时，不因此调用本 Skill，也不需要遵循其报告模板。

目标是找出**哪一步首次偏离预期、为什么偏离，以及什么证据能推翻这个解释**。尽快缩小范围，但不要为了快而把第一个看似合理的猜测写成根因。现有代码、测试和历史分析报告都是线索，不自动证明行为正确或根因成立。

## 从现场开始

- 用户给了 GitHub Issue 编号时，先读正文和全部评论；报告里的“根因”按待验证假设处理。明确环境、任务或请求标识、发生时间、用户动作、预期结果和实际结果。
- 查实际运行的代码版本、启动参数及相关配置。本地 `main` 只能用来比较；不能把“仓库已修复”当作“生产已部署”，也不能把旧版现场当作新版回归。生产取证默认只读；不要读取或输出令牌、密码、完整环境变量。
- 先确定证据是否完整：日志是否截断、采样是否只取尾部、事件是否有开始和结束配对、多个文件是否来自同一时刻。缺一段记录不等于该动作没有发生。

## 还原最短完整链路

从最后一个确认正常的事实追到**第一个异常事实**。根据问题选择相关环节：页面操作与请求、服务端入口、状态读写、Agent 工具调用、宿主执行、Git/平台返回、再次读取与页面展示。无需机械检查所有层，但要查到产生错误结果的真实动作，不停在错误文案或最终状态。

对关键跳转同时核对三件事：**当时输入或状态是什么、运行代码会走哪个条件分支、该分支真实执行结果是什么**。结合事件时间线、请求响应、任务状态和外部结果交叉验证；仅凭一处 `if`、一次时间相关性或一个 SHA 不一致，不能宣称它阻止了操作。

优先找一个可比样本：同任务上一次成功动作、同环境的正常任务，或修复前后的版本差异。说明两者具体差在哪里，不拿不同环境、不同代码版本的结果直接对比。

## 挑战自己的解释

提出候选原因后，先问：“如果它是真的，现场还应看到什么？”去找这条必要证据，并主动检查最有可能的另一种解释。常见替代解释包括旧版未部署、配置不同、任务自己尚未执行、外部操作失败、用户或其他人改了分支、日志不完整，以及后续工具报错掩盖了更早的失败。

区分**症状**、**直接触发条件**和**可修复的根因**。例如“本地 HEAD 与远端不同”是现象；只有查到推送实际调用、返回、远端分支和状态更新顺序，才可能断定是谁拦了推送。若 Agent 收到的是被截断的测试日志，还要查原始日志是否有失败用例，不能仅以末尾覆盖率工具报错定因。

确认根因至少需要：异常事实的现场证据、触发它的运行代码或外部行为、以及两者在同一次执行中的对应关系。缺少其中一项，就明确写“待验证假设”，继续做最小补证；不要用“应该是”“大概率”包装成已确认。只要相关现场仍可读取，就继续找最能区分候选原因的证据，不把可由自己完成的取证留给别人。确实无法继续时，点明缺少的文件、权限或外部结果。能安全地本地复现时，用最小输入让旧行为出现，并验证修复后的结果；不为复现而改动生产任务。

## 最终输出：可直接提交的 GitHub Issue

最终给出**标题和正文**，让用户可以直接复制到本仓 GitHub Issue。若用户提供了已有 Issue，就给出该 Issue 的建议更新文本，不另造重复问题；不要未经要求自动创建 Issue 或发表评论。定时批量巡检仍按 `task-patrol` 的报告格式输出，不走本节。

标题描述可观察的错误及影响对象，不把未证实的根因写进标题。正文用下面的简短结构，缺少的事实标为“待核实”，不要编造：

```markdown
标题：<任务或功能>在<触发条件>下<实际错误>

正文：
## 现象与影响
<用户要做什么；预期与实际；受影响的任务或范围>

## 现场证据
<环境、运行版本、时间及一条短时间线；每个关键事实附可核对的位置>

## 定位结论
<已确认的触发条件和根因；若未证实，写“待验证假设”及缺哪条证据>
<已排除的主要替代解释及依据>

## 处理建议与验收
<最小修改或下一项具体取证动作；用什么真实场景证明问题解决且未引入同源问题>
```

证据位置可以是 Issue 评论、事件 ID、任务文件、日志行、运行版本、源码文件与行号。时间、次数和影响面没有完整数据就不估算。已有修复时，在“处理建议与验收”写明提交、定向测试和部署验证状态，不能把“代码已推送”写成“生产已恢复”。

收到修复请求时，先沿同一机制横向检查其他入口和恢复路径，再做最小改动及对应的定向测试；需求交付流程还须遵循仓库的 `kernel-simplification` 指引。若只是定位请求，不自行推进生产任务、重跑流水线或部署。中途可以汇报“已确认的事实”和“还在验证的解释”，但不要提前宣布问题已找到或已修好。
