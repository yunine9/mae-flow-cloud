# 分析规则与例子

## 两条主线

**平台制造的无效消耗**：明确确认被备注覆盖；相同内容反复确认；空行/排版反复返工；同一失败反复唤醒但没有新输入；无结果的收据查询；旧 SHA 的失败触发当前代码返修；同一动作重复执行；已排队的回复又派给 Agent 写一遍。先核对身份、内容和实际副作用，不把正常轮询次数当重复构建。

**代码与编译效率**：首次依赖/UT 命令是否正确，错误是环境还是代码，Agent 是否收到真实完整日志，是否反复猜命令，是否重读已经查清的内容，是否重复全量构建。需要 UT 不代表可以跳 UT；只能建议正确命令、输入补全、复用有效证据或验证过的增量构建。知识缺口可建议沉淀进现有 skill/TS 提示词，必须提供“当前缺什么 → 建议给 Agent 什么 → 如何验证有用”的具体例子。

## 判定标尺

- **bug**：有明确预期及相反事实，能够引用现场证据。根因尚未证实也可报告行为 Bug，但 analysis 必须分开写“已证实的异常”和“尚未证实的根因”。一次超时不等于死循环；至少找到重复触发链或明确的无限等待代码。
- **optimization**：流程能完成，但具体重复工作/等待没有体现质量收益。优先删除，再合并或简化，工作方法优先提示词。建议写明保留的边界，以及是否需要修改内核源仓或仅 Cloud TS。不要为了观察再造评分、审批和收据系统。
- **hypothesis**：截断、版本未知、时序不完整或仅有相关性。点名下一步最小取证动作。不得以“确定根因”措辞输出。

计算时间时使用同一时区的真实时间戳。等待审批从卡创建到 resolved，未回答只能算截至采集时的开放区间。模型调用与编译、远端操作可能重叠：重叠区间不能简单相加。Bash 次数不是编码用时；缺工具开始/结束配对不能声称耗时。默认采集只含日志尾部，计数是“已采集范围内”，不是整个任务总计。

## 反例，必须会区分

- 已选“确认推送”，有渠道备注后立即被标要求调整，并再次举卡：可报告行为 Bug；须查运行版本是否仍有 notes 判拒绝代码，不能照旧报告引用历史源码。
- 同一失败连续出现三次，但分别对应三次不同代码修改：不是已证明的无效循环。
- 两次构建都失败，日志只给链接：可报告诊断输入不足；不能断言模型不会写 C++。
- 旧流水线失败，新版本构建成功且未再派修：正常保留历史，不是 SHA Bug。
- 新版代码已推送，生产未部署：仍是旧版问题，不是“修复无效”。
- 第一次修好后没有再采到同类任务：只能说尚未观察到复现，不能宣布已修复。

## 深挖而非复述实现

对每个优化候选，在 analysis/recommendation 中回答以下问题（内容重要，不要求机械填标题）：

1. 用户要达成什么结果？当前机制额外要求了哪些动作、信息或等待？
2. 它防止的具体缺陷是什么？有现实证据，还是仅有“万一不安全”的猜测？
3. 删除它的最小方案是什么？已有授权、真实测试或外部结果能否承担边界？
4. 不能删的部分能否合并、提示词化或收敛到 Cloud TS？不要推荐新增另一层核验来证明旧核验。
5. 哪些质量/权限约束必须保留？怎么用一个真实场景验证不会误通过、重复副作用或丢失用户决定？
6. 观测到的浪费与推测收益分别是什么？需要更大重构的建议也列出，注明风险，不能因暂时不好改而压掉。

例：确认卡因空行变化重新弹出，源码确实比较了全文摘要。浅层结论是“摘要变了，二次确认符合逻辑”；正确分析是“为什么空行应使授权失效？用户是否修改了交付范围？删掉全文摘要校验后，真正的授权范围是否仍可约束推送？”即使没有程序异常，也可能是明确的流程优化候选。

例：构建报错后等人 100 分钟，不能止于“人工响应慢”。检查问的是业务选择还是 Agent 可以自行查证的技术事实，其他不依赖答案的工作能否继续，以及提示词是否诱导不必要的确认。

例：某机制现有测试全绿，测试却明确要求重复审批。这只能证明实现符合旧测试，不能作为保留重复审批的质量证据。

正常任务也要评估“能完成但绕远路”，不要只筛 failed/stalled。不要把所有改动都压缩成“补文档/加提示词”；能删除多余代码时直接指出最小删除边界。建议可尖锐，事实必须克制。

## 最终输出

输出一个 JSON 对象。报告格式仅供本机保存，不影响生产任务。不确定就如实写，不要伪造字段。

```json
{
  "coverage": "prod；部署版本未核实；采集 30/45 个需求任务；日志尾部存在截断",
  "limitations": ["缺完整构建日志，无法计算编译耗时"],
  "findings": [
    {
      "key": "push-confirmation-notes-override",
      "category": "hypothesis",
      "title": "确认推送后仍再次要求调整",
      "evidence": ["prod/task-5/events.jsonl#eventId=123", "prod/task-5/waiting.json#waiting_id=example"],
      "analysis": "示例，不能照抄为事实。描述已观察到的前后关系、实际影响、替代解释及缺失证据。",
      "recommendation": "先读取部署版本中的确认分支；若备注确实覆盖明确选择，删除该否决条件，横向检查其他审批入口。",
      "impact": "先写观测到的影响；没有完整时间线不估算损失小时数"
    }
  ]
}
```

证据引用保持稳定，不把本轮采集时间附在每条引用后。相同 key 与相同证据集合只改措辞，不算新告警。不同任务发生同一机制问题，追加证据到原 key。没有新发现输出 `findings: []`；仍需填写覆盖与限制，不能把部分巡检描述为全量健康。
