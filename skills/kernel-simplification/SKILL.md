# 内核问题：先删机制，再做简化

本文“内核”指 mae-flow，“Cloud”指宿主 mae-flow-cloud。

目标是让用户意图尽快闭环，减少内核对 Agent 工作方法的干预。不要默认用新增状态、指纹、凭证、拦截条件或重试流程修补旧机制。也不要把本技能当作一次全面重写内核的授权：围绕当前问题和同源场景处理。

## 先查清机制，再决定去留

沿真实调用链找到触发条件、状态写入、判定、恢复和外部操作，区分事实失败与宿主自行制造的流程失败。不要仅凭报错文案或旧设计说明决定保留机制。

设计修复前，按以下顺序判断：

1. **能否删除？** 说明该机制到底防止什么具体错误；删除后是否仍有真实权限、用户明确决定和外部系统结果作为边界。若只是替 Agent 判断工作方法、重复证明已有事实，或强制维护内部凭证，优先删除，并清理依赖它的状态、提示词、配置及恢复分支。
2. **不能删除，能否简化？** 给出删除后会发生的具体错误及代码或场景依据，不能只说“为了安全”。优先复用现有事实和执行入口，减少状态、跨语言调用、重复检查和重复确认。
3. **能否交给提示词？** 修复策略、探索范围、检视材料如何整理、首次编译如何包含 UT 等工作方法，优先通过现有 skill 或提示词表达。将相关指令接入 Cloud 实际使用的 TS 提示词构造或注入路径，确认 Agent 能收到；不要只新增一份不会被读取的文档，也不要另加执行器硬门禁验证 Agent 是否逐项服从。
4. **剩余逻辑放在哪里？** Cloud 专属的必要逻辑优先内化到现有 TS 模块，尽量只做事实读取、明确动作执行和必要的恢复。迁移要收掉旧运行路径及重复状态，不能同时保留 Python、脚本和 TS 三套裁决。真正被其他宿主使用的通用能力，依据调用方决定归属，不为变薄而盲搬。

## 横向排查必须覆盖同源场景

删除或简化前，搜索同一概念的字段、别名、错误文案和状态转换，检查当前可达的相关路径：

- Web、移动审批、工具调用等入口是否执行同一种语义；明确选择与备注是否混淆。
- 手动、自动、重试、异步回调和重启恢复是否重复判定或重复执行；旧任务状态如何继续运行。
- SHA、指纹、收据等是否同时被用作事实标识和流程否决条件；更新后会不会重开已完成工作。
- 提示词、配置、部署脚本、测试和文档是否仍要求已删除机制，导致 Agent 将它重新补回来。

按同一职责统一处理这些场景；不因文本相似就顺手改动无关机制。已有相似问题可参考 [审批与 SHA 排查记录](../../docs/approval-and-sha-audit-2026-09-12.md)，但以当前代码为准。

## 保留必要事实，不让事实衍生无用流程

用户明确拒绝、真实授权范围、外部操作成败不能交给提示词猜测。涉及重复推送或重复触发等外部副作用，仍需有明确的操作身份与恢复语义。

SHA 可用于标识构建、流水线和远端代码版本。检查它如何参与后续判定：旧版本的成功不能冒充当前版本成功，旧版本的失败也不应反复唤醒 Agent 修复当前代码。保留必要的版本关联，不因 SHA 变化自动推导“用户授权失效”或“全部检视意见需要重做”。

## 用场景验收，收掉旧路径

针对本次修改验证用户可观察的结果：例如确认后不重复询问、备注不改变明确决定、恢复不重复外部操作、旧流水线结果不污染当前判断。按影响范围选择测试，避免通过测试把待删除的内部机制固定下来。

若涉及内核源码修改，先修改并提交内核源仓，再通过 Cloud 的 `harness/sync-kernel.sh` 同步快照；不要只改 `kernel/` 快照。提交、推送和部署沿用当前会话授权，不因本技能额外增加审批。

交付时简要说明：删了什么、为什么仍需保留什么、横向覆盖了哪些场景，以及测试和源仓同步结果。不要为了执行本技能再引入一套凭证或流程门禁。
