# 交付前 CodeCheck 自查

在当前任务授权范围内完成检查与修复，沿用已有分支、提交规范和人工决定。`.codecheckcli/` 整个目录只留本地，禁止暂存、提交或加入交付清单。只做本地检查及必要修复；推送、MR 和正式流水线由原任务负责，不另启交付流程。

## 1. 固定检查范围

按顺序确定 `base`：用户指定的起点 → 当前任务提供的修改前提交 → 确认尚未开始修改时的 `HEAD`。已经开始修改且没有记录时，核实实际目标分支并取 `merge-base`，注明来源；不能把已有功能提交后的 `HEAD` 当起点。

确认 `base` 可读取且是当前 `HEAD` 的祖先。同一任务始终复用它，修复提交也纳入范围；无法恢复可靠基点时，报告检查未完成。

将仓库、任务/分支、完整 `base` 及来源保存在已有任务记录中；无记录位置时使用本地 `.codecheckcli/prepush-context.json`，不提交。恢复时核对归属。开工时调用只需记下基点，并在已有任务计划中注明交付前自查，然后继续实现。

## 2. 扫描已提交变更

使用环境或 Skill 包提供的 `codecheck`，首次使用先核对 CLI 帮助。`--range` 只覆盖已提交历史：按任务权限精确提交本次改动，保留无关的暂存及未提交内容；无法提交时报告覆盖缺口。工作区干净不代表没有待查提交。

记录当前完整 `HEAD` 为 `checked_head`，替换占位符后在仓库根目录执行：

```bash
codecheck increcheck --range <base>,<checked_head> --mode json
```

等待扫描完成，结合命令输出、退出状态和结果更新时间确认本轮结果有效，再读取 `.codecheckcli/codecheck-result.json`（版本差异以实际帮助和输出为准）。失败时可查 `codecheck tasklog`，不能拿上轮 JSON 当本轮结果。同一仓库串行扫描；多仓分别记录基点和结果。

## 3. 修复并复查

结合差异和调用上下文确认告警归属，只修本次引入且在授权范围内的问题；存量、疑似误报和归属不明项保留说明。告警不在改动行上，也可能由本次修改引起。

对最新结果中已确认待修复且 `fixType === 1` 的告警，按 UUID 执行：

```bash
codecheck fix --id <uuid1>,<uuid2>
```

其他告警做最小必要修复。检查实际 diff 和受影响的功能，运行必要的定向测试或编译；不靠禁用规则、抑制告警或削弱测试消除问题。

按原规范提交修复，更新 `checked_head`，复用同一 `base` 重新扫描。根据最新结果继续处理本次引入的问题，直到修复完成，并对最终待推送代码完成复查。

## 4. 返回检查结果

最终结果必须覆盖待交付代码；检查后改过代码则复查。比较范围、代码及检查配置均未变时可复用有效结果，不因推送重试重复扫描。

完成后简要报告 `base` 及来源、最终 `checked_head`、结果文件、修复内容和实际验证结果。区分工具零告警与经核实的存量、误报，说明依据。

结论仅代表本地 CodeCheck；编译、测试、正式流水线分别如实报告。把结果交回原任务，由原有交付规则决定后续动作。
