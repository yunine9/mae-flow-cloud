# DTS 问题定位诊断通用技能

本篇是团队货架的通用定位方法论：取用次序与阶段关卡以所在问题会话的工作流（技能 issue-analysis）为准——业务仓根目录 `.cac/skills/` 有问题 skill 用业务仓的，否则用本篇。

## 核心方法论：五步诊断法

```
问题描述 → ①结构化信息提取 → ②正向流程梳理 → ③可能性穷举 → ④证据验证 → ⑤根因判定 → 分析报告
```

---

## ① 结构化信息提取

从问题单/用户描述中提取完整的结构化信息，作为后续分析的基础。

### 提取规则

| 字段     | 来源                  | 优先级     | 回退策略                                                     |
| -------- | --------------------- | ---------- | ------------------------------------------------------------ |
| 问题描述 | detailDesc / probDesc | 必填       | 无法获取则要求用户手动提供                                   |
| 发生时间 | occurTime             | 极重要     | occurTime为空→用createAt                                     |
| 版本信息 | verInfo               | 极重要     | 正则 `R0(\d+)` 提取；>=27→master，<=26→`br_MAEV100R0{NN}C10_release` |
| 环境信息 | envInfo               | 重要       | 为空时查图片分析中的IP信息                                   |
| 代码分支 | verInfo推导           | 极重要     | 无法推导→询问用户                                            |
| 图片     | HTML中`<img src>`     | 如有必分析 | 平台自动落工作区，见下                                       |

信息入口：登记元信息用 `get_issue_meta` 重查，单据详情用 `dts_get_ticket`——人填的查元信息，平台拉的查拿单。

### 图片分析（如有图片）

1. **获取**：调 `dts_get_ticket`，工单内嵌截图已由平台自动落到工作区 `ticket-images/<单号>/`（平台代取，不要自行下载描述里的外链图——容器无凭据，签名会过期）；
2. **分析**：用 `inspect_image` 识图（主上下文只收文字结论），提示词："分析此DTS问题单截图，提取：1)错误信息/错误码 2)界面异常现象 3)关键数据/参数值 4)其他诊断相关信息"；
3. **回填**：摘要写进分析报告「问题现象」节。

### 问题单过滤

以下类型问题单跳过代码级诊断，直接按非问题收口，仅在报告里记录判定原因：

- **安全类型**：密文密码/安全扫描/墨子/skyeye/漏洞/安全编码
- **代码优化**：代码优化/代码重构/性能优化/代码清理
- **资料类型**：资料/文档/帮助/联机帮助/用户指南
- **提示级别**：severity = Suggestion

## ② 正向流程梳理

### 前置：读取服务设计文档（两步法）

在目标仓库根目录下查找 `docs/codewiki/DESIGN-*.md` 文件。

**第1步：读概述（前50行）** — 获取系统定位、核心交互、功能清单、架构图

**第2步：Grep关键词** — 根据问题描述搜索相关段落，获取模块职责、接口说明、数据流

**规则**：DESIGN文档通常很大（60K+ tokens），禁止全文读取，必须分步按需读取。不存在则跳过。

### 正向流程梳理

1. **核对分支**：代码仓已由平台拉到 `repo/<仓名>/`（有单场景自动切好修复分支 `master_<工号>_<单号>`）——`git branch --show-current` 核对，分析按当前分支进行；①推导出的问题版本分支写进报告「问题现象」节，与当前 checkout 不同时（如问题在 R026 版本分支、分析基线在 master），差异写进报告「置信度」节——定位结论只对分析时的代码基线负责
2. **识别入口**：根据REST接口/CORBA接口/按钮名称在代码中匹配入口
3. **关键词匹配**：无明确入口时，根据问题描述/图片识别关键词在代码仓中匹配
4. **跨仓追踪**：识别包名/导入路径/服务名/接口名，匹配所属代码仓，自动补全跨仓定义
5. **多态/重载推断**：根据方法名/参数/注解/上下文推断真实执行方法，无法唯一确定则输出所有合理分支
6. **设计模式识别**：识别责任链/策略/观察者/工厂/代理/装饰器等模式，按模式结构补全流程
7. **异步流程追踪**：ACE消息队列、线程池、等待响应、定时器、数据库进度表、文件共享
8. **配置驱动流程**：BPMN/YAML/XML/JSON/状态机配置 → 节点映射到代码类/方法/接口

### 关键增强特性

| 特性           | 方法                                                         |
| -------------- | ------------------------------------------------------------ |
| 跨语言统一解析 | Java/Go/Python/C++/JS 按语言规则提取，跨语言调用点自动桥接(gRPC/HTTP/MQ/JNI) |
| 日志关键字识别 | C++: #define宏定义(LOG_XXX) → Java: LOGGER.info/error → JS: 框架调度 |
| 日志名称识别   | C++: iMAP.XXX_agentXXX.trace* → Java: root* → JS: 控制台     |

### 产出

- 正向流程图（含多仓调用架构 + 调用链时序 + 正常/异常日志索引），写进报告「问题现象」节
- 微服务映射（涉及的代码仓和服务列表）
- 诊断决策树（③的输入）

## ③ 可能性穷举

### 六大故障模式（必须逐条检查）

| #    | 故障模式     | 说明                                                         | 案例                                                 |
| ---- | ------------ | ------------------------------------------------------------ | ---------------------------------------------------- |
| 1    | 单服务故障   | 代码错误/资源管理/多线程时序/异常保护不足/CBB接口/OS命令/容器使用不当 | 业务方法NPE、资源未释放                              |
| 2    | 树形传导故障 | 根源服务异常引发一连串服务故障                               | CMServer启动慢→界面网元树异常；安全服务异常→鉴权失败 |
| 3    | 环境问题     | OS资源/配置/硬盘/网络问题                                    | 存储IO慢→文件生成慢；CPU高→业务慢                    |
| 4    | 公共组件异常 | 平台/中间件/CBB故障                                          | ACE高低水位→消息队列挂死                             |
| 5    | 历史垃圾数据 | 历史残留/旧版本数据与新版本规则冲突                          | 启动时网元未加载完→MML失败；旧证书新校验→异常        |
| 6    | 用户误操作   | 参数设置/操作顺序错误                                        | 界面参数配置错误→业务异常                            |

### 穷举规则

1. 每个故障模式都要在正向流程图中标注可能的故障点
2. 对每个故障点，输出**正常日志流**和**异常日志流**（从代码中提取日志关键字）
3. **不允许跳过任何分支**——可能性低不等于不可能

### 诊断决策树结构

```
问题A
├─── 分支1: 原因X（单服务故障）
│       ├─── 可能性X1: 代码NPE
│       └─── 可能性X2: 资源未释放
├─── 分支2: 原因Y（传导故障）
│       └─── 可能性Y1: 下游服务超时
├─── 分支3: 原因Z（环境问题）
│       └─── 可能性Z1: 磁盘IO慢
└─── ...
```

## ④ 证据验证

### 验证方法一：日志证据查找（有日志时）

对每种可能性：

1. 在日志中搜索相关证据关键词（`fetch_logs` 拉到 `local-logs/` 后 grep）
2. 找到的日志证据必须可追溯:**时间戳 + 出处指针**(local-logs 目录+grep 关键字;报告里引关键行不超过两行当锚点,整段原文不贴)
3. 结合代码逻辑验证证据与代码行为是否一致
4. 标记验证结果

| 验证结果     | 含义                              |
| ------------ | --------------------------------- |
| 已确认       | 有正向日志证据支撑                |
| 已排除       | 有排除依据（日志/代码证明不可能） |
| 需进一步确认 | 有间接证据但不足以定论            |

### 验证方法二：关键流程加日志法（无日志且推理陷入僵局时）

当纯代码推理无法确定根因时（特别是异步回调、状态共享、多入口修改同一变量的场景），**不要继续绕圈推理，改为设计加日志验证方案**。

**适用场景**：

- 多处代码修改同一共享变量
- 异步回调链中存在竞态条件
- 事件驱动/轮询机制中的时序问题
- 纯代码阅读能列出多种可能根因但无法排除

**方法步骤**：

1. 识别关键流程节点：在问题涉及的完整链路上标记每个状态变更点
2. 设计编号日志：每个节点加 `编号 + 关键变量值` 的输出
3. 触发正常场景：收集完整日志序列，建立**正常流程路径**
4. 触发问题场景：收集日志序列，建立**问题场景路径**
5. 对比差异：找到分叉点——分叉点就是根因

**阶段边界**：分析阶段没有部署工具——加日志要修改代码并换库部署采集，那属于修改→验证闸的流程。分析阶段把它作为已设计好的验证方案写进报告「下一步建议」（标清关键流程节点与编号日志方案），由修复阶段执行；日志只用于定位，定位完成后必须清除。

**核心原则**：先设计验证再继续推理，不要在多种假设间反复推理而不验证。

### 验证方法三：代码推理（无日志且无法加日志时）

1. 在代码中定位对应逻辑
2. 分析代码路径的所有分支
3. 结合正向流程图判断哪条分支会导致问题现象
4. 标记置信度

## ⑤ 根因判定

### 判定规则

| 验证结果模式             | 判定结论                       |
| ------------------------ | ------------------------------ |
| 仅1个可能性"已确认"      | 该可能性为根因                 |
| 多个可能性"已确认"       | 需进一步分析因果链             |
| 所有可能性"已排除"       | 存在未知分支，需重新梳理决策树 |
| 部分可能性"需进一步确认" | 输出待确认清单                 |

### 未定位根因时的处理

1. 按正向流程梳理方法重新梳理流程
2. 识别是否其他分支正向流程没有梳理到，补充流程图
3. 输出需要进一步分析的清单（写进报告「下一步建议」）

## 产出：issue-analysis.md（五章节）

分析报告落工作区根目录,章节结构由所在会话的平台门票钉死(`submit_analysis` 机械校验,缺章节打回),五步法的产出全部组织进五章节。报告的读者是确认卡前的用户——一句话总结先行、节名即问题、证据指针化、提交前收敛:五步法的中间产物(决策树、穷举标注、正常/异常日志流)不整块搬进报告,`submit_analysis` 交的是**结论版**。

```markdown
# 问题分析:<问题标题>
(首行=一句话总结:串联 现象→根因→方案,≤60字,只读这一行就能拍板)
## 问题现象
(≤5行:问题描述/发生时间/版本与分支/网管环境/截图分析摘要;正向流程图
 等大块参考资料挂本节末尾——覆盖主流程和关键分支)
## 问题根因
(写定论:因果链 步骤1→步骤2→…;未收敛时如实列可疑点按可能性排序;所
 有可能性被排除→写明"存在未梳理分支"并给待确认清单;非问题写判定依据)
## 修改方案
(fix 阶段照此执行的承诺,不是建议:按仓一行一条——改哪里/怎么改;加日
 志验证方案写明关键流程节点与编号日志设计;非问题写"无需修改"与归档/补
 单建议)
## 证据链
(每条一行=事实一句话+出处指针:代码 File:行号/日志证据(时间戳+指针:
 local-logs 目录+grep 关键字,关键行≤2行)/截图;只收支撑根因与修改方案
 的证据,上限 5 条;与结论冲突的反证必须有一条,或声明"未见反证"——日
 志与代码原文不贴,顺着指针去工作区核)
## 置信度
(高/中/低 + 为什么不是更高,≤2行;分析基线与问题版本分支的差异写这里)
```

### 报告质量检查（完整路径 9/9 强制）

| #    | 检查项                 | 要求                                                         |
| ---- | ---------------------- | ------------------------------------------------------------ |
| 1    | 现象节完整             | 问题描述/发生时间/版本分支/环境均有值                        |
| 2    | 业务流程图             | 必须包含完整流程图，至少覆盖主流程和关键分支                 |
| 3    | 可能性穷举             | ≥3个可能性，且必须涵盖"代码逻辑"+"环境/资源"+"数据/状态"三大类 |
| 4    | 每个可能性结构完整     | 含：故障模式/验证方法/代码位置/代码证据/日志证据/验证结果   |
| 5    | 日志证据可追溯         | 含时间戳与出处指针(目录+grep 关键字),禁止模糊描述            |
| 6    | 结论与证据一致         | "已确认"须有正向证据；"已排除"须有排除依据                   |
| 7    | 根因定位               | 有"已确认"可能性时结论必须输出根因与因果链                   |
| 8    | 未定位时输出待确认清单 | 无"已确认"可能性时「下一步建议」须明确                       |
| 9    | 建议措施具体           | 禁止"建议排查"等空话，须含具体命令/关键字/修改方向           |

**适用范围**：上表 9 项约束**完整路径**；轻量路径（已知问题、一眼可定位的配置错误，分流由所在会话工作流 issue-analysis 判定）免 2/3/4/7/8（流程图与可能性穷举类）——1/5/6/9（现象完整、证据可追溯、结论与证据一致、建议具体）不免。

**检查流程**：生成报告后按适用范围逐项对照，不通过则补充后重新检查，直到全部通过。通过后在报告末尾追加 `<!-- 报告质量检查：9/9 通过 -->`（轻量路径追加 `<!-- 报告质量检查：轻量 4/4 通过 -->`）

## 纪律归属（不复述平台契约）

流程、停机节奏、轻量/完整分流、非问题收口由所在会话工作流（技能 issue-analysis）与平台契约决定，本篇不复述不另立，相抵时以外层为准。本篇只保留一条方法内迭代自由：**分支可回退**——发现新情况（日志暴露另一个根因）直接回到②重新梳理，不须经谁批准。
