# 修复交付

前置:方案经用户确认,会话已绑定单号;没绑定请用户去页面绑定。

怎么改码调用 implement 技能,验证范围按下面的「按需本地验证」判断,交付动作以本 skill 为准。

## 按需本地验证

- 根据改动影响判断验证投入:简单明确、影响可核实的局部修改,检查差异并完成必要的静态检查后可以直接提交推送,无需专门启动本地编译。接口、依赖或构建配置、跨模块行为等改动,以及仅看代码无法确认的修复,按需编译相关仓并运行直接相关的测试;判断依据是风险,不是文件数量。
- 本地验证用于更快发现问题,减少每轮等待远端全量流水线的时间。优先复用已有输出和依赖做增量编译;真正首次构建某仓时先读该仓构建 Skill 和真实构建入口,遵守其环境准备、首次构建和 UT 要求。已有 .mae-flow-work/build-notes.md 时可参考,按当前文件核实。只构建与本问题相关的业务仓,不为凑验证编译其他仓,也不反复 clean。
- 编译输出缺失时按仓库构建方法重新配置、生成所需文件后继续。准备、下载和编译命令设合理超时;同一错误先查原因再重试,环境或依赖确实无法恢复时如实说明阻碍,按当前介入档位反馈,避免无限等待或原样重试。
- 实际执行的 UT 用 `report_ut` 如实上报;未做本地编译或测试就在交付说明中写明范围与原因。全量回归交给平台流水线,交付仍以平台核实的当前提交真实流水线结果为准,推送成功不等于流水线通过。

## 1. 分支

修复分支 `<基线>_<工号>_<单号>_<时间戳>` 由平台在 `pull_repo` 时生成并自动切好,同一会话所有仓同名,开工前 `git branch --show-current` 核实;回执报过「基线分支不可用」的仓没有分支,问用户定分支来源。

## 2. 提交

提交信息必须匹配 `[单号][类型] 描述`(CodeHub pre-receive 会拒收不合规提交):
- 类型白名单:feat/fix/refactor/test/chore/docs/style(修 bug 用 fix);
- 例:`[DTS2026082001317][fix] 修复登录超时`;
- `git add` 只加本次范围的文件;工作区可留未提交改动,推送只发已提交历史,如实说明未包含的改动。

## 3. 推送

`git push` 在容器里被禁用,推送用 `push_branch`(不受阶段限制),多仓改过的仓各自调,`repo` 传该仓地址。

推送被 non-fast-forward 拒绝说明远端已有同名分支(新命名下正常流程不会撞名,属罕见异动,回执会点名):与用户核对远端状态后带 `force: true` 重推覆盖(平台覆盖前先现查远端旧位置,对不上即拒推,不盲盖)。该分支已有 MR 的,覆盖后原 MR 自动更新,不重复建。拿不准远端状态,先 AskUserQuestion 核对。

## 4. 提 MR

`create_mr` 逐仓调用,`repo` 参数指定仓;标题由平台按绑定单号自动填写、自动关联,不用填。合入由用户决定,不由你执行。

## 5. 申报验绿

建齐 MR 后调 `complete_stage` 申报 MR 清单(mrs 参数:MR 链接或仓地址)。平台核对清单台账(少报/多报点名打回)并验流水线:有红当场打回,修完同分支再推、重建 MR 后重新申报;流水线在跑则停等,绿了自动收口。

## 多仓口径

- 只给真正改过的仓建 MR,没改的不硬凑。
- 每个改过的仓:各自分支(同名)→ 各自 push_branch → 各自 create_mr → 一起申报。
- UT 结果(`report_ut`)只是事实上报,不是建 MR 的前置。

## 边界

- 只改与这张单相关的代码;发现顺带问题,先问用户是另开问题还是本单处理。
