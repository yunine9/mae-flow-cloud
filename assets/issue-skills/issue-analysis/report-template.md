# 产出:issue-analysis.md(五章节固定 + 条件章节「关键决策」,缺一章打回)

报告是双读者的:**现象/根因/方案/置信度**写给确认卡前的用户——一眼看懂是硬要求(一句话总结先行、节名即问题、提交前收敛);**证据链**写给下一棒的 AI——证明证据真被找过。

```markdown
# 问题分析:<问题标题>
<一句话总结>   ← 紧跟标题的一行,串联 现象→根因→方案(≤60字),只读这一行就能拍板
## 问题现象    ← ≤5行:现象/影响范围/发生条件/版本分支;流程图等参考资料挂节末
## 问题根因    ← 写定论;未收敛时如实列可疑点(按可能性)+缺什么条件——这些就是给用户看的「遗留问题」,不硬编排序
## 修改方案    ← fix 阶段照此执行的承诺,不是建议:按仓一行一条,改哪里/怎么改/怎么验证
## 证据链      ← 每条一行=事实一句话+出处指针,上限 5 条(收什么、怎么核,见取证清单)
## 置信度      ← 高/中/低 + 为什么不是更高(≤2行)
## 关键决策    ← 条件章节,见下方写法;自动档必须写
```

- **证据链只收与结论相关的证据**:支撑为主,反证至少一条(或声明"未见反证")——确认偏误是这条链要防的第一个病;每条真实可核(顺着指针能走到),不为凑数堆无关发现。
- **证据指针化**:出处指针=`repo/<仓名>/路径/File.java:120`、`local-logs/<目录>/ grep "关键字"`、`ticket-images/<单号>/xx.png`、单据字段;日志与代码原文不进报告——要核真伪顺着指针去工作区核,可复核靠指针可走,不靠原文在场。
- 结论必须能沿证据链逐条走回去;写不出证据链的结论不许提交——这是本阶段的铁律。
- **非问题出口**:证据链写判定依据,「修改方案」写"无需修改(结论:非问题)"或补单建议,不为走流程制造代码修改。
- **关键决策的写法**:每条一行=AI 举卡的问题 + 选中的答案,只写选中项,未选的选项不写。**自动档(用户全程未参与,开场说明有标注)必须写**——这是用户复盘 AI 决策的唯一入口;非自动档发生过关键举卡对齐时也写,没有就整章省略。
- **工作期追加,提交前收敛**:分析中新证据往里追加,重启/续聊先读这份报告再继续,不重新分析;但 `submit_analysis` 提交的是**结论版**——提交前把过程探索压掉(被排除的假设一行带过或只留指针),只留支撑最终结论的内容。报告是决策材料,不是过程回放。

## 提交与关卡

`submit_analysis` 以**报告在场且五章节齐全**为门票,缺章节直接打回(章节名单以本模板为准);过了平台举确认卡等用户:有单确认后进问题修改,无单给 conclusion(issue/non_issue)由用户定夺挂起或闭环。被闸打回就补证据再交,不与闸争论。

**报告确认即本工作流完成**:后续修改与交付的纪律在技能 issue-delivery——业务 skill 的约定影响面止于分析报告,不延伸进交付环节。
