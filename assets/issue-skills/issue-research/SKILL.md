# 问题研究与根因定位

定位方法论的仓内兜底(取用次序见 issue-analysis:业务仓问题 skill、团队货架通用定位 skill 在前,都没有才用本篇)。

## 方法

1. **复述现象**:用自己的话把问题现象、影响范围、发生条件重述一遍——答非所问的研究比不研究更浪费。
2. **备齐材料**:
   - 找仓:`lookup_modules` 按问题里的业务关键词检索模块(跨端问题常对应多个模块),命中就 `bind_module` 登记再逐仓 `pull_repo`;检索不到用 AskUserQuestion 问用户;
   - 读代码:在 `repo/<仓名>/` 里定位相关模块,git log/blame 找最近变更——多仓问题每个仓都要看,别只盯一个;
   - 拉日志:调 `fetch_logs`(多服务可一次拉),在 local-logs/ 里 grep 报错栈、时间线;
   - 查单据:有单号时调 `dts_get_ticket` 看处理历史,避免重复别人已排除的方向。
3. **形成假设→找证据证实/证伪**,循环;证据不足就提问或补取证。中途发现还缺仓,`pull_repo` 随时补。

## 提问纪律

现象、根因、修改方案里任何一环拿不准,用 AskUserQuestion 问用户。固定流程的关键确认由平台在 submit_analysis 后举卡把关,靠你的是把证据做实;自由探索在动手改码前主动对齐方案。

**选项题必须给推荐**(recommended 填所推荐选项的原文,平台机械校验:缺失或与选项对不上,整卡打回)。推荐要有依据——把理由写进问题正文或 context;拿不准就去补研究,而不是空着推荐。开放题(不带 options)不填推荐。

## 产出:issue-analysis.md

写在工作区根目录,章节结构与机械门票**以技能 issue-analysis 为准**(五章节,首行一句话总结)。本方法论补充的内容要求:

- **结论**节首行给一句话根因;修改范围**按仓列清**(每个仓改什么),验证与回滚方式一并写进「修改方案」;
- **证据链**每条=一句话+出处指针(文件路径:行号、日志目录+grep 关键字、截图文件),原文不贴;
- 不确定事项写进「置信度」(为什么不是更高)。

后续编码与 MR 描述都以报告为源。

## 非问题出口

研究结论是"非问题"(误报/环境问题/需求误解/无法复现)时:在 issue-analysis.md 写清证据与结论 → `submit_analysis` 提交(无单场景结论=non_issue)→ 向用户说明,建议归档。代码修改只属于真实缺陷,不为走流程而制造。
