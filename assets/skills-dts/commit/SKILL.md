# 提交修复分支的变更

把当前分支上的修改按项目钩子要求的严格格式提交。平台的 pre-receive
钩子会拒绝不符合格式的提交信息,所以**提交信息必须精确匹配**,写好后
先验证再提交。

## 提交信息格式(强制)

```
[单号][类型] 提交描述
```

- **单号**:`[DTS2026082001317]` 这样的方括号单号(`\w+`)
- **类型**:只能是下方白名单之一,方括号包裹
- **提交描述**:必须有非空描述

| 类型 | 含义 | 示例描述 |
|------|------|---------|
| fix | 修复缺陷 | 修复登录超时 |
| feat | 新增功能 | 新增导出功能 |
| refactor | 重构 | 抽取公共工具类 |
| test | 测试相关 | 补充单元测试 |
| chore | 杂项/构建 | 升级依赖版本 |
| docs | 文档 | 更新 README |
| style | 代码风格 | 格式化代码 |

合法:`[DTS2026082001317][fix] 修复登录超时`
非法:`修复登录超时`(缺单号)、`[DTS2026082001317]修复登录超时`(缺类型段)、`[DTS2026082001317][fixbug] 描述`(类型不在白名单)

## 步骤

1. **拿单号**。分支名 `<基线>_<工号>_<单号>` 的尾部段即是单号
   (如 `master_y00965296_DTS2026082001317` → `DTS2026082001317`),
   或从开场事实取。缺失时停下询问。
   - 完成:拿到非空的单号字符串。

2. **核对改动范围**。查看当前仓库的变更与当前分支,确认要提交的内容
   是正确的、完整的、不夹带无关文件。
   ```bash
   git status --short            # 哪些文件变更
   git branch --show-current     # 当前分支
   git diff --stat               # 改动规模
   ```
   与用户确认改的就是这张单的范围;发现无关改动先分开处理。
   - 完成:明确本次要提交的文件清单,且与当前问题单范围一致。

3. **选类型**。按上表从白名单挑一个最贴切的类型(修 bug → fix,
   新功能 → feat,重构 → refactor,其余看语义)。拿不准时问用户。
   - 完成:类型在白名单 {feat, fix, refactor, test, chore, docs, style} 内。

4. **写提交信息并验证格式**。拼出 `[单号][类型] 提交描述`,核对:
   - 单号与分支名/开场事实一致
   - 类型在步骤 3 选中、拼写无误
   - 描述非空、有实际内容(不是占位符)
   - 不匹配就重写,直到满足再继续
   - 完成:提交信息三段齐全、类型合法、描述非空。

5. **仅暂存本次改动并提交**。明确 `git add` 本次范围的文件
   (**禁止 `git add -A`**,防夹带),再提交:
   ```bash
   git add <本次范围的文件...>
   git commit -m "[DTS2026082001317][fix] 修复登录超时"
   ```
   - 完成:`git log -1 --format=%s` 显示的提交信息与步骤 4 拼写的
     完全一致,且只含本次范围文件。

6. **汇报**。告知用户:提交的单号、类型、描述、涉及文件数。
   push 与 MR 不在此处理——收口由 RequestDelivery 工具申请、宿主执行。
