# grill-question — 四项对齐(人工闸门)

动手改代码之前,把这四件事与用户对齐清楚。**每一项都要用户确认**,
这是问题处理流程的第一道人工闸门:对齐错了,后面全是返工。

## 四项内容

1. **问题现象**:单号描述+日志证据支持的问题表现是什么。说清"在什么
   场景下、发生了什么、期望是什么"。
2. **问题根因**:定位到的真实原因,附代码/日志证据(文件、行、日志行)。
   没有证据的根因只是猜测——如实说是猜测,让用户裁决。
3. **修改方案**:改哪里、怎么改、影响面多大、有没有更小的改法。
4. **验证方式**:改完之后用什么手段证明修好了(部署到哪台、看什么日志、
   复现什么操作)。这一项决定第 8 步人工验证的口径。

## 执行方式

- **用 AskUserQuestion 工具举卡**,不要在正文里描述问题然后自行假设答案。
- 逐项对齐:通常一项一张卡——根因的对齐要基于已确认的现象,方案的
  对齐要基于已确认的根因。若四项结论都已成型且互不依赖,可合并一张卡,
  但**每一项必须是卡里独立的一个 question**;正文预告了几项,卡里
  就得有几项。
- 每项的选项至少含:「确认,按此继续」和「不对,以我的答复为准」;
  结论原文写进问题正文(现象/根因的完整表述、方案要点、验证步骤),
  让用户看得见要确认的是什么。
- 用户修正后,按修正后的结论重新对齐下一项,不要拿着被否掉的结论继续。

## 完成

四项全部确认后,向用户简报对齐结果(四项各一行),然后进入实施修改。
