# 执行阶段：深挖一条链路中的一跳

你只负责步骤说明中 `hop` 指定的这一跳。`sibling_hops` 告诉你同一子功能的其他跳，用来确定你的边界——上一跳的结束处就是你的起点，你的终点是下一跳的起点。

## 步骤

1. **读任务**：`hop.questions` 是你必须回答的问题；`hop.related_code` 是起点。如果任务中列出了已存在的公共组件文档，先读，公共机制直接引用，不要重复解释。
2. **追代码**：找到这一跳的入口和出口（精确到文件、行号或符号）。沿着数据和控制流跨过边界，重点记录：线程/进程切换、消息 ID 与结构、定时器、配置项与开关、错误处理、重试、超时、状态机迁移、持久化。
3. **挖"为什么"**：读注释和业务文档中的意图与约束，沿无线豆包返回的真实 AR 查需求、设计和历史。当前没有提交历史工具时记录未查范围，不能声称已执行 Git 命令。
4. **问领域问答工具**（如已配置）：围绕 `hop.questions` 中代码回答不了的部分。
5. **写 findings**（原始证据，可以详细）。
6. **写 section**（精炼的文档片段，会被后续会话组装成完整文档）。
7. **写附带产出**：代码和问答都回答不了的问题写入待确认问题；遇到的术语对应写入术语候选。

## 产出 1：data.findings（仅保留在执行记录中）

```markdown
# <跳标题> —— 证据记录

## 代码追踪
<按调用顺序记录关键位置与观察，每条带代码引用>

## 业务文档要点
<只摘录意图和约束，带〔文档:…〕出处>

## 领域问答记录
### qa-<任务id>-1
- 问：……
- 答（要点）：……

## 提交记录线索
<相关提交的 hash 与说明要点>

## 推断与存疑
<哪些是推断、依据是什么；哪些问题没有答案>
```

## 产出 2：data.section（供后续整理的知识片段）

不需要 frontmatter。结构：

```markdown
### <跳标题>

**这一跳做什么**：一两句话，说明它在链路中的作用。

**入口与出口**：入口 `仓:路径#符号`，出口 `仓:路径#符号`；跨越的边界（进程/消息/仓）。

**约束与原因**：
<逐条说明约束，每条讲清"是什么、为什么、出处"。这是最重要的部分。>

**易错点**：
<改这一跳时最容易犯的错，及后果>

**存疑**：
<没有确认的点，对应待确认问题编号 Q-…>
```

目标长度 30～120 行。对 `hop.questions` 中的每个问题，要么在 section 中回答，要么列入待确认问题——不能静默跳过。

## 质量自查（写完后逐条检查）

- 删掉任何一段，一个能读代码的人会损失信息吗？不会就删。
- 每条事实都有出处吗？代码引用的行号亲自打开核对过吗？
- 有没有复述业务文档、罗列函数或逐行叙述流程？
- 有没有"相关模块""进行处理""等等"这类空泛表述？

## 修订轮

如果任务提示中有上一轮评审意见，逐条处理：在已有 findings 和 section 基础上修改；评审指出的错误引用必须修正；评审认为空泛的段落要么补充具体内容，要么删除。
