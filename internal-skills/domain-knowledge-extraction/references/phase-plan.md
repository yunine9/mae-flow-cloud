# 规划阶段：把一个模块拆成子功能和链路跳

输入是任务中的模块信息（来自盘点）。你的产出是这个模块的任务清单，后续每一跳都会由一个独立会话去深挖，所以**拆得好不好直接决定文档质量**。

## 步骤

1. **定位入口**。在模块的 `repos` 范围内找：前台页面与接口调用、后台服务入口、配置/开关处理、定时任务与调度、消息处理函数、算法主类、南向适配与消息收发。也要找网元上报等"外部触发"的入口。
2. **读业务文档中对应特性的章节**，了解有哪些子功能、开关、参数。只用来识别子功能，不要在这里写内容。
3. **识别子功能**。拆分标准：有自己的触发条件、有相对独立的一段代码。合并标准：只是参数或分支不同、链路大部分相同——合成一个子功能，并在 `summary` 里注明变体。公共组件模块的"子功能"是它提供的几种机制。
4. **为每个子功能划分链路跳**。一条链路从触发（前台配置、定时任务、网元上报……）到效果（南向下发、结果呈现、告警……）。**每一跳是一次跨边界**：跨仓、跨进程、跨模块、跨线程、经过消息或存储。一般 3～10 跳。
5. **为每一跳写 3～6 个具体问题**。这些问题就是后续会话要回答的内容，要聚焦于读代码读不出来的东西：
   - 好问题："MroTask 在参数下发失败后是否重试？重试期间新的优化周期到来会怎样？"
   - 好问题："为什么切换参数的调整步长限制在 ±2dB？依据是协议、现网经验还是算法稳定性？"
   - 坏问题："介绍一下 MroTask 类。""这一跳做了什么？"
6. **控制规模**。步骤说明给出 `max_hops` 时遵循该上限；未给出则按实际复杂度拆分。超出时按价值取舍（问题多、改动频繁、业务核心的优先），被舍弃的写入 `deferred`。

## 产出：knowledge_work_result.data

```json
{
  "module": "mro",
  "subfeatures": [
    {
      "id": "param-tuning",
      "name": "切换参数自动调整",
      "summary": "一两句话说明这个子功能解决什么问题；有变体时注明",
      "trigger": "周期性优化任务 / 前台手动触发",
      "doc_refs": ["〔文档:MRO特性描述.md#参数自动调整〕"],
      "hops": [
        {
          "id": "h1",
          "title": "前台配置下发到后台优化任务",
          "from": "frontend 配置页",
          "to": "backend MRO 任务调度",
          "related_code": ["frontend:src/views/son/mro/**", "backend:src/son/mro/task/**"],
          "questions": [
            "配置变更是立即生效还是等下一个优化周期？为什么？",
            "……"
          ]
        }
      ]
    }
  ],
  "deferred": [{"what": "……", "reason": "……"}],
  "notes": "拿不准的判断"
}
```

本方法的记录约定：子功能 `id` 与跳 `id` 只能用小写字母、数字、连字符；每一跳必须有 `id` 和 `title`。`related_code` 的格式为 `仓名:路径或glob`。

## 不要做的事

- 不要写文档正文。
- 不要把"读代码就能回答"的问题放进 questions。
