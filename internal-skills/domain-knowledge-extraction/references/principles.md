# 写作准则（所有执行会话必读）

## 这些文档写给谁

读者是**会读代码、但不了解这块业务历史**的工程师和 Agent。他们随时可以自己打开代码，所以文档唯一的价值，是提供**读代码读不出来**的东西。写之前先问自己：一个能读代码的人读完代码后，还需要知道这句话吗？不需要，就不写。

## 写什么（按价值从高到低）

1. **为什么**：为什么这样设计；为什么不用看起来更简单的做法（被否决的方案及原因）。
2. **跨边界的约束**：跨模块、跨仓、跨进程、跨网元的时序、顺序依赖、幂等、并发、超时、重试、回滚、一致性要求。单看任何一处代码都看不出来的，最值得写。
3. **外部依据**：协议条款、网元/网管行为、现网配置特征、客户场景。
4. **易错点**：改这里最容易犯的错，以及犯错的后果（现象是什么、影响多大）。
5. **不该模仿的现状**：遗留写法、临时绕过方案、计划淘汰的机制。Agent 会模仿周围代码，必须明确告诉它哪些不能学。
6. **业务意图**：这段逻辑要达成什么业务效果。代码可能有 bug，意图不会；写清意图才能发现代码与意图不符。
7. **术语对应**：业务说法 ↔ 代码命名 ↔ 协议术语。

## 不写什么

- 目录结构、文件清单、类清单、函数清单。
- 接口签名、参数列表、字段列表的罗列——给出位置引用即可。
- 逐行复述流程（"先调用 A，再调用 B，然后返回"）。只在跨边界、有约束时说明调用关系，并说清约束。
- 业务文档（尤其是面向客户的 support 文档）的复述：功能介绍、操作步骤、参数说明。只提取其中代码里没有的**意图和约束**。
- 空泛表述：“相关模块”“进行处理”“等等”“一些逻辑”“负责管理”“起到关键作用”“较为复杂”。每句话都要具体到能被验证或反驳。

## 证据：每条事实都要有出处

证据保存在 knowledge_draft.sources 和 knowledge_work_result.data.findings 中。记录实际仓编号、版本、路径与行号，或上传资料编号、章节、豆包真实返回的 evidence_id；评审通过 knowledge_source_check 与原文工具核对。

最终 Markdown 面向没有本平台上下文的读者，只写知识本身：业务含义、适用条件、约束、原因、示例和易错点。不要写研究日志、工作编号、仓库 UUID、提交 SHA、查询编号、模型或工具调用状态，也不要加“来源”清单、generated_by 或 status: draft。必要的外部标准名称、公开链接、业务文档名称或代码符号可自然融入叙述，不能依赖本地编号才能理解。

没有出处的内容只有三种处理方式：删掉；写成"推断：……（依据：……）"；转成待确认问题。

## 不编造

推不出来、查不到、问不到的"为什么"，**不要**补一个听起来合理的解释。把它写成待确认问题交给专家。一个具体的好问题，比一个编造的答案有价值得多；编造的内容一旦进入知识库，会被后来的 Agent 当成事实反复引用。

历史设计原因通过上传资料核对；无线豆包只提供领域背景，不能证明本系统的历史原因。没有提交历史工具时如实记录未查范围。

## 领域问答工具（如已配置）

- 根据当前证据缺口提出具体问题，优先问：为什么这样设计、有什么约束、历史上出过什么问题、现网有什么特殊情况。
- 问题要具体，带上代码里看到的名称和现象，不要问"介绍一下 XX"。
- 在 findings 中记录每一问：编号 `qa-<任务id>-<序号>`、原问题、回答要点。
- 回答与代码矛盾时，分别记录业务意图与当前实现及各自版本，写入待确认问题；不能用实现否定设计意图，也不能用检索摘要证明当前行为。

## 附带产出的格式

**待确认问题**（保存到 data.questions，没有就不写）：

```markdown
### Q-<任务id>-<序号>
- 范围：<模块 / 子功能 / 跳>
- 问题：<一句话，具体到可以直接回答>
- 已知：<已经确认的事实及出处>
- 为什么重要：<答案会影响什么判断或改动>
- 建议请教：<角色，如"南向适配负责人""MRO 算法设计者"，不写人名>
```

**术语候选**（保存到 data.glossary，没有就不写）：

```markdown
| 业务术语 | 代码命名 | 协议/标准术语 | 出处 |
|---|---|---|---|
| 邻区 | NCell / Nrt | Neighbour Cell | `backend:src/son/anr/NcellMgr.h#NcellMgr` |
```

## 格式要求

- 中文书写，代码标识符、协议术语保留原文。
- 最终文档从清晰的业务标题开始，不要求机器字段或平台状态。
- 一篇文档回答一个问题。以段落和表格为主，避免多层嵌套列表。
- 篇幅服务于信息量：宁可短而准，不要长而空。

## 边界

- 只写入任务指定的路径，严禁修改代码仓，严禁 git 写操作、构建、安装。
- 只使用平台注入的源码、上传资料和无线豆包工具，不使用 Bash、Claude CLI 或自行构造外部命令。提交历史工具未提供时记录限制，不伪造已查历史。
- 只做本任务，不要替其他任务提前写内容。
