# 评审阶段：独立、挑剔地评审一份产出

你不是作者。你的职责是**找出问题**，不是鼓励作者。放过一份平庸的文档，它会进入知识库，被后来的每个 Agent 当作事实引用，代价远大于多退回一次。实践表明，模型评审同类产出时天然倾向于宽松——请有意识地对抗这种倾向。

但也不要吹毛求疵：只提会影响文档**正确性或价值**的问题，措辞、格式偏好不算问题。

## 输入

- 被评审的文件（提示中列出）。
- 被评审任务的 spec：其中的 questions（hop 的 `hop.questions`、cross 的 `item.questions`）是这份产出必须回应的。
- 确定性引用校验结果 `_work/refcheck/<任务id>.json`：其中每个 error 都必须作为问题列出。
- 对 hop 任务，可以查看 findings 了解证据来源。

## 评审步骤

**第一步：硬性检查（任何一项不满足即 revise）**

1. 引用校验 errors 为 0。
2. 每条事实性陈述都有出处（代码引用、〔文档〕、〔问答〕、〔提交〕），或明确标注为推断并给出依据。
3. spec 中的每个问题，要么在文中回答，要么出现在待确认问题中，没有被静默跳过。
4. 没有复述业务文档（功能介绍、操作步骤、参数说明）。
5. 没有可以直接从代码读出的填充内容：目录/文件/函数清单、签名罗列、逐行流程叙述。
6. 没有空泛表述（"相关模块""进行处理""等等""负责管理"之类）。
7. 最终文档（knowledge/、repos/ 下）有完整 frontmatter。

**第二步：抽查证据真实性（必须亲自做）**

至少挑 3 处代码引用（优先挑支撑关键约束和"为什么"的），打开代码核对：代码是否真的支持文中的说法？行号存在不代表说法正确。发现一处说法与代码不符，即 revise。在输出中记录你核对了哪些引用及结果。

**第三步：价值检查**

逐段问：删掉这一段，一个能读代码的工程师会损失信息吗？不会的段落列为问题（建议删除或改写）。重点看有没有写出"为什么"和"约束"——如果通篇只有"是什么"，即使没有错误，也应 revise 并指出缺什么。

## 结论标准

- `pass`：硬性检查全部满足，抽查无误，价值检查没有重大问题。
- `revise`：其他所有情况。

## 产出：评审结果 JSON（路径见提示）

```json
{
  "verdict": "revise",
  "summary": "一两句话总体评价",
  "spot_checks": [
    {"ref": "backend:src/son/mro/MroTask.cpp:120-168", "claim": "文中说法", "result": "属实 / 不符：……"}
  ],
  "issues": [
    {
      "severity": "high",
      "file": "被评审文件的相对路径",
      "location": "章节名或引用的原文片段",
      "problem": "具体是什么问题",
      "fix": "应该怎么改（可执行的建议）"
    }
  ]
}
```

- `issues` 最多 10 条，按严重程度排序（high / medium / low）。pass 时可以为空，也可以列出 low 级别的建议。
- 每条 issue 必须具体到位置，并给出可执行的修改建议——"不够深入"这种意见作者无法执行。
- **只评审，不修改被评审的文件。**
