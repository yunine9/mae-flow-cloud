# 收尾阶段：模块导航、子功能交互、仓内设计要点

这是一个模块的最后一个任务。输入是本模块已完成的所有文档：`knowledge/chains/<模块>/` 下的 common.md 与各子功能文档（部分子功能可能因评审未通过而标记为需人工，但文件仍在）。

## 产出 1：`knowledge/chains/<模块>/README.md`（模块导航）

使用模板 `module-readme.md`。它是 Agent 进入这个模块时读的第一页，所以要**短**：
- 模块的业务目的（一两句，带出处）。
- 子功能表：名称、一句话说明、文档链接。
- 共用段：指向 common.md。
- 依赖的其他模块及依赖方式（调用、消息、共享数据）。
- 各仓中的入口位置（代码引用）。
- "改这个模块前必须知道的三件事"：从各文档中挑出最关键、最容易出事的约束。

## 产出 2：`knowledge/chains/<模块>/interactions.md`（子功能之间的相互影响）

使用模板 `interactions.md`。这往往是整个模块最有价值、也最容易漏掉的一篇。重点找：
- **共享数据**：多个子功能读写同一张表、同一个缓存、同一组参数。谁写、谁读、并发时怎样。
- **优先级与冲突**：两个子功能对同一对象做相反的决策时谁说了算（例如自动添加与黑名单、自动调整与人工锁定）。
- **顺序依赖**：一个子功能的结果是另一个的输入。
- **互相抑制**：一个子功能运行期间另一个是否暂停。

每一条都要有代码证据。去代码里确认，不要只凭各子功能文档推测。如果确实没有交互，不生成空文档；将检查范围和结论保存到 data。

## 产出 3：`repos/<仓名>/docs/modules/<模块>/design.md`（仓内设计要点）

对模块涉及的每个仓各写一篇（使用平台提供的仓编号和默认目录），使用模板 `repo-design.md`。只写**在这个仓里改这个模块时**需要知道的：仓内的不变量、易错点、不该模仿的遗留写法，以及指向上层链路文档的链接。跨仓的内容不要写在这里——它们属于上层文档。

如果某个仓里这个模块只有很薄的一层（例如只转发），没有值得写的内容，就不写这个仓的文件，并在结果文件的 summary 中说明。
