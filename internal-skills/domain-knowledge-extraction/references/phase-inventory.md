# 盘点阶段：识别模块、公共组件与执行顺序

你是整个流水线的第一个会话。你的产出决定了后面几百个会话做什么，所以宁可多花时间核实，也不要草率。

## 输入

- `_work/scan-summary.md`：脚本对所有代码仓做的确定性结构扫描摘要（构建单元、依赖关系、被依赖次数、近一年提交数）。**先读它**。
- `_work/scan.json`：完整扫描数据，需要细节时查阅。
- 业务文档：只读目录/功能清单/特性列表部分，用来知道"业务上有哪些能力、叫什么名字"，不要通读。
- 代码仓：用于核实，看目录命名、入口类、配置项。

## 步骤

1. **读扫描摘要**，了解每个仓的规模、构建单元分布、跨仓依赖。
2. **读业务文档的功能清单**，列出业务能力的名字。
3. **把构建单元归并成业务模块。** 模块是"团队讨论时当作一个整体的业务能力"（例如 ANR、MRO、MLB），通常跨越多个仓、多个构建单元。依据：命名、目录位置、业务文档的功能名、依赖关系。不要按构建单元机械地一对一映射，也不要把几个独立特性硬合成一个。
4. **识别公共组件**（kind = public）：被多个模块依赖的基础机制，例如消息总线、南向适配框架、任务调度、配置管理、公共数据模型。判断依据是被依赖次数高、且理解业务链路时绕不开。纯工具类（字符串、日志封装）不单独成模块。
5. **识别排除项**：测试工具、第三方代码、生成代码、明显废弃的代码。判断废弃的信号：近一年零提交、没有被任何单元依赖、名字带 old/legacy/bak/v1 等。确定的写入 `excluded`；拿不准的仍作为模块保留，但标 `suspect_legacy: true`。
6. **为每个模块填写信息**（见下方格式），`repos` 中的 glob 要实际能匹配到文件。
7. **确定执行顺序 `order`**：公共组件在前（被依赖多的更靠前）；业务模块按价值排序——近一年提交多、业务文档中重要、被其他模块依赖的靠前。流水线中途若出现意外，排在前面的模块最先保证完成。

典型规模是 15～40 个模块。明显超出这个范围时，重新检查拆分粒度。

## 产出 1：`_work/inventory.json`

```json
{
  "modules": [
    {
      "id": "mro",
      "name": "MRO 移动鲁棒性优化",
      "kind": "business",
      "summary": "一两句话说明业务目的，附出处，如〔文档:xxx.md#概述〕",
      "repos": {
        "frontend": ["src/views/son/mro/**"],
        "backend": ["src/son/mro/**"],
        "southbound": ["src/adapter/mro/**"]
      },
      "depends_on": ["msg-bus", "sb-adapter"],
      "subfeature_hints": ["切换参数自动调整", "乒乓切换检测"],
      "signals": {"commits_1y": 342, "fan_in": 2, "doc_sections": 5},
      "suspect_legacy": false
    }
  ],
  "order": ["msg-bus", "sb-adapter", "mro"],
  "excluded": [
    {"path": "backend:src/son/anr_v1/**", "reason": "近一年无提交且无依赖方，疑似被 anr 替代"}
  ],
  "notes": "对盘点结果的补充说明、拿不准的判断"
}
```

硬性要求（脚本会校验，不满足则本任务失败重跑）：
- `id` 只能用小写字母、数字、连字符，全局唯一，不超过 60 字符。
- `kind` 只能是 `public` 或 `business`。
- `repos` 的键必须是配置中的仓名，至少一项。
- `depends_on` 只写模块 id。

## 产出 2：`_work/inventory.md`

给人看的一页摘要：模块表（id、名称、类型、涉及的仓、一句话说明）、执行顺序、排除项、拿不准的判断。校准点人工确认时会先看这一页。

## 不要做的事

- 不要开始写任何模块的文档内容。
- 不要为了显得全面而把每个目录都列成模块。
