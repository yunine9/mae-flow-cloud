# 完整单元测试示例

目标是让开发者按项目已有的测试方式验证该用法。测试代码与使用代码分别编写，测试的正确性依据实际代码核对。

## 检索与展开

1. 用 code_search、purpose="unit-test" 检索目标接口、调用方类型、测试命名和断言。结合 purpose="usage" 的生产调用定位对应测试目录。
2. 展开测试函数全文，追踪 fixture 的 setup/teardown、mock 的行为与期望、assertion/matcher、helper 的实现、被测对象依赖及必要数据。
3. 读取真实测试构建配置、运行入口、依赖库、环境参数和数据路径。基础仓配置用 component_source 核对，跨仓配置与 helper 用 everycode 展开。
4. 将实际展开的测试编号写 test_evidence。搜索命中或文件名只用于定位，完整断言及前提才支持示例结论。

完成条件是能说明输入如何构造、依赖如何隔离、被测调用如何发生、结果如何断言、资源如何释放，以及该测试在真实项目中如何构建运行。

## 编写代码

unit_tests 包含完整测试代码和实际运行配置，可用四级标题组织：

- 正常路径：给出输入、操作、明确期望与完整断言。
- 适用边界：按真实契约选择空值、范围、容量等条件。
- 失败行为：有确定失败语义时断言返回值、异常或状态，并核对恢复行为。
- 异步行为：按项目实际设施等待确定的完成条件，断言事件、结果或回调。
- 资源清理：按真实生命周期核对释放、关闭或取消，包含相应清理代码及可观察断言。

只选择当前场景适用的类别。fixture/mock 和 helper 的定义、必要导入、测试依赖和数据准备一起给出；读者能沿完整代码运行，而不是补写占位函数或省略号。模拟对象沿用项目实际依赖接口及测试框架。

使用示例仍采用正常发布依赖；测试专用 API、内部构造器和私有测试目标在单元测试区明确限定到测试环境。

## 运行事实

构建和执行命令来自真实配置，写清相对执行目录、目标和必要参数。这里记录的是读者可使用的命令；实际执行情况另写任务 findings，仅在确实运行后记录结果。阅读到断言和完成代码编写不等于测试已经通过。
