# 基础组件知识研究

目标是让使用方掌握组件能力、正常接入和重要边界。源码仓不是组件粒度上限：同一能力可以跨仓实现，一个仓也可以提供多种独立能力。结合接口、实现、构建发布、示例和真实调用建立联合视图，避免分仓扫描后简单拼接。

## 查证对外能力

这里的“对外”指向组件使用方提供的受支持入口，包含公司内部团队，不等于公网 API。public、可链接或其他仓已经调用，只能证明技术可访问或存在用法，不能单独证明推荐使用。

关注 interface/、idl/、include/、api/、SDK 入口和发布配置，但不把目录名当最终白名单。协议定义继续追踪生成入口与发布产物；内部实现、测试夹具和 Mock 可作研究证据，不自动成为推荐依赖。真实调用也可能是历史违规用法，须核对。

配置范围存在 sdk/pom.xml 时实际读取，并追踪子模块、parent、properties、profiles、发布插件和相关脚本。区分构建聚合、依赖引用与对外发布；modules 或 dependencies 不是发布清单。记录有依据的 groupId:artifactId:version、packaging 及必要 classifier，解释继承与启用条件。聚合 POM 或 BOM 不是运行时 JAR，配置也不能证明某版本已发布。

C/C++ 核对实际发布的头文件、库与链接目标；Java 核对受支持包、模块与发布 JAR；其他语言核对 exports 和包入口。没有某个构建系统就使用真实机制，不套用 Maven/CMake。关键证据在允许范围外时报告缺口，不自行扩大访问范围。

有研究价值但对外属性未确认的候选可进入审查，标注“待核实”；内部机制标注“内部实现参考”，解释不可直接依赖的边界。不能为了多产出拆出无独立用途的内部函数。

## 研究实际用法

在指定语言和版本内读取 API、类型、实现、构建及测试，再搜索具体接口的跨仓调用并展开上下文；列表截断继续分页。归纳不同场景的调用顺序、错误处理、资源所有权与释放、并发/异步、取消以及 UT/Mock。重复调用去重，有不同语义的变体继续研究，不把某个偶然写法称作团队规范。

全量模式覆盖选定范围的能力，指定主题只研究相关内容；讨论和局部修订服从本轮选中范围，不再次全量盘点。只有定义没有真实调用时就地说明“仅依据接口定义”，不能伪造使用案例。

## 文档与示例

沿用一篇联合文档：概述说明跨仓关系与组合方式，各能力章节写适用场景、用法、接口及对外依据、集成产物/依赖、完整示例、约束与来源。分段保存用于避免输出截断，不把每个章节另行发布为一篇知识。保留章节稳定编号与关联能力。

示例站在组件使用方视角，包含导入或依赖、初始化、实际调用、错误处理与资源清理。C/C++ 给出实际发布布局下的 include，按真实构建方式提供链接配置；CMake target、库名和文件名分清，不编造 find_package 或 target。Java 给出实际 import 与 Maven/Gradle 依赖；其他语言给出对应包与导入。

候选示例的发布或依赖条件未核实时就地标明，缺证据不编 API。测试专用头文件和内部类不能作为推荐接入方式。未经编译运行的示例注明未验证；保留必要版本限制、例外和来源，研究过程与覆盖记录放任务记录，不塞进使用指南正文。
