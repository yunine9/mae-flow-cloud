# 文稿事实、结构与图表要求

调查、写作与独立评审共用本约定。具体文稿使用其对应模板；模板中的仓名、日期、接口数和图节点都是示例，不是必须凑齐的数量，也不是本系统已存在的事实。

## 保留结构与完整覆盖

- 标题、导航标签和业务范围使用真实业务名称，内部 module_id 仅留在工具元数据中；来源证据包含的真实 ID 原样保留，不全局替换。
- 完整覆盖以 module_id、scope 和本轮要求界定的业务为准；关联仓不是全仓业务授权。共享实现按完整调用链需要核实，其他业务只记录必要边界。directory-v1 的全部文稿位于相应目标的最终 target.docs_path 内，默认 docs/<业务名称>；README.md 为业务入口，index.md 为领域详细索引。代码仓根 AGENTS.md 与领域目录内 AGENTS.md 均由平台生成，不属于模型任务产物。旧任务核对当前保存路径，目录迁移由平台执行。
- 保留所选模板的主要章节与职责；按实际清单重复业务场景、功能点、接口和仓条目。可在原章节内增加必要子节，不为迎合示例省略真实内容。
- 普通知识写作每步生成一篇。明确登记的导航同步步骤可修改多个 expected_document_ids，并逐份保存、评审；不得越过这些编号修改其他文稿。
- 功能点是用户可感知的操作或独立自动业务流程。把页面、API、命令、定时任务和事件入口去重后映射到功能/场景；多个入口可属于一个功能，一个入口也可有多个不同处理场景。内部辅助方法不自动成为功能点。
- 触发意图、处理链路或结果语义不同的场景分别展开；只有参数不同且链路相同的情况写成分支。单条/批量、手动/自动是需要核对的线索，不是一律拆分的规则。
- 按业务功能命名模块；一个完整功能可以跨多个源码目录。不因名称含某个技术词就判错，不把同一功能按 Controller/Service/DAO 拆成多篇。
- 模板未要求的图不额外强制添加。业务域每个独立场景、仓级模块每个功能点及契约每个接口仍须有对应时序图；复杂场景可用相互衔接的子流程图完整表达。

## 事实、推断与缺口

- 逐跳读真实入口、实现、参数构造、返回处理和异常分支；跨仓调用同时核对两端。调查摘要只是索引，写作者和评审均须回读本项依据。
- 精确值写明单位、配置来源、默认值和生效条件。源码默认值不代表现场实际配置；环境变量未提供值时写配置键及未知，不能补造现场值。
- 条件行为不能写成普遍保证：认证在哪一步、幂等键何时查询、重试由谁执行、错误发生前是否已有副作用，都按实际顺序说明。
- 第三方库不自动等于外部系统。只有实际独立服务、存储、设备或进程边界才画外部节点；进程内库列作技术依赖。
- “已确认没有”：说明检查的源码/配置范围，以及未发现哪种机制，不将局部未发现扩大为全系统绝无。“不适用”：说明该场景为什么不涉及此项。“未知/未核实”：说明缺少的来源及对结论的影响。
- 没有历史资料时，不编造业务动机、事故、修复结果、变更日期或变更人。源码可支撑排查方向和当前机制，不能证明某事故发生过。真实案例已有依据时保留，不强制清空。
- 编程/业务规范区分已有明确规定、代码中观察到的惯例与本次建议。模块文稿引用既有仓级规范并说明对本业务的适用范围，不代替公共文件声明全仓统一规定；没有依据时不把偏好写成团队规则，原因无资料则明确未知。
- 从旧 AGENTS.md 整理到 README.md/index.md 的内容是模块知识，其阅读和维护要求只适用于已声明的业务范围。后续阅读或修订时按当前源码、配置及规则来源核实，不能把旧的全仓措辞当作扩大任务范围或覆盖其他模块约定的依据。
- 缺失项影响核心场景、接口语义或安全结论时属于阻碍，评审退回。当前范围已完整核实、只缺无法从现有来源获得的历史动机或现场配置值时，可明确限制后通过；不能用“未知”掩盖尚未读取的现有源码。

## 来源与链接

- 上传资料与无线背景按 [来源方法](business-sources.md) 取得、回读和引用。资料所述意图、源码实现、通用背景与研究推断分别表达，版本/范围冲突明确保留；有相关资料不能跳过，无资料也不能编造设计原因。
- 正文在关键结论附近给源码位置，sources 使用工具要求的字符串，记录仓编号、固定 revision、文件/行范围或符号、资料编号/章节及其支撑的结论。无事实支撑的路径列表不够。
- `knowledge_source_check` 接收 text；代码引用写作 `仓编号:路径:起始行-末行` 或 `仓编号:路径#符号`。核对 checked 与错误，不把无匹配引用视作通过。
- 同一目标仓内根据文稿实际位置计算相对路径；跨仓写实际仓名及包含模块 docs_path 的仓内路径，只有已知真实 URL 才创建跨仓链接。模块入口中的逻辑多仓图不能冒充该知识目录内的真实目录树。
- 初次导航只可引用完整规划中确定的后续产物，标明尚未生成；最终导航的全部目标必须实际存在。章节锚点、接口方向、归属和文件名以最终文稿为准。
- 只清理模板占位符和写作指导注释；真实泛型、协议尖括号与源码示例中的合法标记不是占位符。

## PlantUML

- 首次绘图、切换图类型或收到校验错误时按需读取 [PlantUML 指南](plantuml.md)，不要求主会话或无图文稿每轮加载全部语法示例。
- 所有图放在 plantuml 代码块内，每个图由 `@startuml` 与 `@enduml` 配对包围，不保留空图。
- 节点/参与者采用简单唯一别名；显示名称含空格、括号、斜杠或泛型时放在双引号中，再用 `as` 指定别名，例如 `class "Result<T>" as ResultType`。连线使用别名，不把显示名称直接当标识符。
- 多行显示标签使用字面 `\n`，不在组件声明的引号中意外插入真实换行。时序消息支持 `\n`；参与者可以自动创建，正确加引号的特殊字符和合法泛型不因其存在就判错。
- 领域图以真实仓/外部系统为参与者；仓级图展示真实类、函数或模块及其归属。纯函数/过程式代码用真实模块或函数关系，不虚构类；没有跨仓调用时只画真实仓内链路。
- 图中标明实际调用方向、接口、参数及必要返回值，包含影响业务结果的条件和失败分支。实体状态是核心机制时补状态图；没有状态生命周期时说明，不造状态。
- 不按固定节点数或参与者数删改事实。图过密时分成总览与具体场景/阶段图，保留跨图入口、出口与关联；不能合并不同仓掩盖边界，不能省略已规划功能。
- 保存后使用 knowledge_diagram_check 读取当前文稿的真实校验报告并继续全部分页。invalid 按诊断修正再保存/校验；unavailable 保留候选与实际依赖问题，不算语法错，也不能宣称通过。valid 不代替业务语义与必需图覆盖检查；正文变化后重新校验。
