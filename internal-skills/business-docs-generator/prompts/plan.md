# 规划阶段提示词

## 一、目标

在用户本次范围内，**穷举**上下文 repositories 中的所有来源仓、业务域、外部系统和业务功能，生成完整、详尽的文档规划。工具映射与路径约定见 [平台执行约定](../references/platform-execution.md)。

## 二、执行步骤

1. **识别仓列表（穷举）**：
   - 用 knowledge_structure 列仓，逐仓 component_source list 并继续分页；工具默认过滤的依赖与生成目录不当作自有业务模块。不要把已有知识文稿当作源码实现；构建、部署和业务配置仍在调查范围
   - **不可遗漏任何代码仓**。即使某仓只有部分目录与本项目相关（如仅一个子模块），也必须列出
   - 对每个仓读取构建文件（`pom.xml` / `package.json` / `CMakeLists.txt` / `app_define.json` 等），识别技术栈

2. **分配独立调查，再深入源码**：
   主会话先依据仓列表、构建文件和目录入口划分调查单元，不先把全部业务实现读入自己的上下文。按仓与业务入口划分，再按完整业务场景细分；同一场景的关键调用链保持完整，不按任意行数截断。每个单元说明仓编号、源码范围、具体待回答问题、依赖单元和对应产物。调查步骤通过 knowledge_work schedule 登记 readonly=true，互不依赖的单元可用 run 的 concurrency=1～4 并行执行，本方法默认 3。可执行的参数与结果示例见 [独立调查](../references/platform-execution.md#独立调查)。

   以下深入读取由对应独立调查单元完成：
   - 读取构建文件识别技术栈（语言、框架、构建工具）
   - **深入源码目录**，不可仅看顶层目录名就推断模块结构。必须进入各源码子目录，识别实际的包/模块划分
   - 对于 Java 仓：从实际源码根目录识别入口、业务实现及存在的分层，常见位置如 `src/main/java/`
   - 对于 C++ 仓：从构建目标与实际源码目录识别业务模块，不能假定所有文件都在 `src/`
   - 对于前端仓：从实际路由/页面/状态入口识别业务，`src/containers/`、`src/components/`、`src/store/` 仅为常见示例
   - 其他语言同样按构建、入口和调用实现调查；记录真实核心类/函数及关键文件，不套用固定目录或分层

   instructions 只传本单元范围、方法入口、证据索引和问题。单元启动时按 id 回读必要结果并重新打开原始源码，knowledge_work_result 的 summary 只写主要发现，data 保存关键路径/行范围、跨仓调用与待核实问题，document_ids=[]。结果由平台持久保存，只读单元不调用 save_document。主会话按编号读取必要结果，维护短摘要与编号引用；发现尚未调查的范围时继续登记具体单元，不集中展开全部源码。

   每个范围内目录和业务入口应归入已调查功能，或说明不相关/生成内容的依据。尚未调查、无法读取和来源失败单独列为待解决范围，不计作已穷尽。调查不要求机械逐行扫描几十万行源码，但必须沿完整入口清单追踪有关实现，不能用若干代表性入口替代全部功能覆盖。

3. **识别跨仓关系（穷举所有调用链）**：
   - 需要构建依赖候选时，以 repository_id 和 include_dependencies=true 调用 knowledge_structure；该操作显式扫描配置的来源仓，候选仍需源码核实
   - 各调查单元通过构建依赖、IDL、REST 路径、import/include 及调用实现识别范围内仓间关系；主会话汇总有来源的关系，待确认的双方调用交给独立调查核实
   - **穷举所有外部系统**，包括但不限于：
     - 独立数据库或数据库服务；进程内数据库和本地 SQLite 记录为存储机制，不自动视作独立系统
     - 文件存储（NFS、HDFS、HOfS 等）
     - 消息/事件中间件（CORBA Event Service、Kafka 等）
     - 独立认证/权限服务；进程内安全库记录为技术依赖
     - 命名服务（CORBA Naming Service 等）
     - 其他平台服务（拓扑服务、网管服务、配置管理等）
     - 网元设备（通过各类协议对接）
   - **不可仅列出最明显的外部系统。** 检查各仓实际网络/消息/存储交互点。第三方 import 或构建依赖只是线索；进程内工具库不是独立外部系统，不为它生成虚构的协议和系统画像
   - 用 PlantUML 画出有证据的仓与外部系统关系；没有关系的仓可作为独立节点。复杂关系可分图并保留衔接，不能为了图小删掉真实节点

4. **识别业务域（穷举范围内业务意图与完整链路）**：
   - 从实际业务入口出发：页面操作、公开 API、命令、定时任务、事件或消息消费均需覆盖。存在前端/BFF/核心分层时沿该链路追踪；没有这些层时不补造
   - **穷举所有业务域，不可遗漏。** 常见的业务域包括：任务管理、结果查询、数据导入导出、实时分析、模板管理、网元管理、系统监控、安全/匿名化等
   - 对于每个业务域，列出：
     - 涉及的仓（完整列表）
     - 核心链路（一句话描述端到端流程）
   - **业务域判断标准**：一组围绕独立业务意图、具有完整数据流的功能构成业务域，可跨仓，也可仅落在一个仓。按业务边界合并相关场景，不按仓数或函数数量硬拆；不可因为功能"较小"就省略

5. **规划文档列表**：
   - 按文档类型列出所有待生成文档，并另行标明真实执行依赖；不能把阅读导航的顺序变成整包串行执行
   - 每个文档标注 layer（domain / repository）、对应模板；templates/repo 是模板目录名，不是 layer 值
   - **领域文档**：标注需要通读的仓列表及各仓的业务源码范围
     - 已确认入口与关键实现使用实际仓编号、文件或符号定位，例如 `repo-api:src/task/TaskController.java#create`；相关模型、配置继续列出。待展开目录另列为未核实范围，不把目录名冒充完成的精确调查
     - 范围覆盖实际存在的入口、业务实现、模型、状态与配置。采用 Controller/Service 等分层时逐层核对，非分层或函数式代码按真实结构记录，不补造类
   - **仓级文档**：标注该仓内需要覆盖的**业务功能**及每个功能涉及的源码范围
     - 已确认入口与关键实现定位到实际文件/符号，说明它们如何构成该功能；目录只用于标注所属范围或仍待展开的区域
     - 一个业务功能可能跨多个源码目录，须列出所有相关目录和关键文件
   - **模块划分维度：按业务功能划分，不按代码目录划分**。模块文档名使用业务功能名（如 `trace-task-create`），不使用代码目录名（如 `domain-task-create`）。一个业务功能可能跨多个代码目录，合并为一个模块文档。
   - **穷举所有业务功能模块**，不可遗漏。每个仓的业务功能模块应覆盖该仓的所有核心业务逻辑，不可只列主要功能而省略次要功能
   - 每个调查单元保留去重后的业务入口到功能/场景的对应关系。多个入口可以服务同一功能，一个入口也可能有多个真实场景；说明对应关系，不要求入口数量等于功能数量
   - 在执行关联中保留相关调查单元编号，写作步骤据此定位原始来源；每篇开始时回读对应源码和资料，不把协调器摘要当作本篇已经完成的阅读
   - 最终导航同步单独安排：每份导航依赖其覆盖的全部文稿写作及最后修订步骤；已有初稿时依赖初稿步骤，没有则可直接生成最终版。根导航列出仓 AGENTS 时也依赖这些目标；不同导航不要互相等待形成循环。声明全部实际改动编号

6. **保存并登记完整规划**：按 `prompts/plan-template.md` 保存 Markdown，使用 knowledge_work save_document，id=current-plan。正文保留全部产物条目、范围边界和调查结果编号，不复制源码或全部调查报告。填写稳定 document_id、实际 target_id、仓内 path、模板及写作步骤；instructions 带本条目必要字段和证据索引，不要求每个 writer 加载整份规划。用 knowledge_diagram_check({work_document_id:"current-plan"}) 查图，按 next_start 读完报告；invalid 修正正文再查，unavailable 保留规划与依赖问题。图通过后用 action=plan、work_document_id=current-plan 登记全部 document_ids，宿主登记前也会校验。规划不进入知识发布；已登记产物是否齐全由宿主检查，业务完整性仍需独立核查。

7. **独立核查**：由主会话安排 readonly=true 的独立步骤，读取本提示词、规划模板、current-plan 和 read_plan 全部清单/排除说明分页，用 knowledge_diagram_check 的 work_document_id=current-plan 读取当前图表报告，按调查索引回查各仓业务入口。核对清单与正文一一对应、入口到功能/场景有对应、适用文档类型齐全。大范围可分仓或业务域核查，主会话汇总各范围结论。用 knowledge_work_result 返回 review: {pass, feedback} 和 document_ids=[]；invalid/unavailable 不能通过。普通只读步骤的 done 只表示返回结果，主会话须检查 review.pass；有明确修订后再用新编号核查，没有新证据的相同失败不反复重建步骤。新发现先补正文和 plan；旧排除项保留原因。

## 三、规划输出格式

使用 `prompts/plan-template.md` 模板生成规划文件。

## 四、自检清单

规划完成后，逐项自检，不通过则补充后再次自检：

- [ ] **仓完整性**：是否遗漏了 repositories 中的任何来源仓？即使某仓只有部分目录相关，是否也已列出并遵守用户范围？
- [ ] **业务域完整性**：实际页面、API、命令、定时和事件入口是否都能对应到业务域/场景？是否遗漏无前端或单仓业务？
- [ ] **外部系统完整性**：实际独立数据库、存储、消息、认证和命名服务是否覆盖？是否把进程内库或本地存储误作独立系统？
- [ ] **源码范围精度**：已确认入口和关键实现是否有文件/符号定位？待调查目录、来源失败是否仍明确标为未完成，未被算作已经精确覆盖？
- [ ] **模块命名**：所有模块文档名是否表达业务功能，而非机械复制目录名？技术词只有在确为业务名称且有依据时保留，不能只因包含某个词就判错。
- [ ] **模块覆盖度**：每个仓的业务功能模块是否覆盖了该仓的所有核心业务逻辑？是否有被遗漏的功能模块？
- [ ] **模板符合性**：保留规划模板的主要章节与执行关联；示例仓、接口和功能按实际清单展开，没有为凑示例数量补造条目？
- [ ] **输出覆盖**：是否列全范围内基础文档、各业务域、真实交互仓对、外部系统与各仓业务功能？经验文稿仅在有真实案例时规划。
- [ ] **执行对应**：每篇是否有唯一稳定文稿编号、目标编号、仓内路径和写作步骤编号？是否将逻辑仓前缀误当作仓内路径？

## 五、约束

- 规划阶段保存规划过程文稿，不生成待发布的知识正文
- 规划通过独立核查后无需用户确认，直接登记全部写作步骤并自动生成
- **穷举原则**：仓、业务域、外部系统、业务功能模块都必须穷举，不可因为"较小"或"次要"而省略
- **精度原则**：扫描源码时必须深入到类/文件级别，不可仅看目录名就推断模块结构。
