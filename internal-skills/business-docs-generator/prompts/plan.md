# 规划阶段提示词

## 一、目标

在用户本次范围内，**穷举**上下文 repositories 中的所有来源仓、业务域、外部系统和业务功能，生成完整、详尽的文档规划。工具映射与路径约定见 [平台执行约定](../references/platform-execution.md)。

## 二、执行步骤

1. **识别仓列表（穷举）**：
   - 用 knowledge_structure 列仓，逐仓 component_source list 并继续分页；排除 `.cac`、`.codegraph`、`.idea`、`.opencode`、`domain-docs`、`business-docs-generator`、`node_modules` 等非代码目录
   - **不可遗漏任何代码仓**。即使某仓只有部分目录与本项目相关（如仅一个子模块），也必须列出
   - 对每个仓读取构建文件（`pom.xml` / `package.json` / `CMakeLists.txt` / `app_define.json` 等），识别技术栈

2. **分配独立调查，再深入源码**：
   主会话先依据仓列表、构建文件和目录入口划分调查单元，不先把全部业务实现读入自己的上下文。按仓与业务入口划分，再按完整业务场景细分；同一场景的关键调用链保持完整，不按任意行数截断。每个单元说明仓编号、源码范围、具体待回答问题、依赖单元和对应产物。调查步骤通过 knowledge_work schedule 登记 readonly=true，互不依赖的单元可用 run 的 concurrency=1～4 并行执行，本方法默认 3。可执行的参数与结果示例见 [独立调查](../references/platform-execution.md#独立调查)。

   以下深入读取由对应独立调查单元完成：
   - 读取构建文件识别技术栈（语言、框架、构建工具）
   - **深入源码目录**，不可仅看顶层目录名就推断模块结构。必须进入各源码子目录，识别实际的包/模块划分
   - 对于 Java 仓：扫描 `src/main/java/` 下的包结构，识别 Controller、Service、Domain 等分层
   - 对于 C++ 仓：扫描 `src/` 下的模块目录，识别各功能模块
   - 对于前端仓：扫描 `src/containers/`、`src/components/`、`src/store/` 等，识别业务容器和组件
   - 识别各仓的核心类名和关键文件，作为后续源码范围的精度基础

   instructions 只传本单元范围、方法入口、证据索引和问题。单元启动时按 id 回读必要结果并重新打开原始源码，knowledge_work_result 的 summary 只写主要发现，data 保存关键路径/行范围、跨仓调用与待核实问题，document_ids=[]。结果由平台持久保存，只读单元不调用 save_document。主会话按编号读取必要结果，维护短摘要与编号引用；发现尚未调查的范围时继续登记具体单元，不集中展开全部源码。

3. **识别跨仓关系（穷举所有调用链）**：
   - 需要构建依赖候选时，以 repository_id 和 include_dependencies=true 调用 knowledge_structure；该操作显式扫描配置的来源仓，候选仍需源码核实
   - 通过 pom.xml 依赖、IDL 文件、REST Controller 路径、import/inlude 语句，识别**所有**仓间调用关系
   - **穷举所有外部系统**，包括但不限于：
     - 数据库（内存数据库、关系型数据库、SQLite 等）
     - 文件存储（NFS、HDFS、HOfS 等）
     - 消息/事件中间件（CORBA Event Service、Kafka 等）
     - 安全框架（WSF、认证服务、权限管理）
     - 命名服务（CORBA Naming Service 等）
     - 其他平台服务（拓扑服务、网管服务、配置管理等）
     - 网元设备（通过各类协议对接）
   - **不可仅列出最明显的外部系统。** 必须追踪每个仓的 import/include/依赖配置，找出所有外部交互点
   - 用 PlantUML 画出完整的跨仓关系图，包括所有仓和所有外部系统

4. **识别业务域（穷举所有跨仓业务功能）**：
   - 从前端容器的业务功能出发，追踪到 BFF 层，再到核心服务，识别所有跨仓业务链路
   - **穷举所有业务域，不可遗漏。** 常见的业务域包括：任务管理、结果查询、数据导入导出、实时分析、模板管理、网元管理、系统监控、安全/匿名化等
   - 对于每个业务域，列出：
     - 涉及的仓（完整列表）
     - 核心链路（一句话描述端到端流程）
   - **业务域判断标准**：如果一组功能有独立的业务意图、跨多个仓、有完整的数据流，则应作为独立业务域。不可因为功能"较小"就省略

5. **规划文档列表**：
   - 按文档类型列出所有待生成文档，并另行标明真实执行依赖；不能把阅读导航的顺序变成整包串行执行
   - 每个文档标注类型（domain / repo）、对应模板
   - **领域文档**：标注需要通读的仓列表及各仓的业务源码范围
     - 源码范围**必须精确到具体类名/文件名**，不可仅写目录名。格式示例：`FarsFrontendService(TraceTaskCreateDelegateImpl+app.service.tracetask.TaskCreateService+domain.task.create)`
     - 范围必须覆盖：接口层（Controller/Delegate）、业务逻辑层（Service/Domain）、数据模型、状态管理代码、配置文件
   - **仓级文档**：标注该仓内需要覆盖的**业务功能**及每个功能涉及的源码范围
     - 源码范围**必须精确到具体类名/文件名**，格式示例：`app/service/tracetask/TaskCreateService.java, api/impl/TraceTaskCreateDelegateImpl.java, domain/task/create/`
     - 一个业务功能可能跨多个源码目录，须列出所有相关目录和关键文件
   - **模块划分维度：按业务功能划分，不按代码目录划分**。模块文档名使用业务功能名（如 `trace-task-create`），不使用代码目录名（如 `domain-task-create`）。一个业务功能可能跨多个代码目录，合并为一个模块文档。
   - **穷举所有业务功能模块**，不可遗漏。每个仓的业务功能模块应覆盖该仓的所有核心业务逻辑，不可只列主要功能而省略次要功能
   - 在执行关联中保留相关调查单元编号，写作步骤据此定位原始来源；每篇开始时回读对应源码和资料，不把协调器摘要当作本篇已经完成的阅读
   - 最终导航同步单独安排：每份导航依赖其覆盖的全部文稿写作及最后修订步骤，也依赖导航自身初次生成步骤；声明全部实际改动编号。相关文稿尚未完成时不运行最终导航核查，不同仓导航可独立执行

6. **保存并登记完整规划**：按 `prompts/plan-template.md` 保存完整 Markdown，使用 knowledge_work save_document，id=current-plan。填写每篇的稳定 document_id、实际 target_id、仓内 path 与写作步骤编号。随后 knowledge_work action=plan，work_document_id=current-plan，document_ids 填全部清单编号。过程文稿是原 current-plan.md 的平台对应，不进入知识发布；结构化 plan 让宿主核对漏排产物。

7. **独立核查**：由主会话安排 readonly=true 的独立步骤，knowledge_work read_plan 读取全部清单与排除说明分页，再读本提示词、规划模板和 current-plan，回查各仓业务入口。核对结构清单与正文一一对应、仓/业务域/外部系统/功能及模板类型无遗漏。通过 knowledge_work_result 返回 review: {pass, feedback}，无知识文稿时 document_ids=[]。主会话修正正文与 plan 后再次独立核查；通过后登记带评审的写作步骤。后续发现新功能先补正文和 plan，确实不适用的旧条目逐项保留 exclusions 原因，不能静默删除。

## 三、规划输出格式

使用 `prompts/plan-template.md` 模板生成规划文件。

## 四、自检清单

规划完成后，逐项自检，不通过则补充后再次自检：

- [ ] **仓完整性**：是否遗漏了 repositories 中的任何来源仓？即使某仓只有部分目录相关，是否也已列出并遵守用户范围？
- [ ] **业务域完整性**：业务域是否覆盖了所有跨仓业务功能？是否存在被遗漏的业务链路？（检查方式：从前端容器的每个业务页面出发，是否能找到对应的业务域文档？）
- [ ] **外部系统完整性**：外部系统是否穷举？是否遗漏了数据库、存储、消息中间件、安全框架、命名服务等？
- [ ] **源码范围精度**：每个文档的预估源码范围是否精确到具体类名/文件名？是否存在仅写目录名的情况？
- [ ] **模块命名**：所有模块文档名是否使用业务功能名，而非代码目录名？是否包含 `domain-`、`interface-`、`common-`、`proxy-` 等技术分层前缀？
- [ ] **模块覆盖度**：每个仓的业务功能模块是否覆盖了该仓的所有核心业务逻辑？是否有被遗漏的功能模块？
- [ ] **模板符合性**：规划文件是否严格符合 `prompts/plan-template.md` 的章节结构？无增减章节、无改变结构？
- [ ] **输出覆盖**：是否列全范围内基础文档、各业务域、真实交互仓对、外部系统与各仓业务功能？经验文稿仅在有真实案例时规划。
- [ ] **执行对应**：每篇是否有唯一稳定文稿编号、目标编号、仓内路径和写作步骤编号？是否将逻辑仓前缀误当作仓内路径？

## 五、约束

- 规划阶段不生成任何文档正文
- 规划通过独立核查后无需用户确认，直接登记全部写作步骤并自动生成
- **穷举原则**：仓、业务域、外部系统、业务功能模块都必须穷举，不可因为"较小"或"次要"而省略
- **精度原则**：扫描源码时必须深入到类/文件级别，不可仅看目录名就推断模块结构。
