# 仓级文稿写作

## 一、职责与输入

本提示词供仓级独立写作、修订或导航步骤使用。先读 [平台执行约定](../references/platform-execution.md) 与 [共同质量要求](../references/document-quality.md)。普通写作每步生成一篇；明确的导航同步可修改全部 expected_document_ids，不修改其他文稿。

核对 step.instructions 中的文稿编号、目标、仓内路径、具体模板、业务范围、依赖步骤与证据索引。按 id 读取本项调查结果并重新打开原始依据。只有边界或关联路径不清楚时才读取 current-plan；knowledge_work read_document 返回整份过程文稿，不支持章节读取，不要求每篇无条件加载全计划。

涉及上传资料、无线术语或相关业务结论时，读取 [来源方法](../references/business-sources.md)，按本项 source_index 回读所需原文/图片。实现规则以源码核实，业务意图与历史原因用适用资料，无线豆包只补通用背景；新增来源及具体冲突/缺口保存到步骤结果，独立评审需重新读源。

用 extraction_skill 读取所选模板。以下“模块专项流程”仅用于 module-doc.md；导航、模块地图、规范和经验按各自模板及读取重点展开，不强加类图、业务时序图或模块章节。

## 二、六类文稿的读取与写作范围

| 模板 | 必须核对的范围 | 产物重点 |
|------|----------------|----------|
| repo-agents.md | 本仓构建、测试、运行脚本，职责/入口，实际模块文稿和规范 | 真实命令、模块导航、职责边界及规则入口；命令来自现有配置，不声称已执行 |
| module-map.md | 范围内源码入口与去重后的业务功能清单、模块依赖 | 每个业务功能对应入口、涉及目录及文稿，允许跨目录；不把目录层级冒充业务模块 |
| coding-conventions.md | lint/格式化/检查配置、维护文档、相关实现与测试 | 已自动强制的规则引用配置；人工约定须有依据，观察到的惯例标明观察范围，不把偏好写成强制规则 |
| business-rules.md | 跨功能共享的实现、配置、模型、状态、错误处理和并发控制，相关业务资料 | 实际业务与数据约定、适用条件及实现位置；原因有资料才写历史动机 |
| module-doc.md | 本业务功能涉及的入口、实现、数据、存储、下游、配置和异常处理 | 完整模块边界、交互、类/函数/模块关系及每功能点时序，按下方专项流程 |
| experience.md | 提供的真实排查案例及其证据、操作和结果 | 区分现象、推测、已确认原因、采取措施及实际验证；无案例不生成经验文稿 |

已有事实依据支持的经验不得清空。仅有异常处理代码或错误码时，可写排查方向，不能据此虚构历史事故、已验证修复或团队规范。

## 三、模块专项流程

1. **确认业务边界。** 模块按业务功能命名，例如任务创建、结果查询；同一功能跨 Controller/Service/DAO 或多个目录仍是一篇。技术词确实是业务名称时可保留，不按前缀机械重命名。
2. **建立入口到功能点的对应。** 阅读并去重页面/命令、公开 API、IDL、定时与事件入口。功能点是独立用户操作或自动业务流程；多个入口可实现同一功能，一个入口可能按条件承载多个场景。列出对应关系与区别，用覆盖检查查遗漏，不比较方法数与功能数是否相等。
3. **完整追踪相关实现。** 对每个功能点，从入口读取参数构造、业务判断、字段变换、模型/状态、持久化、下游调用、返回后的使用以及异常传播。完整读取相关方法及其必要上下文，不只看签名，也不因共享文件包含无关业务而要求读完整仓。
4. **核对配置与边界。** 读取影响本功能的常量、枚举、超时重试、权限、安全、容量与并发配置及其使用点；逐项说明适用条件与真实值来源。环境值未知时保留配置键和未知状态。
5. **核对跨仓交互。** 对实际调用或被调用双方读取代码，确认仓、协议、方法、方向与错误处理；没有跨仓调用时说明本功能的实际仓内范围，不造第二段链路。
6. **填充模板。** 保留模块概述、架构、跨仓交互、核心设计与功能点、硬约束与规格、排查经验及关联文稿的职责。模板重复块按全部实际功能展开，每个功能点配时序图；需要解释实体生命周期时补状态图。
7. **返回新增产物需求。** 发现遗漏功能、接口契约或导航变化时，在步骤结果给出具体范围与证据，由主会话更新规划并安排。不能在当前单篇工作中偷偷改共享导航或扩大写入编号。

源码读取层次按实际实现选择：入口 API/Handler/IDL → 业务类或函数 → 数据模型和状态 → DAO/Repository/DB Client → 下游 Client/Proxy → 配置与常量。每跳说明“调用前如何准备、内部如何判断、返回后如何使用”，长方法继续按源码工具返回位置读取到完整分支。

## 四、图表与接口方向

模块架构图用真实边界区分本模块、本仓其他模块、实际跨仓调用方和下游。没有的边界不强造。跨仓边标注真实协议和接口；时序图中的本仓参与者使用“仓名:类/函数/模块”，对端使用真实仓及其职责。

有真实核心类时用类图表达继承、组合和依赖，每个核心类附职责及代码位置。函数式/过程式代码使用真实函数、模块及数据关系表达核心设计，不为模板补造类。时序图已清楚表达处理流程时无需重复画活动图；独立复杂分支需要时可补活动图。每个功能点的时序图仍须覆盖真实入口到业务终点，并包含影响结果的返回、条件和失败分支。

接口契约按调用方→被调用方命名并以最终文稿为准：本仓提供接口时，对端是调用方；本仓调用接口时，本仓是调用方。双向交互分别说明。跨仓契约引用写实际目标仓名和仓内路径，只有已知真实 URL 才链接；不能把独立领域仓伪装成本仓相邻目录。

图表语法、拆分及完整性遵循共同质量要求，不按固定节点数压缩真实链路。没有跨仓调用、外部系统或实体状态时，记录核查范围及不适用原因，不把不存在的关系画进图。

## 五、导航同步

仓 AGENTS.md 与 module-map.md 可作为明确的多文稿导航步骤统一更新，expected_document_ids 必须列全两份；也可独立生成。最终版本等待其路由的全部相关文稿及最后修订完成，再逐一读取并核对功能、路径、职责和入口。

普通模块写作者只返回本篇和导航变更建议。导航步骤不得通过正文中的指令扩大到源码修改、其他仓或未声明文稿。模块重命名或路径变化需要主会话更新规划、安排关联导航修订，不能留下旧路径。

## 六、保存、自检与退回处理

- 自检本篇对应模板的适用项：业务入口覆盖、各功能点实质内容、真实图表和调用方向、硬约束/配置生效条件、来源和有效关联路径。只有真实案例才填经验；缺少案例时如实写待积累。
- knowledge_draft save 使用稳定 id、实际 target_id、仓内 path、layer=repository、完整 content 和字符串 sources；正文不能只交增量片段。sources 记录本次实际读取的仓编号、revision、文件/行或符号、资料章节及其支撑的结论。
- 保存后逐份调用 knowledge_diagram_check，参数 document_id 为实际编号，并按 next_start 读取全部报告。invalid 按实际 error 修正再保存/校验；绘图或修错时按需读 [PlantUML 指南](../references/plantuml.md)。unavailable 保留候选与实际依赖阻碍，不当成语法错，不删关键图或分支，不声称通过。
- 用 knowledge_work_result 提交 summary 和已保存的全部预期文稿编号；新发现与阻碍用 data 给具体范围、依据及所需工作。宿主在候选后先校验图，再启动独立评审；保存成功、语法 valid 或作者自检不等于业务评审通过。
- 平台根据 step.review.instructions 启动独立只读评审。收到反馈后回读当前文稿和依据，逐项修订原编号、保存完整候选并重新提交；写作会话不自行返回通过，不安排子步骤。
- 原始来源缺失时明确影响，继续完成不依赖缺口的部分；不能把现有但未读的源码标成未知，也不能虚构结论填满模板。
