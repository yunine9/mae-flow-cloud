# 仓级文档生成提示词

## 一、目标

根据规划，读取单个仓的源码，按模板生成仓级文档。

## 二、执行步骤

本提示词供独立写作步骤使用，只生成 step.instructions 指定的本篇文稿。先读 [平台执行约定](../references/platform-execution.md)，用 knowledge_work read_document 回读 current-plan 对应条目。包内文件通过 extraction_skill 读取，文稿通过 knowledge_draft 保存；独立评审由本步骤的 review 配置安排。

模板中的关联路径与方向是待核实示例。接口契约按实际调用方→被调用方组织：本仓提供接口时，对端是调用方；本仓调用接口时，本仓是调用方。以已规划或已保存的契约文件为准填写路径，不机械复制模块模板示例中的仓对顺序。同仓章节引用应实际存在，跨仓引用标明仓名和仓内路径。

1. **读取模板**：从 `templates/repo/` 读取对应模板
2. **读取源码（深度读取，不可浅尝辄止）**：
   根据文档类型和规划中标注的业务功能，**完整读取该业务功能涉及的所有源码文件**，不可只读入口文件或接口定义就猜测内部逻辑。读取层次：
   - **入口层**：Controller / API / Handler / IDL — 找到所有对外暴露的接口和入口方法
   - **业务逻辑层**：Service / Delegate / Manager / Processor — 逐方法读取实现，理解业务判断、条件分支、数据变换
   - **数据模型层**：Entity / DTO / Model / VO — 理解数据结构和字段含义
   - **持久层**：DAO / Repository / Mapper / DB Client — 理解数据存储和查询逻辑
   - **调用层**：Proxy / Client / Feign / RestTemplate — 理解跨仓调用的触发点和参数构造
   - **配置层**：YAML / properties / XML / JSON — 理解超时、重试、限流等配置
   - **常量/枚举层**：Constants / Enums — 理解状态值、错误码、路径常量
   - **使用 component_source search/read 沿真实方法名追踪调用链**，确保从入口到最终执行的每一跳都有源码依据；分别核对调用前的参数构造、内部实现和返回后的使用
   - **对每个源码文件逐方法阅读**，不可跳读或只读方法签名
   - 返回“后续从…读取”或截断提示时继续读取相关范围，默认首段不是全文

3. **分析内容**：
   - **按业务功能维度识别模块**：模块按业务功能划分（如"追踪任务创建""结果查询"），不按代码目录划分（如"domain""interface""common"）。一个业务功能可能跨多个代码目录。
   - **功能点穷举（关键步骤，不可遗漏）**：在读取源码后，逐一列出该业务功能包含的所有功能点。功能点 = 用户可感知的操作或系统自动执行的业务流程。检查方法：
     - 遍历入口层的每个公开方法 → 每个对应一个功能点
     - 遍历 Controller 的每个 endpoint（@RequestMapping / @GetMapping / @PostMapping 等）→ 每个对应一个功能点
     - 遍历 IDL 接口的每个方法 → 每个对应一个功能点
     - 遍历定时任务（@Scheduled / cron / Timer）→ 每个对应一个功能点
     - 遍历事件监听（@EventListener / 消息消费）→ 每个对应一个功能点
     - 确认无遗漏：将功能点列表与入口方法的数量对比，数量不匹配则回查源码
   - 识别模块边界和职责
   - 识别类间关系和方法调用链
   - **仓内调用链路深度追踪**：从入口类开始，逐方法追踪本仓内模块间的调用路径，记录每跳的方法签名、参数、返回值、关键判断逻辑。不可只列方法名，必须讲清楚：
     - 调用前准备：为什么调、参数如何构造
     - 内部处理：关键判断、条件分支、异常处理
     - 返回后使用：返回值如何被后续流程使用
   - 识别跨仓调用：搜索对其他仓的接口调用（REST Client / CORBA / gRPC / RPC 等），记录对端仓名、接口名、协议
   - 识别对外接口和下游依赖，区分本仓内依赖和跨仓依赖
   - 识别 lint/格式化配置
   - 识别跨模块业务约定
4. **填充模板**：
   - 将 `<占位符>` 替换为实际内容
   - 删除 `<!-- 指引说明 -->` 并替换为实际内容
   - 生成 PlantUML 图表（架构图、时序图、类图、状态图等），所有图表使用 `@startuml` / `@enduml` 语法，并包裹在 ` ```plantuml ` 代码块中
   - **PlantUML 语法规范（严格遵守，否则渲染异常）**：
     - 组件/类名含特殊字符（`::`、`<>`、`()`、`/`）时，必须用双引号包裹并给 `as` 别名，如 `component "TraceTask\n(任务管理界面)" as FE_MGR`
     - **组件标签内不可直接换行**：`component "..."` 引号内的标签文本不能包含真实换行符，多行内容必须用 `\n` 表示，如 `component "SONWebsite\n(React/Redux)\n容器化部署" as FE`
     - 类名中的泛型 `<T>` 不可直接写，须改为 `class "FarsDBTable<T>" as FDT` 或去掉泛型标记
     - 箭头标签中使用 `\n` 换行时，确保整个标签在引号内或 `\n` 前后无特殊字符干扰
     - 架构图/组件图节点数控制在 40 以内，超过时拆分为多张图或精简非核心节点
     - 时序图参与者控制在 8 个以内，超过时合并次要参与者
     - 每个 `@startuml` 必须有配对的 `@enduml`，且外层有 ` ```plantuml ` 代码块
5. **命名自检**（模块文档专用）：
   - [ ] 模块文档名是否使用业务功能名称（如 `trace-task-create`），而非代码目录名称（如 `domain-task-create`）？
   - [ ] 文档名是否包含技术分层前缀（如 `domain-`、`interface-`、`common-`）？如有，改为业务功能名。
   - [ ] 一个业务功能是否被拆分到多个文档中？如是，合并为一个文档。
6. **保存候选并交付独立评审**：
   - knowledge_draft save 保存完整候选，沿用规划中的稳定 document_id、target_id 和仓内 path；sources 记录实际源码文件行范围、资料章节与对应结论
   - knowledge_work_result 返回本步骤结论和本篇文稿编号；候选保存不等于评审通过
   - 宿主按本步骤 review.instructions 启动只读评审，读取 `prompts/verify-doc.md`、本篇模板、最新正文与原始依据
   - 收到退回反馈时，逐项补读依据并修改原编号文稿，再提交结果接受重新评审；写作会话不自行声明评审通过
7. **保持本篇范围**：后续文稿和导航回填由主会话安排。本步骤只返回自己保存的真实文稿。

## 三、各文档类型的源码读取重点

### 1. repo-agents.md（仓 AGENTS.md）
- 读取构建配置获取技术栈
- 读取构建/测试/运行脚本获取命令
- 扫描源码目录获取模块清单
- 识别对外接口和下游依赖

### 2. module-map.md（模块路由表）
- 扫描所有源码目录，识别模块边界
- 识别入口类/入口文件
- 识别模块间依赖关系

### 3. coding-conventions.md（编程规范）
- 读取 lint 配置文件（.eslintrc / checkstyle / clang-format 等）
- 读取格式化配置
- 读取 pom.xml / package.json 中的插件配置
- 只记录 lint 未强制的规则，已强制的引用配置文件

### 4. business-rules.md（业务规范）
- 识别跨模块共享的业务逻辑
- 读取配置文件中的业务参数
- 识别数据格式约定
- 识别错误处理和并发约定

### 5. module-doc.md（模块主文档）
- 读取该模块所有源码文件
- 识别核心类及其职责（一句话）
- 识别类间关系（继承/组合/依赖），画类图（PlantUML class diagram）
- 识别功能点和处理流程
- **仓内调用链路追踪**：从模块入口（Controller / Service / Handler）开始，追踪本仓内模块间的调用路径，用流程图（PlantUML activity diagram）展示，节点标注"类名.方法名"
- **跨仓调用识别**：搜索以下跨仓调用模式：
  - REST 客户端调用（RestTemplate / Feign / HttpClient / fetch / axios 等）
  - RPC / CORBA / gRPC 调用
  - 消息队列发送/订阅
  - 分布式文件系统接口调用
  - 记录每处跨仓调用的：对端仓名、接口/方法名、协议、调用方向（提供/调用）
- 识别对外接口和下游依赖，**区分本仓内依赖和跨仓依赖**
- 识别硬约束（性能/安全/兼容性）和规格（数据格式/业务规则/配置项）
- 排查经验初始为空，不要编造

### 6. experience.md（排查经验）
- 仅按本次提供的真实排查案例记录现象、证据、过程和解决结果
- 代码异常处理及错误码可支持排查方向，不能据此虚构已经发生的事故或已经验证的修复
- 无真实案例时保持模块文档的排查经验为空，不生成虚构的经验文稿

## 四、模块文档生成要点

### 1. 模块架构图
- 展示模块内部核心组件
- **用 package 区分"跨仓调用方""本仓内组件""跨仓下游"三个边界**
- 跨仓调用方和跨仓下游用虚线箭头（`..>`）连接，标注协议/接口名
- 本仓其他模块单独 package，与本模块内部区分

### 2. 跨仓交互
- 列出本模块与外部仓的所有交互点
- 标注调用方向（提供/调用）、对端仓名、接口/方法、协议
- 指向 `domain-docs/interfaces/` 下的接口契约文档

### 4. 类设计
- 用 PlantUML class diagram 展示核心类之间的关系
- 每个核心类用一句话说明其职责，标注文件位置
- 不需要列出所有属性和方法，聚焦类间关系和核心职责

### 4. 功能点时序图与状态图
- 每个功能点一个时序图
- **参与者以仓为单位命名：本仓参与者用"本仓:类名"，跨仓参与者用"仓名:模块名"**
- **跨仓调用箭头上标注协议和接口名**（如 `CORBA/importFile`）
- 仓内调用用实线箭头，跨仓调用在箭头上标注协议
- 展示从入口到下游的完整调用链，包含仓内和跨仓两段
- 标注内部处理步骤
- **按需补充状态图**：当功能涉及实体状态流转时，用 PlantUML state diagram 展示状态转换，目的是讲清楚业务逻辑
- 不是每个功能都需要状态图，仅在状态流转是业务核心时才画

### 5. 对外提供/向下依赖（简写）
- 对外提供和向下依赖分别在"跨仓交互"节中以表格形式记录
- 方法签名 + 一句话用途 + 协议 + 对端仓 + 契约文档路径

## 五、约束

- 每次只生成一个文档
- 严格按模板结构填充
- PlantUML 图表必须语法正确，使用 `@startuml` / `@enduml` 包裹，并放在 ` ```plantuml ` 代码块中
- **PlantUML 语法注意**：组件/类名含特殊字符时用双引号包裹并给 `as` 别名；泛型 `<T>` 不可直接写类名中；箭头标签 `\n` 换行时确保在引号内；架构图节点数 ≤40；时序图参与者 ≤8
- 代码引用格式：`<文件路径>:<行号>`
- 模块文档不设行数上限，但要确保每节内容充实不空洞

## 六、模块文档自检清单

生成模块文档后，逐项检查：

### 1. 命名规范（关键校验项）
- [ ] 模块文档名是否使用**业务功能名称**（如 `trace-task-create`），而非代码目录名称（如 `domain-task-create`）？
- [ ] 文档名是否包含技术分层前缀（如 `domain-`、`interface-`、`common-`）？如有，改为业务功能名。
- [ ] 一个业务功能是否被拆分到多个文档中？如是，合并为一个文档。

### 2. 跨仓交互完整性
- [ ] "跨仓交互"表是否列出了本模块所有的跨仓调用和被调用
- [ ] 每条跨仓交互是否标注了协议（REST / CORBA / gRPC / HTTP 等）
- [ ] 跨仓交互是否指向 `domain-docs/interfaces/` 下的契约文档
- [ ] 模块架构图中跨仓边界是否用虚线箭头（`..>`）标注
- [ ] 搜索代码中是否存在未被记录的跨仓调用（搜索 RestTemplate / Feign / CORBA / fetch / axios / HttpClient 等）

### 3. 类设计
- [ ] 是否有 PlantUML class diagram 展示核心类间关系
- [ ] 每个核心类是否有一句话职责说明和文件位置

### 4. 功能点图表质量
- [ ] **每个功能点是否都有时序图？** 不可省略
- [ ] 参与者是否以仓为单位命名（本仓:类名 / 仓名:模块名）
- [ ] 跨仓调用箭头是否标注了协议和接口名
- [ ] 时序图是否同时包含仓内调用和跨仓调用两段
- [ ] 涉及状态流转的功能是否按需补充了状态图
- [ ] 图表方法名和参数是否来自真实代码追踪，未编造

### 4.1 PlantUML 语法正确性（关键校验项，逐图检查）
- [ ] **组件名/类名特殊字符**：组件 `as` 别名后的显示名中是否含 `::`、`<>`、`()` 等特殊字符？如有，须用双引号包裹并给 `as` 别名
- [ ] **泛型尖括号**：类图中的泛型 `<T>` 是否直接写在类名中？须改为 `class "FarsDBTable<T>" as FDT` 或去掉泛型
- [ ] **箭头标签换行**：箭头标签是否使用 `\n` 换行？确保整个标签在引号内或 `\n` 前后无特殊字符干扰
- [ ] **引号使用**：含空格、括号、斜杠的标签是否用双引号包裹？
- [ ] **图的大小**：单个 PlantUML 图的节点数是否超过 40？超过时拆分为多张图或精简
- [ ] **时序图参与者数量**：时序图参与者是否超过 8 个？超过时合并次要参与者
- [ ] **`@startuml`/`@enduml` 配对**：每个 `@startuml` 是否都有配对的 `@enduml`？是否包裹在 ` ```plantuml ` 代码块中？
- [ ] **`participant` 声明**：时序图中每个参与者是否都有 `participant` 声明和 `as` 别名？

### 5. 排查经验
- [ ] 排查经验是否初始为空（未编造内容）

### 6. 自检不通过信号
- **模块名使用代码目录名而非业务功能名 → 必须重命名**
- **功能点没有时序图 → 必须补画**
- **PlantUML 图表含特殊字符未用引号包裹、组件标签内直接换行未用 `\n`、泛型 `<T>` 直接写类名中、节点数超过 40 → 必须修复语法**
- 类设计列了大量属性/方法表 → 未精简为类图+核心职责
- 每个功能点都画了状态图 → 状态图应按需，不是每个都需要
- 硬约束和规格分成了两个章节 → 应合并为"硬约束与规格"
- 排查经验有编造内容 → 应初始为空
- 时序图参与者仍是 Caller/Entry/Svc/Dep 等通用名 → 未按仓维度命名
- 模块架构图未区分本仓内/跨仓边界 → package 划分不正确
- 跨仓调用只写了接口名未标注协议 → 追踪深度不够
