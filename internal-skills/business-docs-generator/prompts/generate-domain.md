# 领域文档生成提示词

## 一、核心原则

**领域文档必须通读多个仓的业务逻辑源码，而非仅读接口层。**

领域文档描述的是跨仓业务链路，只有深入每个仓的业务逻辑代码，才能准确描绘：
- 数据在仓间如何流转和变换
- 每个仓在链路中承担什么业务职责
- 业务实体的状态在哪个仓、哪段代码中发生转换
- 异常在哪个环节产生、如何传播

## 二、执行步骤

本提示词供独立写作步骤使用，只生成 step.instructions 指定的本篇文稿。先读 [平台执行约定](../references/platform-execution.md)，用 knowledge_work read_document 回读 current-plan 中对应条目。生成提示词和模板通过 extraction_skill 读取，文稿通过 knowledge_draft 保存；独立评审由本步骤的 review 配置安排。

先确认具体模板，再使用对应的源码读取重点。下面的域边界、场景枚举、逐场景时序图和全套存储/清理/DFX检查适用于 domain.md；glossary、architecture、接口、外部系统和导航文稿按各自模板展开，不额外增加业务域章节。root-agents 与 domain-agents 回读完整规划和已保存文稿，填写真实仓路由、领域关键词和索引；后续文稿由主会话持续回填。

导航文字也按实际产物校正。原导航模板提到“规则归属表”，但业务域模板没有同名章节；生成时改为实际承载职责与规则的“域边界”“端到端链路”及具体场景位置。逐项确认引用的章节和文件确实存在；不为保留模板示例措辞，指引读者查找不存在的表或章节。跨仓引用明确仓名与仓内路径。

1. **读取模板**：从 `templates/domain/` 读取对应模板

2. **确定源码范围**：根据规划中标注的涉及仓列表，确定需要通读的源码范围

3. **域边界校验（关键步骤）**：
   在通读源码之前，先明确该域的业务边界：
   - **什么属于本域**：该域的核心业务目标是什么？哪些功能是直接服务于这个目标的？
   - **什么不属于本域**：代码目录上相邻但业务目标不同的功能，必须排除并记录原因
   - **判断依据**：以用户操作场景和业务价值为依据，而非代码目录结构。例如"数据导入"和"模板创建"可能在同一目录下，但前者是"文件→数据"，后者是"模板→数据"，业务目标不同
   - 将边界判定结果写入文档的"域边界"章节

4. **逐仓通读业务源码**（按实际仓编号分别读取并继续分页）：

   对每个涉及的仓，按以下层次从上到下通读：

   | 层次 | 读什么 | 为什么读 |
   |------|--------|---------|
   | **接口层** | IDL 文件、REST Controller、API 定义、RPC 接口定义 | 识别跨仓调用点、协议、参数 |
   | **Service/业务逻辑层** | Delegate 实现、Service 类、Manager 类、Processor 类 | 理解每个仓在链路中做了什么业务处理 |
   | **数据模型层** | Entity、DTO、Model、数据结构定义 | 理解数据在仓间如何流转和变换 |
   | **状态管理层** | 状态枚举、状态机、状态转换逻辑 | 理解业务实体的状态流转 |
   | **配置层** | 配置文件、YAML、properties、XML 配置 | 理解超时、重试、路由等策略 |
   | **下游调用层** | Proxy、Client、Feign、RPC Client 调用代码 | 理解仓间调用的实际触发点 |
   | **文件传输层** | 分布式文件传输、共享存储读写、文件上传/下载代码 | 理解文件在仓间如何物理传输（不是调用参数，是独立传输链路） |
   | **外部系统调用层** | 外部服务客户端（任务中心、消息队列、对象存储等）、第三方库调用 | 识别对外部系统的依赖 |
   | **存储与容量层** | 常量类中的路径定义、配置文件中的路径/容量/大小限制、临时目录路径 | 理解数据在各阶段存储在什么位置、容量上限是多少 |
   | **定时清理层** | 定时任务注解（@Scheduled/cron/Timer）、清理方法、TTL 常量、缓存过期配置 | 理解临时文件和内存对象的清理策略（调度周期、TTL、清理范围） |
   | **DFX 层** | 流量控制（并发限制/队列/流控配置）、超时/重试常量、安全校验（权限/加密/路径校验）、审计日志、监控/健康检查代码 | 理解系统的可靠性、安全性、可观测性设计 |

5. **主链路追踪**：从链路入口开始，逐方法追踪到下游仓，直到链路终点：
   - 仓A入口方法 → 仓A内部处理 → 仓A调用仓B的代码 → 仓B入口方法 → 仓B内部处理 → ...
   - 使用 component_source search/read，沿真实方法名追踪调用链；逐跳核对参数构造、内部处理与返回后的使用
   - 对每个涉及仓分别读取，超过单次返回范围时继续分页；需要额外独立研究时向主会话提交具体范围和问题

6. **场景枚举（关键步骤）**：
   在分析链路之前，先枚举该域的所有**独立用户场景**，而非只看一个主流程：
   - 同一域内可能有多个场景（如"单条操作"和"批量操作"是不同场景，不是同一场景的分支）
   - 判断标准：用户操作不同、UI 流程不同、或后端处理链路不同 → 独立场景
   - 仅参数不同但链路完全相同 → 同一场景的决策分支，不单独拆分
   - 将枚举结果作为"端到端链路"章节（即合并后的四、端到端链路）的场景列表

7. **外部系统识别（关键步骤）**：
   在通读源码时，**递归发现**外部系统依赖，不局限于规划阶段已识别的外部系统：
   - 检查代码中引用的外部服务调用（任务中心、消息队列、文件传输服务等）
   - 检查 import 语句中来自非本仓的第三方库（非项目内部的包）
   - 检查配置文件中外部服务地址、端口、连接参数
   - 将新发现的外部系统补充到架构图

8. **分析内容**：
   - 识别跨仓调用链路的完整路径
   - 识别每跳的协议和技术栈
   - 识别业务实体在各仓间的数据变换
   - 识别状态流转的完整生命周期（哪个仓触发、哪个仓执行、哪个仓确认）
   - 识别接口参数、返回值、约束
   - **对比同一域内不同场景的机制差异**
   - **识别存储路径和容量限制**：数据在各链路阶段存储在什么位置（物理路径/桶名），各阶段的容量上限是多少
   - **识别定时清理机制**：临时文件和内存对象的清理策略（调度方式、周期、TTL、清理范围、即时清理 vs 定时清理）
   - **识别 DFX 设计**：流量控制（并发限制/排队/拒绝）、超时与重试策略、安全机制（权限/加密/路径校验/审计日志）、可观测性（日志/监控/健康检查）

9. **填充模板**：
   - 将 `<占位符>` 替换为实际内容
   - 删除 `<!-- 指引说明 -->` 并替换为实际内容
   - 生成 PlantUML 图表（架构图、时序图、状态图等），所有图表使用 `@startuml` / `@enduml` 语法，并包裹在 ` ```plantuml ` 代码块中
   - 时序图参与者粒度：以**仓**为单位（如仓A、仓B、仓C、外部系统），不拆分到仓内模块/类级别。仓内类的详细交互属于仓级模块文档的范围
   - 时序图中的跨仓调用要标注真实接口名和参数，仓内处理用自调用简写
   - **PlantUML 语法规范（严格遵守，否则渲染异常）**：
     - 组件/类名含特殊字符（`::`、`<>`、`()`、`/`）时，必须用双引号包裹并给 `as` 别名，如 `component "TraceTask\n(任务管理界面)" as FE_MGR`
     - **组件标签内不可直接换行**：`component "..."` 引号内的标签文本不能包含真实换行符，多行内容必须用 `\n` 表示，如 `component "SONWebsite\n(React/Redux)\n容器化部署" as FE`
     - 类名中的泛型 `<T>` 不可直接写，须改为 `class "FarsDBTable<T>" as FDT` 或去掉泛型标记
     - 箭头标签中使用 `\n` 换行时，确保整个标签在引号内或 `\n` 前后无特殊字符干扰
     - 架构图/组件图节点数控制在 40 以内，超过时拆分为多张图或精简非核心节点
     - 时序图参与者控制在 8 个以内，超过时合并次要参与者
     - 每个 `@startuml` 必须有配对的 `@enduml`，且外层有 ` ```plantuml ` 代码块

10. **生成后自检（关键步骤）**：
    文档写完后，逐项检查以下清单。任何一项无法回答"已覆盖"的，必须补充源码追踪后补写：

    **场景完整性**：
    - [ ] 是否枚举了所有独立用户场景？（检查：同一操作是否有单条/批量两种模式？是否有手动/自动两种触发方式？）
    - [ ] 场景列表表中是否写明了各场景的差异？

    **时序图完整性（关键校验项，不可偷懒）**：
    - [ ] **每个场景是否都有时序图？** 逐个检查"端到端链路"章节下的每个场景，确认每个场景内部都有 `@startuml` 时序图
    - [ ] **是否有场景只写了文字描述但没有时序图？** 时序图是讲清楚端到端调用链路的核心手段，不可省略
    - [ ] 时序图参与者是否以仓为单位命名（如"仓A"、"仓B"、"外部系统"），而非使用通用名？
    - [ ] 跨仓调用箭头是否标注了真实接口名和参数？
    - [ ] 时序图中的方法名和参数是否来自真实代码追踪，未编造？

    **外部系统**：
    - [ ] 架构图是否包含外部系统节点？
    - [ ] 排查清单是否包含外部系统检查项？
    - [ ] 是否有遗漏的外部系统？（检查代码中的外部服务调用、第三方库 import）

    **机制差异对比**：
    - [ ] 如果有多个场景，是否对比了它们的差异？

    **环境存储与容量**：
    - [ ] 是否列出了数据在各链路阶段的存储位置（物理路径/桶名）？
    - [ ] 是否列出了容量限制配置（各阶段的容量上限、文件大小/数量限制）？
    - [ ] 检查：是否遗漏了某个仓的临时目录路径？（搜索常量类、配置文件中的 path/dir/tmp 等关键词）

    **定时清理**：
    - [ ] 是否记录了各仓的临时文件清理策略（调度方式、周期、TTL）？
    - [ ] 是否区分了定时清理和即时清理（事件触发型）？
    - [ ] 是否记录了内存对象/缓存的清理策略（如 LRU、TTL、过期淘汰）？
    - [ ] 检查：搜索 @Scheduled/cron/Timer/expire/LRU/Caffeine/cache 等关键词，是否遗漏了清理机制？

    **DFX 场景**：
    - [ ] 流量控制：是否列出了并发限制、排队策略、流控配置？
    - [ ] 超时与重试：是否列出了各跨仓调用的超时值和重试策略？
    - [ ] 安全机制：是否列出了权限校验、加密、路径校验、审计日志？
    - [ ] 可观测性：是否列出了关键日志、进度查询接口、健康检查/监控机制？
    - [ ] 检查：搜索 timeout/retry/limit/concurrent/encrypt/permission/audit/log/monitor/health 等关键词，是否遗漏了 DFX 机制？

    **自检不通过的常见信号**：
    - **场景没有时序图 → 必须补画，这是硬性要求，不可省略**
    - 架构图没有外部系统节点但代码中有外部服务客户端/文件传输库等调用 → 补充外部系统
    - 只有一个场景但代码中有按数量分支的逻辑（如单条 vs 批量） → 拆分为独立场景
    - 存储位置表只写了最终存储位置但没有中间临时路径 → 重新搜索 temp/tmp/dir/path 常量和配置
    - 清理机制只写了"定时清理"但没有写明调度方式（cron/注解/Timer）和 TTL → 重新读取清理方法实现
    - DFX 章节为空但代码中有并发限制注解/超时常量/权限校验/审计日志 → 重新搜索 limit/timeout/retry/encrypt/audit/permission 等关键词

11. **保存候选并交付独立评审**：
    - 用 knowledge_draft save 保存本篇完整候选，沿用规划中的 document_id、target_id 和仓内 path；sources 记录实际读取的文件行范围、资料章节与对应结论
    - 调用 knowledge_work_result 提交本步骤结论和文稿编号。保存成功表示候选已保留，独立评审通过才表示本篇完成
    - 宿主按本步骤 review.instructions 新开只读会话，读取 `prompts/verify-doc.md`、本篇模板、最新正文和原始源码依据
    - 收到退回反馈时，逐项补读依据并修改原编号文稿，再提交结果接受重新评审；不在写作会话自行声明评审通过

12. **保持本篇范围**：文稿通过后由主会话安排后续文档及导航回填。本步骤只返回自己生成的真实文稿，不重新规划或处理下一篇。

## 三、各文档类型的源码读取重点

### 1. glossary.md（术语表）
需要通读全部仓，但关注点是词汇层面：
- 读取各仓的核心类名、枚举、常量定义
- 读取接口参数名称和数据模型字段名
- 读取错误码定义（各仓的错误码常量类、异常类）
- 读取配置项名称
- 识别同一概念在不同仓中的不同命名（如仓A叫"task"，仓B叫"job"）

### 2. architecture.md（架构全景）
需要通读全部仓，关注点是协议和拓扑：
- 读取各仓的构建配置（pom.xml / package.json / CMakeLists.txt）— 技术栈
- 读取各仓的接口定义文件 — 识别所有跨仓调用点
- 读取各仓的下游调用代码（Proxy、Client）— 确认实际通信协议
- 读取部署配置（chart/、deployment/）— 部署拓扑
- 读取各仓的启动入口和注册逻辑 — 理解服务发现机制

### 3. domain.md（业务域）
**需要深度通读该域涉及的所有仓的业务逻辑**，这是最需要深度阅读的文档：
- 读取链路上每个仓的 **接口层** → 找到跨仓调用入口
- 读取链路上每个仓的 **Service/业务逻辑层** → 理解每个仓做了什么
- 读取链路上每个仓的 **数据模型** → 理解数据如何变换
- 读取链路上每个仓的 **状态管理代码** → 理解状态流转
- 读取链路上每个仓的 **文件传输代码** → 理解文件如何在仓间物理传输
- 读取链路上每个仓的 **外部系统调用代码** → 识别任务中心、文件传输服务等外部依赖
- 读取链路上每个仓的 **存储路径和容量配置** → 识别数据在各阶段的物理存储位置和容量上限
- 读取链路上每个仓的 **定时清理代码** → 识别临时文件/内存对象的清理策略（调度方式、TTL、清理范围）
- 读取链路上每个仓的 **DFX 代码** → 识别流量控制、超时/重试、安全校验、审计日志、可观测性机制
- 逐方法追踪：从触发入口到最终执行的每一跳
- 枚举所有独立用户场景（如单条操作 vs 批量操作）
- 对比不同场景的机制差异
- **每个场景内部完整讲清楚核心实体、状态机、端到端调用链路，不拆分到多个章节**

### 4. interface-contract.md（接口契约）
需要深度通读上游和下游两个仓：
- 读取上游仓的 **调用代码** — 理解上游如何构造请求、处理响应
- 读取下游仓的 **实现代码** — 理解下游如何处理请求、构造响应
- 读取 IDL / 接口定义文件 — 接口签名
- 读取上游和下游的 **超时/重试配置** — 实际容错策略
- 读取上游和下游的 **异常处理** — 错误码定义和传播
- 读取上游的 **调用上下文** — 什么业务场景触发此接口

### 5. external-system.md（外部系统画像）
需要通读对接仓的外部通信相关代码：
- 读取对接仓的外部通信模块 **全部源码** — 协议细节
- 读取协议配置文件 — 连接参数
- 读取数据编解码代码 — 数据格式
- 读取异常处理和重连逻辑 — 容错策略

## 四、多仓读取记录

涉及多仓时，按规划逐仓阅读；将每个仓的发现与实际来源写入 sources 或步骤结果。主会话需要进一步拆分研究时可安排独立只读步骤，写作步骤不调用不存在的图工具或嵌套子代理。

```
# 示例：生成 domain.md 时
component_source(仓A源码) → 仓A在链路中的业务逻辑与来源
component_source(仓B源码) → 仓B在链路中的业务逻辑与来源
component_source(仓C源码) → 仓C在链路中的业务逻辑与来源
# 汇总后填充模板
```

每个仓的读取记录应包含：
- 要读取的仓路径
- 要追踪的链路描述（具体到场景，如"单条导出的完整链路"而非笼统的"导出代码"）
- 要关注的源码层次（接口层/Service层/数据模型/状态管理/文件传输/外部系统调用）
- **必须识别的外部系统依赖**：检查代码中调用的外部服务客户端、第三方库
- **逐仓发现格式**：
  ```
  ## 主链路
  <入口方法 → 内部处理 → 跨仓调用 → ... 完整到链路终点>

  ## 外部系统依赖
  <本仓调用的所有外部服务、第三方库>
  如无，写"无"

  ## 场景差异
  <如果存在单条/批量等不同模式，说明差异>
  如无差异，写"无"
