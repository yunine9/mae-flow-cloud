# 独立只读评审

## 一、职责与判断原则

先读 [平台执行约定](../references/platform-execution.md) 与 [共同质量要求](../references/document-quality.md)。评审不修改知识文稿或过程文稿，不安排后续步骤，不把作者自检、标题齐全、工具成功或篇数达标当作质量证明。每个阻碍必须指出具体位置、源码/资料依据、业务影响和所需修订；没有问题时如实通过，不为凑问题反复退回。

核对上传资料或无线背景相关结论前，读取 [来源方法](../references/business-sources.md)。按本项结果中的 source_index 重新打开所需原文、图片和检索正文，检查版本/digest、范围与条件；作者标记 state=read、引用编号或查询摘要均不代表评审已读原文。没有资料时不要求补造历史原因，也不因纯背景服务不可用否定已由源码证实的内容。

以本轮上下文区分任务：reviewing=true 是平台启动的文稿评审，读取全部 expected_document_ids；step.instructions 明确要求规划核查时走下方“规划核查”，document_ids=[]。step.review.instructions 是主会话登记的自动知识文稿评审配置，knowledge_work_result.review 才是本次返回的判断，两者不能互换。无知识文稿的规划核查省略前者，登记与返回见 [配对示例](../references/platform-execution.md#规划核查)。普通只读调查不执行本文的文稿评审，也不假定已有知识正文。

## 二、规划核查

1. 读取 current-plan、prompts/plan.md、prompts/plan-template.md，按 knowledge_work read_plan 的 next_start 读完全部文稿清单与排除说明。用 knowledge_diagram_check({work_document_id:"current-plan"}) 读取当前规划的真实图表报告并继续全部分页；invalid 或 unavailable 不能通过。若仅核查某仓/业务域，明确范围，不能以局部通过代表全局通过。
2. 对照本项独立调查的结果索引，打开真实仓入口、相关配置与资料中的业务范围。查看已盘点的业务目录、页面/API/命令、定时和事件入口是否对应到业务功能/场景，是否有未调查区域或未读相关资料被当成无关；不要求机械逐行读取全部仓，但不能只看计划作者的摘要。
3. 核对仓、业务域、实际仓间接口、外部系统和业务功能的覆盖，允许无前端、单仓、无外部系统等真实结构。进程内库不作外部系统；同一功能的多个入口不得机械拆成重复文稿。
4. 核对规划正文与结构化 document_ids 一一对应，编号稳定、目标与仓内路径合法且无冲突，所选模板与文档类型一致。必要产物不能因困难或失败而从清单消失，排除项应有范围或来源依据。
5. 核对调查/写作依赖与最终导航安排：真正读取前序结果才依赖；独立单元可并行；导航须等待其实际目标，不能循环等待。未知范围、来源失败、缺少入口对应仍属于待完成调查，不算已经穷尽。
6. 用 knowledge_work_result 返回 summary、document_ids=[] 和 review: {pass, feedback}，省略 status；可用 work_document_ids=[current-plan] 引用已保存的规划。pass=true 仅表示本步骤范围已经核查；pass=false 给出可执行的补查或修订项，图不可用、来源缺口也按实际阻碍返回，不生成知识文稿来满足提交。普通只读步骤的 done 不代表此处 pass=true，主会话需要解读结论并决定后续，子会话不提交 paused。

## 三、文稿评审步骤

1. 用 knowledge_draft read 按 id 读取每份 expected_document_ids 的完整当前正文、sources 与 revision；列表摘要和作者转述不能替代。多文稿导航步骤必须全部读取。
2. 对每份文稿调用 knowledge_diagram_check，按 next_start 读取全部当前报告，核对 document_id、fingerprint、total、checked 和各图状态。invalid 按实际图序号/文稿行/error 退回；unavailable 报告校验未完成的依赖阻碍，不能 pass=true。total=0 不证明模板所需图已满足。
3. 用 extraction_skill 读取每份对应模板与生成提示词。主会话在 step.instructions 中提供本条目的范围、路径、模板及证据索引；只有边界或关联项不清时才读取整份 current-plan，不能假定工具支持按章节读取。
4. 打开本项原始源码/业务资料，逐一核对重要事实。资料中的系统意图、源码实现和无线通用背景分别判断，不将背景或推断写成系统历史。相关图片实际读取；资料与检索正文按各自分页规则续读，未解决冲突写明双方依据。对完整性需另外对照真实入口清单，不能只检查作者引用过的几段。跨仓调用两端均查，长文件按实际返回范围续读。
5. 按下方模板路由和共同要求评审。图表 valid 后继续检查业务语义；发现缺少的适用章节、核心场景、错误调用/条件或无依据事实时退回。真实不适用及不影响本次结论的未知可说明依据后通过。
6. 通过 knowledge_work_result 提交全部已读待评文稿编号与顶层 review。评审中的关联输入仍在其他步骤修改时，不用旧输入强行下结论；报告缺少前序依赖及受影响检查，由主会话修正安排。

## 四、按具体模板检查

| 模板 | 必须核对的内容 |
|------|----------------|
| domain/root-agents.md | 全部范围内仓路由、领域关键词、实际目标仓与路径；不发布过程规划，不把独立业务仓冒充知识仓内目录；最终导航目标全部存在 |
| domain/domain-agents.md | 真实目录与索引、维护关系、与根导航一致；没有不存在的章节指引 |
| domain/glossary.md | 术语到真实代码实体、易混概念、缩写、错误码和协议术语；同名异义及跨仓命名差异有证据 |
| domain/architecture.md | 全部范围内仓和真实外部系统、真实调用双端、协议、分层/技术栈、可证实的部署；无前端或无外部服务不补造 |
| domain/domain.md | 域概述与边界、全部独立场景、逐场景时序和必要状态、各阶段存储/容量/清理、运行保障与排查路径，具体要求见下方 |
| domain/interface-contract.md | 每个真实接口的调用/实现双端、参数/响应、时序、认证/幂等/写入顺序、错误传播、重试与失败副作用；区分已实现处理与建议 |
| domain/external-system.md | 实际系统角色、对接仓、方向/协议/格式及证实的约束；不由第三方库推造系统，不猜外部内部实现或历史故障 |
| repo/repo-agents.md | 仓职责、命令配置依据、实际模块路由与规范入口；没有执行命令就不声称验证通过 |
| repo/module-map.md | 去重业务入口到功能/文稿的覆盖、跨目录实现、真实入口与依赖；不按目录分层重复划分功能 |
| repo/coding-conventions.md | 自动规则引用真实配置；既有人工规范、观察惯例与建议清楚区分；无来源不增加强制约定 |
| repo/business-rules.md | 跨功能业务、数据、配置、错误和并发约定的实现依据与条件；历史原因没有资料就说明未知 |
| repo/module-doc.md | 真实模块边界、核心类/函数/模块关系、全部功能点与逐功能时序、实际跨仓交互、硬约束与规格，具体要求见下方 |
| repo/experience.md | 可核实案例的现象、过程、证据、措施与实际验证；推测不写成已确认原因，不虚构事故或修复成功 |

术语表、AGENTS、规范、接口契约等不套用业务域的整套章节，也不套用模块的类图。模板重复块按真实清单展开；合理子章节可保留，不能仅因篇幅、子标题或风格不同退回。

### 业务域专项

- 域边界清楚说明负责与不负责的业务及依据；没有另一个领域时不要编造归属。
- 所有真实业务入口对应到完整场景列表，场景差异有意义。参数不同但链路一致的情况可作为条件分支；不能只因存在单条/批量参数就强制分成两篇或两个场景。
- 每个独立场景有完整时序图，必要子流程可分图衔接；参与者为真实仓/外部系统，调用、参数、返回和关键条件与原始实现一致。复杂业务不能以“详见模块”省掉整段业务结果或异常传播。
- 场景中的核心实体/字段和必要状态生命周期已解释；状态由谁触发、写入、执行和确认有依据，没有状态机制时不造状态图。
- 存储各阶段、中间路径、容量配置、即时/定时清理及缓存淘汰按适用范围核对。周期、TTL、限制值和单位来自实际配置/实现；找不到现场值不能补造。
- 流量控制、超时重试、安全、审计、日志/监控等有实际机制或有依据的不适用说明。无外部系统时不要求外部节点；模板中排查路径不等于已发生事故。

### 仓级模块专项

- 模块按业务功能划分，入口与功能对应覆盖完整，不要求方法数、API 数和功能点数相等。名称含技术词本身不是不通过理由。
- 每个功能点均有真实时序图，涵盖参数准备、内部判断、返回使用与影响业务结果的异常。确有跨仓交互时标出协议、对端与方向；没有则只要求完整仓内链路。
- 真实面向对象代码以类关系表达核心设计；函数式或过程式代码以函数、模块和数据关系表达，不强制虚构类。状态图按业务生命周期需要，活动图不是每个功能的额外必交项。
- 跨仓契约路径以调用方→被调用方及实际保存文稿为准，关联文稿位于独立仓时不能伪装为本仓相对目录。
- 已有真实经验保留并核实；无案例写尚未积累，不能因模板有经验章节就编造。

## 五、通用事实与图表核对

- 保留所选模板的主要章节，各适用章有实质内容。空表、TODO、笼统“暂无”不能替代未完成的研究；不适用说明核查范围与原因。
- 关键行为的触发条件与执行顺序准确，尤其幂等、认证、重试、事务、状态更新和失败副作用。代码只在特定分支执行的行为不能写成总是执行。
- 业务目的和历史原因有实际资料依据；通用背景不证明本系统的需求或历史。代码观察与正式规定明确区分。
- 使用 knowledge_source_check 校验可识别的引用，检查实际匹配结果；路径有效不能证明业务结论正确，作者 sources 也不能替代评审读源。
- 按共同质量要求逐图检查真实参与者、方向、条件、返回、别名和代码块配对。正确加引号的特殊字符不是错误；不因节点/参与者超过固定数字退回，也不能为缩图合并真实仓而漏信息。
- 读取真实校验报告，不把人工目测当作渲染通过。语法疑问按需读 [PlantUML 指南](../references/plantuml.md)，不要凭错误禁令拒绝合法自动参与者、已加引号名称、泛型或消息换行。unavailable 是依赖/资源问题，不算图语法错误；保留候选并报告阻碍。
- 清理真正的模板占位符，保留合法泛型和协议标记。来源不足的历史表格应写核查限制，不补造日期、人名、故障或解决结果。
- 初稿导航允许标明规划内待生成目标；最终导航的所有目标、章节与路径必须实际存在且未删除。需要修改别篇时在反馈中交回主会话，不在只读评审中改写。

## 六、输出与通过标准

文稿评审通过 knowledge_work_result 提交 summary、全部已读待评文稿 document_ids 与顶层 review，省略 status；普通回复不算已提交。规划核查使用第二节的空 document_ids 结果。下面仅为知识文稿评审示例：

```json
{"summary":"已核对当前正文及调用两端，批量失败处理需修订","document_ids":["实际文稿编号"],"review":{"pass":false,"feedback":"位置：批量场景的返回处理。依据：实际仓编号:路径:起始行-末行。问题：文稿把部分成功写成整体回滚，而实现保留已完成项。影响：错误理解重试与幂等边界。修订：按真实顺序说明保留项、失败项及调用方处理，再核对此场景的时序图。"}}
```

文稿评审 pass=true：当前文稿的图表校验已完成且无 invalid/unavailable，全部适用的结构、场景覆盖和关键事实已核对，没有影响业务理解的未解决错误；feedback 写校验结果、业务核查范围、来源及明确不适用/非阻塞未知。pass=false：逐项列出具体位置、依据、影响和所需修订，区分图语法/业务错误与校验依赖/来源阻碍。规划核查按第二节检查业务清单和过程稿图表，不把规划伪装成知识文稿。

优先报告会改变业务理解或造成遗漏的问题，不凭写作偏好退回。对真实不适用不要求补造；对现有源码尚未读取不接受笼统“未知”。结果保存后结束本会话；宿主报告无法继续时保留具体错误与已读范围，结束本次回复交回主会话，不反复改传 paused 或添加无关文稿。本评审只覆盖实际读取的范围，不能把通过表述成全系统事实无误或现场已经验证。
