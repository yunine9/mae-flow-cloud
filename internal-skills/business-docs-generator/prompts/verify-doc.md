# 文档校验提示词（子 Agent 用）

## 一、目标

对刚生成的文档进行独立只读评审，核对模板结构、业务覆盖和源码事实。评审回读原始证据，不仅判断文字是否像完整文档。先读 [平台执行约定](../references/platform-execution.md)，只评审本步骤指定的候选。

## 二、输入

- expected_document_ids 中的全部文稿编号、规划中的路径及当前 revision
- 文档类型（domain / repo）与本次具体模板
- 对应模板路径
- 对应生成提示词路径
- sources 中实际读取过的源码位置与业务资料位置；需要核实的问题

规划核查没有知识文稿时，先 knowledge_work read_plan 读完文稿编号与排除说明的全部分页，再读过程文稿 current-plan、prompts/plan.md 和 prompts/plan-template.md，逐项对照结构化清单、规划正文和真实仓入口，检查仓/业务域/外部系统/功能/输出路径完整性；不套用下方业务文稿章节检查。

## 三、校验步骤

### 1. 读取文档和模板

先用 knowledge_draft read 逐一读取 expected_document_ids 的全部当前正文、sources 与 revision，再用 extraction_skill 读取对应模板和生成提示词。逐节对比结构，按实际模板选择专项规则；不能把作者的摘要或“已经自检”当作证据。

上下文只提供本项范围与证据索引，评审开始时按文稿 id 读取完整正文，并重新打开原始依据。列表接口返回的是分页摘要，使用 next_start 读完所需范围；其他步骤尚在写作的关联文稿，须等其完成并作为真实依赖，不能评审一份仍在变化的关联输入。

| 对应模板 | 专项检查 |
|----------|----------|
| domain/root-agents.md | 仓路由、领域关键词路由、真实文档路径、与本次规划的一致性 |
| domain/domain-agents.md | 实际目录索引、维护规则、与根路由一致 |
| domain/glossary.md | 术语到真实代码实体、易混概念、缩写、错误码和协议术语 |
| domain/architecture.md | 全部仓和实际外部依赖、真实跨仓调用、协议、分层、技术栈及部署依据 |
| domain/domain.md | 下方“领域文档专项校验”的全部适用项 |
| domain/interface-contract.md | 调用与实现双端、参数/响应、错误传播、超时重试幂等、真实时序图 |
| domain/external-system.md | 实际角色、交互、方向/协议/格式、可证实的约束与依赖 |
| repo/repo-agents.md | 本仓职责、命令依据、模块路由与全局规范 |
| repo/module-map.md | 下方模块清单专项校验、入口与下游依赖、对规划内全部业务功能的覆盖 |
| repo/coding-conventions.md | 真实 lint/格式化配置，已自动强制与需要人工遵守的规则区分 |
| repo/business-rules.md | 有原始依据的跨模块业务、数据、配置、错误处理与并发约定 |
| repo/module-doc.md | 下方“仓级模块文档专项校验”的全部适用项 |
| repo/experience.md | 真实案例的现象、过程、证据和验证结果；无法证实的历史事件不得补写 |

术语表、AGENTS、规范、接口契约等各有模板，不能给它们强加业务域文稿的域边界/DFX章节或模块文稿的类图。图表要求按具体模板与实际场景判断。

### 2. 通用校验项

逐项检查以下内容：

**模板结构合规性**：
- [ ] 文档是否包含模板中定义的所有章节？是否有遗漏的章节？
- [ ] 是否有多出的、模板中未定义的章节？
- [ ] 章节顺序是否与模板一致？

**占位符清理**：
- [ ] 文档中是否残留 `<占位符>` 形式的内容？（搜索 `<` 和 `>` 包裹的占位符）
- [ ] 文档中是否残留 `<!-- 指引说明 -->` 形式的 HTML 注释？（搜索 `<!--` 标记）

**PlantUML 图表合规性**：
- [ ] 所有 PlantUML 图表是否使用 `@startuml` / `@enduml` 包裹？
- [ ] 所有 PlantUML 图表是否包裹在 ` ```plantuml ` 代码块中？（搜索 `@startuml`，确认其前一行是 ` ```plantuml `）
- [ ] 每个 `@startuml` 是否都有对应的 `@enduml`？无遗漏、无多余？
- [ ] 是否有空的 PlantUML 代码块（`@startuml` 后直接 `@enduml`，无实际内容）？
- [ ] 图表方法、参数、调用方向和关键分支是否与本次实际回读的代码一致？只看名称不像占位符不算核实。

**PlantUML 语法正确性（关键校验项，逐图检查）**：
- [ ] **组件名/类名特殊字符**：组件 `as` 别名后的显示名中是否含 `::`、`<>`、`()` 等特殊字符？这些字符在 PlantUML 中会导致解析错误。检查方式：搜索 `component "`、`class "`，查看引号内的名称。如有特殊字符，须改为纯文字或用引号包裹的简单名称
- [ ] **组件标签内真实换行**：`component "..."` 引号内的标签文本是否包含真实换行符（多行文本直接写在引号内）？PlantUML 不支持引号内直接换行，必须用 `\n` 表示换行。检查方式：搜索 `component "`，查看引号内是否有跨行内容。如有，将真实换行替换为 `\n`
- [ ] **泛型尖括号**：类图中的泛型 `<T>` 是否直接写在类名中（如 `class FarsDBTable<T>`）？PlantUML 会将 `<T>` 误解析为 HTML 标签。须改为 `class "FarsDBTable<T>" as FDT` 或去掉泛型
- [ ] **箭头标签中的换行**：箭头标签是否使用 `\n` 换行（如 `A --> B : REST/HTTP\ncreate-task`）？部分渲染器不识别 `\n`。须改为单行标签或用 `\n` 时确保在引号内
- [ ] **引号使用**：含空格、括号、斜杠的标签是否用双引号包裹（如 `component "TraceTask\n(任务管理界面)" as FE`）？未包裹的括号和斜杠会导致解析错误
- [ ] **图的大小**：单个 PlantUML 图的节点数是否超过 40？超过 40 个节点的图布局容易崩溃或不可读。如超过，须拆分为多个图或精简非核心节点
- [ ] **时序图参与者数量**：时序图参与者是否超过 8 个？超过 8 个时布局拥挤。如超过，考虑合并次要参与者
- [ ] **`participant` 声明**：时序图中每个参与者是否都有 `participant` 声明和 `as` 别名？未声明的参与者名含特殊字符时会导致错误
- [ ] **状态图语法**：状态图中 `[*]` 是否正确使用？状态转换箭头 `-->` 是否使用了正确的语法？
- [ ] **class diagram 语法**：类图中可见性标记 `+`/`-`/`#` 是否后跟方法或属性？类间关系箭头是否使用了正确的 PlantUML 语法（`-->`、`..>`、`*--`、`o--`）？

**内容完整性**：
- [ ] 是否有章节只有标题但没有正文内容？
- [ ] 是否有表格只有表头但没有数据行？
- [ ] 是否用 TODO、空表或笼统“暂无”掩盖尚未完成的研究？真实“不适用”须有查证范围与原因；业务意图缺资料时可明确未知，不能为填满模板编造。
- [ ] 仅排查经验章节允许原模板的“暂无排查经验，待积累”；其余必需章节应有实质内容，受阻章节应明确问题、核查范围和影响。

**来源与事实一致性**：
- [ ] 是否实际 component_source read 关键入口、实现、返回处理与异常分支，而非仅读文稿的来源列表？检查多仓调用两端，并对长文件继续分页到相关方法。
- [ ] 关键状态、参数、容量、路径、定时清理周期和超时值是否与实现一致？是否把条件成立时的行为写成总是发生？
- [ ] 文中声称的业务意图或历史原因是否有上传资料等实际依据，而非代码推测或无线豆包通用背景？有资料时实际回读相关章节。
- [ ] 将代码引用转为平台支持的仓编号:路径:行号或仓编号:路径#符号，调用 knowledge_source_check 处理错误；checked 为空不代表引用全部有效。
- [ ] 源码入口中的独立场景、公开接口、定时任务与事件处理是否在规划及文稿中覆盖？重要遗漏须退回。
- [ ] 导航指向已保存的文稿或本次完整规划中的明确后续产物？最终导航复核时全部目标须真实存在且未被删除。
- [ ] 引用的章节或表是否在目标文稿中实际存在？原导航模板提到的“规则归属表”不是业务域模板的现有章节，应改为真实的域边界/端到端链路及场景位置，而不是照抄示例措辞。
- [ ] 模块文稿的接口契约路径是否按真实调用方→被调用方对齐已保存契约？本仓提供接口与本仓调用接口的方向不能仅按模板箭头猜测。

### 3. 领域文档专项校验（仅 templates/domain/domain.md）

**时序图完整性（关键校验项）**：
- [ ] **每个场景是否都有时序图？** 逐个检查"端到端链路"章节下的每个场景，确认每个场景内部都有 `@startuml` 时序图。**不可省略，不可偷懒。**
- [ ] 时序图参与者是否以仓为单位命名（如"仓A"、"仓B"、"外部系统"），而非使用通用名（如 Caller、Service）？
- [ ] 跨仓调用箭头是否标注了真实接口名和参数？

**域边界**：
- [ ] "域边界"章节是否同时列出"属于本域"和"不属于本域"的功能？
- [ ] 不属于本域的功能是否标注了原因和所属域？

**场景枚举**：
- [ ] 场景列表表是否列出了所有独立场景？
- [ ] 各场景是否写明了差异？

**外部系统**：
- [ ] 架构图是否包含外部系统节点？
- [ ] 排查清单是否包含外部系统检查项？

**环境存储与清理**：
- [ ] 是否列出了数据在各链路阶段的存储位置？
- [ ] 是否列出了容量限制配置？
- [ ] 是否记录了各仓的临时文件清理策略？

**DFX 场景**：
- [ ] 流量控制、超时与重试、安全机制、审计日志、可观测性是否都有内容（非空表格）？

### 4. 仓级模块文档专项校验（仅 templates/repo/module-doc.md）

**模块文档命名（关键校验项）**：
- [ ] 模块文档名是否使用**业务功能名称**（如 `trace-task-create`），而非代码目录名称（如 `domain-task-create`）？
- [ ] 文档名是否包含技术分层前缀（如 `domain-`、`interface-`、`common-`）？如有，标记为**不通过**。
- [ ] 一个业务功能是否被拆分到多个文档中？如是，标记为**不通过**。

**模块文档功能点时序图**：
- [ ] 每个功能点是否都有时序图？
- [ ] 时序图参与者是否以仓为单位命名（"本仓:类名" / "仓名:模块名"）？
- [ ] 跨仓调用箭头是否标注了协议和接口名？

**跨仓交互**：
- [ ] 跨仓交互表是否列出了所有跨仓调用和被调用？
- [ ] 每条跨仓交互是否标注了协议？
- [ ] 是否指向 `domain-docs/interfaces/` 下的契约文档？

**类设计**：
- [ ] 是否有 PlantUML class diagram 展示核心类间关系？
- [ ] 每个核心类是否有一句话职责说明和文件位置？

**排查经验**：
- [ ] 排查经验是否初始为空（未编造内容）？

### 5. module-map.md 专项校验

- [ ] 模块清单中的模块名是否使用业务功能名？
- [ ] "涉及源码目录"列是否允许跨多个目录（一个业务功能可跨多个代码目录）？

## 四、输出格式

通过 knowledge_work_result 提交 summary、全部已读待评文稿 document_ids，以及顶层 review 对象。review.pass 必须是布尔值；review.feedback 包含以下逐项检查结果、问题定位、证据与修订要求。规划核查 document_ids=[]，summary 写实际核查范围。示例：

```json
{"summary":"已核对当前版本及原始依据，存在需修订问题","document_ids":["实际文稿编号"],"review":{"pass":false,"feedback":"具体检查结果、章节与源码位置、问题影响及所需修订"}}
```

feedback 使用以下结构；适用项全部通过才能返回 pass=true，真实不适用项注明原因。保存普通回复不代表评审结果已提交。

```
## 校验结果：<通过/不通过>

### 通用校验
- 模板结构合规性：通过/不通过（原因）
- 占位符清理：通过/不通过（原因）
- PlantUML 图表合规性：通过/不通过（原因）
- 内容完整性：通过/不通过（原因）

### 专项校验
- <各专项校验项>：通过/不通过（原因）

### 问题清单
1. <问题描述 + 定位（章节名/行号）>
2. <问题描述 + 定位>

### 建议
1. <修复建议>
```

## 五、约束

- **只读操作**：不修改文档内容，只读取和检查
- **客观判断**：基于具体模板、完整场景和原始依据判断，不以写作风格喜好或篇幅长短决定通过
- **定位精确**：发现问题时要定位到具体章节和（如可能）行号
- **不编造问题**：如果没有问题，明确返回"通过"，不编造问题
- **候选隔离**：不修改正文，不把工具执行成功当作通过，不用旧版本评审覆盖刚更新的候选
