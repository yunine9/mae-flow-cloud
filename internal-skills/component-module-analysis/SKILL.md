# 组件模块与场景分析

在独立会话中分析当前技术栈有哪些功能组件、各自解决哪些开发需求。组件是文件操作、数据库操作、P2P 等功能能力，具体清单由实际代码和调用分析得到。参考仓提供定位线索，一个组件可以跨多个仓实现，一个仓也可以包含多种能力。

## 开始分析

先读 [平台协议](references/platform-pipeline.md) 和 [输出格式](references/schema.md)。inventory 阶段读 [模块盘点](references/phase-inventory.md)，plan 阶段读 [场景规划](references/phase-plan.md)，独立评审读 [评审标准](references/phase-review.md)。接口候选按 [能力边界](references/api-boundary.md) 核对。

## 分析顺序

1. 从 component_structure 和真实源码定位入口、实现、构建、发布与测试，再用 everycode 展开使用方调用。完成条件是能够解释能力的具体用途与代码范围。
2. 按开发者要完成的工作归组功能组件，综合各参考仓和 everycode 线索明确能力边界及必要依赖。完成条件是同一能力的跨仓实现得到合并，同仓的不同能力分别组织，覆盖主要独立能力；协作完成同一用途的函数归在一起。
3. 为当前模块规划可独立讲清的使用场景，用真实调用与测试核对场景之间的区别。完成条件是每个场景都有具体需求、前提、代码起点及需要继续核对的问题。
4. 通过 component_work_result 提交目录或规划、发现与问题。结构化结果承接研究过程，后续会话依据它继续核对。

功能组件与场景从当前代码和实际使用中产生，名称表达开发能力；仓、构建目录、函数和类均是代码定位线索。每次只完成当前任务，调度、并行会话与重试由平台负责。

## 判断边界

候选能力允许保留待查问题；使用者是否得到受支持入口、依赖如何获得和测试如何运行，分别核对并记录依据。正文指南由后续萃取会话生成，本阶段交付可追溯的分析结果。
