# 模块与场景输出

通过 component_work_result 提交当前任务结果，普通回复不替代结构化提交。

## inventory

components 中每项包括：

| 字段 | 内容 |
|---|---|
| id | 小写字母、数字和连字符组成的稳定编号 |
| title | 面向开发者的能力名称 |
| repository_ids | 当前允许研究的基础仓编号 |
| scope | 代码起点、范围、能力边界和需要继续核对的问题 |
| dependencies | 可选，其他已列模块的编号数组，描述能力依赖关系 |

模块来自当前组件的实现、接口、构建及实际调用。依赖只表达事实关系，执行并发由平台安排。

## plan

paradigms 中每项包含 id、title、need：id 是稳定场景编号；title 表达开发场景；need 写明使用方要完成的工作与必要前提。

同一用途下共同完成初始化、调用和清理的函数组成一个场景。不同目标、前提或生命周期产生独立用法时再拆分，并说明其区别。

## 发现、证据与问题

findings 写清实际读取的代码起点、固定版本、使用方调用与测试线索、模块或场景边界的判断依据。open_questions 保存缺失证据及受影响的结论。后续会话通过 component_work 读取结果，并回查原始代码。

没有足够依据时如实提交缺口和已覆盖范围；不填写预设模块或为数量补造用法。独立评审使用 pass 与 feedback，反馈给出具体位置、依据和修改建议。
