## 总纲：我对产品的架构与预期定位

> 这是整个建设过程中逐步拍板形成的总纲。放在时间线最前面，便于先理解“为什么做”，不表示所有细节都在第一天一次性提出。

**我的输入：** 我要打造的不是一个把 CLI 搬到网页上的聊天工具，也不只是一个任务看板，而是一套**好用、易用、敏捷，代码质量高、可管控、可观测的云上 Agent 需求交付平台**。

具体定位是：

1. **对开发真正好用。** 开发进入平台先看到自己的需求，能够在一个任务工作台里完成确认、检视、批注、看代码、看产物、控制任务和必要的人工介入，不需要在多个系统之间来回寻找现场。
2. **让团队真正看得见。** 团队总览不是简单堆任务数量，而是要看见团队正在推进什么、卡在哪里、谁在等待、交付是否稳定、时间和 Token 花在哪里，以及知识有没有真正帮助交付。
3. **一套模型覆盖单仓和跨仓。** 单仓需求就是只有一个仓库节点的跨仓需求；多仓先把理解和依赖关系确认正确，再按照依赖拆分和调度，不建设两套互相割裂的流程。
4. **与 Mae-Flow 内核亲和，但不被内核拖住。** 内核负责核心流程、人工决策语义和关键裁决；Cloud 负责任务、会话、容器、Git、MR、流水线、通知和页面。需要轻量处理的云端场景，不应被不必要的流程门禁卡死。
5. **质量保障要快，也要可信。** 每次 push 前先在统一任务容器中完成编译和 UT，尽早发现问题；正式流水线继续作为最终交付裁判，旧代码的绿灯不能替新代码背书。
6. **用户始终拥有现场控制权。** Agent 走偏时，用户可以暂停、插话、批注，或者直接使用开发助手查看、修改和运行代码。用户主动介入代表更高优先级的人工意志，交还后内核要理解现场，而不是用僵硬的哈希和版本规则把人卡住。
7. **业务知识跟着代码走。** 文档、规则和 Skill 应沉淀在业务仓，由用户按任务选择，Agent 自行判断何时使用；平台记录真实消费，再帮助团队发现高价值知识和知识缺口，形成持续改进飞轮。
8. **平台必须可治理。** 账号、角色、凭据、任务状态、容器生命周期、交付证据和操作记录都要有清晰边界。宁可暂时不做某项功能，也不要为了堆功能引入严重问题。

**Agent 的输出或结果：** 当前产品已经围绕这套定位形成以下架构：

```text
开发人员 ──→ 我的工作 / 任务工作台 / 开发助手
团队运营与平台管理 ──→ 团队总览 / 服务治理 / 知识效能

                    Mae-Flow Cloud
       任务与账号 · 会话 · 通知 · Git/MR · 流水线 · 可观测
                         │
          ┌──────────────┼──────────────┐
          │              │              │
    Mae-Flow 内核     Pi Agent      统一任务容器
   流程与关键裁决   理解与代码执行   编译、UT与任务命令
          │              │              │
          └──────────────┼──────────────┘
                         │
             业务代码仓、文档、规则与 Skill
                         │
                 Git / MR / 权威流水线
```

它相对本地 CLI 多提供的价值，不是“替用户多包一层”，而是把个人 Agent 能力变成团队可以共同使用、检视、恢复、度量和持续改进的交付能力。

## 2026-08-14：确定架构，跑通第一条完整链路

### 1. Cloud 与内核的基本分工

**我的输入：** Mae-Flow 内核继续作为流程、门禁和证据裁决的权威。Cloud 不重新复制一套流程规则，而是负责承载云端任务和会话。

**Agent 的输出或结果：** Cloud 使用 TypeScript 进程内集成 Pi，把 Pi 的工具调用和会话事件转换成 Mae-Flow 能识别的 Hook 与 transcript；内核继续负责裁决，Cloud 负责运行现场。

### 2. 为什么服务层使用 TypeScript

**我的输入：** 技术语言按亲和度选择。Pi 本身是 TypeScript，云端需要同步拦截工具调用、挂起人工问题和启动子 Agent。

**Agent 的输出或结果：** 服务层采用 TypeScript，直接进程内使用 Pi SDK；早期 Python 子进程加 HTTP 桥的两层转发被移除。

### 3. 外部依赖先模拟，再接真实服务

**我的输入：** 目标环境的外部服务未全部就绪时，先用模拟服务继续建设，不要因为等待环境而停住产品进度；正式部署时再接入真实服务。

**Agent 的输出或结果：** 建立小鲁班、Git 平台、MR 和流水线模拟服务，并为每项保留真实服务切换入口；两种形态共享同一套行为测试。

### 4. 第一版平台闭环

**我的输入：** 先把需求从发起、Agent 执行、人工确认一直走到代码交付，不要只做一个聊天页面。

**Agent 的输出或结果：** 建成 REST、SSE、审批页、Git 推送、MR、流水线、通知和任务恢复的第一条纵向链路。真模型试跑完成了需求理解、编码、质量检查、交付检视、push、MR 和流水线，并经历多次断点续跑而没有丢失任务进度。

### 5. 服务可靠性与数据

**我的输入：** 进程可以退出，但任务不能丢；等待和旁路能力不能让任务无限卡死。

**Agent 的输出或结果：** 增加任务恢复、并发控制、重启演练和上线自查。PostgreSQL 被定位为历史与事件投影，不作为任务阶段真相；任务现场仍以工作区状态为准。

## 2026-08-15：从“能跑”转向真正的人机协作工作台

### 1. 个人工作和团队协作需要不同视角

**我的输入：** 界面太丑，需要重新设计。团队需要随时掌握整体任务进展，开发也要能一站式处理自己的需求。

**Agent 的输出或结果：** 平台逐步形成“团队总览”和“我的工作”两个视角。开发优先看到自己的任务，团队视角用于了解阶段、卡点和交付。

### 2. 任务工作台

**我的输入：** 过程产物属于某一个需求，不应该放在全局页面。问答和审批也应该回到具体任务；任务进行中直接用进度条说明走到哪一步。

**Agent 的输出或结果：** 每个需求形成独立任务工作台，集中展示阶段进度、待办、过程产物、代码变更和执行记录。决策发生在哪，相关证据就展示在哪。

### 3. 文档、图形和代码变更

**我的输入：** PlantUML 渲染有问题；文档和代码是两个维度。Git 区域要能看全文、行号、新文件、分支和完整路径，不能只有一个“git diff”。

**Agent 的输出或结果：** 文档产物和代码产物分开呈现；修复 PlantUML 和类图渲染；Git 视图逐步支持完整文件、行号、未跟踪文件和源码阅读，并过滤 Mae-Flow 自己的中间状态文件。

### 4. 插话、批注和检视

**我的输入：** Agent 运行时用户不能只能干等；批注要能直接指着代码或文档说。谁提出的检视意见，谁才可以编辑和删除。

**Agent 的输出或结果：** 增加运行中插话、回执、代码/文档批注、批注作者权限和返工闭环。页面会显示 Agent 收到批注后的回复，但不引入复杂的逐条状态机。

### 5. 流水线红灯不能成为终点

**我的输入：** 流水线失败后需要继续修复，全绿才算完成。

**Agent 的输出或结果：** 增加流水线修复环，失败详情进入后续修复会话，修复产生新提交后重新触发新 SHA 的流水线。

## 2026-08-16：配置、身份、修复和知识能力成形

### 1. 配置应该让人看得懂

**我的输入：** 个人设置本质上是邮箱、CodeHub Token 和小鲁班 Token。管理员不应该理解底层 JSON；模型网关只需要地址、Key 和模型名。代码仓在下单时必填，不需要默认代码仓。

**Agent 的输出或结果：** 形成个人连接设置、管理页运行设置和统一 `serve.json`。密钥只写不读、页面只显示掩码；未完成必要个人设置时不能发起任务，并明确提示如何解锁。

### 2. 修复环要能持续收敛

**我的输入：** 修复不应该有僵硬的最大轮数；应该一次尽量修全再提交。如果一直没有进展，要换思路或者如实停下来。

**Agent 的输出或结果：** 修复轮默认不限，轮数只作为手刹；增加“同 SHA 不重复修复”“原地打转需要转向”和环境问题诊断出口。

### 3. CodeCheck 的位置

**我的输入：** Cloud 当前没有适合运行 CodeCheck 的环境。lightcheck 可以保留，正式 CodeCheck 交给流水线。

**Agent 的输出或结果：** Cloud 不再空跑 CodeCheck 安装和扫描；本地 lightcheck 保留，最终静态检查由流水线负责。

### 4. Agent 进入大仓前需要路标

**我的输入：** 大仓中 Agent 不应该一上来就全仓乱找，需要 repo map、业务知识和“定位先于修改”。

**Agent 的输出或结果：** 增加仓库地图、按触发词注入的 `.mae-flow/knowledge` 知识块，并在修复使命中要求先定位到文件、函数和依据，再开始修改。

### 5. Cloud 成为独立产品

**我的输入：** Cloud 应该是独立的集成产品，用户不应该再单独部署一套内核。

**Agent 的输出或结果：** Mae-Flow 内核快照收编进 Cloud 的 `kernel/`，一个 clone 就能启动完整产品；后续由同步脚本维护内核版本。

## 2026-08-17 ～ 08-18：MR 闭环和部署准备

### 1. MR 之后也要持续托管

**我的输入：** 平台不能只负责把 MR 创建出来，还需要处理检视意见、冲突、CI 失败和最终合入。

**Agent 的输出或结果：** 建成 MR 闭环：按检视、冲突和 CI 分类派发修复会话，持续监控 MR，直到合入或明确需要人工处理。

### 2. 环境接入不要修改产品代码

**我的输入：** 部署环境有自己的 CodeHub CLI、代理和网络条件，希望接入时主要填写配置，不要重新修改 Cloud 逻辑。

**Agent 的输出或结果：** 建立 CodeHub 适配层和部署手册。部署 Agent 只负责环境配置和联调；Windows CLI 可以通过 WSL 互操作，也可以让适配层直接运行在 Windows。

### 3. 下单事实不要让模型反复追问

**我的输入：** 单号、基线、邮箱、仓库和交付方式在下单时就应该收齐。管理员不负责发起业务任务，开发和管理员是两个角色。

**Agent 的输出或结果：** 下单表单收齐任务事实并机械传给内核；管理员页面和开发工作台分离，个人凭据、提交署名和任务归属绑定登录账号。

### 4. 真实运行暴露的稳定性问题

**我的输入：** 服务不能因为一次模型错误、输出管道断开或上下文过长就整体退出。

**Agent 的输出或结果：** 修复未处理 Promise rejection、EPIPE 递归、上下文溢出和 Windows 换行等问题；长上下文支持压缩后重试，失败原因会进入任务详情。

## 2026-08-19：单仓与跨仓交付统一

### 1. 跨仓依赖必须先理解正确

**我的输入：** Chain 模式要展示仓库之间的依赖，有些仓不能并行开发。需求理解阶段必须先由人工检视方案和依赖图；有问题就继续修改，不要引入复杂的 V1/V2 冻结。

**Agent 的输出或结果：** 建成跨仓分析流程：先克隆只读现场，产出方案、仓库列表和依赖图，经一次人工确认后再自动拆单。

### 2. 单仓和跨仓不是两套系统

**我的输入：** 单仓需求可以看成只有一个仓的跨仓需求，我们不是要做两套系统。

**Agent 的输出或结果：** 单仓和多仓统一为一套任务模型。父分析任务确认后硬收口，下游任务根据依赖关系启动，不再重复举确认卡。

### 3. 页面和通知要能真正使用

**我的输入：** 依赖图、小字、文档位置和确认入口必须清楚；通知链接不能是别人打不开的 `127.0.0.1`；全站时间不能一部分是 UTC。

**Agent 的输出或结果：** 修复依赖方向、文档与依赖图布局、重复确认卡、任务深链、白昼主题 Diff 和全站本地时间；通知链接进入部署自检。

## 2026-08-20：全面审视 Cloud 与内核的摩擦

### 1. 原则重新校准

**我的输入：** 全面检查 Mae-Flow 内核在编码阶段与 Cloud 的定位摩擦。核心原则是与内核亲和，但不能让内核把云端需要轻量化或省略的流程卡住。

**Agent 的输出或结果：** 对 Cloud、内核和测试契约做横向审计，修复文件工具路径、工作区边界、终态分叉、恢复、子 Agent 证据、流水线事实和 Hook 错误处理等接缝。

### 2. “不许卡死”的正确含义

**我的输入：** 不希望严格校验把 Agent 卡死，但也不能因为基础设施失败就假装流程通过。

**Agent 的输出或结果：** 口径从“故障时普通放行”改成“带预算重试，仍失败就如实停下让人接手”。关键门禁和证据登记失败不再 fail-open，普通辅助能力仍然不阻塞任务。

### 3. 真实试跑驱动的集中纠偏

**我的输入：** 根据真实运行暴露的问题继续修，不接受页面完成但流水线红、旧绿灯背书新代码或恢复后重复审批。

**Agent 的输出或结果：** 集中修复了验证等待无出路、旧任务被重新丈量、基础设施抖动误判、终态旧单上继续改代码、内核纠偏话没有送回模型、失败日志不足、修复维度遗漏和执行面板截断等问题。

### 4. 执行现场开始形成

**我的输入：** 原始 SSE 对机器有用，但人很难盯，需要把真正重要的信息提炼出来。

**Agent 的输出或结果：** 增加执行心流/执行现场，把大量 SSE 事件折叠成当前动作、关键变化和异常，同时保留原始事件流供排查。

## 2026-08-21：业务仓 Skill 和推送前验证

### 1. 业务仓 Skill 可选加载

**我的输入：** 业务代码仓自带的 Skill 应该列出来让用户选择。跨仓时每个仓都有自己的 Skill；还要读取 `.cac`。用户不需要指定在哪一步使用，让 Agent 自己判断。

**Agent 的输出或结果：** 支持扫描 `.agents/skills`、`.pi/skills`、`.claude/skills`、`.cac/skills` 下的标准 `SKILL.md`。下单和 Chain 最终确认时按仓选择，只有选中的 Skill 会交给 Pi；Skill 不增加权限，也不成为内核门禁。

### 2. 完全依赖流水线太慢

**我的输入：** 编译和 UT 全等流水线反馈太慢。每次准备 push 前，应该调用一个专门 Agent，把编译和 UT 处理到通过再 push；流水线红灯也应该轻量自动修复，不要重走内核完整流程。

**Agent 的输出或结果：** 增加推送前验证 Agent，在 push 前执行编译和 UT。代码问题可以自动修改和重试，环境问题输出诊断；最终流水线仍是权威裁判，CodeCheck 继续由流水线执行。

### 3. 首批构建语言

**我的输入：** 至少支持 Java、JavaScript 和 C++。内部很多项目使用 Maven；C++ 虽然过去依赖 MCDE，但服务器也能本地编译，不需要把 MCDE 流程照搬进来。

**Agent 的输出或结果：** 整理统一构建规则：仓库真实脚本和配置优先，Skill 只做辅助；Java 分开执行 compile/test，JS 按需准备依赖，C++ 保留仓库声明的 Maven/DT 参数并优先增量验证。

## 2026-08-21 ～ 08-22：统一任务命令容器化

### 1. 为什么需要容器

**我的输入：** 所有编译环境都在同一台机器上，需要隔离。希望统一将任务命令容器化，同时重点关注容器生命周期和问题定位。

**Agent 的输出或结果：** 主 Agent、子 Agent、开发助手、修复会话和推送前验证的 Bash 命令进入任务容器；Cloud 控制面、Git 凭据、MR 和通知留在可信宿主。

### 2. 容器的运行边界

**我的输入：** 容器不能只是“能启动”，还要避免任务互相影响，失败时不能偷偷回宿主执行。

**Agent 的输出或结果：** 增加非 root 用户、只读根、CPU/内存/PID 限制、分仓 Maven/npm/ccache/XDG 缓存和网络限制。镜像、Daemon、挂载或权限失败都会明确停止，不回退宿主。

### 3. 生命周期和排障

**我的输入：** 重点关注暂停、取消、服务重启后的容器回收，以及编译问题能不能定位。

**Agent 的输出或结果：** 增加容器所有权标签、孤儿清理、暂停/取消销毁、服务退出回收和等待审批时释放资源；长构建输出写入任务工作区，页面和 Agent 都能继续读取完整日志。

### 4. 安全与可靠性补强

**我的输入：** 宁可功能少一点，也不要为了容器和自动化引入严重问题。

**Agent 的输出或结果：** 修复容器修改 `.git` 后影响宿主 push、宿主 Git 配置和 hook 注入、软链接越界读写、凭据文件权限、同数据目录多进程误清理等问题，并用真实 Docker 测试容器工具链和回收。

## 2026-08-23：工作台、可观测、手机审批和开发助手

### 1. 工作台信息层级继续收敛

**我的输入：** 任务页不能把 Token、执行现场和重复的当前进展都放在最显眼位置。进度条要醒目，批注优先级要高，右侧四个区域需要重新组织并用不同色块区分。
