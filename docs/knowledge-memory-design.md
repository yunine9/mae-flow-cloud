# 任务记忆(语料库)设计稿

## 2026-09-19：交付完成后集中沉淀（当前实现）

本节取代历史稿的“逐条批注闭环 / Build-Fix 修好即自动提炼”。

- MR 已合入且任务真正完成后，Cloud 在后台启动独立经验整理子 Agent，使用任务主模型，不占主任务、不增加完成门禁。人工主动记下来、手工新增仍即时保存待审查草稿。
- 首次成功交付到 MR 时单独冻结版本，结合最终交付源版本差异、批注及否决/答复、MR 反馈和验证记录分析。首次交付不是第一个 commit；squash 使用完成时已核对的源版本，不把目标分支其他变动当任务返工。
- 按根因聚合，考虑业务规则与边界、组件与接口用法、设计与实现约束、编码规范、测试与验证、分析与工作方法六个维度，不逐类凑数，不设草稿条数上限；用正反例引导抽象，独立根因不为压缩数量强行合并。新增需求、个人偏好、无效 AI 意见不能自动升格成规范。
- 范围与维度分开：平台/仓库/模块沿用现有范围；语言、组件、版本、例外必须明确写进适用条件。候选需人修改、采纳后才检索复用，支持合并已有经验。
- 草稿统一进入团队资产 → 经验沉淀，审查页展示维度、首次问题与最终修正、版本与来源依据。过程文档保留 `交付经验复盘.md`，有候选时小鲁班通知责任人并直达审查。
- `delivery-experience/first.json` 保存首次版本，`input.json`/`output.json` 保存依据与结果，`events.jsonl`/`transcript.jsonl` 可查实际模型与工具过程，`state.json` 如实记录完成或失败。完成回调幂等，重启复用已生成结果；没有首次快照的历史任务不猜版本。失败不阻塞交付，也不反复自动消耗模型。


## 2026-09-16：经验维护与复用闭环

- 唯一入口是团队资产的「经验沉淀」，待确认、已采纳、已停用、全部记录是同一份经验库的状态视图。支持标题搜索、范围筛选、手工新增、保存草稿、直接编辑已采纳经验、停用与恢复；自然语言沉淀仍直达这里。
- 平台、业务模块、代码仓三种复用范围在编辑区维护。模块与产品版本选项读取配置中心，模块经验按当前模块—代码仓映射跨仓使用；明确版本不匹配时不返回。未限定版本仍由 Agent 核对正文条件。
- 历史保存每版完整内容、操作者、时间、维护说明和原始依据。「载入此版本」仅填充编辑区，人工保存才成为新版本；历史本身不删除。人工保存草稿后，迟到的模型输出不能覆盖它。
- 重复经验由人判断：先把需要保留的内容补入目标经验，再「关联目标并停用本条」。来源内容与历史保留，可跳转目标；不会让模型自动合并两条互相矛盾的结论。使用反馈、冲突与处理说明放在同一编辑区，保存后进入历史。
- 团队成员均可维护经验、工程知识和团队 Skill，保留登录边界与真实操作人记录。任务推送、审批等权限没有随知识维护放开。已采纳经验修改无需先撤销；修订号仅防止多人编辑互相覆盖，不参与任务流程门禁。
- Agent 后续检索、全文读取及自动记忆补充以当前状态和范围为准，停用条目不因旧向量索引而复活；已在历史对话中出现的文字不会被追溯抹除。存量数据不用迁移，未采纳记录仍然待确认。
- 本机验收覆盖普通成员新增/采纳/编辑/停用/恢复、原始证据和历史、并发旧版本提交、迟到模型、模块跨仓/版本筛选、匿名拒绝、真实 memsearch 以及桌面页面。生产部署另行执行。


状态:2026-09-03 与用户多轮对齐后定稿,进入第一期开发。配套实测见
`docs/memsearch-deploy.md`(内网 memsearch 0.4.19:CLI 冷启动 2.8s、常驻
1.2 GB、中文换说法 5/5 命中、索引可重建)。

## 2026-09-16：统一检索核心（当前实现）

本节更新检索链路，优先于下文旧稿中按仓分别检索、只靠定时推送的描述。本轮不改变经验审查权限或页面。

- 主会话、开发助手通过 `knowledge(action="search", query="具体工作问题")` 查已发布团队工程资料、当前生效 Skill 正文、当前关联模块资料和已采纳经验，通过 `knowledge(action="read", id="结果ID")` 展开。`corpus_write` 继续负责写候选。新的会话工具清单不再同时暴露旧的 `corpus_search/corpus_expand`；恢复的历史会话保留旧名兼容入口，避免在途调用失效；后台自动记忆补充复用同一检索核心。
- PI 工具提示词明确提供异步回调、YAML、首次构建 UT 示例；同一问题不反复查，新的工作内容再查。检索不可用、没有结果都不产生任务门禁。
- Cloud 按当前发布/采纳状态、仓库和模块映射生成候选清单，然后让 memsearch 在同一集合内搜索；不混排不同分区的 RRF 分数。模块映射可随当前仓库发现，不要求开局准确识别全部模块。技术标签随适用条件返回，不按不完整的开局技术画像硬排除。
- 模块资料的数字 `version` 是文档修订号，绝不当作产品版本。正文可以在 YAML frontmatter 里显式写 `product_versions: ["2.7B"]`（JSON 数组格式）；声明后按任务 `product_version` 筛选。未声明或格式无法识别时如实显示“未单独声明，请核对正文”，不从正文出现过的版本号猜适用范围，也不自动替历史资料补标签。无版本任务保留不同版本候选并显示条件。
- Skill 从当前生效货架读取，不从候选的发布回执读取旧正文；技能附件的装载仍沿用现有 Skill 运行时，本工具不宣称附件已经加载。
- 正本仍在原有资料库。`corpus/_knowledge/` 仅为可重建索引镜像，按资产稳定路径更新；不进入经验审查列表。镜像不具备独立的发布权限，搜索和展开仍由原始目录状态决定；查找期间发生修改或停用，旧结果不返回。
- 索引不嵌入审计 frontmatter。短经验将标题中的适用场景、结论和例外一起索引，避免 memsearch 丢弃只有标题的段落；长文片段携带主题，同一资产只占一个搜索结果。索引格式变化在首次读取对应文件时自动刷新，不要求人工删除数据库。
- 使用实际余弦分数过滤明显噪声，RRF 仅用于排序，不解释为可信度。BGE-M3 ONNX 使用本机样例检验过的保守噪声下限 0.50；准确命中的代码标识符可保留。其他模型不套用这个下限，须单独评估。此下限不保证没有误召回或漏召回，不用于阻止任务行动。
- 本机中文纯文本查询中的 BM25 曾返回空，因此仍依赖 BGE-M3 中文语义召回，不声称已完善中文分词。结果统一表达为候选；Agent 必须核对适用条件，必要时展开全文。
- 索引准备最多前台等待 1.2 秒，检索最多等待 1.5 秒（含重启等待）。索引作业在后台串行合并，同一修订不重复排队。只读正文不依赖 memsearch 服务。
- 知识搜索/展开 ID 写入任务使用足迹；只有经验 ID 进入经验台账，避免把团队文档错算成经验。读过不代表正确应用。

本机复现及精度边界见 [检索穿刺报告](knowledge-search-probe-2026-09-16.md)。

## 2026-09-16：经验沉淀与人工采纳（当前实现）

本节取代下文历史稿中的“闭环即可复用、无需审查、只读页签”等约定；其余历史设计保留供追溯。

- 开发现场可在“说给 Agent”中自然表达“帮我沉淀这条经验”。主会话与开发助手共用 `corpus_write`，不要求关联某条意见或文件。Agent 忠实记录原话和提炼结论，保存成功后在原对话告知“已保存、待审查”，返回直达该候选的链接；普通“这次这样改”不视作沉淀请求。没有新增现场审批卡，也不自动采纳、修改代码或推送。
- 入口统一为 **团队资产 → 经验沉淀**。任务的知识足迹只显示候选数量和导航链接，不再分散编辑、采纳按钮。
- 闭环反馈、构建修复和主动记录先形成候选。自动提炼通过 Cloud 的 `memoryDraft.ts` 旁路提示词运行；Agent 主动 `corpus_write` 同样只能提交候选。模型失败或未配置时保留原记录，允许人工修订，不重试阻塞任务。
- 提炼优先寻找可迁移的因果关系和判断方法，去掉偶然的文件名、任务号，但保留改变结论的前提。以“换仓库还成立吗、哪些情况不能照搬”检验抽象范围，不能把个人偏好或一次验证成功泛化为普遍规则。
- 审查页集中展示原始反馈、当时处理结论、候选结论与适用例外，并链接来源任务供核对实际代码与验证。没有取得的 diff 或测试证明不虚构。登录团队成员可修改后“采纳供 Agent 复用”，或“停用，保留历史”；完成的任务也可审查。未采纳不暂停、重启或推进原任务。
- `review.status=accepted` 是复用资格；`judged_by=human` 只是来源中的判定者，不能等同于经验已获采纳。没有明确采纳记录的历史条目保留为待确认，不做静默追认。
- 采纳时可选本仓相关位置、本仓通用、跨仓通用，或仅检索参考（one_off，不主动推荐）。跨仓范围会同步调整索引源路径，来源仓信息仍保留。适用例外与结论一起保存、检索和注入，不能只推送脱离前提的短结论。
- 原始依据保留在 `basis` 中，人工编辑前的候选保留在 `review.original`，修订追加到索引历史。正在生成的模型草稿不得覆盖人工保存过的草稿或已处置内容；旧页面提交以实际版本冲突提示重新查看。
- 手动搜索、展开、每轮自动上下文都按当前采纳状态和范围读取。撤销采纳后，下轮临时上下文即移除，即使侧车索引或会话 ID 缓存尚未刷新。不能清除 Agent 已经读过的历史信息，也不自动回滚已生成代码。
- 向量检索仅索引已采纳的记录；重建不纳入候选。没有语义检索服务时仍可记录、审查、按 ID 展开已采纳经验；自动推荐需要检索服务正常运行。
- 使用足迹能证明提供、搜索和展开，不能直接证明被正确应用或代码质量提升。是否改善结果仍需结合代码和实际验证判断。

验收覆盖：候选隔离、人工权限、跨仓迁移、实际下一任务上下文、例外保留、撤销与缓存、重启、迟到草稿、无模型兜底及桌面交互。

## 一页纸

- **平台不建知识库,平台有记忆。** 知识在仓和团队 Skill 货架;平台只记住
  自己干过的活,让下一单少踩一遍坑。
- **需求流零知识负担**:闭环即入库,人不做标记、不填问卷、不审核记忆。
- **来源只有一个标准**:一个被人或权威来源关掉的环。第一期收三种:闭环的
  检视意见、推送前构建修复、人圈选「记为记忆」。
- **记忆不用筛干净,只要排得对**:低质的沉底,错的被覆盖,老的衰减,
  失锚的不推,反复出现的升成 Skill。全部自动。
- **消费由宿主定时机**:开局、阶段切换、首次改目录三次替 Agent 查并推送;
  `corpus_search` 只给追问。Agent 不会自己想起来查,不指望它。
- **正本是 md 文件,memsearch 只是索引**,删了能重建。
- **可见但不可管**:任务面板「这单记下的 / 这单用到的」、执行现场里的推送
  事件、团队效能页只读页签。没有编辑页、没有人用的检索门户、没有分类管理。

## 1. 定位与边界

| | 系统的知识 | 记忆(本稿) |
|---|---|---|
| 从哪来 | 人写的:docs、AGENTS.md、Skill | 干活的副产品:闭环的批注、修复、圈选 |
| 谁拥有 | 有作者、负责人、版本 | 没有作者,任务过程自动留下 |
| 住在哪 | 仓里、团队 Skill 货架 | 部署数据目录 `corpus/`,索引可随时重建 |
| 谁维护 | 人整编、上下架 | 没人维护,只增不改,久了自然沉底 |
| 给谁用 | 人和 Agent | 只给 Agent,在下一单干活时用 |

刻意不做:语料编辑页/管理页;面向人的检索门户;分类体系(位置就是分类);
第二真相源(索引以外不存副本);把 Skill 或仓内 docs 丢进索引(暂缓,见 §10);
让人给记忆打分或审核入库。

记忆里反复出现、值得成为正式知识的,走提案进团队 Skill 货架(另案「所有
资产都是 Skill」)。平台没有第二个知识源。

## 2. 两条流

- **需求流**只做两件事:消费知识、产生语料。过程中没有"沉淀"按钮、没有
  收口问卷、没有"这条是规矩"标记。
- **知识流**是另一个工作面(Skill 货架 + 修订收件箱),有自己的人和节奏。
  本稿不展开。

两条流之间只有两个只读接口:语料库(需求流写、Agent 读)、货架(知识流
写、需求流读)。

## 3. 语料记录契约

一条记录 = 一个 Markdown 文件(memsearch 按文件与标题切块,frontmatter 进
元数据;一条记录切出两三块,每块自带标题,搜到哪块都能读懂,`expand` 一次
就是整条)。

```markdown
---
id: c-000412
source: annotation            # §4 来源表
judged_by: human              # human | pipeline
scope: local                  # one_off | local | general(§5;user_note 固定 general)
repo: notify-service
paths: [src/main/java/com/x/filter/FilterEngine.java]
line: 88                      # 可选
module: 通知                  # 可选
phase: 写代码                  # 内核七段词表之一;来源决定,不猜
task: task-38
evidence: annotation:a-91     # 可回溯到现场的指针
supersedes: c-000390          # 可选:覆盖旧记录
at: 2026-09-01
---
# 改 FilterEngine 的过滤顺序时

## 原文
> if (channelEnabled) { blacklist.check(...) }

## 问题
黑名单判断放在了渠道开关之后,被关掉的渠道也会跑黑名单。

## 结论
黑名单判断必须在渠道开关之前(diff 见 task-38 批注 a-91 的回应)。
```

- 标题 = `trigger`(什么情况下);正文固定「原文(圈选或锚点快照,可空)、
  问题、结论」。五个问题每条都答:什么情况下、预期、实际、怎么解决、谁判的。
- 只追加不改写。要改就追加一条带 `supersedes` 的新记录;撤回也是追加
  (结论为空、`supersedes` 指向被撤回的)。
- 单条正文上限 2000 字,超过拒收并提示「这更像一条 Skill,去货架提交」。
- 目录:`<data>/corpus/<repo>/<yyyy-mm>/<id>.md`;跨仓的放
  `<data>/corpus/_module/<module>/`。另有 `<data>/corpus/index.jsonl` 按
  任务号、来源、状态做轻量索引,供任务面板与效能页读,不进检索。

## 4. 来源

标准只有一条:**一个被人或权威来源关掉的环**。

| `source` | 触发时刻 | trigger / 原文 / 问题 / 结论 从哪来 | judged_by |
|---|---|---|---|
| annotation | 批注路由给 Agent、回执 fixed、人确认通过 | 锚点位置 / 锚定原文 / 意见 / 回执 summary | human |
| prepush_fix | Build-Fix 失败后修好并通过 | 构建文件 / 报错首行 / 报错原文 / 修复 diff 摘要 | pipeline |
| user_note | 人在材料上圈选「记为记忆」 | 锚点位置 / 圈选原文 / — / 人写的一句话 | human |
| requirement_revision(二期) | 需求确认每轮修订被确认 | 锚点 / 原文 / 意见 / 该轮 diff 摘要 | human |
| pipeline_repair(二期) | 流水线失败→修复环收口(绑 SHA 绿) | 平台事实 / — / 失败原文 / 修复回执 | pipeline |
| mr_discussion(二期) | MR 平台检视讨论闭环 | 讨论位置 / — / 意见 / 回执 | human |
| assistant_takeover(二期) | 开发助手交还且有变更 | 变更文件 / — / 人的指令 / 助手总结 | human |
| decision_override(三期) | 决定卡人选了自定义或非推荐项 | 问题 / — / 推荐项 / 人的说明 | human |
| chain_rework(三期) | 拆分方案退回后再确认 | 方案 / — / 退回原因 / 新旧差异 | human |
| issue_rca(三期) | 问题流根因分析确认并修复验证 | 结论 / — / 现象 / 修复与验证 | human |

不进库:原始事件流、Agent 自述、未验证回执、Agent 自己一次走通的路
(没人判过它对)、许愿墙。入库是旁路:写失败只记日志,绝不影响任务流程。

### 4.1 「记为记忆」

批注框在「给 Agent」「给负责人」之外加第三个去向「记为记忆」。圈选一段、
写一句话、提交:不发给任何人、不进决定卡,直接落一条 `user_note`。
位置从锚点来(代码/变更 = 文件+行,过程文档 = 文档名,需求原文 = 任务级),
引文是圈选原文快照。记忆条目不参与重锚定和回执,是快照。批注面板里以
「记忆」条目只读展示。空口一句缺的就是引文和位置,圈选自动补齐。

## 5. 质量:不筛,只排

- **结构过滤**(免费):annotation 只收「路由给 Agent、回执 fixed、人确认」
  三件套齐的;prepush_fix 只收失败后真通过的。
- **范围标签**:入库时一次主模型短调用(单发、无工具、预算 90 s——旁路不在主会话路上,内网网关慢就给宽)起草
  `trigger` 并打 `scope`:one_off / local / general,依据不只是意见原文,
  还有回执摘要与 diff。one_off 和起草失败的只进全文检索,不进推送与目录
  摘要。user_note 不过这道,固定 general。**三期已落**:入库那一刻先用模板
  (「改 <文件> 第 N 行附近时」)落盘，随后使用任务当前主模型异步单发起草。
  无需单独配模型；任务未单独选择时使用平台主模型。90 s 预算、无工具，失败保留候选，
  不带主会话历史、不自动重试，也不补跑历史候选。回来后在同一条记录上收尾：md 更新标题与范围，
  索引追加一版(revision+1,读侧取最后一版),人写的原文/问题/结论一字不动;
  模型出错或形状不对标 `draft: failed`、模板保留。这不是改写别人——是平台
  自己那条记录几秒内的收尾。
- **权重**:judged_by(human > pipeline)× 时间 × 反复出现。推送只取前几条,
  低质的排不到眼前;某目录只有它一条时给出去也不算错。
- **措辞**:推给 Agent 的是「2026-09 有人在这里要求过 X」,不是「必须 X」。
  它是线索,判断仍在 Agent 与后面的门禁。
- **覆盖**:同一位置后来出现相反结论,新记录 supersedes 旧的,旧的权重归零。
- 认一条风险:scope 是模型判断,会误标;误标只影响推不推,不影响进不进库。

## 6. 老化:自动沉底,不删

- **时间衰减**:排序带时间因子(一年减半)。推送每条带日期,Agent 自己掂量。
- **失锚**:消费时宿主用这单的仓 `existsSync` 记录路径,文件没了或挪了标
  失锚,不再推送,只留全文检索。与批注重锚定同一思路。
- **被覆盖**:`supersedes` 链。
- **效果反馈**(三期已落):台账 `corpus/ledger.jsonl` 只追加记 push/search/
  expand/rework/unanchored/archive;推过的记忆所在文件在同一单里又被人提了
  意见(路由给 Agent 的代码批注)→ 记一笔 rework,权重每笔减 0.4(命中每次
  只加 0.1),同单同条只记一次。权重公式在 `memoryWeight`:
  人判 1.0 / 流水线 0.6,一年减半,general +0.1,下限 0.05。
- **沉底**(三期已落):失锚超 180 天、或入库超 365 天且从未被推送/命中的,
  md 移到 `corpus/_archive/` 同路径,台账记 archive;不进索引但文件仍在、
  仍可读(总览页勾「含已沉底」)。扫描起服务 30 s 后一次、之后每天一次;
  归档了东西就让 sidecar 重建索引,重建没完成前归档的仍可能被搜到——如实
  记日志。失锚只在真现场(有 .git 的 cwd)里记账,假 cwd 不算。
  与现场保留期同纪律:不删历史。
- **升级**:反复命中的升成 Skill 后,记忆加「已入 Skill X」指针,推送时优先
  给 Skill。

## 7. 检索旁路进程(sidecar)

宿主是 Node,memsearch 是 Python;CLI 冷启动 2.8 s,所以必须常驻。

- 宿主启动时拉起 `memsearch-run`(包装脚本带 HF_HOME/OFFLINE/TMPDIR/
  milvus.uri),stdio JSON lines;挂了自动重拉,退避与次数上限。
- 四个动作:`health`、`ingest {path}`、`search {query, repo, path_prefix?, limit≤8}`、
  `expand {id}`。
- 预算:search 1.5 s、expand 1 s、ingest 5 s、health 500 ms。超时返回空结果加
  一句「检索暂不可用」,绝不卡 Agent。
- 单 writer:ingest 宿主侧串行。资源:常驻 1.2 GB,部署预留 2 GB,写进 preflight。
- 索引与正本分离:`milvus.db` 可删,`corpus/` 是正本;preflight 含「删索引→
  重建→对拍」演练。

## 8. 消费:三个时刻 + 一个工具

1. **开局**:按这单的仓和负责面 `search`,结果并进开局使命(≤8 条,每条
   一行结论 + 日期 + id)。
2. **阶段切换**:内核步骤进入定规格/写代码等阶段时按范围再查,以插话送入
   (两行:几条、在哪、建议先读)。与「提醒 Agent 使用」同一送达路径,不碰内核。
3. **首次改某目录**:工具钩子看到 Edit/Write 路径,该目录有语料且本会话未
   提示过,附一句(最重的一条 + id)。每目录每会话一次。钩子不能「放行加
   一句」就退回插话。

工具 `corpus_search` 经 pi 扩展 `registerTool` 注册在门禁扩展旁,所有会话
自动同有。参数 `query`、`path_prefix?`、`limit?`;`repo` 宿主固定,不能跨仓。
`promptGuidelines` 写动作锚定的触发:「改一个没改过的目录之前、修一个报错
之前、对某个约定拿不准的时候,先用 corpus_search 查这个仓的历史语料;结果
里的 id 可用 expand 看全文」。不给 Agent 写记忆的工具(人说「记下来」走
圈选,见 §4.1)。

推送与工具结果都进知识足迹(kind: corpus)。

### 平台范围与当前工作召回（2026-09-14）

`scope: platform` 表示跨仓库适用，存于 `corpus/_platform/`，`repo/task/author`
仍保留原始来源。`local/general` 继续只适用于来源仓库；旧 general 不自动升级，
以免把某仓约定广播全平台。Agent 可通过 `corpus_write` 显式选择 platform，
但来源始终是 agent_note，不因此变成人工决定。平台范围必须来自明确适用条件，
不能仅凭“平台记忆”等正文措辞推断权威。已有条目须核实范围后重新记录，不能只改
md 的 scope 而不更新索引与存储位置。

侧车分别查询当前仓和平台目录，再合并结果；Cloud 对结果按当前正本核对范围、
撤回、替代和归档状态，展开采用相同条件。跨仓平台记忆不受来源仓相对路径失锚限制。
开局（含反馈修复重启）与阶段切换按当前使命、最新用户补充及失败证据检索，原始需求
仅作补充。开局结果与使命一起注入，并记录查询和条目 ID；不增加等待审批或执行器门禁。
索引不可用沿用现有有界降级；Agent 仍可主动 search/expand 深挖。

提示词保留来源和范围，不把历史经验与明确人为约定一概降格为无约束线索；同时明确
Agent 记录不等于人工决定，当前用户要求优先。每次至多推送 8 条，结论保留原文，
附带 ID 供展开。使用足迹证明查询/选取，不等于证明模型已经遵守。

参考 memsearch 官方集成方式：
[SDK 示例](https://github.com/zilliztech/memsearch/blob/main/docs/getting-started.md)
采用 recall → think → remember；
[DSH 插件](https://github.com/zilliztech/memsearch/blob/main/plugins/dsh/README.md)
在第一步按当前问题有界检索并注入，也保留按需深挖。这里复用现有 Cloud 交接点，
不引入第二套记忆服务，不把召回结果作为自动授权或质量证明。

### 模型调用前统一召回（2026-09-14，取代上述阶段注入）

主任务与开发助手的 PI `context` 事件成为唯一自动记忆注入入口；同一个阶段内，
新的用户输入或工具文本结果也能触发召回。每个 PI 会话独立建立检索缓存，子会话不共享
查询状态。只使用可见用户/工具文本与当前使命，跳过 assistant 思考、图片和本模块注入。

查询最多保留最近三条用户/工具文本及当前目标，长结果保留首尾。相同查询 30 秒内复用
ID，正本每轮重新读取，撤回/替代/归档即时过滤；缓存刷新只是性能策略，不是流程门禁。
侧车未就绪时不等待冷启动；检索默认预算为 3000ms，前台上下文预算跟随侧车实际预算并多留 500ms（默认 3500ms），避免外层抢先丢弃正常秒级结果。同会话只允许一条在途查询，真正超时仍降级继续任务。
超时照常调用模型，迟到结果仅在查询仍一致时可供后续轮使用。没有结果不注入；不拿随机
高权重经验填充。Agent 的 corpus_search/expand/write 工具保留。

临时 custom 消息只进入本次模型请求的副本，不改工具结果和原生会话历史，不在每轮累积。
旧 memoryBriefing、阶段 steer、首次改目录提醒和相应目录摘要生成路径已删除。
旧使用足迹仍可展示；新 context 足迹记录查询、条目和是否可用，表示准备提供的上下文，
不声称模型已经遵守，也不替代授权或验收。记忆故障不得阻断代码工具或推进任何任务状态。

当前是有界接入验证，不是召回质量保证。真实生产回放仍需验证长日志中部信息遗漏、
跨问题混合查询的准确率、额外耗时，以及相关记忆是否在无效探索前实际送达。
