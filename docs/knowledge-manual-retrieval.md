# 长手册的分块与检索

原始 MD 仍是唯一正文。发布后的团队工程文档、模块知识和已采纳经验由现有 `knowledge` 工具消费；不新增 Agent 阅读审批，也不把整本手册注入系统提示词。

## 分块规则

`harness/knowledge_chunks.py` 按 Markdown 标题树划分主题。较短主题保留子标题、规则、示例与例外；超过约 6000 字符的主题继续沿子标题拆分，无子标题时在段落边界拆分。围栏代码块、表格和不可再拆的长段落允许超过软预算，不为了长度截断内容。支持 ATX/Setext 标题、反引号/波浪号围栏、CRLF；文档 frontmatter 不进入语义正文。

这是结构化分块，不是模型重写。不能保证相隔很远的例外自动归并；片段带完整标题路径和原文行号，Agent 需要根据前后章节继续核对。缺少标题的混合长文档仍可按段落检索，但应补充清晰章节以改善定位。

索引文本附带资料主题和章节路径，原文不修改。向量索引仍用 memsearch，关键词 BM25 与语义向量共同召回。统一知识查询允许同一手册的多个相关章节返回；旧记忆查询继续按经验记录去重。排名代表候选相关性，不是规范正确性的证明。

## 发布和读取

- 服务启动以及知识发布、编辑后的成功响应会启动后台预索引。不同版本共享去重队列，旧片段在新片段写入成功后清理。
- 长手册向量化在后台运行，可等待最多十分钟；搜索的索引等待仍有短预算，不能把这个后台预算变成任务等待时间。
- 部分资产未就绪时，查询已就绪资产并明确说明结果范围不完整。侧车忙碌或不可用时照常返回不可用，不把它解释成没有规则。
- 查询结果包含文档 ID、章节路径、原文起止行、版本和适用条件。`knowledge(action=read, id=..., start_line=..., end_line=..., revision=...)` 直接读取命中原文。
- read 每次最多 600 行、通常不超过 24000 字符，提供继续读取行号，不再无提示地截断整份输出。独立超长行仍作为一个原文单位保留。
- 文档版本变更后旧行号提示重新搜索；停用和产品版本过滤仍查当前正本。此检查只保护引用正确性，不阻塞开发流程。

## Google C++ Style Guide 实测

公开来源：[Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html)，Google，CC BY 3.0。该规范只用于检索评估，不默认发布成团队规范。

探针在指定输出目录的独立语料和 Milvus 数据库里使用真实本地 ONNX 模型，覆盖中文开发意图、接口名查询、原文位置、代码围栏边界以及文档替换后的旧片段清理。重复执行复用该目录的索引。输入来源、内容 SHA256 和逐条结果写入报告，不使用生产语料。

2026-09-17 本机实测（memsearch 0.4.19、`gpahal/bge-m3-onnx-int8`，CPU）：

| 验证项 | 结果 |
| --- | --- |
| 全文分块 | 5713 行、123 个片段，最长 6370 字符 |
| 原文完整性 | 非空行全部覆盖、不重叠、围栏代码块未截断、行号逐块匹配 |
| 14 个具体问题 | 正确章节全部进入前 5 个候选；11 个排第一 |
| 2 个无关问题 | 均无命中 |
| 文档替换 | 旧片段全部移除 |
| 整本手册首次索引 | 593 秒；重复索引无需重新向量化，约 0.01 秒 |
| 索引就绪后的查询 | 本轮 14 题各 13–26 毫秒（Python 侧车内，不含上层网络开销） |

初次实测有 3/10 个查询未命中目标章节；原因之一是 `C++` 这种全书常见词干扰关键词排名。统一章节检索现在只用有区分度的词或代码标识符补充关键词排名。修正后原 10 题全部进入前 5；另加 4 题和 2 个无关问题复核。以上是这份手册的小样本检索结果，不代表所有内部文档的准确率，更不代表 Agent 已正确应用规则。

## 一个具体的输入和输出

输入整份 Google 手册后，Agent 问：

```text
knowledge(action="search", query="对象所有权转移时应该使用哪种智能指针？")
```

实际首位命中 `Google C++ Style Guide > Other C++ Features > Ownership and Smart Pointers`，对应转换后的原文第 1948–2050 行，共 103 行。Python 探针的索引镜像有 4 行元数据前缀，因此底层记录为 1952–2054；Cloud 工具会减去镜像前缀，返回原始资产的行号。

```text
knowledge(action="read", id=<搜索返回的文档ID>, start_line=1948,
          end_line=2050, revision=<搜索返回的版本>)
```

read 返回这一节的原文，而不是模型改写的结论。Agent 需要核对其中单一所有权、共享所有权及各自适用条件，再选择实现。实施规划使用现有 Task 工具派发 `component-knowledge-agent`；它复用同一 knowledge 工具，查阅原文后将组件与规范补入指定的 implementation 文档。

## 团队资产入口

团队资产的“知识库”分为文档和 Skill 两个入口：文档包含手册、规则、模块资料与已采纳经验，使用 knowledge 按章节检索；Skill 通过原生技能目录发现并按需加载，不进行语义分块、索引或试搜。既有资料直接读取原记录；需要维护 Skill、原模块资料或经验时进入原维护界面并可返回知识库。“经验沉淀”继续处理现场经验的待采纳草稿，不复制已采纳记录。

“上传知识”支持直接上传 UTF-8 Markdown（最大 2 MiB），也支持指定 HTTP/HTTPS Git 仓库、分支与文件路径导入。仓库导入复用操作者个人 Git 凭据沙箱，只读取普通 Markdown blob；不检出文件、不运行仓内脚本、不跟随符号链接。记录来源仓库、分支、路径和提交版本，使用“从仓库更新”主动刷新。更新失败保留旧文档。原文件正文保存在 `knowledge-documents/` 原子记录中，操作者与修改时间一并留痕。

语言、范围、模块和产品版本使用现有选择组件；模块和版本选项来自配置中心。索引状态由真实后台作业提供，可重试失败项。试搜和 Agent 使用同一检索服务，试搜限定当前资料，返回原文行号；停用后不再参与检索。页面支持 1920×1080 和 1366×768 桌面窗口。


## 实施计划中的组件分析

Cloud 的 Task 工具提示词在存在 knowledge 能力时引导主 Agent：涉及组件选型的实施计划先派发一次 `component-knowledge-agent`。任务卡带上需求、仓库、业务模块、语言、产品版本、准确代码入口与计划路径。子 Agent 按具体能力检索，而不是整本注入手册；核对原文章节和真实 API 后，把“组件/API、用法、异常处理、适用条件、来源”写回该计划，并对应具体实施任务。

主 Agent 派发期间不同时编辑该计划；收到报告后读取并落实结论。新问题补查，已确认内容直接复用。纯文案等无组件变更不要求派发。索引不可用、无命中和接口不匹配分别报告，按现有代码证据继续；无法派发时主 Agent 自行完成分析。没有新增审批、状态机或完成门禁，因此提示词引导不能被表述为每次都强制执行或保证代码符合全部规范。

子会话只继承 `knowledge`，且闭包仍绑定主任务的仓库、模块与产品版本范围；不会继承推送、阶段推进、经验写入等其他扩展工具。此修正也使原有 Story、实现或检视子 Agent 可以按需查阅同一套知识。知识使用沿用现有日志。

本机端到端探针（独立虚构组件和资料，不写生产知识）:

```bash
npx tsx harness/component-knowledge-probe.ts
```

默认读取 `.local/models.json` 的 `glm` 配置和本机 memsearch 环境；可用 `COMPONENT_MODELS`、`COMPONENT_PROVIDER`、`COMPONENT_MODEL`、`MFC_MEMSEARCH_PYTHON` 指定已有配置。输出报告、任务轨迹和实际 implementation 文档用于人工核对；脚本化回归仅验证工具传递及文件更新，不冒充真实模型理解准确率。

### 2026-09-17 真实模型消费验证

本机 `glm-5.3-flash` + bge-m3 ONNX / memsearch，使用独立虚构的报表导出需求、平台文件规范和模块网元查询规范。任务只要求完善计划，未指定必须派发；实际主会话派发一次组件子 Agent，主/子共调用 knowledge 5 次（1 次搜索、4 次原文读取），子会话正常返回。

实际计划采用 `AcmeFileWriter` 与 `NeConfig::getName`，保留禁止 `std::ofstream`/`fopen`、创建者释放/借用者不释放、查询空值报错的规则及来源 ID；原有任务和四项验证保持不变，未修改业务代码。此样本验证“知识到实施计划”的真实链路，不代表所有知识都能正确应用，也不是业务实现/编译合格证明。首次受限工具探针漏开放 Task/knowledge，已纠正探针工具列表；该次无效试验不计入成功结果。

补充实测：显式委派的一轮同样完成主/子链路，但在 `open` 失败后是否调用 `close` 上，用常见库习惯推断覆盖了文档要求。已在子 Agent 指引中明确：不能以惯常做法覆盖原文；API 不支持时标冲突/待核实，不可声称采纳后写相反方案。此例说明“成功检索并引用”不等于“每条规则都正确应用”，不应把该能力宣传成编码规范的强制合规校验。


Skill 与普通 MD 的消费路径明确分开：团队技能包沿用 `materializeHostSkills` 与 PI 技能发现；模块 Skill 沿用 `businessModuleRuntime` 产出的 `SKILL.md` 和 `skill_paths`。管理界面在知识库内读取当前技能说明并完成维护，但 knowledge 的 search/read 及后台 prepare 均不包含 Skill，也不会从旧向量记录恢复 Skill 结果。


### 模块隔离与目录导入（2026-09-18）

需求的 `business_module` 优先决定 knowledge 检索范围，子任务使用父需求的模块。旧任务没有归属时沿用显式选择的模块；没有选择时仅在仓库唯一映射一个启用模块的情况下自动匹配。仓库映射多个模块且没有选择时提示歧义，不把全部模块混在候选中。平台通用文档仍可检索。search 和 read 共用范围筛选，旧向量命中也不能绕过。语言作为适用条件交给当前行动核对，避免混合语言仓在开局过滤掉后续需要的知识；产品版本有明确声明时按版本筛选。标错为平台通用的业务规则不能靠语义匹配自动纠正，上传者应正确维护范围。

CodeHub 导入可读取 Markdown 文件树，勾选单个文件或文件夹。目录勾选展开为本次树中所有 Markdown 路径，导入固定在浏览时的 revision；分支随后变化不会混入本批内容。每批最多 200 篇、单篇 2 MiB、总内容 32 MiB；符号链接、二进制、Skill 包及包内引用文档不混入普通知识。服务只读取 Git 对象，不执行仓内代码。

每篇文档分别存储 `source.repository / branch / path / revision`，原文不拼接、不改写。完整相对路径与文件名参与检索，列表显示路径，搜索结果携带来源路径供 Agent 判断。相同文件名在不同目录下分别存储；同一来源与相同模块/仓库/语言/版本范围重复导入更新原记录，避免制造重复命中。目录不自动推断业务模块；一次导入的文档共用表单所选范围，不同范围应分批导入或导入后调整。部分文件失败会列出具体路径，成功部分保留，只需重试失败部分。

本地验证包括真实 Git 固定版本批量读取、同名不同路径、链接与 Skill 排除、批量接口重试不重复，以及共仓模块相反规则隔离与子任务继承。另以 Google styleguide 的 `gh-pages` 真仓验证文件树，勾选 `docguide/` 的 5 篇文档和根目录 `README.md`，导入 6 篇并保留两个不同路径的 README。
