# Issue 413：打开任务时，大日志读取阻塞其他请求

## 现场证据与原因

[Issue 413](https://github.com/yunine9/mae-flow-cloud/issues/413) 报告的部署版本是 `bad09415`：任务 15 的事件日志约 40 MB，批注接口耗时最高 29.4 秒；任务 20、43 分别约 34 MB、19 MB。诊断记录显示事件循环占用 100%，延迟约一秒，CPU 热点集中在 `readAppendOnlyJsonl` 和 `readFileSync`。批注文件本身最多约 339 KB，体积不是主要原因。

代码调用链与报告吻合：`listAnnotationsAsync → annotationReply → EventLog.replay → readAppendOnlyJsonl`。接口虽有 async 名称，但查找批注提交后的几段回复时，仍会同步读取、解析整份事件日志。Node 主线程被占用后，普通文档请求也一起等待。前一版对入口和文档列表的优化没有消除这条调用链。

横向检查还发现，会话接口会重复读取同一日志，插话、活动、开发助手和时间线也各自读取完整历史；原始 SSE 首次连接时一次读取并发送整份历史。这些入口同时打开，会放大同一问题。

## 修改

- 页面查询共用一个只读增量索引。首次以 64 KB 分块异步读取，每块后让出主线程；同任务的并发请求共用一次读取。日志未变化时不读正文，追加时只读新增字节。
- 索引只保留页面需要的事件字段，工具的大段原始输出继续保留在源日志和执行过程里。缓存按最近访问淘汰，限制为 16 个文件、约 32 MB；不缓存送达判定等实时任务状态。
- 批注回复保持原有规则：最后一批提交之后，主会话最先出现的八段非空回复，每段最多 1500 字，并保留截断提示和旧 UTC 时间格式兼容。
- 会话、插话、活动、开发助手 GET 和时间线使用同一索引。时间线的构建历史也分块读取；原始 SSE 每次最多读取 256 KB，并等待客户端消费，避免一次性发送全部历史。
- 页面读取不再调用恢复回放，不会修写或截短源日志。坏行跳过，未写完的尾行等待后续追加；文件替换、截短或等长改写后重新读取。执行与恢复使用的 `EventLog` 规则不变。

## 验证

本机合成约 40 MB 日志，包含 2048 条工具大输出；以下是单次本机实测，不代表内网部署后的耗时：

| 场景 | 结果 |
| --- | --- |
| 单独首次读取索引 | 40 ms；读取过程中最大计时器间隔 1 ms |
| 六个真实 HTTP 查询并发首次读取 | 约 63～66 ms；历史正文总共只读一遍 |
| 大日志仍在读取时打开普通文档 | 2 ms，早于大日志读取结束返回 |
| 后续批注 / 会话查询 | 3 / 4 ms，不重读历史正文 |
| 追加一条回复后查询 | 3 ms，只读取追加字节，立即包含新回复 |

新增测试覆盖并发读取、追加、缓存淘汰、UTF-8 半行、缺换行尾行、日志替换、展示内容一致性、插话状态即时变化以及 SSE 慢客户端与超长行。真实 HTTP 测试禁止调用 `EventLog.replay`，六个查询仍正常返回。相关现有业务测试 144 项通过，包含批注、会话、插话、开发助手、时间线、事件恢复和服务响应性；类型检查通过。

临时 HTTP 服务在测试结束后全部关闭并删除测试数据。保留预览实例未重启。

## 部署后核对

部署包含本修复的版本后，重复打开原任务 15、20、43 及其文档。已有 `[http-timing]` 和 `[runtime-diagnostics]` 会继续记录慢请求与主线程状态；新增 `[display-events]` 在读取超过 250 ms 或存在坏行时记录读取字节数、解析行数及耗时，不记录文档和工具正文。首次读取允许加载历史，后续轮询应只读新增字节，且不再出现批注请求触发 `readAppendOnlyJsonl` 全量回放的 CPU 热点。

本机未连接内网生产实例，生产上的实际延迟仍需部署后用这些记录核对。
