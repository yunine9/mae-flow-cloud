## 2. 目标形态

### 2.1 领域线：知识工厂

```
资料/无线豆包/源码 ─▶ 研究任务 ─▶ 草稿 ─▶ 文稿审查 ─▶ 发布(平台验收版本) ─▶ MR 交付 ─▶ 业务合入
                                     ▲                         │
                                     └── 增量更新 / 人工修订 ◀──┘
```

- **平台上的"已发布"= 平台验收版本**，供人在知识库阅读、作为增量更新基线。它**不进入任何需求单**。Codex 在途的"发布先写平台、再异步提 MR"（domainKnowledgeExtraction.ts:547-562）保留，但语义从"生效"改为"验收"。
- **MR 合入才是交付**。界面上平台发布与 Git 交付分开显示，交付状态由后台跟踪。
- Git 不反向覆盖平台正文（Codex 已改，knowledgeMrPublisher.ts refresh 段）；归档内容与平台版本不同时如实提示。

### 2.2 组件线：生产 + 消费

### 2.6 修改意见与版本：闭环的是"一次修改"，不是知识

用户 2026-10-02 追问："什么时候可以对领域文档和组件知识提修改意见？闭环后是不是就不能改了？"答案：**任何时候都能提，闭环后也能改**。被"闭环"的是一次修改（一条意见、一次修订），知识本身没有终态。

三个对象，各有各的生命周期：

| 对象 | 是什么 | 怎么闭环 | 闭环后 |
|---|---|---|---|
| 版本 | 某篇知识在平台上的一次发布（v1、v2…），身份 kd-id 不变 | 发布即定稿，**版本内容不可变** | 只能产生新版本，旧版本保留可读、可比较、可恢复为新版本 |
| 修订 | 从某个基线版本出发的一次改动（人直接改，或交给 Agent 的更新任务），产出草稿 | 草稿审查后发布成新版本，或明确放弃 | 再改就开新修订，以最新版本为基线 |
| 意见 | 人对某个版本某处（行 / 选区 / 整篇）的批注 | 人标记"已解决"或"不采纳（附理由）"；Agent 说已修复不算 | 不能重开，可以在新版本上提新意见；历史意见保留 |

**意见必须绑定版本**（kd-id@revision + 位置）。版本更新后：原位置能唯一定位就跟随；定位不了就保留原文、显示差异、标"针对旧版本"，不自动解决。

**什么时候能提、提了触发什么：**

| 阶段 | 领域知识 | 基础组件 |
|---|---|---|
| 研究中 | 可以提，排队到本轮结束后一起处理，不打断运行 | 同左 |
| 草稿待审查 | 主战场：行级意见 → 交给 Agent 修订或自己直接改；发布前每条意见要么解决、要么明确保留 | 同左 |
| 已发布，MR 未合入 | 小改直接编辑 → 新版本，**追加进同一个未合入的 MR**；需要查证 → 交给 Agent 更新 → 新草稿走审查 | 发布即被下一张需求单使用；改动同样产生新版本 |
| MR 已合入（领域）/ 已被消费（组件） | 照常可改，下一次改动开新 MR | 照常可改；见下方"组件改版的副作用" |
| 外部来源 | 业务在 MR 上的评论、业务直接改了仓里的文档 → 平台拉回来，作为"外部意见 / 远端差异"挂到该知识上，由人决定吸收进新修订还是保留平台版本；**绝不自动覆盖任何一方** | 需求单里的误报、豁免、范式缺口、检视中指出的"造轮子" → 作为该组件知识的意见进入治理，可一键转成修订 |

**组件改版的副作用**（领域不进需求单，没有这一层）：

- 在途需求单**钉住开工时的组件知识版本**，计划校验按钉住的版本做，不因中途改版报错。
- 普通改进只供之后的新需求单使用。
- **纠错或撤回**（发布时明确标记）要通知引用了该版本的在途需求单重新核对（#447 Q10）。
- 源内容变化的规则退回"只记录"，由负责人重新启用（现有机制保留）。

**现状缺口**（2026-10-02 代码核对，按严重度）：

1. 领域 MR 合入后，若业务在仓里改过该文档，平台把同步标为失败且不显示；推断之后所有归档都会在"已合入文档尚未同步"处失败，人工核对也解不开（knowledgeMrPublisher.ts:81-83 与 :216-219）。需要先用测试复现，再改成"显示差异、由人决定"。**已在第 0 批修复（d3b27327）**：测试复现属实（吸收远端与保留平台版本两条路都卡死），现在记为"远端待核对"、人核对当前远端后可继续发布；后台轮询与 MR 评论导入仍待后续批次。
2. 意见不绑定版本，界面只有整篇意见（knowledgeReviewNoteTypes.ts:4；KnowledgeReviewNotes.tsx:29）。
3. 组件知识被归档页、版本恢复或旧页面改过后，研究记录的基线落后，"更新知识"被永久拒绝（componentResearch.ts:480）。
4. 已发布组件知识上的意见只能保存，不能交给 Agent；阅读页对组件不带更新说明（knowledgeReviewNotes.ts:105；KnowledgeModuleReader.tsx 更新对话框）。
5. 需求单读组件知识是实时最新，没有钉版本；改版、停用、删除都不通知在途任务。
6. 业务在 MR 上的评论完全不导入；MR 状态只能手动刷新。
7. 消费侧反馈只亮"需要复核"，不能转成修订；范式缺口不回流。

## 4. 界面方案

基线是 #447 评论里的拍板与 Codex 已做的新知识库。整改要解决的是审计发现的问题，按严重度：

**P0：路径断裂或与拍板相反**
1. 任务详情里的知识链接（KnowledgeFootprint.tsx:245、ComponentKnowledgeCheck.tsx:21）、配置中心组件仓链接全部落到旧页面 → 改指新阅读页，删 legacy 页。
2. 同一对象多个页面（业务知识 3 处、Skill 4 处、工作流 2 处）→ 每类对象只留一个页面。
3. 状态叫法：同屏出现"待处理 / 待检视 / 待审查 / 新稿 / 待审核"，且前端各算一套 → 后端给唯一 status_label，全流程统一"待审查"；浏览器测试夹具改用后端真实文案。
4. 组件萃取方法维护入口被暴露（KnowledgeResearchCreate.tsx:34），与"暂不开放"相反 → 组件模式隐藏。
