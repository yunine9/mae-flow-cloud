# 分支同步后的交付范围与失败恢复

针对 task-27 报告的范围整理失败，Cloud 有两处比较口径不一致：MR 贡献已按目标分支共同祖先计算，工作区展示及平台目录历史仍优先使用任务创建时的提交。合入更新后的 master 时，后者可能把上游文件误认成本次新增。

现在交付快照、同步与异步材料读取、平台目录历史检查都优先使用远端目标分支与 HEAD 的共同祖先；任务创建时的提交仍由 `frozenTaskBaseline` 独立读取，用于检查提交历史是否完整。上次推送尚未包含新目标基线时，不把两次 HEAD 的直接差异冒充本轮修复，而展示 MR 净贡献。

删除“有未提交业务修改就拒绝整理”的判断，也删除整理中的 `reset --mixed` 和从工作区 `git add`。临时索引只读取已提交对象，将明确排除路径恢复为比较基线内容，复核后再移动分支；工作区、未跟踪文件和其余业务暂存内容不参与整理。仍保留用户明确排除、平台注入目录不得新增到提交历史、已推送提交不得被重写以及远端 SHA 核验。这些边界分别防止违背用户选择、泄漏本地资产、覆盖他人提交或把未推送代码当作已交付；未对 `toolType.dat`、`imap/` 等业务名称增加硬编码过滤。

失败页面提供“查看代码与未提交文件”“补充处理要求”；补充入口聚焦已有对话，用户发送后由原任务接收，不自动清理文件、不直接推送，也不增加审批状态。旧任务从现有失败状态同样可以使用。原流程重试仍保留，但明确要求先处理原因。

真实 Git 回归覆盖上游平台目录、排除项、暂存与未暂存分离、编译产物保留、远端分支提交以及真实内核接受同步后的发布 SHA。内核没有新增阻断，未修改内核源仓或快照。旧版本流水线成功仍不能证明新提交成功；本次不删除版本关联检查。
