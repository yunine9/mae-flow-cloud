# 检视批注定位：修复范围与边界

## 当前如何处理漂移

批注保存材料、文件、原行号、原文快照及选区正文。读取批注时，服务端在当前
材料中重新匹配原文，优先使用完整选区来区分重复表头，并返回当前起止行。
原文唯一且只是被前面的增删挤走，返回 moved；出现多处是 ambiguous；普通
文档找不到原文是 gone。它不是文档版本之间的行号映射，也不是修改是否正确
的验收，不能代替人工检视。

## 这次确认并修复的断点

1. 模块/依赖批注误进普通文档标签，图没有定位节点。现在打开模块与依赖，
   按模块 ID / 依赖两端 ID 定位，支持模块改名和排序变化，自动展开折叠图。
2. 代码块、图表、引用块可能跨多行，只有块首行有 DOM 标记。现在使用源文件
   行范围选择包含目标行的最小渲染块；引用和表格优先定位具体行。
3. 页面只等两秒就放弃，已打开的文档也不一定刷新。改为显式刷新材料，等待
   本次读取与渲染完成后定位；读取失败单独提示。连续点击只处理最后一次。
4. diff 的文本行号与代码文件行号不同，也可能跨文件误匹配。现在在指定文件
   的 hunk 内匹配变更后正文，再换算为真实代码行号。前端同步选择文件、展开
   被折叠的行；显式定位的文件若之前被隐藏，会恢复可见。
5. 双栏 diff 行号来自变更后文件，但快照可能误取左边旧代码。新批注优先取
   变更后代码，避免保存时就产生不一致的坐标。
6. 读不到材料、空文本或“第 N 行”占位锚以前按 hit 放行。仍保留允许提交的
   语义，同时返回 location_verified=false，禁止前端据此硬跳到旧行。
7. 重锚定与 Markdown 渲染统一 CR/LF/Unicode 换行的计数口径。

## 仍然存在的边界

- 原文被大幅改写/删除，或重复原文缺少足够的选区上下文，不能保证自动定位。
- 历史批注若已经采错新旧代码快照，不会凭推测篡改旧记录；可能仍无法定位。
- diff 不是文件全文。目标移出当前 hunk / 当前对比范围时，报告位置未验证，
  不把“diff 里找不到”当成原文已删除，也不跳到同号的其他代码。
- 不支持的 Git 路径转义/重命名等情况可能无法重定位；没有自动迁移文件身份。
- 当前正文与锚点检查是独立读取，尚无同一 revision 的原子快照协议。
- 此次是本地逻辑、组件渲染和构建验证；未复现用户内网某一条真实批注，未宣称
  所有历史批注均已恢复，也未在内网完成部署验收。

上述定位状态不拒绝检视意见提交，不恢复段落范围拒收规则。
