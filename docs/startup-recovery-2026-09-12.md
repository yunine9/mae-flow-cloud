# 生产服务启动阻塞修复

现场最后一行是“反馈状态同步未完成”，但这条日志对应的异常在 `projectionOnly` 分支已经被捕获并返回，不能据此认定异常抛出了恢复流程。没有取得生产进程堆栈，因此不把最后一行日志当作唯一卡点的证据。

代码确认的问题：

- `4ca0a81` 将队列位次展示改成 `runnableQueueIndex`，经 `concurrentTicketConflict` 对其他任务调用 `dependencyCompleted`。后者同步执行 Python 收据核验，而且旧顺序先核验、后过滤仓库和 AR。恢复期间的投影和落盘会反复走这条路径，将历史任务核验放大。`eb21233` 只改前端与测试，没有引入恢复逻辑。
- HTTP 原本在平台预检、容器清扫、问题与需求恢复、第一轮磁盘回收之后才监听。任何耗时恢复都会呈现“进程在、端口不在”。
- 已完成任务的反馈展示投影仍尝试重建缺收据的旧批次；没有必要在恢复展示时重新核验它。

修复：展示只读取已有状态；实际调度继续核验完成事实，先过滤无关仓库/AR，同一次同步调度扫描复用裁决，不跨 `await` 缓存。已完成/取消任务跳过反馈投影重建，不伪造 close、流水线通过或删除原始反馈。

HTTP 先监听，再执行原有恢复。保留“清扫遗留容器 → 恢复两流 → 接单”的顺序，不在索引加载到一半时派出新的队列任务。`GET /health` 在恢复中返回 503 `recovering`，就绪返回 200 `ready`，顶层恢复失败返回 503 `failed`；恢复期间业务请求返回 503 和 Retry-After，避免半份索引导致重复任务号。单任务原有异常隔离继续有效。回收首轮移到恢复完成后。

验证：36 项启动、调度、终态及持续检视回归通过；`npm run gate` 通过。真实 `src/serve.ts` 使用隔离数据目录，载入两个 completed 任务，其中保留 `feedback_triage` 状态：验证端口日志先于恢复日志、两任务均恢复、`/health` 返回 200 ready，最后正常 SIGTERM 退出。证据在 `.pilot/startup-recovery-evidence/`。

边界：这次没有把全部同步内核调用或磁盘 I/O 改为异步；保留原有恢复顺序，避免引入恢复中并发派单。生产 task-19 原始数据、远端 MR 和生产进程堆栈未在本机验证。部署后可通过每单“开始恢复任务”日志和 `/health` 区分恢复进度、就绪与失败。
