# 宿主操作后继续原会话（#395）

此前每次 `task_control` 操作都会销毁 Pi 会话、停止容器，再恢复历史并发送完整启动提示词。原生检查点能恢复历史，但反复启动仍增加准备开销，也容易让 Agent 重复探索。事件数量本身不能直接换算成浪费时间。

现在普通操作只在本轮模型和工具调用结束后暂存原会话，让宿主执行。执行结果、新目标及期间收到的插话和检视意见，由原会话继续处理。仍经过已有并发队列，不增加审批或新的完成凭证。

| 场景 | 会话与环境 |
| --- | --- |
| 登记目标、暂缓反馈、读取关联仓、MR/API 操作 | 保留原会话和容器，只返回本次结果 |
| 推送、分支同步、恢复交付路径、主动 Build-Fix | 保留原会话；先停止旧编码容器，避免后台命令与宿主同时改工作树；后续命令按需获取容器 |
| 等待推送确认、MR 描述 | 暂存原会话，人工决定仍走现有入口 |
| 明确重启、执行权被撤销 | 释放旧会话，沿用既有检查点恢复机制 |
| 正式等待流水线、终态、暂停、取消、关机 | 清理暂存会话；不让旧执行者继续推进 |

暂存句柄不写入任务文件。进程重启后仍使用现有原生检查点；已执行操作继续依据宿主操作记录恢复，不因会话丢失重复远端操作。普通交接不再改变执行代次；取消、重启等真实撤权继续生效，流水线结果仍关联其实际 SHA。

专项测试覆盖连续操作、真实 Pi 历史和工具绑定、宿主失败、交接期间插话、推送确认、暂停/取消、停止验证后的撤权，以及宿主尚未完成时队列不得提前启动会话。真实 Pi 调度测试中连续两次 `task_control` 只产生一次 `session_started`，原工具证据保留；进入正式验证等待后清理暂存会话。
