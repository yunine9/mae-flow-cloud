## 各条细账

### 1. 平台自证提效 —— 最高优先

- **业界**:SWE-bench/verified 的评测纪律:改动是否更好,跑一遍就知道。
- **已有**:PG 投影(事件/外部动作台账)、.pilot 归档现场、
  run-report 对拍脚本。
- **可借**:
  - 指标看板页:下单→await_merge 周期、一次通过率、修复轮均值、
    每单人工触碰次数——数据都在投影里,缺一张页面;
  - 归档任务变回归评测:内核/提示词改动后重放 .pilot/archive 的
    真实任务对拍,防"越改越差"。
- **为什么第一**:它既是提效的证据,也是与团队/领导沟通最硬的语言。

### 2. 修复先定位

- **业界**:Agentless(论文)——"定位→修复→验证"的固定管线在修 bug
  上打赢复杂 agent 循环,成本可预测;GitLab Duo 的流水线修复按钮同构。
- **已有**:修复环分诊使命(列全类别、按类派专职)。
- **可借**:分诊之后、动手之前,把"先定位到文件/函数,说出定位依据"
  写成使命的显式一步——别拿着日志全仓乱撞。

### 3. 分类月光

- **业界**:Cline/Roo 的 auto-approve 按动作类别勾选,不是总闸。
- **已有**:月光模式(全有全无)+ 交付方式预答,自动交卷通路(decide 同路)。
- **可借**:月光演进为按卡类别的粒度(如:文档确认类免批,交付/配置
  类保留)。识别类别要小心红线——按内核卡自带的语义字段来,宿主不猜。

### 4. repo map

- **业界**:Aider 的 tree-sitter 排序代码地图,大仓上下文效率的关键。
- **已有**:AGENTS.md 索引 docs/ 的知识约定(pi 稳定消费已验证)。
- **可借**:大仓(内网巨型 Java 仓)自动生成 repo map 注入会话;
  另一半是 OpenHands microagents 式"带触发词的知识块"——命中才注入,
  与"知识在仓不在平台"路线一致。

### 5. 环境即代码

- **业界**:devcontainer / E2B / Daytona——环境声明进仓。
- **已有**:`--isolate-image` 已是正式内核模式的必选边界，普通 Agent、
  子 Agent、修复与 prepush 的 Bash 共用统一加固运行时。
- **可借**:未来可评估仓内 devcontainer 声明，但必须先转换成平台审批过的
  镜像与资源契约，不能让业务仓直接放宽当前安全边界。

### 6. recipes 众筹

- **业界**:goose 的 recipes(可分享任务配方)。
- **已有**:用户已拍板 skill 收编进 git、众筹修改;两个内网 UT skill
  待进场收编。
- **可借**:形态即"配方文件在仓、平台只消费",无平台配置面。

### 7. IM 入口(待内网确认)

- **业界**:Devin/Cursor 后台 agent 的 Slack 派活——采纳率最高的入口。
- **已有**:WeLink 通知出口 + 深链直达决策卡(半程)。
- **前提**:WeLink 是否有机器人接收消息/回调的能力,进场确认;没有
  就停在半程,不硬做。

### 8. 团队知识资产运营(2026-08-26 用户拍板:"我要这个效果")

- **诉求原话**:"慢慢搞一个团队级的 skill 或者知识的可视化,包括我们的
  ut 的 skill 本质上也不应该内置"——UT skill 现在是部署事实(运维放进
  `<数据目录>/skills/`,重启才换,团队看不见版本、看不见谁在用),但它
  本质是团队资产,应该看得见、管得着、有足迹、能演进。平台只提供货架
  和足迹,资产归团队。
- **已有地基**(2026-08-25/26 已落):knowledge-events 消费足迹
  (available/read 绑任务/步骤/会话,run9 实测记录到
  `java-autout read @ 自由实现与定稿`);TeamKnowledgeInsights 团队聚合
  与工作台展示;仓库级 skill 的资产化待遇(勾选/快照/digest/来源)——
  团队级缺的正是同样待遇,是补齐不是新发明。
- **三步走,每步独立可用**:
  1. **货架(只读)**:管理页列出当前生效的团队 skill/知识——名称、
     描述、digest、更新时间、来源。把内置黑盒变成看得见的货架。
     纯读文件,半天量级。
  2. **管理(可写)**:上传/更新/下线走页面,写进数据目录即对下一单
     生效(不用运维、不用重启);digest 留版本痕可回退;权限归管理员,
     操作留痕(与令牌同纪律)。落地后部署包可以一个 skill 都不带,
     全由团队在页面上养——"内置"彻底消失。
     **2026-08-26 已落**(hostSkillLibrary + /skills 路由 + 货架管理面):
     写路径 fail-closed(装载器裁决/密钥掩码扫描/路径与预算边界),
     权限显式归一 0644/0755,覆盖与下线先归档(每 skill 留 20 版可
     回退),操作逐条进 skill-operations.jsonl。下面钉死的三条容器
     权限纪律全部按写法落进了代码与测试。
  3. **飞轮闭环(效果说话)**:消费率×效果挂钩——装载 N 单/真被
     read M 单/read 过的单 prepush 一次过率;低消费或高失败的 skill
     就是修订信号;检视意见与流水线失败沉淀为知识块/skill 修订,
     下一单足迹验证。与第 1 条(平台自证提效)共用指标语言。
     **2026-08-26 已落**(buildHostSkillEffects):货架条目按 skill 名
     跨版本关联足迹,展示装载/读取/读后一次过与未读对照;低消费
     (≥3 单装载零读取)与高摩擦(读了的单返修占严格多数)亮
     "待修订"牌。口径纪律:environment_error/preparing 不计任何
     skill 的账;对照只是相关性,不包装成因果。三步走至此闭环,
     后续是运营(内容修订靠人,数据只给方向)。
- **运营愿景(用户原话)**:"这样就能运营起来了,平台就会越来越好用了"
  ——货架让资产可见,足迹让消费可证,效果指标让修订有方向,三者合成
  团队知识的正循环。
- **不变的边界**:skill 永远是写法指南不是执行器、不构成任何交付证据、
  不许改流程与门禁(内核唯一权威);管理面只碰资产与足迹,不碰裁决权。
- **容器权限的坑(2026-08-26 用户点名,设计期就钉死)**:pi 的
  Read/Edit 在宿主执行、只有 Bash 进容器,所以模型 read SKILL.md 正文
  不受容器 uid 影响;但三处必须留意——①skill 附带的脚本/资产若被
  Bash 使用就进了容器,文件属主是宿主服务账号,容器 builder(10001,
  内网 uid 与服务账号对不上是已知事实)只能靠权限位读,**materialize
  快照时显式归一权限(文件 0644/目录 0755),不依赖上传时的 umask**;
  ②页面上传落盘**不得**沿用密钥文件的 0600 纪律——skill 是公开指南,
  谁都该读得到;反过来说,正因为权限全开,**skill 文件里永远不许出现
  令牌/密码**,上传入口做一道掩码扫描兜底;③容器对 skill 快照只读
  不写(快照本来就是每任务重造的,容器里改了也该作废)。

## 刻意不抄的

- 复杂 agent 编排框架(状态机化的多 agent 图):用户已拍板"提示词
  就行",Agentless 的结论也站这边;
- 平台侧知识库/技能市场:知识在仓(AGENTS.md+docs),skill 在 git。
  **2026-08-26 演进(不是翻案)**:仓库级知识与 skill 仍在仓;但**团队级**
  skill 的"家"本来就在平台数据目录(部署事实),第 8 条把它从"运维
  文件系统"升级为"平台管理的资产库+消费足迹",内容仍是文件、平台仍
  只消费,不做内容创作平台、不做市场;
- 全自动合入:MR 合入永远留给人,交付点是人机边界。
