# Issue 412：启动自检与界面延迟

新增现场数据是在故障恢复后采集的：`/health` 约 136ms，数据库接受连接，自检约 5.49 秒。这能证明采集时已恢复，不能证明之前 120 秒超时发生在哪一步。PostgreSQL 的连接列表也不包含 Node 连接池内尚未取得连接的等待请求。

## 已确认并修复

- 自检原来串行等待数据库、平台、容器。数据库检查共用业务连接池，还等待建表，没有连接或查询超时。现在各项独立执行；数据库使用短命连接，连接、查询各限 3 秒并关闭连接；并发自检共用正在执行的一次检查。自检不再为了取得模型名称读取全部 Skill 和知识目录。
- 恢复时原来把全部历史事件一次性提交给 4 个连接。现在按文件逐条读取和补写，只保留待处理文件；实时事件正常写入，已有主键继续去重。源日志不修改；故障停止当前文件的补写并留下错误，下次恢复可再次补齐。删除历史时停止该任务的补写，不能在删除后重新写回。
- 任务文件读取和事件流原来调用完整 `get()`；事件流每 300ms 仅为检查状态也重建详情。完整详情在缓存未命中时同步运行 Python，最多阻塞主线程 5 秒。文件与事件流现只读必要元数据；HTTP 任务详情异步查询 Python，相同版本的并发读取合并，查询结果及内核告警保持原语义。

本地验证采用真实 HTTP 接口、真实 `pg` 客户端和模拟数据库协议对端，不代表已取得生产 CPU 堆栈。生产的持续高 CPU 来源仍须由下面的同一时间窗口证据确认。

## 部署后自动采集

无需增加启动参数，也无需重启采集工具。执行服务启动后自动采样前三分钟：

| 日志标记 | 内容 |
| --- | --- |
| `[runtime-diagnostics]` | 每 5 秒记录 PID、CPU、事件循环利用率/延迟、内存、Linux 各线程 CPU 计数、数据库池等待数、历史补写任务、自检阶段及正在处理的请求；每 30 秒记录 CPU 热点与调用者，三分钟后自动停止采样 |
| `[startup-phase]` / `[task-recovery]` | 平台预检、遗留容器清理、两类任务恢复及逐需求任务恢复耗时 |
| `[system-check]` | 每次自检独立编号，数据库、平台、容器启动/执行/清理的开始、结束、耗时，以及最终检查状态 |
| `[container-prepare]` | root 服务为容器准备工作区文件权限的开始与耗时 |
| `[http-timing]` | 超过 500ms 的 HTTP 请求、首字节与总耗时；自检请求无论快慢均记录；SSE 统计建立响应耗时，正常长连接不当成慢请求 |
| `[task-read]` | 慢任务详情中的 Python 查询时间与详情组装时间 |
| `[browser-timing]` | 页面打开后三分钟内的慢请求首字节/下载耗时，以及超过 200ms 的浏览器主线程长任务；每 10 秒汇总上报，只含数字和固定分类 |

如果采用 Web/API 入口与执行服务分离部署，慢 HTTP 日志分别标记 `gateway` 和 `runtime`，CPU 采样在执行服务中。仅重启入口不会重新采集执行服务的启动样本；升级本次后端代码应按现有部署方式更新执行服务。

下一次部署时，在启动后的前三分钟打开任务页面、产出文档和代码，复现原来的操作。保留**从这次进程启动开始，到 `[runtime-diagnostics]` 的 `stop` 以及自检结束**的完整时间段；如分离部署，同时保留入口与执行服务的日志。无需再次分别运行 curl、数据库检查或 CPU 命令。

日志不记录 Token、Cookie、请求体、查询参数、业务文档正文、SQL 参数或进程环境。CPU 记录只有代码调用位置，不采集堆或局部变量。诊断留在部署日志中，不自动上传 Issue 或其他外部平台。

## 如何判断剩余问题

- `postgres.waiting` 增长而事件循环延迟低：Node 数据库池等待；不能用 `pg_isready` 排除。
- 自检某阶段有开始无结束：对照同窗口 CPU 热点、事件循环延迟和正在处理的请求，定位具体等待阶段。
- 事件循环延迟与 CPU 热点同时升高：查热点对应的同步解析、文件扫描或计算；若进程 CPU 高但事件循环正常，结合线程计数检查原生工作线程。
- `container-prepare` 耗时明显升高：检查递归权限准备和磁盘，不误判为 Docker 容器内自检慢。
- `task-read.plan_ms` 高但其他请求正常：内核只读查询耗时；`projection_ms` 高则继续定位详情组装。
- 对照同一时间段的 `http-timing` 与 `browser-timing`：服务端快但浏览器请求慢时检查传输与客户端调度；请求快但浏览器长任务明显时检查渲染与解析。浏览器不支持长任务 API 时该指标缺席，不能当成没有卡顿。上线必须同时更新前端构建，旧页面需刷新后才会产生浏览器统计。
