# 知识库萃取工作台

知识库按业务模块展示远端正式分支的文档，萃取和检视放在独立任务入口。模块首页不再用“建设中／已归档”决定阅读入口，也不跳到最新萃取任务。领域正文由 Git 保存，平台的目录、阅读与问答只消费同步快照；草稿、意见、候选和研究历史保存在任务中。基础组件与 Skill 保留各自已有的维护链路。本文描述代码实现；内网无线豆包、真实业务仓及 CodeHub 的联合验收仍需在部署环境完成。

领域知识仓及正式分支由平台统一提供，模块不重复配置。在“配置中心 → 模块与代码仓 → 编辑”内的小区块中只维护仓内相对路径，与模块一起保存，默认 `Function_Knowledge/Access Function/<模块名>`。正式读取与后续任务的 MR 共用此路径，不追加模块编号；改模块名称不迁移已存路径。已有任务保留创建时的位置，未创建 MR 的旧任务可以在路径预览中采用已保存的模块位置，保留原成果。

正式文件在后台同步，打开知识库不等待拉仓。服务启动 5 秒后首次检查，此后每 60 秒检查；同一模块同步完成后至少间隔 60 秒，最多两个模块并发，优先处理等待最久的模块。无排队时，下一轮通常在上次完成后 60～120 秒启动，再加 Git 读取耗时；模块多或网络慢时会更久，不能将一分钟视为同步完成时限。每轮都会获取远端正式分支提交，提交未变才复用文稿。MR 合入和直接更新正式分支走同一同步链路，不依赖任务上的 MR 状态是否已刷新。失败来源保留上次成功内容，页面显示失败或部分同步，下轮继续尝试；“同步”按钮可立即发起本模块同步。

知识库首页和正式阅读页可见时，每 30 秒只检查本地同步快照的阅读版本，回到标签或窗口时立即检查；版本未变不重载目录与正文。版本包含正式文稿、来源提交和模块配置，能识别新增、删除、移位及只更新图片的提交，忽略单纯同步时间变化。后台成功保存新快照后，可见页面正常情况下在下一次检查时更新，额外等待最多约 30 秒再加请求耗时；后台标签暂停检查，返回时补查。自动刷新保留所选文稿及阅读位置，已删除文稿不继续当成现行正式文件。任务内固定的检视材料不随正式库刷新。浏览器缓存和本地阅读索引都是读取加速，不是新的内容来源，也不会触发重新萃取。

## 页面与人工修订

两类萃取共用工作台外壳、任务列表布局、阶段导航、资料上传，以及正文与讨论分栏的审查布局。领域审查按「仓库 → 文件名」展示已生成的知识文件，不再叠加模型生成的主题和章节树；同名文件显示相对路径以便区分。组件保留联合文档预览和知识结构导航。领域文档的相对链接可跳转到同一归档目标内已萃取的内容，未包含的引用会提示。

- 切换两个子页面保留各自任务与未保存输入。服务重启不会取消萃取：领域与组件研究沿用原任务、原轮次及持久化的 Pi 会话上下文，接续未完成部分，保留工具结果、源码版本、草稿和修订建议。进程退出会断开在途请求，启动后接续原会话；用户明确停止或删除的任务不自动执行。修订建议的原文版本也会保存，接续后仍不能覆盖人工的新版本。
- 研究过程共用一条最新记录在上的动态流，直接显示时间、动作和简要说明，不按活动类型分组。默认展示最近 40 条，更早记录从底部加载；源码、目录输出和完整参数默认折叠，滚轮统一滚动外层详情。
- 两类萃取任务均可删除。领域任务在详情右上角提供删除与确认，运行中或排队中的研究会停止，任务及草稿从列表移除，删除状态在重启后保留。已创建 MR、仓库文件和正式知识文档不受影响，后台保留来源记录及删除人；归档或远端核对进行中需等待当前操作完成。
- 只讨论不写正文；修订和来源更新生成当前任务候选。可反复反馈、人工编辑、查看来源和恢复历史版本；提交 MR 只处理已选文稿，不替未选稿采纳建议，不直接写正式知识库。
- 每份建议绑定启动时的正文版本。期间发生人工编辑，旧建议不能覆盖新正文；维护人可复制需要的部分到编辑区手工合并，或重新生成建议。
- “开始检视”有两个入口，共用全屏界面：未合入的任务文稿在原任务继续修订；正式知识阅读页创建独立检视任务，固定正文、来源提交及所引用图片，不要求原萃取任务存在。跨文稿连续添加行、整篇和整体意见，期间只保存。结束检视才统一调用修订 Agent；无意见则直接结束，不运行模型。未保存的整篇/整体输入先保存，行编辑未保存时提示先记下或取消。“研究过程”持续展示修订步骤、候选保存和独立评审，以及“检视意见修订进度”过程文稿。
- 已保存的行意见由 `KnowledgeInlineReviewNotes` 组件放在引用正文块下，用淡色卡片显示作者、意见与提交状态。原文唯一匹配或前后文能唯一确定位置时才展示，跨段引用放在末块之后；定位不确定时保留在意见列表，不使用旧行号猜测当前位置。
- 领域修订的初选文稿是定位起点，可修改同任务相关文稿，实际改动全部纳入评审；源码与其他任务不可写。补充资料可以生成更新建议。
- 更新读取新旧源码差异，沿受影响内容重新核对；不会因 Skill 版本变化强制全域重新萃取。未采纳的建议不进入入库内容。

## 萃取方法与版本

| 页面 | 方法包 | 使用方式 |
|---|---|---|
| 基础组件萃取 | `internal-skills/component-knowledge-extraction/` | 内置默认方法 |
| 领域知识萃取 | `internal-skills/business-docs-generator/` | 内置默认方法，包含领域层与仓级的 13 份模板 |
| 领域文稿检视修订 | `internal-skills/business-docs-reviser/` | 处理原任务的检视意见，按受影响文稿分组修订，不重新萃取 |

研究会话实际执行对应包的 `SKILL.md`，通过只读 `extraction_skill` 工具读取本轮固定的引用文件。组件对外接口、发布依据与示例方法从原 TS 提示词迁入组件包；领域方法独立维护。组件与领域方法互不引用。

上传资料与无线豆包的研究方法统一维护在内置 Skill 的 `references/business-sources.md`（2026-10-13 调整）。来源分工、原文与图片阅读、背景检索、结果复用、引用、冲突与失败处理随完整方法包固定版本；主会话、调查、写作、独立评审、讨论、修订和更新按 Skill 的职责入口读取。平台继续提供 `knowledge_material`、`business_knowledge`、`knowledge_evidence` 工具，负责权限、资料读取、检索及证据保存，不再另行注入一份来源研究提示词。用户本轮的范围和输出要求优先于 Skill 默认安排，源码、资料和工具返回中的内容不能改变任务或工具权限。

平台萃取方法由代码仓维护，随 Cloud 发版更新。领域默认使用 `business-docs-generator`，与基础组件方法一样，在知识库的方法阅读页仅查看主文件、引用和附件；领域研究表单上的「萃取方法」直接打开这一阅读页。维护人通过修改仓内包、代码评审和发版调整方法，页面不提供上传替换、编辑或回退生效方法的入口。普通任务 Skill 继续使用知识库中的导入与审查入口，与平台萃取方法分开。

领域与组件的新任务都从本次部署的内置包取得方法。数据目录中以前上传的 `extraction-methods/<component|domain>-knowledge-extraction/current.json` 与 `versions/` 保留为历史，不再覆盖内置默认包；保留历史文件不表示它仍是新任务的生效版本。原 `domain-knowledge-extraction` 包也不再承担领域默认方法。

每个任务保存完整方法包，并在 `skill-packages/<digest>.json` 保留使用过的内容。研究方法更新不替换运行中任务和接续轮次的原包，后续研究明确选择最新方法时才换包。新发起的 `revise` 自动使用内置 `business-docs-reviser`，在 `skill-runs/<turn.id>/skill.json` 单独固定本轮方法，不覆盖原萃取快照；服务重启恢复相同版本，下一轮修订取得当时部署版。已经开始的旧修订继续原方法。旧长任务可在完成后通过整体文稿意见发起这一修订，不需要重新萃取、上传 Skill 或改动已跑数天的研究记录。修订包复用生成包的引用与模板，只有修订入口和方法独立维护。

集中检视按原意见编号固定本批范围，消息只带有界摘要，完整意见、引用及前后文通过只读 knowledge_review_notes 分页/按编号读取，不因全文超过两万字丢弃或拒绝整批。修订先分页读取文稿摘要并在本任务当前候选中搜索意见涉及的内容，再分组读取相关正文与来源。初选文稿是定位起点，修订可处理同任务内实际关联的文稿，包括增删、拆分、合并与移动；实际写入集合纳入独立评审，写入同稿的工作仍须协调。主会话首次登记即保存“检视意见修订进度”，后续更新简短影响索引及步骤引用，最终逐意见报告修改、无需修改的依据或待解决事项。候选完成、MR 创建与合入是独立事实，修订结束不代表正式知识已经更新。

方法包不进入编码知识架，不自动混入普通编码任务。平台系统提示词保留工具权限、持久计划、独立步骤、图校验和接续的执行约定；内置包决定来源使用、调查方法、规划、文稿模板和评审要求。上下文压缩后的恢复信息保留固定方法的名称与内容摘要，提示会话先回读该包的 `SKILL.md`，再读取当前职责需要的引用文件。

## 完整业务文档与独立评审

`business-docs-generator` 将附件的多仓文档体系映射到平台工具。领域层包括业务模块入口、领域索引、术语表、业务架构、逐业务域文稿、实际交互仓对的接口契约和外部系统画像；仓级包括本业务在各仓的入口、功能路由、适用编程约定、业务规范和按业务功能划分的模块文稿。排查经验只记录真实案例。覆盖范围是所选业务及解释完整调用链所需的共享实现，不把共享仓中的其他业务扩为整套产物，也不由一个业务的研究声明全仓统一规范。文档数量随范围内的业务域、仓间交互和功能变化，不以生成固定篇数作为结束条件。业务域的每个独立场景、模块的每个功能点沿用模板的 PlantUML 时序图要求，并核对实际调用、参数、分支、状态、存储、清理与可靠性机制。

PlantUML 使用平台提供的实际渲染校验工具检查，语法错误按图的位置和诊断反馈修正后重新校验；存在语法错误时不能宣布相关文稿完整完成。缺少 Java、渲染超时或其他运行条件不足须记录为未验证，不能冒充通过。渲染成功只说明图能被当前渲染器解析，业务含义仍由独立评审对照源码核实。复杂图按真实子流程拆分并保留衔接，不按固定节点数或参与者数删除业务分支、调用方或边界。

方法的 `SKILL.md` 显式声明 `execution: reviewed-document-plan`，选择平台的完整文稿执行约定。宿主不根据包名或文件名猜测模式，也不把上述文档种类写死在 TypeScript 中：Skill 决定调查方法、产物范围、模板和评审标准，平台保存计划、执行独立步骤、控制写入范围并核对结果。严格的完整清单要求用于首次萃取；讨论、局部修订和来源更新继续尊重本轮指定范围。

主会话先按仓、业务入口和完整场景安排独立只读调查，汇总结果索引形成完整规划。规划正文通过 `knowledge_work save_document` 保存为过程文稿 `current-plan`，随后用 `plan` 登记全部稳定文稿编号和规划正文编号。独立规划核查读取清单、规划及源码入口，对照业务页面、公开接口、定时任务和事件处理查遗漏；主会话按反馈修订后，再安排写作。后续新发现先补规划，移除原必需条目须保留逐项排除原因。结构化清单可发现已登记文稿未完成，业务范围是否穷尽仍由调查和独立核查判断。

规划核查直接保存 `document_ids: []` 与结果中的 `review: { pass, feedback }`；不通过也属于已完成的核查，由主会话依据反馈调整工作。步骤配置中的 `review.instructions` 专用于知识文稿的自动独立评审，不能与核查结论混用。平台对未声明待评知识文稿的只读步骤取消多余的自动评审配置，新登记和历史工作记录采用同一规则；明确声明 `expected_document_ids` 的只读文稿复核仍执行自动评审和版本核对。

这项执行修复适用于已有任务固定的旧 Skill，无需重新萃取或更换方法。服务升级重启后，原先排队或运行的任务自动沿原轮次接续；已失败或人工停止的任务从原任务继续研究。平台保留原步骤编号、依赖、调查结果、完整规划、草稿和会话记录，已经保存的核查结论直接复用；尚未成功保存的结论需要该步骤补交或重新核对。子会话连续三次提交结果被拒绝时，平台结束该子会话并把失败原因交回主会话，其他并行步骤继续，避免反复读记录掩盖提交阻塞。此限制不按研究耗时触发，也不替核查生成通过结论。

每篇首次萃取的写作步骤声明 `expected_document_ids` 与 `review.instructions`。主会话用 `knowledge_work schedule` 登记后，以 `run` 执行；省略步骤编号时按真实依赖推进，默认最多三个独立单元并行，可选一至四个。只有依赖已完成且写入文稿不交叉的步骤才能并行；未声明写入范围的可写步骤串行。首次写作不能越过声明范围，修订允许按实际影响联动同任务关联文稿并记录真实写入；规划由主会话维护，导航同步声明依赖并重新评审最新正文。

候选文稿先保存，再启动独立只读评审。评审必须逐一回读全部预期文稿的当前版本；Skill 还要求回查原始源码和资料，按具体模板核对完整场景与事实，不能只检查标题、篇数或引用是否存在。评审用 `review: { pass, feedback }` 返回结论，未通过时反馈交回写作会话修订，每项最多自动尝试三轮。候选、反馈与已完成结果持续保存；中断后接续原工作，单项失败不抹掉其他成果。通过结论绑定实际正文及来源，文稿变化后原结论不能用于宣布完成。全部适用计划文稿都已生成、最新版本通过且导航一致时，主会话才报告完整完成；实际阻碍保留为未完成并说明接续条件。

大规模源码的原文与步骤历史按需回读，主会话只保留范围、短摘要和结果编号。每个调查、写作和评审单元接收自己的范围、方法入口与证据索引，开始时重新打开原始依据，避免把主会话摘要当成已经读过源码。初始上下文与压缩后的恢复信息只携带资料编号、版本、状态及章节、文件、图片和警告数量；完整 ZIP 目录与图片清单通过 `knowledge_material` 按需读取。`knowledge_work read` 不带编号时只返回工作摘要；清单、步骤列表、过程文稿列表和知识文稿列表均分页，默认 30 项、最多 100 项，按 `next_start` 继续；完整正文及步骤结果按编号读取。跨仓构建依赖通过 `knowledge_structure` 的 `include_dependencies: true` 显式取得候选，仍需核对真实调用两端。

自动生成与独立评审不增加文档之间的人工确认。维护人继续在工作台审查成果、采纳修订建议和发起归档；完整计划与评审通过不等于已发布，也不单独证明业务知识准确。该包的真实模型质量、长程执行和大型业务仓覆盖，应以实际产物对照固定源码及模板验收，不能由机制测试或小规模案例替代；内网效果仍需部署后的业务验证。

## 输入与无线豆包

领域新任务选择已维护的业务模块，只填写关联单号与统一基准分支（默认 `master`），按需上传资料。无线豆包内置启用，不在新建表单中显示开关或连接检查。服务端从模块维护中取得全部关联仓库、稳定模块编号和模块名称，按 Skill 完整萃取本业务范围；关联仓可同时承载其他业务，不代表研究范围扩为全仓。页面不再要求主题、研究范围或逐仓配置。创建时保存研究仓快照，后续更新继续核对这些源码。仓库地址不能携带凭据。

领域任务点击“创建 MR”后，在同一个窗口预览目标目录和最终文件路径，确认后直接提交候选，不经过“确认并发布”。领域位置来自模块长期配置；代码仓默认回到研究仓及基准分支。未配置位置的旧任务可以保留研究成果，但不能借本地发布绕过 Git 进入正式知识库。已有批次继续使用冻结文稿和位置重试，新模块设置不改写旧批次。

新领域任务使用 `knowledge_layout: directory-v1`。每个归档目标的 `docs_path` 是最终仓根相对目录，完整文稿 path 已包含它时不重复拼接。领域知识仓使用模块保存的路径，默认 `Function_Knowledge/Access Function/<模块名>`；代码仓的本业务知识默认位于 `docs/<业务名称>`。`module_id` 仅用于内部业务归属，读者可见标题、导航及范围说明使用业务名称，不用内部 UUID 命名目录，也不将工作区仓名写入目标仓内路径。

领域位置长期在模块设置中维护，任务使用固定位置，避免单次 MR 写到知识库不会读取的目录。各代码仓使用 `docs/` 下的业务目录。模型所有领域与仓级文稿均保存到对应最终目录：README.md 是业务入口，index.md 是领域详细索引，module-map.md 是代码仓功能地图；rules/、modules/、domains/、interfaces/、external/ 按实际文稿需要置于同目录内。原有 13 个模板标识保留，模板名不规定产物文件名。

历史任务研究接续仍使用固定原方法包和当前文稿位置。旧 module-v1、repository-v1 及未指定布局任务，在创建 MR 的路径预览中由平台统一整理到 directory-v1。原先散落在 docs/、domain-docs/、仓根 index.md 或 AGENTS.md 中的模型文稿收拢到最终业务目录，AGENTS.md 中的研究正文转为普通 README.md。整理保留文稿 ID、正文、调查、历史版本及固定 Skill，不调用模型重新研究。归档只采用本次选定候选；正式版本与并发修改仍核对。来源正文中的真实业务 ID 保持原样，不做全文替换。

文件重名或被其他正式文稿占用时，平台以稳定文稿 ID 后缀、必要时序号避让，同步相对链接和可读导航。用户无需手动解决文件撞名。历史规划和步骤记录保持原样，后续研究采用当前保存位置；原失败归档批次重试使用冻结文稿、目标路径和布局，包括旧 module-v1 与 repository-v1 批次，已推送提交和已有 MR 按原记录恢复。新建归档采用整理后的目录。

两类任务都支持上传 MD、TXT、DOCX、PDF、XLSX、PPTX，以及包含这些文档与 PNG/JPEG/GIF/WebP 图片的 ZIP。原文件与解析内容保存在 `knowledge-materials/<id>/`，资料自动用于所关联的萃取任务，不要求重复填写范围。资料版本作为可选备注，支持真实版本号或文档发布日期，不知道可留空；系统记录上传时间与文件指纹，不把上传时间当业务版本。单文件最多 20 MiB，一次最多 30 份、合计 100 MiB；上传与解析未结束时不能提交研究。

ZIP 最多 1000 个条目、展开后 100 MiB，单个文档或图片最多 10 MiB。文本总量不另设 5 MiB 限制；解析结果与子进程输出预算均为 128 MiB，包含正文、定位及图片索引，超限时明确提示拆包，不截断正文。保留包内相对路径和 Markdown 图片引用；工具按需读取章节与图片内容，每次一张。模型不支持图片时工具明确返回未读取原因，不假装识别；不支持的附件格式列入未解析提醒，受支持文档解析失败、无效图片或文件名编码异常使整份资料失败并保留错误。拒绝路径穿越、链接、重复条目、加密包与超限展开，不执行包内文件。

研究表单的未提交输入保存在当前知识库页面中。填写或修改关联单号不会清空人工填写的描述；查看萃取方法后，页面返回、浏览器后退或「使用此 Skill」均恢复原表单及已上传的资料，只有创建成功后才清理草稿。刷新页面或离开知识库导致页面重建时不保留草稿。

萃取方法阅读页显示当前内置方法及其文件，只提供阅读与返回任务的操作。方法内容的变更通过代码发版生效，运行中任务仍使用本轮固定包。

解析结果按章节序号分段读取，用实际返回的 `source_path`、`location` 和单元格位置定位原文；章节也可能是连续文本的片段。PDF 页码和幻灯片位置仅在转换结果带有对应标记时引用，不能把转换文本行号当成原件页码。Excel 公式使用文件内缓存值并明确标注；不运行宏。扫描件不自动执行 OCR；图片和版式未完整提取时保留具体限制，失败资料保留可见的错误，不冒充已读取。

上传业务资料是业务意图、规则与设计原因的主要依据，没有上传资料也能开始，只是业务原因如实留作未知。无线豆包只用来查询基站、网管等无线业务的背景信息（术语、概念、场景与通行规则），帮助读懂代码和资料，不能证明本系统的需求、设计或历史原因；工具只保留知识检索，原先按 AR 查需求、设计、MR 差异与相近历史的动作及任务上的 AR 编号字段已撤掉。两类来源的用法随 Skill 版本发布与固定，平台不规定必须检索多少次或运行多少小时。

`knowledge_evidence list` 按关键词检索本任务主、子 Agent 已取得的业务资料，分页返回去重摘要、原查询时间及空结果/失败状态；`read` 按资料编号分页回读无线豆包返回正文，上传资料则定位原章节或图片。子 Agent 只有实际回读过的资料才可作为报告引用，列表不算已读。查询结果与回读记录持久保存，重启、上下文压缩后可继续使用；回读仅记录来源编号和范围，不重复保存整份响应。旧结果不是实时缓存，资料更新时仍应重新查询；失败记录不保存查询正文。

领域研究中，超过 16000 字符的业务检索结果先返回 8000 字符和后续读取位置，全文保存在原证据中，再按需分页读取，避免一次长响应占满上下文。没有可回查引用的其他工具响应保留原行为。

Cloud 调用已有 CLI 的真实协议：

```text
<CLI> --timeout 150 tools call <tool> --json <参数 JSON> --raw
```

只调用 `knowledge_search`（查询基站、网管等无线业务背景）。使用环境变量传递鉴权，不把令牌传入模型或命令参数；不拼接 shell。适配 JSON-RPC raw 响应、文本内 JSON 与 structuredContent，识别退出码正常但实际鉴权失败的响应，区分无数据与查询失败。查询、结果位置、版本限制与失败记录在任务证据中。

服务进程需要配置：

| 配置 | 用途 |
|---|---|
| `MAE_FLOW_WXDOUBAO_BIN` | CLI 绝对路径，默认 `/opt/wxdoubao/wxdoubao` |
| `WXDOUBAO_USERID`、`WXDOUBAO_TOKEN` | 通过部署环境注入，不写入仓库或 Issue |
| `WXDOUBAO_URL` | 可选，CLI 服务地址 |
| `MAE_FLOW_WXDOUBAO_TIMEOUT_MS` | 默认 150000 毫秒，允许 1000～600000 |
| `MAE_FLOW_PYTHON_BIN` | 资料解析 Python 3，默认 `python3` |
| `MAE_FLOW_PDFTOTEXT_BIN` | 可选 Poppler `pdftotext` 路径，默认从 PATH 查找 |

环境变量应注入运行 Cloud 的服务进程，不能依赖交互式 shell 的启动文件。所有领域研究会话固定提供业务检索工具，首次萃取按 Skill 查询业务背景，后续按更新或问题范围查询。服务不可用时记录失败与受影响结论，可继续不依赖该来源的研究，不能伪造结果。

## 两层归档与 MR

领域文稿集中于知识仓的最终业务目录，仓级文稿集中于对应代码仓 docs/ 下的业务目录。模型生成普通 README.md、index.md 及研究文稿；AGENTS.md 由平台根据正式知识生成，不进入模型产物清单。代码仓只保留根 AGENTS.md，统一导航各业务目录；领域知识仓在领域 docs_path 内生成 AGENTS.md，导航仅覆盖该目录，不将它写到代码仓根或领域仓根。

平台入口沿用“项目概述／模块索引／阅读与维护约定”三部分，只输出可读指引，不写平台标记或隐藏元数据。固定正文说明定位、按需阅读、来源与版本核对、业务边界和文稿同步；索引按实际知识入口列出，不逐业务复制规则或摘要，不编造项目命令。入口更新覆盖对应位置的旧正文，Git 历史保留原文。先按源码路径、接口或业务术语定位，再读相关业务 README 及必要文稿，避免全量加载。当前实现与业务目标分别核对源码配置和资料；冲突保留双方依据，不设“代码永远正确”的绝对优先级。

整理旧文稿后，归档器按原归档或基线精确核对需迁走的文件；已被其他正式知识占用或正文与已知版本不同的文件不直接覆盖。目录内研究正文迁为普通文稿，与平台入口分开维护，模型不改写其他业务知识。原失败批次按原记录恢复，新归档使用当前正式知识和最终目录。

研究、人工编辑和 Agent 修订只更新任务文稿。点击“创建 MR”预览本次候选、目录和文件路径，确认后使用任务关联单号提交；关闭窗口不创建 MR。不需要先发布到本地正式库。自动图检查和独立语义评审继续保留，首次萃取不强制人工检视，满意即可创建 MR；原任务在合入前仍能继续检视和改稿。

维护人发起归档后：

1. 按目标仓核对已选候选、个人 Git 身份、当前远端文件和正文基线。
2. 未合入的改稿继续推送原分支并复用原 MR。原分支被外部更新、文件正文不再匹配基线时拒绝覆盖，保留候选和具体原因。创建结果丢失时先发现原 MR，再继续提交。
3. 推送与 MR 事实分别保存，一个仓失败不抹掉其他仓的结果。失败批次提供原批次重试入口，仅处理失败目标。
4. 平台后台查询真实 MR 状态，查询不会锁住修订或覆盖并行保存的正文。部分目标合入不代表全部完成，剩余失败目标仍可补建 MR；已合入目标不再续推，正文后续修改从正式知识库创建新检视任务。
5. 正式 Git 同步独立于 MR 记录，手工维护的仓库文件也会同步。按来源固定提交；不变提交复用快照，增改删切换正式视图，单仓失败保留其上次内容并显示部分同步。正文与图片均按来源读取，检索索引可以重建；任务中的旧基线和图片不会被同步覆盖。

正式目录按仓库、分支和路径保持稳定文档编号，共享代码仓的资料保留仓级归属。平台不直接修改 Git 正式正文或本地恢复成另一版本；业务正文的修改、改名和删除都通过任务 MR，合入后再同步。

组件结果沿用既有知识采纳和索引链路：选定章节形成一篇 Markdown，采纳后可从同一任务开始更新，正式版本发生外部修改时拒绝无提示覆盖。

## CodeHub 适配

知识归档要求操作者个人 Git 用户、令牌与提交邮箱，不升级系统只读凭据。平台适配层需要 MR 创建、`GET /mr/discover` 与 `GET /mr/gates`；组件原有的替换 MR 流程还使用 `POST /mr/close` 撤销旧 MR。领域任务未合入前复用原分支和 MR。无法确认上次创建结果时停止重复创建，恢复查询后可重试。

知识请求通过 `purpose: "knowledge"` 选择 `mr_create_knowledge` 模板。仓库的 `deploy/adapter-config/adapter.codehub.json` 已提供携带关联单号的独立模板；部署时把它合并到实际适配层配置。普通需求和问题 MR 继续使用原 `mr_create` 模板。未配置独立模板时可复用包含 `{dts_no}` 的普通模板；旧的无单号模板需要更新后才能创建知识 MR。

- `domainKnowledgeAgent.ts` 执行领域 Skill，复用只读源码工具，连接资料、无线豆包和证据回读工具；每个会话均可读取本轮固定包的来源研究方法。

- `knowledgeMrPublisher.ts` 管理临时 Git 工作区、文档冲突和 MR 恢复，清理临时目录。
- `businessModuleKnowledge.ts` 解析模块长期目录；`knowledgeRepositorySync.ts` 同步远端；`knowledgeRepositorySnapshots.ts` 管理正式快照、资源与冻结的检视图片引用。
- `knowledgeExtractionSkills.ts` 读取组件与领域的内置默认包，保存任务固定版本并保留历史方法内容。
- `knowledgeProcess.ts` 对工具进程实行超时、输出限制和取消；Unix 下终止同组解析子进程。
- `taskService.ts` 装配模型、源码、发布与后台知识同步；本次没有重构需求交付或问题处理机制。

## 验证与部署后核对

本地定向验证包含真实 Pi 会话与脚本模型、真实 Git 临时仓和 MR 服务替身、HTTP 登录权限、多格式资料解析，以及 Chrome 桌面交互（1920×1080、1366×768）。替身验证协议与行为，不代表真实内网服务已通过联合验收。

运行 `npm run typecheck` 和 `npm --prefix web run build`；按改动域运行 `componentResearch`、`componentApiBoundary`、`domainKnowledgeExtraction`、`knowledgeExtractionSkills`、`knowledgeExtractionRoutes`、`knowledgeMaterials`、`knowledgeMrPublisher`、`wxdoubao`、`platformAdapter`、知识文档与导航的定向测试。浏览器测试为 `componentResearchBrowser.test.ts` 和 `knowledgeLibraryBrowser.test.ts`，PDF 测试需指定实际 `MAE_FLOW_PDFTOTEXT_BIN`。不运行全量套件或聚合 gate。

部署后用 2～3 个相关业务仓和脱敏资料执行一次领域萃取：确认无线豆包真实权限、两层文档路径和来源，人工修订并创建 MR，维护者合入后等待正式分支同步，最后从知识文档页核对适用范围、来源版本和索引状态。再从正式文档开始检视，确认固定基线、图片、意见汇总和同一 MR 续推。此步骤需要内网服务与个人写权限；本地开发没有对真实业务仓推送或创建 MR。

### MR 关联单号

新建领域萃取任务时必须填写一个关联单号，同一任务向各仓创建的 MR 都关联此单号。已有任务缺少单号时，在任务详情补填后才能创建 MR；已发起 MR 创建后不能更换单号，避免任务记录与平台关联不一致。

平台适配配置 `mr_create_knowledge` 必须传递 `{dts_no}`（CodeHub 使用 `--e2e-issues`）。MR 创建成功并返回链接即完成提交，不等待流水线变绿，也不自动合并。

### 基础组件归档与已有文件处理

基础组件萃取在“入库与更新”中提供“提交到代码仓”：配置仓地址、分支、目录、Markdown 文件名及关联单号。勾选章节生成一篇完整文档，可在归档阶段编辑合并稿。首次准备会读取同路径的远端文件，展示原文与差异；有差异时人工确认后提交，原文不变则不创建空 MR。提交前重新核对远端内容，变化时要求重新比较。组件与领域归档共享 MR 创建、重试、历史、冲突保护和合入同步能力；组件归档记录不出现在领域萃取任务列表中。

### 可选的萃取前清理

发起领域研究时可勾选“萃取前清理旧知识”，默认关闭。勾选后先保存研究信息，进入清理页面，不执行研究。清理范围由人填写仓内相对目录或文件路径，不受新归档目录、文件扩展名或任务布局限制，AGENTS.md 也可明确选入清理。目录会展开成实际文件供勾选；不接受仓根 `.`、绝对路径或含上级目录的路径。留空跳过该仓。预览列出实际文件，取消勾选即保留。查看方法或返回任务中心后再进来，当前知识库页面保留未提交的路径和文件选择；刷新页面采用服务器保存记录。

操作顺序为：预览待删文件 → 创建清理 MR → 人工审查、合入 → 手动开始萃取。每个仓只为选中的旧文件创建删除提交和独立 MR，不直接修改目标分支。MR 创建成功后收起清单并突出链接；多仓部分失败保留成功结果，人工重试只处理未成功的仓。每步只有一个主按钮，也可直接跳过清理并开始研究，不增加保存或确认保存环节。系统不自动追踪清理 MR，不自动开始萃取；人工开始时读取基准分支最新代码。

清理范围内的远端文件发生变化时，提交前要求重新预览。清理分支沿用需求交付的“基准分支_个人 Git 账号_关联单号”命名；同名分支已存在且不属于本次清理记录时停止，不覆盖外部提交。已推送的仓保持原选择和分支，响应丢失时人工重试先查询原 MR，防止重复创建；未推送的旧失败记录重试时采用正确分支名。单仓预览最多 20 个路径、1000 个文件，拒绝仓根、越界及 .git 路径。清理只针对仓库文件，平台正式知识仍按自身的人工维护操作处理。
