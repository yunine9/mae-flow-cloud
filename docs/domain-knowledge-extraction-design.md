# 知识库萃取工作台

本次实现把「知识库」作为一级入口，与「团队资产」并列。知识文档、基础组件萃取、领域知识萃取在知识库内切换。本文描述实际实现和部署接线；内网无线豆包、真实业务仓及 CodeHub 的联合验收仍需在部署环境完成。

## 页面与人工修订

两类萃取共用工作台外壳、任务列表布局、阶段导航、资料上传、Skill 编辑器，以及正文与讨论分栏的审查布局。阶段为「范围与资料」「研究过程」「审查与修订」「入库与更新」。审查阶段统一展示萃取成果的「知识主题 → 章节」结构，可搜索、展开并点击定位 Markdown 正文；目录不按仓库或落盘路径分组。组件保留联合文档预览，领域文档的相对链接可跳转到同一归档目标内已萃取的内容，未包含的引用会提示。到「入库与更新」才按目标仓展示文档路径、可选清理和 MR。

- 切换两个子页面保留各自任务与未保存输入。后台执行可停止、失败可重试，进程重启保留草稿并如实标记中断。
- 只讨论不写正文；修订和来源更新生成待采纳建议，比较后才采纳。可反复反馈，直接人工编辑、查看来源和恢复历史版本。
- 每份建议绑定启动时的正文版本。期间发生人工编辑，旧建议不能覆盖新正文；维护人可复制需要的部分到编辑区手工合并，或重新生成建议。
- 领域侧可同时处理已勾选关联文档；服务端仅允许修改本轮选中的文档。补充资料可以生成更新建议。
- 更新读取新旧源码差异，沿受影响内容重新核对；不会因 Skill 版本变化强制全域重新萃取。未采纳的建议不进入入库内容。

## 两个独立 Skill

| 页面 | 方法包 |
|---|---|
| 基础组件萃取 | `internal-skills/component-knowledge-extraction/` |
| 领域知识萃取 | `internal-skills/domain-knowledge-extraction/` |

研究会话实际执行对应包的 `SKILL.md`，通过只读 `extraction_skill` 工具读取本轮固定的引用文件。组件对外接口、发布依据与示例方法从原 TS 提示词迁入组件包；领域方法独立维护。两包互不引用。

页面的「维护萃取 Skill」支持编辑入口和引用、添加/删除 Markdown 文件、查看发布前差异、发布新版本和回退。登录用户可读，管理员可发布；关闭登录鉴权的本地模式可维护。保存校验完整包、引用路径、名称与敏感信息，并检查当前版本，防止覆盖其他维护人的修改。

默认包来自仓库；修改后放在数据目录的 `extraction-methods/<skill-name>/current.json`，历史放在 `versions/`，服务启动不会覆盖修改。方法包不进入编码知识架，不会自动混入普通编码任务。

每个任务保存完整方法包，并在 `skill-packages/<digest>.json` 保留各轮使用的内容。新任务取当前版本，已有任务默认沿用固定包，可显式选择下一轮使用最新版本。修改方法不需要重发 Cloud；增加实际工具、数据字段或权限仍需要开发。

## 输入与无线豆包

领域新任务可从业务模块加载仓库，或自行选择多个 HTTP/HTTPS 业务仓；逐仓指定分支、研究目录与归档文档目录。领域知识仓单独指定，可继承配置中心的知识仓地址、默认归档分支与目录。仓库地址不能携带凭据。

两类任务都支持上传 MD、TXT、DOCX、PDF、XLSX、PPTX。原文件与解析内容保存在 `knowledge-materials/<id>/`，关联任务记录保留资料编号、版本、范围和内容摘要。单文件最多 20 MiB，一次最多 30 份、合计 100 MiB；上传与解析未结束时不能提交研究。

解析结果按需读取，保留行、段落、表格行列、页码、工作表单元格或幻灯片位置。Excel 公式使用文件内缓存值并明确标注；不运行宏。PDF 要有可提取文本，扫描件需先完成 OCR。失败资料保留可见的错误，不冒充已读取。

无线豆包是领域知识检索来源，与上传文件解析分别处理。Cloud 调用已有 CLI 的真实协议：

```text
<CLI> --timeout 150 tools call <tool> --json <参数 JSON> --raw
```

支持 `knowledge_search`、`ar_fur_info`、`ar_idp_docs`、`ar_mr_diff`、`ar_history_similar`。使用环境变量传递鉴权，不把令牌传入模型或命令参数；不拼接 shell。适配 JSON-RPC raw 响应、文本内 JSON 与 structuredContent，识别退出码正常但实际鉴权失败的响应，区分无数据与查询失败。查询、结果位置、版本限制与失败记录在任务证据中。

服务进程需要配置：

| 配置 | 用途 |
|---|---|
| `MAE_FLOW_WXDOUBAO_BIN` | CLI 绝对路径，默认 `/opt/wxdoubao/wxdoubao` |
| `WXDOUBAO_USERID`、`WXDOUBAO_TOKEN` | 通过部署环境注入，不写入仓库或 Issue |
| `WXDOUBAO_URL` | 可选，CLI 服务地址 |
| `MAE_FLOW_WXDOUBAO_TIMEOUT_MS` | 默认 150000 毫秒，允许 1000～600000 |
| `MAE_FLOW_PYTHON_BIN` | 资料解析 Python 3，默认 `python3` |
| `MAE_FLOW_PDFTOTEXT_BIN` | 可选 Poppler `pdftotext` 路径，默认从 PATH 查找 |

环境变量应注入运行 Cloud 的服务进程，不能依赖交互式 shell 的启动文件。新建领域任务可检查真实检索连接；未选无线豆包时不要求它可用。

## 两层归档与 MR

领域文档进入指定知识仓，仓内文档进入对应业务仓。只允许写入本次配置的 Markdown 文档目录，不允许模型修改源码、创建 MR、自动合并或自行扩大写入范围。研究阶段只保存草稿。

维护人审查后点击「一键创建或更新 MR」：

1. 按目标仓核对当前选中草稿、个人 Git 身份与远端文档。
2. 同一目标的开放 MR 继续使用原分支；已合入或已关闭后建立新分支与 MR。目标文档没有变化时不创建空 MR。
3. 推送与 MR 事实分别保存。推送失败保留上次确认内容；响应丢失时按原仓库、源分支和目标分支查重。一个仓失败不抹掉其他仓的结果。
4. 远端文档被人修改时停止覆盖。审查页的「远端合并」可读取目标分支和 MR 分支、查看差异、编辑合并稿，再明确确认该远端版本。提交前继续检查新的修改；与本次文档无关的源码冲突交由仓维护者处理。
5. 「刷新合入状态并入库」查询真实 MR 状态。合入后按 Git 目标分支当前内容同步正式知识文档；MR 状态、文档同步、检索索引分别显示。同步失败可重试，不创建替代 MR。历史 MR 留在任务内。

无变更且目标文档已存在时，直接按目标分支同步正式文档。正式目录按仓库、分支和路径复用条目，保留用户调整的适用范围与停用状态。领域正文的后续修改回到萃取工作台并通过 MR 完成；知识文档页只调整适用范围、启用状态或查看检索状态。

组件结果沿用既有知识采纳和索引链路：选定章节形成一篇 Markdown，采纳后可从同一任务开始更新，正式版本发生外部修改时拒绝无提示覆盖。

## CodeHub 适配

知识归档要求操作者个人 Git 用户、令牌与提交邮箱，不升级系统只读凭据。平台适配层需要 MR 创建、`GET /mr/discover` 与 `GET /mr/gates`。无法确认上次创建结果时停止重复创建，恢复查询后可重试。

知识请求通过 `purpose: "knowledge"` 选择 `mr_create_knowledge` 模板。仓库的 `deploy/adapter-config/adapter.codehub.json` 已提供携带关联单号的独立模板；部署时把它合并到实际适配层配置。普通需求和问题 MR 继续使用原 `mr_create` 模板。未配置独立模板时可复用包含 `{dts_no}` 的普通模板；旧的无单号模板需要更新后才能创建知识 MR。

## 代码与存储

- `domainKnowledgeExtraction.ts` 管理任务、人工版本、建议、停止、发布状态与持久化。
- `domainKnowledgeAgent.ts` 执行领域 Skill，复用只读源码工具，连接资料与无线豆包工具。
- `knowledgeMrPublisher.ts` 管理临时 Git 工作区、文档冲突、MR 恢复及正式文档同步；任务结束清理临时目录。
- `knowledgeExtractionSkills.ts` 管理两个方法包的独立发布、固定版本与回退。
- `knowledgeProcess.ts` 对工具进程实行超时、输出限制和取消；Unix 下终止同组解析子进程。
- `taskService.ts` 仅装配模型、源码与发布依赖；本次没有重构需求交付或问题处理机制。

## 验证与部署后核对

本地定向验证包含真实 Pi 会话与脚本模型、真实 Git 临时仓和 MR 服务替身、HTTP 登录权限、多格式资料解析，以及 Chrome 桌面交互（1920×1080、1366×768）。替身验证协议与行为，不代表真实内网服务已通过联合验收。

运行 `npm run typecheck` 和 `npm --prefix web run build`；按改动域运行 `componentResearch`、`componentApiBoundary`、`domainKnowledgeExtraction`、`knowledgeExtractionSkills`、`knowledgeExtractionRoutes`、`knowledgeMaterials`、`knowledgeMrPublisher`、`wxdoubao`、`platformAdapter`、知识文档与导航的定向测试。浏览器测试为 `componentResearchBrowser.test.ts` 和 `knowledgeLibraryBrowser.test.ts`，PDF 测试需指定实际 `MAE_FLOW_PDFTOTEXT_BIN`。不运行全量套件或聚合 gate。

部署后用 2～3 个相关业务仓和脱敏资料执行一次领域萃取：确认无线豆包真实权限、两层文档路径和来源，人工修订并创建 MR，维护者合入后刷新入库，最后从知识文档页核对适用范围、来源版本和索引状态。此步骤需要内网服务与个人写权限；本地开发没有对真实业务仓推送或创建 MR。

### MR 关联单号

新建领域萃取任务时必须填写一个关联单号，同一任务向各仓创建的 MR 都关联此单号。该字段独立于无线豆包检索用的 AR 编号。已有任务缺少单号时，在任务详情补填后才能创建 MR；已发起 MR 创建后不能更换单号，避免任务记录与平台关联不一致。

平台适配配置 `mr_create_knowledge` 必须传递 `{dts_no}`（CodeHub 使用 `--e2e-issues`）。MR 创建成功并返回链接即完成提交，不等待流水线变绿，也不自动合并。

### 基础组件归档与已有文件处理

基础组件萃取在“入库与更新”中提供“提交到代码仓”：配置仓地址、分支、目录、Markdown 文件名及关联单号。勾选章节生成一篇完整文档，可在归档阶段编辑合并稿。首次准备会读取同路径的远端文件，展示原文与差异；有差异时人工确认后提交，原文不变则不创建空 MR。提交前重新核对远端内容，变化时要求重新比较。组件与领域归档共享 MR 创建、重试、历史、冲突保护和合入同步能力；组件归档记录不出现在领域萃取任务列表中。

### 可选的提交前清理

“提交前清理旧知识”是一个默认关闭的可选操作。统一填写待删除的仓内目录或文件路径，AGENTS.md / agent.md 也按普通文件参与清理。预览中可以取消勾选需要保留的旧文件。新规范是本次新增内容的一部分，可根据当前待提交知识生成并编辑；不填写新规范时只删除旧文件，不强制生成替代文件。

操作顺序为：从 MR 分支的暂存内容中删除选中的旧文件，再写入本次选中的知识文档与可选新规范，最后生成一个 Git 提交并创建或更新 MR。删除和新增使用同一份清单确认，不直接修改目标分支。

预览记录目标与 MR 分支文件版本、当时选中文档的修订号。清理范围内的远端文件或待提交文档发生变化后需要重新预览；已提交清理不会随后续更新重复执行。合入后，已删除路径对应的正式知识条目停用，防止继续检索过时资料。单次预览最多 20 个路径、1000 个已有文件，拒绝仓根及 .git 路径。
