# 业务模块知识设计

状态：v1 实施基线
日期：2026-08-27

## 1. 要解决的问题

当前系统能观察任务读过的仓库文档，也有全局团队 Skill，但缺少正式的
“业务模块”层。由此产生两个相反的问题：

- 任务自己的需求、附件和过程文档会因为被 Agent 读过而看起来像团队知识；
- 真正跨任务复用的模块架构、接口约定和排障手册没有 Owner、发布版本和
  下单选择入口。

业务模块必须是一等实体，不能从 `docs/` 目录、仓库名或一次读取行为推断。

## 2. 三层边界

| 范围 | 典型内容 | 管理责任 | 任务中的行为 |
| --- | --- | --- | --- |
| 团队公共资产 | 安全规范、公共工程约定、团队 Skill | 团队管理员/资产管理员 | 所有任务可见精简目录，按需读取 |
| 业务模块资产 | 模块架构、接口约定、术语、排障手册、模块 Skill | 模块 Owner 与维护者 | 用户下单选择模块后可见精简目录，按需读取 |
| 任务材料 | 本次需求、附件、方案、过程文档 | 任务参与者 | 只留在本任务，永不自动晋升 |

任务材料只能产生“待沉淀候选”。候选必须脱敏、改写为跨任务内容，并由
对应模块 Owner 主动发布后，才获得正式资产 ID 和版本。

仓库中的 `AGENTS.md` 等项目规则同样属于仓库执行现场：它可以进入相关
任务的知识足迹，但不进入团队资产目录、排行或团队知识统计。

## 3. 领域模型

### 3.1 BusinessModule

- `id`：稳定 ASCII 标识，改名不改变 ID；
- `name`、`description`：给下单人和 Agent 看的业务定义；
- `owner`：唯一主 Owner；
- `maintainers`：可代管资产的人员，避免单点；
- `repositories`：用于推荐的仓库集合，不等同权限边界；一个仓可映射多个
  模块，一个模块也可覆盖多个仓；
- `status`：`active | archived`；归档后不能用于新任务；
- `revision`：模块元数据或资产变化时递增；
- 创建、更新时间和操作者留痕。

### 3.2 KnowledgeAsset

- `id`：模块内稳定标识；
- `title`、`summary`、`when_to_use`：目录检索所需的最小信息；
- `content`：Markdown 正文，不进入任务开场上下文；
- `status`：`published | archived`；
- `version`、`digest`、`bytes`：正文版本与完整性；
- `updated_by`、`updated_at`：责任与审计。

v1 只实现 Markdown 知识资产。模块 Skill 可在后续沿用同一归属、Owner 和
版本模型，但仍交给 Skill 装载器按 description 选择，不把正文全量注入。

### 3.3 TaskKnowledgeSnapshot

任务创建时固定：

- 所选模块 ID、名称、Owner 和模块 revision；
- 当时所有已发布资产的 ID、标题、摘要、适用场景、版本和 digest；
- 对应正文的只读快照。

模块后来更新不会改变运行中或历史任务。服务重启后仍从任务快照恢复，
而不是回头读取“最新版本”造成上下文漂移。

## 4. 权限

- 登录成员可查看活动模块的目录与已发布资产；
- 管理员创建模块、分配或转移 Owner、归档模块；
- 模块 Owner、维护者和管理员可发布、更新、归档本模块资产；
- Owner 可维护模块说明、仓库映射和维护者，但不能把 Owner 转给别人；
  Owner 转移由管理员完成；
- v1 不引入模块级可见性 ACL，团队内统一可见，避免权限模型先于真实需求
  膨胀；
- 所有变更写操作留痕。删除采用归档，历史版本和已创建任务快照不删除。

Owner 离职时由管理员转移；模块至少建议配置一个维护者，界面对此提示但
不作为任务门禁。

## 5. 下单体验

- 模块选择位于代码仓之后，不藏进“高级设置”；它属于业务定位而非运行参数；
- 支持一个主模块和最多三个关联模块。v1 数据层保存有序 ID，界面第一项
  视为主模块；
- 根据代码仓映射给出“推荐”，但不静默选中；用户必须明确勾选；
- 模块不是必填。无法归类的探索任务仍可发起，不能为了知识运营卡住交付；
- 卡片只显示模块说明、Owner、资产数量和更新时间，不在发起页铺开正文；
- 草稿和最近配置保存模块 ID；模块被归档后恢复草稿时自动移除并提示。

## 6. Agent 运行时契约

任务开场只注入有界目录：

```text
业务模块：订单中心（Owner: zhangsan，revision 7）
可按需读取：
- order-api：接口与幂等约定；修改订单接口时读取；路径 …/order-api.md
- order-release：发布与回滚手册；涉及部署时读取；路径 …/order-release.md
```

约束如下：

- 目录包含标题、摘要、适用场景、版本和任务内相对路径，不包含正文；
- 正文物化在任务工作区的只读 `.mae-flow-work/business-modules/` 下；
- Agent 使用受控 Read/Grep 按需读取，主 Agent 与子 Agent看到同一目录；
- 每篇正文限制 256 KiB，每任务最多 4 个模块、60 项资产、8 MiB 快照；
- 文件路径、软链接、digest 和 UTF-8 内容全部由宿主校验；
- 模块知识是参考上下文，不得覆盖系统安全约束、Mae-Flow 步骤、文件/Git
  边界或验证证据；
- 读取失败 fail-open 并记录警告，不得把知识服务故障变成交付阻塞。

团队强制规则与参考知识必须保持不同语义。只有明确标记为规则的资产才可
形成约束；普通知识正文不因措辞像命令就获得更高优先级。

## 7. 版本、撤回与冲突

- 发布或更新资产生成新版本，旧版本只读保留；
- 归档模块/资产只影响新任务，已创建任务继续读取自己的固定快照；
- 安全事件需要“紧急撤回”时可在后续版本增加 deny-list，让旧任务读取时
  明确失败并报告撤回原因；v1 先保留不可变快照，不暗改历史；
- 同名资产按 `module_id + asset_id` 区分，不依赖标题；
- 多模块内容冲突时展示来源和版本，不由宿主猜谁正确。团队强制规则优先，
  业务事实冲突由 Agent 提醒并请求业务确认。

## 8. 观测口径

知识足迹记录 `available / read / searched`，并带：

- `scope=module`；
- 模块 ID、模块名；
- 资产 ID、版本和 digest；
- 任务、会话角色、步骤和时间。

团队知识页只统计团队/模块正式资产以及 Skill。任务需求、仓库中临时选中
的 `docs/` 文档、项目规则和任务过程文档不进入排行、建议或资产数量。
不同模块任务难度不同，结果只作相关性参考，不做简单跨模块绩效排名。

## 9. UI 信息架构

团队知识页分为：

1. 业务模块：默认显示紧凑模块卡，展开后看 Owner、仓库映射和资产；
2. 团队 Skill 资产库：保持默认折叠；
3. 可复用资产消费：按团队或模块分组；
4. 改进候选：以后只生成候选，不自动发布。

资产名称必须可点击查看正文和版本事实。管理操作与内容放在同一区域，避免
设置按钮散落到页面不同位置。

## 10. v1 实施范围

本轮实现：

- 模块注册、Owner/维护者权限、仓库映射、归档；
- Markdown 资产发布/更新/归档、版本与内容查看；
- 发起任务选择模块；
- 创建时固定快照，Agent 只接收目录并按需读取正文；
- 模块知识读取足迹与团队知识聚合；
- 模块管理与发起页 UI。

暂不实现：复杂 ACL、向量检索、自动晋升、双人审核、外部知识库连接器和
紧急 deny-list。这些都应建立在真实使用数据上，而不是提前堆进第一版。
