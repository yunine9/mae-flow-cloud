# 小鲁班手机审批：内网对接交接单

目标只有一个：用户不打开电脑，也能在小鲁班里完成 Mae-Flow 的**单题或
多题审批**。进度查询、任务控制和自由对话不在本次范围。

## 1. Cloud 已经完成什么

Mae-Flow Cloud 已经提供以下能力，内网不需要重做：

- 复用 Cloud 主 HTTP 端口的回调路由：
  `POST /integrations/luban/plugin`；
- 会话式纯文本审批：唯一待办的出站通知会建立短期审批上下文，无需先查询
  “待审批”即可裸回复选项序号、确认语句或具体修改意见；
- `详情 / 选择 / 通过 / 退回` 仍作为无上下文兼容指令；
- 只列出并处理 `sender` 本人的任务；
- 审批码绑定账号、task、`waiting_id` 和 `state_version`，事项变化后旧码
  自动失效；
- `message_id` 幂等，同一条小鲁班消息重试不会重复提交决定；
- 最终复用现有 `TaskService.decide()`，没有第二套审批状态机；
- 多题卡按当前题逐题收集，每次回复后提示下一题；全部答完后才把结构化
  `answers` 一次提交，中间草稿不会冒充已生效决定；
- 选项不合适时可回复 `自由回复：答案或修改要求`，回执会确认原话已保留；
  模糊自然语言不猜、不提交，会明确提示消歧；全选项题支持 `1/2/1` 批量
  回复，逐题模式支持“重答上一题”；
- 启用手机审批后，原有待办通知直接展示当前问题与选项；账号仅有这一项
  待办时可直接回复序号。存在多项待办时，为避免把裸数字批到错误任务，
  必须使用通知里的审批码，或先发送“Mae-Flow 待审批”选择任务。
- “上述配置是否正确”这类依赖前文的问题会连同审批上下文一起发送；若
  上游没有提供被确认内容，Cloud 会禁止裸序号审批并明确要求打开任务链接，
  不让用户在看不到配置时盲批。

因此，内网侧只负责**协议翻译、网络可达和消息展示**，不保存任务状态，
也不调用 Mae-Flow 内核。

## 2. 内网必须完成什么

### 2.1 确认小鲁班插件协议

请从小鲁班平台拿到并记录以下五项，不要靠猜：

| 必须确认 | 用途 |
| --- | --- |
| 一份真实回调 JSON 样例 | 确定消息正文与字段层级 |
| 用户工号字段 | 映射到 Mae-Flow 本地账号 |
| 唯一消息/事件 ID | 映射为 `message_id`，保证重试幂等 |
| 是否能配置固定 HTTP Header | 决定插件能否直连 Cloud |
| HTTP 响应怎样显示给用户 | 决定同步返回还是另发一条小鲁班消息 |
| 首次调用后能否接收后续裸回复 | 保证用户可直接回复 `1`、`2` 或修改意见 |

还需确认回调超时、重试次数、来源网段，以及平台是否提供原生验签。

### 2.2 打通网络

小鲁班**服务器**必须能访问 Cloud，不是手机直接访问 Cloud。注册地址应为
稳定的内网域名或负载均衡地址，例如：

```text
https://mae-flow.example.intra/integrations/luban/plugin
```

禁止注册 `127.0.0.1`、个人电脑临时 IP 或只能从浏览器所在网段访问的地址。
若 Cloud 前有反向代理，只放通该 `POST` 路径即可，不需要开放其他任务 API。

### 2.3 配置固定回调 Token

这个 Token 只证明请求来自受信的小鲁班插件或内网桥：它不是个人小鲁班
发送 Token，也不需要每位用户配置。

Cloud 服务器上创建一次：

```bash
umask 077
openssl rand -hex 32 > /etc/mae-flow-cloud/luban-plugin.token
chmod 600 /etc/mae-flow-cloud/luban-plugin.token
```

在 `serve.json` 增加：

```json
{
  "luban-plugin-token-file": "/etc/mae-flow-cloud/luban-plugin.token"
}
```

此时只代表 Cloud 接收端点准备完毕。真实插件/入站桥完成第 6 节验收后，
才增加下面的能力声明并重启：

```json
{
  "luban-plugin-replies": true
}
```

如果端到端回复再次失效，应先将它改回 `false`：通知继续送达并保留 Web
链接，但不再误导用户回复一个无人接收的 `1`。

插件或内网桥调用 Cloud 时携带：

```text
X-MFC-Luban-Plugin-Token: <文件中的固定值>
```

也兼容标准头 `Authorization: Bearer <固定值>`。Token 不得写进仓库、日志、
小鲁班消息正文或 URL 查询参数。

## 3. 直连还是走桥

### 方案 A：插件直连 Cloud

只有小鲁班插件同时满足以下条件时使用：

- 可自定义回调 URL；
- 可发送固定 Header；
- 请求能直接形成 Cloud 所需的三字段 JSON；
- 能把 Cloud 的 `{"text":"..."}` 响应显示给用户。

Cloud 的稳定请求契约为：

```http
POST /integrations/luban/plugin
Content-Type: application/json
X-MFC-Luban-Plugin-Token: <固定Token>

{
  "message_id": "小鲁班唯一事件ID",
  "sender": "Mae-Flow账户名",
  "content": "mae-flow 待审批"
}
```

### 方案 B：扩展现有 `luban-bridge.py`（更可能）

小鲁班真实字段不一致、不能加 Header，或者响应格式不同，就让现有通知桥
增加一个入站路由。桥只做以下翻译：

```text
小鲁班原生回调
  → 验证小鲁班原生身份（如果平台提供）
  → 提取稳定事件 ID、真实工号、用户输入
  → 去掉 @机器人等平台前缀
  → 组装 {message_id, sender, content}
  → 加 X-MFC-Luban-Plugin-Token
  → POST 到 Cloud
  → 把 Cloud 返回的 text 转成小鲁班要求的响应形状
```

桥不缓存待办、不判断选项、不生成审批码、不调用内核。它必须在插件会话内
继续转发同一用户的后续裸消息，`content` 保留原文。若小鲁班回调不支持
同步展示响应，桥再调用现有小鲁班发送接口，把 Cloud 返回的 `text` 发给
原 `sender`；审批语义仍只在 Cloud。

## 4. 字段映射要求

| Cloud 字段 | 内网映射要求 |
| --- | --- |
| `message_id` | 必须来自小鲁班稳定事件 ID；平台重试时保持不变。没有原生 ID 时，桥对不变的原始事件内容计算稳定哈希，不能每次随机生成 |
| `sender` | 必须是可信回调里的真实工号，并与 Mae-Flow 登录账号完全一致；不要相信用户在消息正文里自报的工号 |
| `content` | 用户主动调用插件和后续会话输入的原文；桥可去除 @机器人/插件固定前缀，但不要补写命令、改选项序号或意见正文 |

若小鲁班工号形状与 Mae-Flow 账号不同，应由管理员提供一份明确、唯一的
映射；映射不到或一对多时拒绝请求，不能猜。

## 5. Cloud 响应与状态码

响应正文固定为 JSON：

```json
{"text":"要展示给用户的纯文本"}
```

| HTTP 状态 | 含义 | 内网处理 |
| --- | --- | --- |
| 200 | 查询成功或决定已提交 | 原样展示 `text` |
| 400 | 指令/选项格式不对 | 原样展示 `text`，不要自动重试 |
| 401 | 固定 Token 不对 | 记桥日志并报警，不向用户泄露 Token |
| 403 | 工号没有启用中的 Mae-Flow 账号 | 提示联系管理员 |
| 409 | 审批码过期、事项变化或 message_id 冲突 | 展示 `text`，让用户重新执行 `mae-flow 待审批` |
| 413 | 回调正文异常过大 | 记桥日志，不重试 |
| 500 | Cloud 临时失败 | 小鲁班按有限次数重试；保持原 message_id |

## 6. 联调顺序

1. 确认 Cloud 当前没有运行中的任务，按现有部署手册重启服务；必须保留
   `--public-url http://<内网地址>:<端口>` 和已有容器/平台参数。
2. 启动日志应出现：
   `小鲁班 Cloud 回调端点已就绪: /integrations/luban/plugin`。
   初次联调时还应出现“尚未声明入站回复已接通”；只有配置
   `luban-plugin-replies: true` 后才应出现“入站回复已由部署显式启用”。
3. 使用一个已启用的开发账号，从内网桥请求 `mae-flow 待审批`；没有待办时
   应返回 `当前没有待审批事项。`。

   可先用占位值核对请求形状；实际 Token 从受控文件读取，不要把它提交到
   脚本仓库或粘贴进共享日志：

   ```bash
   curl -sS -X POST \
     'https://mae-flow.example.intra/integrations/luban/plugin' \
     -H 'Content-Type: application/json' \
     -H 'X-MFC-Luban-Plugin-Token: <实际Token>' \
     --data '{"message_id":"manual-check-001","sender":"<有效账号>","content":"mae-flow 待审批"}'
   ```

4. 先保持 `luban-plugin-replies: false`，通过插件发送 `mae-flow 待审批`
   验证入站、工号映射和响应展示。确认 Cloud 日志出现不含正文与 Token 的
   “小鲁班审批回调已处理”记录后，再把开关设为 `true` 并重启。
5. 创建一张单题待审批任务，确认通知同时出现被确认内容、完整问题与选项；
   不要先发送 `待审批`，直接回复 `1`，决定应一次成功。再创建两张并行待办，确认裸
   序号被安全拒绝，使用通知里的审批码后可处理指定任务。
6. 再创建一张可退回的单题卡，直接回复具体修改意见，确认 Cloud 选择已有的
   修改/退回选项，并在 Web 中保留意见原文。
7. 创建一张三题卡，确认通知和详情包含全部三题；依次回复后，前两次显示
   “已记录、尚未提交”及下一题，第三次回复后 Web 中一次出现三题答案。
   再验证一次 `1/2/1` 批量回复，并用 `自由回复：…` 修改其中一题，确认回执
   和 Web 决定备注都保留用户原话；发送无法判断的普通文字时应提示且不提交。
8. 验证另一账号看不到该任务。
9. 使用同一个 `message_id` 重发决定，确认不会二次审批。
10. 先让电脑端处理事项，再用手机提交旧审批码，应收到“事项已更新或审批码
   已过期”。
11. 使用错误 Token 请求，应返回 401。

## 7. 上线验收标准

- [ ] 手机无需访问 Cloud 内网网页；
- [ ] 小鲁班通知能提示打开“Mae-Flow 待审批”插件；
- [ ] 唯一待办通知直接包含当前问题和选项；
- [ ] 引用“上述/以上配置”的通知同时包含被确认的具体内容；缺内容时禁止裸批；
- [ ] 无需先查询待审批，直接回复 `1`、`2` 或具体意见即可处理唯一待办；
- [ ] 多待办时裸序号不会误批任务，带审批码的回复可精确处理；
- [ ] 只能看到和审批本人任务；
- [ ] 详情中的问题、选项和 Cloud 页面一致；
- [ ] 退回必须带意见；
- [ ] 重试不会产生两次决定；
- [ ] 旧审批码不能批准新事项；
- [ ] 多题通知包含全部问题与选项；逐题回复只在全部完成后统一提交；
- [ ] 选项不合适可显式自由回复且原话不丢；模糊输入不猜并给出明确提示；
      批量回复与“重答上一题”可用；
- [ ] Token 与个人发送 Token 均不出现在日志和响应中；
- [ ] `luban-plugin-replies: false` 时通知不承诺直接回复，原出站通知和 Web
      审批不受影响；去掉 Token 文件后回调端点关闭。

## 9. 可直接交给内网适配 Agent 的提示词

下面这段可以原样交给能访问小鲁班平台、部署机和反向代理的内网 Agent。
它的目标是完成适配与验收，不是再写一份方案：

```text
你负责打通“小鲁班用户回复 → Mae-Flow Cloud 手机审批”的真实入站链路。

现状：
1. Cloud 出站通知已经通过 /etc/mae-flow-cloud/luban-bridge.py:8791 送达；
   这条桥目前只负责 {account,text,link} → 小鲁班发送接口，不能假设它会接收回复。
2. Cloud 已提供 POST /integrations/luban/plugin，稳定内部请求契约是：
   Header: X-MFC-Luban-Plugin-Token: <从 0600 Token 文件读取>
   JSON: {"message_id":"稳定唯一事件ID","sender":"Mae-Flow账号","content":"用户回复原文"}
   响应: {"text":"应展示给用户的纯文本"}。
3. serve.json 中 luban-plugin-token-file 只代表 Cloud 端点就绪；
   luban-plugin-replies 必须保持 false，直到本任务端到端验收全部通过。

必须完成：
1. 从小鲁班平台取得一份真实、脱敏的入站回调样例，确认消息正文、真实工号、
   稳定事件 ID、原生验签、固定 Header 能力、同步响应展示方式、超时和重试规则。
   不得根据字段名猜协议。
2. 优先评估插件能否直连 Cloud；不能时扩展现有 luban-bridge.py 增加入站路由。
   出站通知行为必须保持不变。
3. 入站适配只做：验证小鲁班身份、提取稳定事件 ID/可信工号/回复原文、
   映射 Mae-Flow 账号、加内部固定 Token、转发 Cloud、展示 Cloud 返回的 text。
   不缓存待办、不解释选项、不自行决定、不调用 Mae-Flow 内核。
4. 同一用户收到通知后的后续裸回复“1”“2”或修改意见必须继续进入同一插件
   会话并原样转发。若小鲁班做不到“回复普通通知即触发插件”，必须如实报告，
   并把产品入口改成明确的插件会话动作，不能声称可直接回复。
5. message_id 在平台重试时必须保持不变；sender 必须来自可信回调字段，
   不能相信正文里自报的账号。映射不到或一对多时明确拒绝，不能猜。
6. 日志只记录时间、脱敏事件摘要、sender、HTTP 状态和耗时；禁止记录 Token、
   用户回复正文和完整事件 ID。500 可有限重试，400/401/403/409/413 不盲重试。
7. 打通反向代理和网络：小鲁班服务器访问稳定内网域名的上述 POST 路径，
   不使用 127.0.0.1、个人临时 IP，也不把 Cloud 其他任务 API 暴露给插件。

必须用真实测试账号完成以下验收并保留脱敏证据：
A. 发送“mae-flow 待审批”能看到本人待办和完整审批上下文；
B. 仅一项待办时，收到通知后直接回复“1”，Web 中对应决定一次生效；
C. 同账号两项待办时裸“1”被明确拒绝，审批码可以精确处理；
D. 同 message_id 重放不产生第二次决定；旧审批码返回已更新/已过期；
E. 具体修改意见原文被保留；模糊回复不猜选项并给出明确提示；
F. 另一账号看不到本人的任务；错误 Token 返回 401；
G. “上述完整配置是否正确”通知必须带出具体配置；若材料缺失则禁止裸批；
H. Cloud 日志出现“小鲁班审批回调已处理”，且不含正文、Token、完整事件 ID。

全部通过后才把 serve.json 的 "luban-plugin-replies" 改为 true、重启服务，
再重复 B/C/G。任何一项失败都保持或恢复 false，让通知继续送达但不误导用户。

最终交付：
- 采用直连还是桥接及原因；
- 实际修改的插件/桥/反向代理/systemd 文件；
- 脱敏回调样例和字段映射；
- 每项验收的时间、请求摘要、Cloud 响应与 Web 状态证据；
- 未解决限制及用户将看到的明确提示。

核心原则：不阻塞正常 Web 审批，不糊弄能力状态；处理不了或语义模糊时，
明确告诉用户缺什么、下一步做什么，绝不猜测并提交决定。
```
