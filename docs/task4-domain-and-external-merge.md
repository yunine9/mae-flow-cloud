# task-4 归档与外部合入契约（2026-09-08）

## 领域归档

候选与工作区正文一致，不代表它相对本需求交付基线没有增量。
已经在前一轮提交的领域文档仍可能属于当前 MR 的变更。

prepare 根据本需求范围的 Git 变化，识别需要重新登记的已核对候选；
apply 原样应用并登记这些文档及索引，不要求人为改动文字来制造增量。
后续轮次只 prepare 一个领域时保留其他已有候选，show/apply 一并核对。
真正没有基线增量的 unchanged 仍保持空交付，不制造无意义提交。
未知文档、用户拒绝的领域归档、prepare 后被改动的候选不自动认领。

已停在 applied/unchanged 且 applied_paths 为空的旧现场，可重新执行
domain-archive apply；候选、输入及原确认仍有效时补齐登记。
输入已经变化则先重新 prepare/show/apply，不手改状态中的路径数组。
无候选的已有领域文档仍通过 --adopt-existing 明确认领。

## 外部合入

用户明确：平台外部人工合入默认可信。完成依据是远端 MR 的 merged
事实及源提交 SHA，由宿主签名 close 进入内核终态，不要求旧验证 SHA
与之相同，也不要求人工补造平台缺失的流水线结果。

旧 delivery.sha、git_push、流水线结果保持不变；实际源提交单独存为
delivery.merged_sha 和内核 close 事件。先停止 Agent、Build-Fix 及容器，
再收口。未推送的本地工作保留审计记录，不当作已经交付。
未合入时仍检查版本和质量。分支变化暂停交付但不退出合入监听；
检视回执发布失败不阻止读取平台合入事实。恢复及下游解锁均核对同一
可信 close，不再要求外部 SHA 具有本平台流水线 PASS。

验证覆盖领域多轮归档、已有提交、无增量、归档边界、真实宿主签名、
不同 SHA 合入、失败/缺失验证、回执发布失败、writer 停止及下游解锁。
本地回归使用临时 Git 仓、真实内核和模拟平台；不代表内网部署已验收。
