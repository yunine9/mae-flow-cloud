# 提前开始待启动任务

任务已拆分成串行队列后，主任务责任人可在子任务工作台的“等待前置任务”处点击“提前开始”，直接调整安排。平台计算并展示影响，由责任人判断代码、接口和业务依赖是否允许并行。无需向 Agent 解释、重新拆单或重新走需求确认。

## 行为

- 只对 queued 且尚未建立执行现场的任务开放；不能借此修改已运行任务的分支、提交或 MR。
- 服务重启产生的 `resume` 标记不代表已开工；一直等待前置的任务重启后仍可调整。不可调整时页面直接展示原因。
- A → B → C → D 中解除 D 对 C 的等待，会明确展示 D 不再等待 A、B、C；A、B、C 保持原顺序。
- 可只解除部分直接前置。菱形图中仍通过另一条路径等待的祖先不会被误报为解除。
- 调整中间任务时，后继可能随之提前，预览会列出后继及其失去的等待关系。所有任务原有的其他直接依赖保持不变。
- 不同仓可共用 AR，同仓串行可共用 AR，同仓并行不能共用 AR。检查跨主任务、责任人以及尚未运行的任务，并统一仓库地址别名。目标任务可在本次确认中换 AR；如果影响后继产生同仓同 AR 冲突，会明确指出涉及任务，需先调整该后继的安排与单号。不会偷偷修改其他任务的 AR。
- 有剩余前置时继续等待；无剩余前置时进入可执行队列，有名额才启动。界面不会将其显示成“已经开始”。
- 只认主任务责任人；子任务责任人、检视人和管理员角色本身不能替主责任人决定。独立任务由自己的责任人操作。

## 数据与一致性

`blocked_by` 是调度的唯一依据。本次新 AR、剩余依赖和 `dependency_adjustments` 操作记录一次写入目标任务的 `task.json`，严格落盘成功后才唤醒队列。写入失败回滚内存；同一预览重复请求只重放结果。重启仍读取这份状态。

预览 `revision` 绑定有效依赖、相关任务、归属、AR 及可操作状态；确认时重新计算。期间上游完成、其他任务改变单号或关系等情况会要求重新展示影响，不自动套用旧确认。无关的进度和 token 更新不会让预览失效。

API 显式返回空的 `blocked_by: []`，让前端增量刷新能够清掉旧等待；主任务分工图从子任务实际依赖与 AR 投影。资源排队名次排除尚在等待依赖的任务。主 Story 仍承载业务设计，执行提示和实际物化任务书会附上责任人的新执行安排，覆盖旧的调度与单号口径。

提前开始不会伪造前置完成、流水线通过或 MR 合入，不会另建任务、分支或审批卡。目标正常开工时才按新 AR 和当前基线建立自己的现场。

## 接口

- `POST /tasks/:id/early-start/preview`：可选 `release_ids`、`ticket`，返回影响和 `revision`。
- `POST /tasks/:id/early-start`：提交 `revision`、`release_ids`、`ticket`，返回最新任务。越权为 403；过期或不满足条件为 409。

这是现有任务服务接口，沿用会话认证。Agent 不参与决定和转述操作；它启动后只读取已经生效的安排。

## 验证

`tests/taskEarlyStart.test.ts` 使用真实 TaskService 与 HTTP 服务，覆盖长链、菱形、跨仓与跨责任人 AR、后继影响、过期预览、并发确认、落盘失败、重放、暂停恢复、重启及真实队列选单。仅启动外部 Agent 的执行端口在队列测试中受控替换，证明只选中解除等待的任务，不消耗真实模型。

本地真实服务配合构建后的完整前端实际点击了影响预览、AR 冲突、换号和确认。截图保存在 `.pilot/task-early-start-evidence/`。同时修正公共 Dialog 使用低于工作台的层级导致弹窗被遮挡的问题，采用站点既有 `--z-modal` 令牌。

2026-09-12 补齐“解锁前重启”回归：先落盘并关闭服务，再由新 TaskService 恢复，验证未开工子任务可以换 AR 并解除等待；有实际工作目录、会话、验证或交付记录的仍不可调整。原测试只验证“解锁后重启不丢安排”，漏掉了这一路径。新增用例在修复前稳定失败；修复后关联回归 18 项通过，并在重建后的真实服务点击验证入口。截图保存在 `.pilot/early-start-recovery-evidence/`。
