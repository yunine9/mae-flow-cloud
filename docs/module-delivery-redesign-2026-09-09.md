# 模块交付、验证与检视改造方案

日期：2026-09-09。

状态：本文统一记录用户确认的目标流程与后续修正。主任务 Story 已替代新增 CHAIN，模块拆分与路径参考语义已实现；子 Spec 测试设计、可测试性与用例落实提示词、当前责任人逐条处置已接入。Archify 离线展示、4+1 覆盖说明、Story 定位跳转及注释规范增强已接入，真实业务端到端仍在复测。字段命名、兼容策略和实施顺序是工程建议。

## 1. 已确认的产品基线

1. 整体分析需求与跨仓场景，按仓组织交付，仓内按能力拆模块。模块有职责、消费方和可验证行为；施工步骤留在模块内部。根据需要先交付公共契约、骨架和基础设施；后续按功能模块拆分，每个模块包含自身接口接入、业务逻辑和测试。公共准备任务可单列，不强制每个需求都设置，也不把骨架完成记成业务功能已完成。
2. 模块可以依赖其他模块。契约明确后允许基于 mock 先做，自身验证和真实集成验证分别记录。业务依赖不自动等于必须等待上游合入，也不要求立即实现同仓并行。
3. 文件清单是预计影响位置，不是修改白名单。局部、兼容、影响可控的调整由 Agent 自行完成并说明；影响验收、兼容性或其他责任人工作的变化优先提前说明并请求决策，但不按文件或字段变化机械阻断。
4. 验证高优先级、尽力而为。函数 UT、模块级 UT、接口测试、MST 与真实环境验证持续建设。无法验证时报告原因、证据和影响，由责任人决策；允许继续不能改写失败或未验证事实。
5. 注释是提示词和检视中的强导向，不是硬门禁。编码时同步维护，按需使用补注释 Agent，不默认增加固定环节。
6. 检视人提出意见、补充异议；责任人拥有最终处置和提交决定权，必须逐条闭环，不提供批量闭环。Agent 的处理回执不等于人工闭环。
7. 整体分析阶段生成全局 Story，功能模块拆分及其约束体现在 Story 的 4+1 中，不另建一套拆分用架构设计。全局 Story 可以随设计、实现和验证进展持续更新，保留确认版本及变化记录；子 Story 引用全局约定并细化模块内部设计。工作台交互图与正式文档引用同源的模块和关系信息。

8. 主任务仅维护一份全局 Story，替代独立 CHAIN，沿用原模板；子任务保留 Spec 与 Story，子 Spec 承载本模块行为与具体测试设计。不新增全局 Spec 或独立测试设计文档。
9. 模块级 UT 及设计用例的落实先通过提示词和现有检视流程推进。不新增 hook、门禁、阻断状态或固定审批。用例编号、对应清单和报告是阅读材料，不以格式或完整率控制流程。
10. mock 的原则是“合理隔离外部依赖，保留被测逻辑的真实执行”，不追求数量少。测试目标决定数据库、远端调用等是否替换；公共替身按需复用、按用例隔离状态。

## 3. 目标用户流程

1. 用户给出需求及候选仓。Agent 从整体场景分析职责、依赖和各仓是否需要修改。
2. Agent 在整体分析中编写全局 Story，逐步明确仓内功能模块、关键类与接口、验收场景、依赖条件及 4+1。预计代码位置可供导航，没有路径清单也不应因此否决模块。
3. 责任人检视全局 Story 中的拆分与约定、分配责任人；按需创建公共准备任务，再按功能模块创建任务。子任务分析通过子 Spec 明确本模块行为和测试设计，通过子 Story 细化实现；二者引用全局约定，不等子 Story 都生成后才形成全局设计。
4. Agent 根据全局 Story 落实必要骨架、实现各模块并同步注释；可以调整必要公共代码。全局 Story 随实际发现持续修订，实质设计变化说明影响，按已确认的弹性原则沟通。
5. Agent 尽力执行函数和模块验证，按可用能力执行接口、MST 与真实环境验证。每项结果关联场景、版本和证据，未执行项保留原因。
6. 检视人逐条提出意见；Agent 或责任人给出处理依据，责任人逐条闭环。异议和原始记录保留。
7. 交付确认汇总验证事实、缺口、重要设计变化和意见处置。责任人决定下一步，平台不把其决定写成测试成功。
8. 主需求汇总模块交付和跨模块场景验证情况。所有子任务合入不能自动伪装成完整业务链路已验证；存在缺口时沿用责任人决策原则。

## 4. 能力模块 A：模块分析与交付组织

### 模块描述

每个模块表达稳定标识、所属仓、职责和消费方、对外行为、验收场景、依赖契约及责任人。预计修改位置是可选参考，不承担授权功能。

例如“通知偏好管理”包含保存、查询和生效规则及其测试；“通知过滤”包含基于偏好决定发送或拦截的行为。建表、接口实现和补测属于相应模块内部工作。跨仓的“用户修改偏好后通知行为改变”保留为主需求场景。

### 数据和执行建议

- 保留既有任务标识、仓库绑定和单仓执行任务机制。先扩展现有图协议，不为命名整洁一次性迁移所有历史 `repositories` 字段。
- 新协议把模块描述与可选参考路径分开。旧 `scope.paths` 可读作历史参考，但不能继续被新规则当作文件白名单；须有显式版本区分。
- 架构关系允许循环；执行前置条件需要满足调度可执行性。不能把运行时相互调用直接转成循环等待。
- 明确真正需要等待合入的前置条件，以及仅需契约就绪的依赖。现阶段同仓串行仍可保留，但应呈现为调度安排，不能伪称业务上必须等待。
- 取消交付范围白名单时，只处理模块文件范围语义。分析阶段只读权限、工作区隔离与文件系统安全校验职责不同，应避免误删。

### 验收场景

1. 同仓需求可拆为公共契约与骨架、偏好管理、通知过滤三个任务；后两个任务各自包含逻辑、接入和测试，不拆成所有模块的骨架、所有逻辑、统一补测。
2. 公共设施有明确消费方和验证行为时可以独立成立；一个仓也可以只有一个模块。
3. 修改未列入参考路径的必要公共代码，不触发旧越界放行卡或文件范围推送门禁。
4. 跨仓完整场景可追踪到多个模块；运行依赖不会被全部转换成合入等待。
5. 契约明确、真实依赖未完成时，方案能够表达可先做及后续联调缺口；不以此验收同仓并行能力。

## 5. 能力模块 B：验证事实与交付决策

### 验证语义

内部统一使用函数 UT、模块级 UT、接口测试、MST、真实集成场景等清晰名称。“模块级 UT”尽量从模块入口执行内部真实逻辑，在外部边界使用 mock；MST 按本次讨论指隔离目标微服务、mock 周边微服务。

范围与环境分别描述：REST 是调用入口，mock 是依赖运行条件，不能把二者当作测试充分程度的线性等级。

先由 Agent 在现有报告中说明验收场景、验证方法、环境与依赖、预期行为、实际结果、证据及对应代码版本，区分已通过、实际失败、未执行，以及旧证据不再适用的情形；未执行说明原因。这里是报告内容要求，不新增结构化回执协议、格式校验或流程状态。后续自动关联与统计仅辅助展示。

流水线仍是流水线结果的权威来源；本地测试输出仍是其实际执行证据。责任人的决定另行记录操作者、时间、针对版本和已知缺口，不覆盖原始事实。实现变化后，受影响的旧证据不能静默沿用为当前通过。

### 主任务与子任务的测试设计分工

| 阶段 | 产物与职责 | 测试设计粒度 |
| --- | --- | --- |
| 主任务整体分析 | 全局 Story，沿用原模板第 3 章及验收章节 | 需求级验收、模块验证分工、跨模块场景；不提前猜测具体函数和 mock 对象 |
| 子任务模块分析 | 子 Spec 明确本模块行为，细化验收与测试设计；子 Story 说明内部设计和可测试性边界 | 函数 UT、模块 UT、适用的集成验证；明确入口、真实执行范围、替身和必要环境 |
| 子任务编码 | 测试代码关联设计用例，具体函数确定后继续细化用例 | 预期以已确认行为为依据，不根据现有实现倒改业务规则 |
| 子任务收口与主任务整体验收 | 复用现有报告与检视材料 | 子任务报告本模块证据；主任务保留跨模块验证及缺口，不以所有子任务完成替代整体验收 |

主任务原 Story 模板及章节保持不变。子 Spec 的“验收条件”内容扩展为测试设计，可先保留原章节名，避免为了改标题扩大模板校验改动。子 Story 的既有测试章节保留并引用子 Spec 相应用例及必要技术说明，不手工维护两份完整用例列表。

子 Spec 中的用例采用一句话：

> **SQL001｜函数UT**　**条件：**指定用户和时间范围；**操作：**构造查询；**预期：**查询条件完整，绑定参数顺序正确。

不逐条增加优先级；条件、操作、预期使用加粗标签。工作台可给标签增加颜色，但不能只靠颜色表达含义，也不能把预期颜色解释为执行成功。公共环境、初始化和替身约定在模块测试说明中统一记录，不在每条用例重复。

### 设计用例如何落实（提示词与人工检视）

- 用稳定编号关联设计场景与测试名称或注释，允许一对多、多对一，避免为凑对应关系拆出无意义测试。
- 编码 Agent 收口时按设计逐条说明对应测试位置、实际执行结果和证据；未编写、未执行或覆盖不足的用例说明原因与影响。报告使用自然语言或简表，不强制机器字段。
- 检视核对测试输入、断言和依赖替身是否符合用例意图，不能只检查编号是否存在；函数 UT 与模块测试互补。
- 编号不匹配、缺少报告、某条未执行，不触发新的 hook、门禁或阻断状态。缺口通过现有检视交给责任人决定，不自动关闭意见，也不自动伪造通过。
- 后续若增加编号匹配、证据链接和缺口统计，也只作辅助展示，不建立测试设计驱动的第二套流程状态机。

### 决策体验

复用已有交付确认，集中呈现已验证能力、实际问题、未验证项及原因、潜在影响和建议。无需对每个缺口分别举卡。无法继续开发的事项可以提前询问。

区分“责任人接受验证缺口继续交付”与“外部仓库允许合并”。平台可记录前者，不能改写外部流水线或绕过 Git 平台既有权限。验证缺口复用已有责任人决策和适用的跳过机制，不新建审批路径；用户接受缺口的记录与实际测试结论保持分离。既有权威编译/UT/CodeCheck 流水线规则不被这份测试设计提示词静默改写。

### 验收场景

1. 模块内部函数都通过，但验收场景没有被验证时，不显示为全场景通过。
2. mock 验证成功且真实环境不可用，分别展示成功证据和真实联调缺口。
3. 测试发现行为错误、工具执行失败、环境未配置三种情况具有不同说明。
4. 责任人接受缺口后可进入适用的下一步，历史缺口仍可查看；外部合并限制仍如实显示。
5. 更新实现后，受影响证据过期，旧决定不被无条件套用于新版本。

### 分阶段建设

用户确认模块级 UT 当前先通过提示词强调，复用业务仓已有框架、测试命令和运行环境，由 Agent 结合模块场景建立测试装配并报告真实/mock 边界、实际结果及缺口。不以统一模块测试平台或专门适配器建设为前提，不增加专门门禁；后续根据实战问题逐步优化。

平台层后续贯通已有 UT/流水线证据、模块验收映射和缺口决策，再按真实项目接入 REST、MST 和部署环境。每批保留完整的结果展示与责任人决策，不以所有适配器完成为前提。

## 6. 能力模块 C：责任人逐条检视闭环

### 权限与处置

| 动作 | 检视人 | 当前任务责任人 | Agent |
| --- | --- | --- | --- |
| 提交意见、补充异议 | 可以 | 可以 | 可产出自动检视意见并保留来源 |
| 提供处理依据 | 可以补充讨论 | 可以 | 可以提供逐条回执 |
| 闭环意见 | 不可，除非同时是该任务责任人 | 逐条操作 | 不可 |
| 决定任务提交 | 不可，除非同时是该任务责任人 | 可以 | 不代替人工决定 |

责任人按被检视任务归属解析：主需求意见由主需求责任人处理，子任务意见由子任务责任人处理。跨模块影响按设计变化规则协调，不把主责任人自动变成所有子任务的意见裁决者。

建议将“是否闭环”与“处置结果”分开：已修复、不采纳、延期、接受未解决问题继续均保留真实含义。每条需要处理依据；Agent 已提供充分说明时，责任人不必重复书写。不采纳、延期或未解决仍闭环必须有明确理由。

前端无批量闭环入口，后端也不允许通过最终提交隐式关闭多条意见。责任人的逐条决定绑定意见当前修订，旧版本回应不能用于悄悄关闭新版本问题。

作者编辑、撤回自己的表达与责任人处置属于不同动作：不得再把作者撤回事件无区分地投影为责任人确认通过。保留历史，避免撤回动作成为绕过逐条责任确认的捷径。

### 改动贯通范围

共同修改 annotations 台账、feedbackPolicy/feedbackLoop 的闭环投影、taskService 服务鉴权、server 接口、推送与完成条件、AnnotationPanel、需要我处理的待办、通知、意见回执文案和相关记忆记录。将管理员代作者关闭的现有路径一并核对，防止旧例外绕过新责任规则。

### 验收场景

1. 检视人可发送意见，但调用关闭或任务提交接口被拒绝，不能仅隐藏按钮。
2. 责任人可逐条确认他人提出的意见；未全部处置时，最终提交不能隐式代办。
3. Agent 回执不能关闭意见；责任人不采纳后记录理由，不显示为检视人认可。
4. 意见被修改后旧回执和旧操作不能误关闭新修订；历史已闭环记录不重写操作者。
5. 重启后待办归属、未闭环数量、交付条件保持一致；任务责任人变更后新动作按当前归属鉴权。

## 7. 能力模块 D：注释质量辅助

扩展既有 comment-standard，不另建竞争规范。模块级说明覆盖职责、边界和依赖；接口说明覆盖非显然输入输出、错误、副作用和并发约束；复杂逻辑解释业务原因与设计取舍。

模板只包含适用项目，不强制填空，不以注释比例、字数或固定 ADD/UPDATE/NONE 标记控制流程。现有“三行以上移到设计文档”等形式约束应改成可读性建议，避免压缩必要说明。

编码 Agent 同步编写；工程质量检视显式关注缺失和失真。复杂模块按需使用补注释 Agent，提供真实设计依据；无法确认的原因应报告，不编造。补注释不得借机修改业务行为，也不默认增加新一轮人工确认。

验收：复杂接口的约束获得清晰说明；简单代码不生成逐行复述；没有注释或没有调用补注释 Agent 不自动阻断；注释与实现不一致时作为具体检视问题呈现。
