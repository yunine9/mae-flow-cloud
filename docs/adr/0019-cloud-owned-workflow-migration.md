# 工作流向 Cloud 单仓、单一运行时收敛

日期：2026-09-09。用户确认方向：逐步把内核逻辑迁入 Cloud，最终不再依赖独立内核仓。

## 目标与当前进度

目标是一个仓库维护、一份业务规则、同一任务只有一个状态写入者。迁移不是把现有 Python 门禁逐行翻译成 TypeScript；已撤销的质量、模板、文件来源和提交写法否决权不重新实现。

本次完成维护边界梳理和迁移决策，尚未切换任何业务模块的运行权威。当前任务仍由现有运行链处理。下面的阶段不是已经完成的功能。

## 已有边界

| 能力 | 当前实现 | 迁移处置 |
| --- | --- | --- |
| 会话调度、排队、容器、Build-Fix、Git 推送、MR、流水线 | Cloud 的 `taskService.ts`、会话驱动和各服务模块 | 保留；从大服务类中按职责拆出，不另造执行器 |
| 需求批注、回执消费、反馈闭环 | Cloud 批注与反馈记录，`kernelDelivery.ts` 调 Python delivery 命令 | 优先迁移；明确“已收到回执”和“人工验收通过”的区别，减少跨进程对账 |
| 人工选择、交付清单、审批对象绑定 | Cloud 决定入口与 Python 的 `selection_reconcile`、`approval_subject`、`ack` | 整块交接；同一选择重排、同一正文提交后换 SHA 不重复索取确认 |
| 工作流定义、阶段和步骤、推进与恢复 | `kernel/flow/`，Python 生命周期；Cloud 读脉冲和任务投影 | 后迁移；工作流定义只保留一份，取消、暂停、等待和恢复事实不能丢 |
| 工具前后 Hook、子 Agent 完成记录 | `kernelHost.ts` 通过 `dispatch.py` 登记 | 随对应模块移交；迁完的登记不再同时向 Python 写一份 |
| 模板、Skill、角色说明、流程资料 | 已随 Cloud 发布的 `kernel/` 资源 | 继续作为资源维护，不为去 Python 而重写文档体系 |
| 发布与来源选择 | `sync-kernel.sh`、`preflight.sh`、`kernelDiscovery.ts`、`kernel/VENDORED` | 单仓接管时一起修改，防止旧同步脚本覆盖 Cloud 已接管的源码 |

## 分阶段实施

### 1. 先收敛代码维护

把 Cloud 中现有 `kernel/` 从外仓快照变为本仓维护的过渡 Python 模块，保持运行行为和在途任务格式不变。一次提交同时完成：

- 更新维护规则、来源元数据和发布检查；外仓 SHA 只保留为历史来源。
- 退役整目录覆盖的同步路径，发布不再要求兄弟仓 HEAD 一致。
- 默认运行、测试和发布都使用本仓版本。显式外部内核联调属于过渡能力，应可识别版本，不能参与本仓默认发布验收。
- 列清仍依赖外部仓的部署或独立插件消费者，避免把“Cloud 不再依赖它”误说成“所有消费者都已迁移”。

该阶段完成后，Cloud 的内核修复只在 Cloud 仓提交；不再要求两个远端同步提交。

### 2. 第一块业务迁移：批注与回执闭环

先追通“提交意见 → 入队 → Agent 收到 → 回执登记 → 作者验收 → 当前待办更新”，给同一条意见固定身份与版本。复用 Cloud 已有存储与队列，先消除回执文件、批注状态和 Python 反馈账之间的重复判定。

对外接口和 Agent 命令先保留适配层。模块切换时，该任务的反馈闭环只有一个写入者；原 Python 入口改为委托或退出该模块，不能保留第二套生效判断。不得把“Agent 报告已处理”冒充“检视人已验收”。

### 3. 再迁人工决定与交付状态

把决定绑定、文件选择、同意/返工、MR 外部合入收口合并到 Cloud 的领域服务。保留人的实际回答和真实远端事实，删除内部凭证、字段顺序和机械提交变化造成的重复确认。不要把新逻辑继续堆进 `taskService.ts`。

### 4. 最后迁流程推进与恢复

移交步骤推进、当前状态、重启恢复和必要的工具权限检查。每个任务记录其执行实现版本，已有任务在安全边界交接，不因部署中途更换写入者。迁移前后沿用同一份流程定义，不能重新硬编码另一套阶段表。

Python CLI、Hook 和能力握手的业务调用归零，且在途任务已可由 Cloud 恢复后，再删除运行时依赖。保留有用的模板和 Skill。

## 每块迁移的完成标准

1. 状态和规则只有一个生效入口；旧判断被删除或明确委托，不是再加一层兜底。
2. 同一意见或决定重复提交、换排列顺序，不会新增处理轮次或作废确认。
3. 排队期间重启、回执已落盘但投影未更新、决定已执行但响应丢失，都能续接且不重复执行。
4. 暂停、取消、接管、明确拒绝仍受尊重；外部人工合入按真实远端事实完成任务。
5. 使用真实 Git 和持久化事故夹具对照旧行为；回放不产生第二份线上写入或外部动作。
6. 回滚与状态兼容在切换前验证。未验证新状态可被旧实现读取时，不能直接把任务切回旧 writer。

验收重点是完整场景不再重复撞墙，不以迁移行数、删除门禁数量或测试总数代替结果。
