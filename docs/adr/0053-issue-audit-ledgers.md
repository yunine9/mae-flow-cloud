# 问题流审计账独立成账:JSON lines 双时间,三级关联 id,分期落地

2026-09-22 拍板(#402 图,#406 收口)。问题流(issueFlow)多次生产故障靠人肉考古多份文件定位(issue-131/#383 翻 25,712 条 401、#357 靠 mtime 推断部署态、#366 靠 token 差倒推压缩),而消费方已明确:服务器上的 Agent 直接读文件定位。三张调研票(业界实践/事故考古/账面盘点)的交集:缺口不在"记得少"——会话现场已有 13 类账——而在三块:进程日志无结构、跨进程调用无关联 id、通知与回合投递不落盘(通知投递账纯内存,重启即失,#383 的"死代码通知"若有此账当场可证伪)。

决定:

1. **审计账独立于用户可见协作账**:新建会话级 `audit/`(delivery/decisions/dispatch 三账)与进程级 `logs/`(host-calls/canonical 两账),全部 JSON lines;events.jsonl(ADR-0018 协作投影)不动——读者、留存、格式要求不同,混一本两头不讨好(OWASP:审计与展示日志分开保存)。
2. **双时间**:每行带 `ts`(事实发生)与 `written_at`(落账),平时相等、补记才分叉(OTel Timestamp/ObservedTimestamp 模型)——对"无人值守考古"最诚实。
3. **三级关联 id + 跨进程父指针**:`issue_id/turn_id/request_id`,适配层经 `x-mfc-request-id` 头记宿主 `parent_request_id`;信箱条目沿用 `mrr-*` id 兼作 request_id,不另造。语义对齐 W3C traceparent,升级只加头不改账面。
4. **决策留痕与事实留痕同等**:凡守卫、判定分支、预算耗尽、去重跳过,发 `kind=decision` 行——8 个诊断场景里"平台为什么没做某事"占一半。
5. **canonical 行**:每回合收口必发单行聚合汇总(成败都发,Stripe canonical log line 惯例),Agent 考古第一入口。
6. **脱敏让位定位**(2026-09-22 拍板):内网自用服务,密钥默认掩码但定位需要时字段可明文;对话正文不复制进审计账,原地引 transcript。
7. **分期**:P1=五本账+关联 id(验收=8 场景逐条可定位);P2=存量 121 处 this.log 结构化迁移、fetch-logs 结果账、适配层进程日志翻转纪律——P2 不挡 P1 收口。

接受的代价:

1. 五本账与既有 13 类账并存,事实有重叠(dispatch.jsonl 与 outbox 终态、delivery 与 transcript)——重叠按"流水对终态"分工,以条目 id join,不消除:消除重叠就要合并账,回到取舍 1 的否决项。
2. 双时间要求补记路径诚实记 `written_at`——比单时间戳多一个字段,换来"事后补的账不被当成实时账"。
3. P1 不动存量 this.log,过渡期两套并存(journald 旧风格 + audit 新账)——P2 收口前考古要两处看,但 P1 的场景验收不依赖旧日志。

**曾考虑**:

- 全部塞 events.jsonl(一个文件看全):否——协作投影被运维事件淹没,ADR-0018 语义稀释;
- 每行记文件:行号:否——运行时捕获有代价、转译后失真(zap/pino 皆可选),稳定模块标识仅 ERROR 附调用点;
- 一期连存量日志全改:否——场景矩阵验收不依赖旧日志,121 处逐行改是长周期低回报,挡住 P1 收口。
