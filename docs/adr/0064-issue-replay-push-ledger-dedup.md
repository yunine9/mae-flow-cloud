# 同提交回放推送不计新推送:推送账投影按(仓,分支,提交号)去重

2026-10-15 拍板(grilling 一轮五问,#506):问题单推送账的投影层对同 (仓,分支,提交号) 的重复推送去重、只留首笔。重启续跑等触发的同 SHA 重推不携带任何新提交,定性为「同一推送的回放」而非「一笔新推送」——它不参与推送计数,更不把已按首笔时刻归类的提交从首轮翻转成返工。

**背景**(issue-176,2026-10-14):AI 一次提交单行修复,推后 7 分钟撞平台侧流水线失败(YAML Consistence Check 安全资产基线不一致,与代码无关),服务重启自动续跑后同 SHA 强推回放。推送账由此多出一笔同 SHA 记录;首次生成归属按推送时刻整笔盖章、后写覆盖,这笔晚于返工边界的回放把同一提交从首轮翻成返工——首轮占比 0%,「90%AI生成达标」误判不达标。排查(内网 agent 只读分析,#506 正文)与本地红绿对照均确认:去掉去重回归即红。

**口径(拍板)**:账记事实、计数是投影(CONTEXT「原子事实」词条)。回放推送是真实动作(它确实触发了平台重查、撞了同提交刹车——平台发现同一提交重复推送仍红即自动停机的机制),转移账照记不漏;去重发生在 `ledgerPushes` 投影——它是推送事实的单一投影源,推送计数(metrics.json push_count)、逐笔推送差异、首次生成归属三个消费方一处修一致受益,存量账重算即自愈。ADR-0045 的「边界按时刻」不受影响:去重只是不让同一笔推送被数两次,不是回到按提交号匹配边界。

**连带效果(知情接受)**:push_count 语义从「推送动作次数」变为「携带新提交的推送次数」(issue-176 从 2→1),逐笔差异里的 0 文件重复笔消失;metrics.json 不 bump 版本戳——它是展示数据不是 KPI,达标判定吃的是 code-origin.json(先例:ADR-0045 修订注,metrics.json 版本戳不动、存量不失效);已冻结快照不迁移不改写(冻结纪律)。

**存量处置**:冻结快照的唯一重算通道是删伴生 code-origin.json 后由清扫器回收前补算(`backfillCodeOrigin` 只补缺失、不改写在场);删除伴生属人工确认动作,且以代码现场(repo/ 子树)还在为前提——归属计算没有远端重克隆兜底,现场已回收的按「不猜不补」保留坏账,只在工单记录口径修正。

**曾考虑**:(a) 归属层跳过同 tip 推送——否,只修归属一处,推送计数与逐笔差异照旧虚高,三个消费方口径分裂;(b) 推送工具源头不记账或换文案——否,要么丢事实要么引入第二类账面文案让 PUSH_NOTE 匹配复杂化,且只防新账不治存量;(c) 平台侧/基础设施类流水线失败不设返工边界——真问题但另立专项:失败记账文案不带归因维度(`流水线失败(仓)`),需要先设计失败归因分类,易漂移易误判,不并入本次改动;(d) 修重启续跑让 AI 不重推——否,靠回合提示词约束 AI 行为不可靠,投影去重对一切回放路径(重启、重试、并发误触)都鲁棒。

**验收(实现期)**:定向测试——`ledgerPushes` 去重单测(同仓同分支同提交只留首笔;换分支/换仓不去重;隔笔回放也不进投影);issue-176 场景真仓回归(推送→流水线失败→同 SHA 强推,断言边界回应首笔、全部工作行计首轮、占比 100%、达标),红绿对照(去掉去重该测试红);根 typecheck。存量 issue-176 的重算走删伴生通道,待内网确认现场在场后人工执行。
