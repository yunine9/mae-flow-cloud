# DTS 模块按特性名强匹配列上带出、发起强制,退役 AI 识别路(替代 ADR-0010 预绑锁)

2026-09-23 拍板(grill-with-docs 会话)。所属业务模块此前有三本账互不相认:列表人工预绑(下拉选即存,带锁)、create 时服务端启发式自动匹配(关键词拆分+多档评分,唯一高置信才绑,不带锁)、会话里 AI 现场检索再绑(lookup_modules + bind_module)。三本账没有一本是发起前肉眼可见的事实——机器每单猜一遍、AI 每单再兜一道,是 ADR-0010 时代「列上没有模块事实」的补偿机制;分支列(ADR-0038)已验证「服务端单点规则+列上带出+发起强制」的形态,模块照此办理,补偿机制整体退役。

决定:

1. **强匹配规则**:单据特性名(DTS sFeatureNoName)去掉前后空格后与业务模块名称字符串完全相等即命中;库里多模块同名都命中按未匹配处理。启发式评分与关键词拆分(extractDtsKeywords)整体删除——用户拍板「不要启发式,直接强匹配」:精确相等是事实对齐不是猜测,缺模块闸门会拦,错模块会跑偏,宁缺勿错。
2. **列上带出**:列表查询 fields 补特性名(此前列表一路从未请求过该字段,fields 是空数组;单张详情一直显式要),服务端逐单强匹配,列表响应逐单带出 module_id;单张详情同源补,远程查单入列的单子不缺席。显示=现算、执行=快照;带出值不写预绑映射——映射只存人工选择,规则改了列上跟着变,不多一本要失效的账。
3. **列上交互**:展示优先级人工预绑 > 带出值;人工可随时改选(选即存,走既有绑定映射);未匹配(零命中或重名歧义)格子内必填下拉。
4. **发起强制**:预绑与带出都没有则前端禁勾选(与「已发起/未配置分支」同款),后端 create 对 DTS 来源缺 module_id 硬 400;发起请求恒带 module_id。
5. **AI 识别路退役**:bind_module、lookup_modules 工具,module_locked 锁标志,create 内部自动匹配,预绑锁提示词与回执文案全部删除。三路发起(无单/登记页/DTS)开场必有模块,模块仓 create 时已合并进登记清单——AI 开场对已登记仓逐个 pull_repo,运行时零匹配。ADR-0010 的「临时方案,上游 DTS 原生提供模块字段后整体退役」条款就此兑现:特性名正是那个上游字段。

理由:特性名与模块名在团队实践里就是同一套叫法,规则一句话说得清;与 ADR-0038 同构(规则服务端单点、列上展示、两道闸、现算与快照分离),维护者只需要懂一个模式。曾考虑配置中心加「DTS 名称→模块」映射页签(完全镜像分支)——否:特性名与模块名的对应关系由模块库命名承担,不另设映射表维护面。

后果:列表/详情响应逐单新增 module_id;网关列表查询需内网对拍 listByVersionAndHead 确实返回特性名——不返回时全体呈现未匹配走必填,失败模式可见不静默。module_locked 与预绑锁语义退役,存量会话里的旧字段读作无锁,无消费方,零迁移。前端列显隐系统化:数据列(标题/版本/分支/所属模块/发起状态/发起备注)可按人显隐,勾选列与单号列常驻,模块列单独开关并入统一列设置;模块列即使隐藏,发起闸仍在勾选列禁用态上可见,义务不随视图消失。行尾展开详情与其操作列退役,单号直达 DTS 门户已是详情出口。
