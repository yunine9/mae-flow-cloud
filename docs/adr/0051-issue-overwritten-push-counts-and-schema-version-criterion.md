# 被强制覆盖的平台推送计入工作量;换版纪律按「度量可否换算」划线

2026-09-22 拍板(#377)。首次生成占比在首轮推送被 force push(强制覆盖远端同名分支的重推)覆盖后算成 0% 的修正,及其牵出的 schema 换版纪律修订。

## 一、被覆盖的平台提交按原分类补计工作量

issue-74 复盘:首轮交付被反馈打回,后续两轮以 force push 整体覆盖,最终留存的提交全是返工重写——工作量枚举只走最终历史(base..head),被覆盖提交一行不计,占比 0/122=0%。ADR-0045 已把指标从「最终代码的出身构成」改判为「代码运动的一次率」,推送账记了这笔平台交付、分类账也把它归了类,唯独工作量漏计——口径与实现不自洽。

修正:分类账里有、但不在最终历史里的平台提交,按原分类(边界前的推送计首轮、其后的计返工)逐笔补算源码增删行,计入分子分母与提交明细(带 `overwritten` 标记)。归类复用与留存提交同一判定(外部头观测在案的仍判平台外,不留「被覆盖与留存两种下场分类打架」的角落)。提交对象已被回收(现场重克隆/回收)的补不出,如实跳过,不阻塞整仓;补计行数同受行数预算约束。

效果:issue-74 从 0% 变为首轮工作量/(首轮+返工)。「全军覆没」不再显示成 0%,但返工行仍在分母里压占比,90% 达标线下判定基本不变——判定翻转集中在「内容几乎不变、仅因历史重写被清零」的假返工场景,恰是旧口径失真处。

代价(知情接受):无反馈场景的自我重写(边界前的推倒重来)也按首轮重复计,分母含重复劳动——ADR-0045 接受「同一行改写 N 遍计 N 遍」时就已认下,补计只是把它贯彻到被覆盖提交;0% 的「全军覆没」信号变钝,改由返工工作行承担这个叙事。

## 二、同票顺修:推送对象缺失时的分类下标错位

逐笔解析推送提交对象时,解析不到的跳过,但分类用压缩后数组的下标取推送时刻——中间某笔对象缺失时错位,后面的推送按前面的时刻分类(边界后的返工可被误判成边界前的首轮)。修法:保留原始下标,分类按各自推送时刻取值;统计区间从最近一笔可解析前驱(无则 base)起算。

## 三、schema v4;读侧保留 v2/v3 可读;换版纪律补判据

伴生快照升 schema v4(提交明细带 `overwritten`)。读侧把「版本必须等于当前」放宽为「v2 至当前可读」,前端版本钝化门同步改区间:v2/v3 相对 v4 是**同一度量**(工作量口径)的精度缺口,差异方向恒为保守(旧版数字不高于新版),混读不是编造。起算日不动——v3 换版时挪到 09-23 的决定随本判据退回 09-21,9-21/22 收口、只有 v2 快照的会话重新进分母。

同票修订工单 #380 立的换版纪律。#380 的原始判例仍然成立:**不可换算的两个度量**(v1 留存行 blame → v2 工作量)换版时,起算日必须同步挪到新版口径的上线日、旧版快照退役——那才是「混读等于编造」,且旧版快照会陷入读侧当缺失、清扫器当在场的永久「待算」。**同一度量的精度扩充**(v3 白名单扩后缀、v4 覆盖提交补计)方向恒保守,保留旧版可读、起算日不动。

代价(知情接受):9-21/22 的 v2 快照不含配置类后缀工作量、不含被覆盖补计,与 v4 会话混读存在有界偏低;v1 时代「永久待算」僵尸由起算日退役解决,与本判据不冲突(v1 仍拒收)。

## 曾考虑

- 严格守 #380 原纪律对 v4 也挪起算日——否,会把 9-21/22 已有 v2 快照的会话整段退役:为不可换算度量立的纪律,惩罚可混读的精度扩充,指标上线第二天的数据就丢;
- 删旧重算迁移(v2 文件按版本删除后由清扫器重算)——否,违背「只写一次、永不重写」的冻结纪律,且现场已回收的单子删了旧快照就真丢,重算只能得到「全不可得」;
- 补计不进提交明细、只动行数——否,证据面解释不了「这个提交不在 git log 里为什么占行数」,`overwritten` 标记随 schema 换版一起落,成本为零;
- 补计直接取分类账原始分类——否,被覆盖且被外部头观测记录的提交会与留存提交的判定打架,统一走同一归类函数。
