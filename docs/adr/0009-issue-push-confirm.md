# 问题流推送前过目闸:push_branch 工具级硬闸 + 一次性确认令牌(月光不代)

2026-08-31 拍板:个人设置的「推送前过目」(push_confirmation,交付轴,真人缺省即开)现读现判接入问题流。开着时 push_branch 在执行前置检查:没有有效的一次性确认令牌就不执行 git push,举起 push_confirm 平台闸——固定流程过这道闸(工具级硬闸,不依赖提示词自觉,不绑阶段);卡上带服务端举闸时现查仓库生成的变更摘要(当前分支相对基线的 diff --stat + 最近几条提交题,基线拿不到就退化为提交题列表,不 fail,不靠 Agent 自报)。用户确认 → 一次性令牌写入会话状态(带确认时刻、决策留痕与举闸时的分支 tip,随 issue.json 持久化,recover 不清它)→ 闸落、原阶段续跑,Agent 重试推送成功即消费令牌;下一次推送重新过目(每次过目,防盲签)。令牌绑定过目那一刻的分支 tip:确认之后又有新提交,重推对不上 tip 即作废重举——人看过的是哪份变更,放行的就是哪份。答「暂不推送」(含任何自由文本)不产令牌,原阶段续跑,决策与意见入账。月光开着也永不代这张闸——推送过目是用户显式开启的"我要亲自看一眼",更具体的意志赢过免审批,与需求流 push 前确认同一裁定。create_mr 不加独立闸:分支唯一出门口是 push_branch,闸卡在源头。

理由:人工介入四档里「全程把关/只看交付」两档的承诺是"出门的变更都经我签字"(父票 #49 的轴表),而此前问题修复的 push_branch 直推,交付轴在问题流不存在。闸的位置选工具执行点而非提示词或阶段门:提示词管不住侥幸,阶段门禁管的是"什么阶段能推"而不是"推之前给不给人看",两道门正交。摘要由服务端生成是"过目不是走过场"的底线——人看的是仓里的既成事实,不是 AI 的转述。令牌设计成一次性且成功即消费、并绑定过目时刻的分支 tip,是因为确认的对象是"当时看到的那份变更":变更变了(新提交)就要再看,持久化的令牌解决的是重启不丢已过目的意志、不要求重复点,而不是长期授权。月光不代在代答入口(maybeAutoAnswerGate)显式短路:这张卡连"读月光设置"都不必,任何介入档位都只等真人。

曾考虑:(a) 卡上摘要由 Agent 自报(父票初稿的 AskUserQuestion 路线)——被否,自报可以让过目沦为走过场,服务端现查仓库才与"变更摘要由平台核实"的既有纪律一致;(b) 令牌按仓发放(多仓各确认各的)——从简否决,令牌按会话发放、消费于下一次成功推送,多仓场景逐仓被拦虽多一次确认,但语义是"每次推送重新过目"的直接推论,不值得为它加按仓账;(c) 持久化"已消费"标记留痕——否,消费留痕进转移账(推送台账+「推送过目令牌已消费」注记)已可复盘,盘上不留死令牌,有效性的判据保持"在场即有效"一条。

## 2026-09-11 增补:强制覆盖(同单重跑)的 force 语义

问题:同单重跑时上次运行推过的 `master_<工号>_<单号>` 分支留在远端,本次从基线另起必然非快进,git 拒收——原处置文案只能让用户去代码平台手删远端分支,AI 无法自持闭环(issue-25/issue-14 均踩)。

拍板:push_branch 加 `force` 参数,且**强制推送与普通推送同权跟随「推送前过目」设置**——不搞独立于个人设置的额外确认。设置开着时举的是**强制覆盖卡**(卡面除变更摘要外带远端旧分支指向),确认产出的令牌多带 `force`/`remote` 两样;设置关着时直推。

要点:
- **force 的授权来自令牌,不来自参数**:普通卡确认过的令牌放不了强制覆盖(带 force 重推即作废旧令牌重举强制卡);反向,强制卡确认过的重推不必再带参——确认过的覆盖语义随令牌走,与"人看过的是哪份变更,放行的就是哪份"同一立场的两个方向。
- **覆盖用租赁式核对,不用裸 --force**:推送前 ls-remote 探远端同名分支 tip,`--force-with-lease=ref:tip` 推;强制卡场景以确认时记下的远端 tip(`token.remote`)为期望值,推送时对不上即抛 IssuePushStaleRemoteError——令牌作废、自动重举强制卡,把本地 tip 的防盲签立场扩展到远端 tip(确认后他人又推了,确认对象就变了)。
- **non-fast-forward 拒收回执指路 force=true**(替代"请用户去平台删分支"),含"已有 MR 时覆盖后原 MR 随之更新,勿重复创建"的提醒;分支名单门禁(master_工号_单号)不变,force 也只能落在本单名下。
- 曾考虑:force 无视过目设置一律举闸——否,用户拍板强制推送与普通推送暂时视为一样,遵循用户配置,用户不希望手动确认时就自动执行;独立的 delete_remote_branch 工具——否,删除不可逆且误删面更大,租赁式 force 每个环节都有复核。
