# 外部提交合并:用户推回远端的提交自动并进工作区,force 另加收据门

2026-11-06 拍板(grill-with-docs 会话,预防性加固,无现场单):有单会话的续作回合开始时,宿主对修复分支做一次单引用 `ls-remote` 探针,与推送账里的最后一笔收据比对——远端头没动的照常开工;远端头前进了(是收据 SHA 的后代,即用户把手改拉到本地推回了远端)则 fetch 后 merge 进本地工作区再开工。推送链路复用同款判定兜底(吸收与推送之间远端又动的残余竞态)。判定"哪些提交是外部的"只用推送收据加祖先关系,不看作者是谁、不看代码是不是 AI 写的。

**理由**:平台对"远端被手推"的感知早就齐了(「分支最新提交」的检查目标自动跟随、外部头观测账、验绿时的源分支头复核),但感知落不到工作区——修复分支没有任何 fetch/merge 路径:容器克隆无凭据,`pull_repo` 已克隆即不更新,红灯材料"先拉最新代码、看差异再修"是不可执行的空头指引,AI 只能按旧代码盲改一轮再在推送时撞冲突。盲改一轮的成本(分钟级会话加 token,外加合并解冲突)比每回合一次亚秒级探针贵三个数量级。吸收本身是事件驱动的:用户没在回合之间推代码,fetch/merge 一次都不发生,探针是常态下唯一的开销。

**连带取舍(拍板)**:

- **merge 不 rebase**:平台未推送提交的 SHA 不变,git-ai 行级归因 notes 不断链(省掉 preserveGitAiNotes 补挂);与「基线同步」(ADR-0071)的 merge 口径同形,问题侧两处合并一个做法。已知代价:用户 cherry-pick 平台未推送提交再推回时,merge 保留两个同补丁提交(树正确、历史重复,MR 里人眼可见),不做补丁等价检测——那是 rebase 免费送的能力,为它单独建检测不值。需求侧外来提交用 rebase(task-40 教训沉淀)是另一条通道的有意差异:那边要的是把任务提交接到用户提交之后,这边要的是 SHA 稳定,两边语义本就不同;两条交付通道互不 import 的契约(issueGit 模块头与 ADR-0071 所立)保持,实现独立落在 issueFlow 内。
- **探针经济**:首轮不探(分支按 ADR-0063 时间戳命名刚建,远端必然不存在);该仓还没有推送收据时不探(没有比对锚点,推送链路的无收据门兜底);探针失败 fail-open 不拦回合(网络抖动不该停工,同 ADR-0071 的取回基线失败口径),推送链路的门还在。合并身份沿用需求侧的 `-c user.name/email` 注入形态,合并提交信息按 ADR-0071 的宿主代合并格式(类型 `fix`)。
- **冲突交回当前回合**:机械只试干净合并,撞冲突先 `merge --abort` 还原现场(不留半合并工作区),回合照常继续——通知词点名冲突文件与"外部提交是用户手改、不许回滚"的纪律,Agent 用 `sync_branch` 工具在会话内解决后继续(「基线同步」冲突路径同款;红灯材料的提醒由此获得机械支撑)。工作区有已跟踪未提交改动不做机械合并(同 ADR-0071 脏工作区口径),交 Agent 处理后自行 sync。
- **force 收据门**:force 覆盖前除既有 `--force-with-lease`(防探测到推送之间远端又动)外加一道机械校验——远端 tip 必须是平台历史推送收据(`ledgerPushes` 投影,ADR-0064 去重)中的一笔;不是即硬拒绝:那说明远端有平台不知道的外部提交,lease 防不了会话之外发生的手推,探测到的 tip 本身可能就是用户改好的代码。硬拒绝后人工核对、走显式放行参数才可覆盖;已建 MR 的会话维持机械禁 force(现状不动)。push 被拒的回执文案同步修正:删掉"与用户核对后带 force=true 重推即可覆盖"的建议,改为指向 `sync_branch`。force 的定位从"AI 可自选、靠回执文案引导"收窄为"默认够不着外部提交"。
- **归属账**:吸收事实(被吸收的提交范围)记转移账并喂给外部头观测投影——否则用户提交落进平台推送区间会被「首次生成占比」的区间分类错算成平台工作量。实现时顺带核对需求侧归属层是否有同款漏洞。

**保留**:「分支最新提交」口径不动(检查目标自动跟随外部头,不暂停等人——与需求侧"发现未验证提交即暂停"的差异维持有意,两边分支归属不同);`push_branch` 其余语义不动(单号门禁、在途互斥、多仓逐仓串行);无单形态没有修复分支,天然不涉及;git-ai 现状不动(照旧只发布归因产物,不进任何判定路径)。

曾考虑:(a) 判据迁到 git-ai notes(发布版 note 的 metadata 里已带 `human_author:"mae-flow-cloud"`,平台标识本身存在)——否:notes 是推送核实之后尽力而为发布的旁路,失败只留日志,存在"该有而没有"的时间窗,force 门会误拦自己的提交;宿主制造的合并节点不经容器 git-ai、天然无 notes,会把平台刚吸收完的合并提交当成外部;且它答的是"字是谁打的",门禁要问的是"过没过平台管道",两个问题。(b) 给平台提交打 commit trailer 标识——识别"用户改写后历史里的平台产出"(cherry-pick 认亲)的正确工具,随提交对象走、rebase/cherry-pick 都带得动,但当前没有任何决策消费这个能力,记为非目标,有真实消费者再启用。(c) rebase 接续(需求侧同款)——见连带取舍:每轮分叉都重放改 SHA,历史线性但归因断链,这边 SHA 稳定更要;历史重复的代价更轻。(d) 吸收只做推送时(需求侧形态)——省每回合一次探针,换来 AI 对着旧代码盲改一整轮;需求侧能把吸收嵌在推送前,是它的提交动作本就长在推送流程边上,问题侧 AI 整个回合都在改工作区。(e) 冲突 fail-closed 暂停喊人——每次冲突都硬中断用户,而冲突多数需要判断;交给对话现场可见、用户可纠正的 Agent 更合「Agent 主理」。(f) 脏工作区 stash 后强并——不猜,同 ADR-0071 口径交 Agent。(g) 远端被改写/回滚、无收据而远端有提交这类"非严格后代"形态也自动处理——否:历史被改写意味着用户意图不可机械推断,一律暂停喊人,绝不自动处理、绝不 force(与需求侧"旧验证不背书新历史"同款)。
