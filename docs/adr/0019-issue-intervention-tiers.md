# 问题处理介入档位:两轴旋钮在问题侧退役,改三档

2026-09-09 拍板:问题处理与需求交付的把控分离。需求侧「人工介入程度」四档(月光×推送过目两轴合成)原样保留,一字不动;问题侧不再接月光/推送过目两根轴,改设**单一介入档位**,三档,缺省「仅分析报告」。档位个人级、现读现判(与需求侧同纪律:改档即刻生效,不追溯已挂起的卡)。

三档的闸位策略表:

一档「不问任何内容」的上界=机器自己办得到的事;流水线红灯里只有人能提供的部分(处理/豁免、报错原文)三档都照旧停——那不是询问,是办不到。一档的提醒点=MR 变绿(或异常停),复用既有终态通知(closeMrGreen 的 notifyOutcome 与 notifyPipelineStopped 现成,无需新通道);每次代答(确认闸/问答卡/自动关单)仍各发一条 outcome 通知并落现场账——沿月光代答通道的既有惯例,事后推翻要有账可查。

实现落点(2026-09-09 事实核查后修订):档位在问题流入口解析成两件事——①开场/续聊提示词二选一(三档=guard 档:证据不足主动问、关键节点主动对齐、中间简报;一/二档=月光档:少问、不中间简报、报告写到自足可执行);②闸策略表(env_needed/env_verify 在一/二档不举、缺口记台账入报告;push_confirm 随档位开/关;流水线人工事实闸任何档都举)。analysis_confirm/conclude 的一档代答复用现有月光代答通道(maybeAutoAnswerGate),二档对 analysis_confirm 不代答即停靠。真正的新工作是闸抑制策略:env/push/流水线四类守卫现在位于月光判定之前、任何档位都等人,一/二档需要显式的旁路/降级语义。

理由:需求与问题是两种工作节奏,把控该分开设;问题侧两轴的四档组合暴露了用户不需要的粒度,三档直给心智。二档几乎零新机器——「检视」机制(意见→整体回退→重出分析报告)与确认卡作答协议都是现成的。一档的两次新裁定(环境自决、高置信非问题自动关单)是显式自选档位的后果,通知与现场账留痕可复盘。迁移全员缺省二档:问题处理天然先稳一档,要自动化的人自己升档。

曾考虑:(a) 把两轴四档复制到问题侧(本地草稿曾实现一版)——被否,用户要的是三档心智,不是两轴组合;(b) 存量用户按需求侧现值继承——被否,继承会把「需求全自动⇒问题全自动」悄悄带进来,与默认二档的产品意图相悖;(c) 问题侧保留独立推送过目开关——被否,过目并进档位定义,少一根轴少一个组合;(d) 一档环境闸照旧停问——被否,与零介入矛盾,缺口进报告是可接受的降级。

## 2026-10-31 增补:环境配置卡(env_needed)三档都举

初版把环境配置当「询问」处理(一/二档不举、缺口写进报告并记台账),实践反馈推翻了这个归类:无环境会话(自动接单、转入单)只能产出「缺环境证据、置信度受限」的报告,用户中途想补配没有入口,检视打回后 AI 依旧拿不到环境,反复解决不了。环境由此重新归入「办不到」:网管环境的地址与密码是只有人拿得到的事实,与流水线人工事实闸同族——任何档位都举配置卡,回执统一「请立即结束本回合,等待用户补配或拒绝」(「等待期间可继续不需要环境的工作」的例外退役);一/二档的降级回执与「介入档位不向用户索取环境」台账留痕整支退役;票 93 硬拒绝语义(拒绝后同 scope 不再纠缠)与任何档位永不代答的守卫不变。一档「全自动」的语义边界随之收清:零介入=不问能自查的事、不等人拍板 AI 自己能裁的结论;人办不到的事实(环境配置、流水线人工闸)照旧停。上文表格的 env_needed 行按此修订;env_verify 行的口径纠偏(#246:mr_green 出口验证卡任何档位都举是现状)与 build_deploy 随路验证卡(维持三档独有)不在本次范围。
