# 验证打回冻结分析报告版本——重写来源全覆盖

2026-09-20 拍板:环境验证不通过(env_verify fail)回退问题分析时,平台在回退前把当时的 issue-analysis.md 快照入账(写侧复用 snapshotAnalysisVersion,与检视修改型申报同账)。

**决定**:验证失败与检视意见都是重新生成分析报告的来源,「重写即出版本」的能力必须两边都在;是否真的重写由 AI 判断——对齐后认定报告站得住就原样重提(gate.verify.fail 通知词同步放开,不再硬性要求重写)——但重写发生时版本账必须自动跟上。版本是平台的记账行为,AI 零感知(ADR-0025 原则):不加工具、不改文件名契约、不教版本概念。

**理由**:验证打回是全流程里最需要版本对照的重写场景——真实环境验证失败意味着首轮分析被现实推翻,「打回前的报告长什么样」有复盘价值。ADR-0025 把非检视通道排除出版本时,视野里是「补充意见」这类轻量重写;ADR-0034(2026-09-19)让验证卡成为绿后返工的唯一入口后,这条重写链的版本缺口随之显形:打回重写直接覆盖 live,旧版无任何留存。

**边界**:快照在 fail 分派同步落,报告不在场或写失败不挡回退(fail-open,与申报侧同款);报告最终没改时快照与 live 同文,读侧去重不出假版本。闸卡「补充意见」等其余非检视通道仍不出版本(ADR-0025 的排除句对它们继续有效)。

**统计联动**:report_version_count 现算自版本账(metrics 冻结与现场同源),验证打回的版本自然入账——「一次定位成功率」(版本数 ≤1)自此把「验证失败后重写过分析」的会话也判为未一次过:分析被现实推翻本就不是一版过,口径更真;「一次修复成功率」走转移账 verify_fail_count,不受影响。
