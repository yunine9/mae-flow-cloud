# 自动接单单级排除:第四道闸只拦扫描器,标记按单号存服务端,人人可写

2026-10-31 拍板(与用户逐轮拷问定稿,spec 见工单):自动接单(ADR-0061)此前只有三根杠杆——个人开关(全有或全无)、版本组勾选、扫描间隔,全是人或版本组粒度。用户遇到"某几张单不适合自动发起"时没有任何单级手段(按单,而非按人或按版本组),要么整个关掉个人开关,要么眼睁睁看着单被接走。另有一个实测痛点:去重闸只拦非终态会话,单子的会话取消或失败后,只要 DTS 状态还停在「开发人员实施修改」,下一拍会被自动接单**重新接走**。本篇拍板给扫描器加第四道闸:单级排除(把一张单排除在自动接单之外)。

**决策(拍板)**:

- **能力边界——只拦扫描器,不拦人工**:排除闸插在 runAutoClaimTick 三道预筛(状态/版本组/模块)之后、发起之前;人工从 DTS 列表发起走的是另一条路(issueFlow.create 校验链),零改动——用户点名的是"别替我自动发",不是"这张单不许发"。因排除跳过与其他跳过同待遇:静默不通知,只落审计账,但原因单列「用户排除」并带操作人,与其他跳过(状态不对、版本未参与等)在账上可区分。
- **为何单级**:诉求本身就是"某几张单"。人级开关误伤名下其他单,版本组级误伤整组,间隔是全局的;只有按单号才能精确表达"这张别接"。配合"所有行可改、不限发起状态",它同时是"取消过一次的单别再被接走"的逃生门——终态重拾场景里用户唯一可用的单级手段。
- **为何服务端存**:扫描器在服务端跑,标记必须落服务端(浏览器 localStorage 换台电脑就丢,扫描器也读不到);按单号全局一份,不是按人存——排除的对象是"这张单",DTS 改派责任人后标记留在单上,新责任人接手时事实不丢。形状仿单号→模块映射:`<dataDir>/dts-auto-claim-exclusions.json`,`{version:1, exclusions:Record<单号,{updated_by,updated_at}>}`;条目在场=排除,选「允许」即删条目、不留墓碑——缺省态(允许)就是文件里没有这张单。
- **为何人人可写**:与单号→模块映射同尺——排除是团队共享事实(这张单不适合自动发起,对谁都成立),能看见这单就能改,无审批。风险已知悉接受:误改可以再改回,updated_by 留痕可对账;收益是不引入"谁能改谁的排除"的权限模型,那会把一个逃生门做成审批流。但改写接口留在登录闸后(PUT 设置/DELETE 取消一对),操作人恒取登录身份,不进免登录允许清单(ADR-0069 结构性默认:新增接口默认在闸后)——排除是**有操作人的决定**,不是匿名参考数据。列表数据走既有 `GET /issues/dts` 富集排除标记字段(被排除的单带 `auto_claim_excluded:true`,缺省允许不带字段),不另开读端点。

**界面口径(本期工单只做后端,口径先记档)**:DTS 列表新增「自动接单」列,默认隐藏(照介入档位列的极性与按人显隐记忆),下拉两态「允许/排除」,选即存、失败回滚(照所属模块列交互)。首版不做批量,单格操作。

**曾考虑**:(a) 前端 localStorage 按人存——否,扫描器在服务端读不到,换设备即丢;(b) 按人各存一份排除表——否,改派责任人后旧表失效,排除的是单不是人;(c) 留墓碑+「允许」也落条目——否,两态缺省即允许,条目删除即恢复,文件里只有活事实;(d) 改写接口进免登录允许清单(匿名以 body.account 自报)——否,改写有操作人,登录身份才构成审计事实,ADR-0069 的默认闸后正是为此;(e) 把排除做进 create 校验链(人工发起也拦)——否,破坏"人工发起与自动发起同尺"的铁律,且用户没要这个;(f) 排除需责任人或管理员确认——否,团队共享事实同尺,审批换不来对应对价,误改靠留痕与可逆性兜底。

**验收(实现期)**:定向测试——排除后扫描器跳过并落「用户排除」审计、取消后下一拍恢复;改写接口登录态读写回环(操作人取登录身份)、匿名 401;`GET /issues/dts` 富集字段断言;既有 issueFlow.create 校验链测试零影响;根 typecheck。不跑全量(AGENTS.md 测试纪律)。
