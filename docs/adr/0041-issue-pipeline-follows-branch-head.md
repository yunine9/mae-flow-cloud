# 问题单流水线检查跟随分支最新提交;合入即归档删内部前置

2026-09-19 拍板(#320,父单 #317;合入归档部分承接 ADR-0034,#318 落地)。两个决定:

**一、问题单的流水线检查对象,从「本会话自己推的最后一个提交」改为「MR 源分支上最新的那个提交」(不管谁推的)。** 合入状态循环每轮向平台查 MR 事实时都会拿到分支最新提交的编号;发现它与流水线检查账上的提交不一致,就把检查目标切过去:旧提交的失败计数、上轮报错与同提交刹车账一并作废,查询时限重新起算,并对最新提交启动流水线查询。最新提交不是本会话推的(不在推送账上)时,在检查账上落一个「分支头是平台外提交」的标记;它红灯时,交给 AI 的失败材料开头写明这一点,并附「先拉取最新代码、看差异,再决定怎么修」的指引——工作方法进提示词,不建机械门禁。自己照常推送时照旧按推送账重挂检查,标记自然清除。

**理由**:问题单的修复分支按单号命名(`master_<工号>_<单号>`),这条分支上的一切改动都属于本单——不管是会话里的 AI 推的,还是人在平台页面上直接推的。分支最新提交的流水线,就是本单此刻真实的质量信号;盯住一个已经不在分支头上的旧提交,绿灯背书不了任何会被合入的代码。发现外部推送后自动跟随,失败材料里说清「头不是你推的」,把「先拉代码、看差异」的处置交给 AI 现场判断。

**与需求交付流程的策略差异是有意为之,不互相改**:需求侧(任务流)发现分支头指向未验证提交会暂停自动交付,问题侧(问题流)选择跟随继续检查。两边面对的分支归属不同——需求分支可能承载多方合写的任务,问题分支按单号独占,「分支上一切皆属本单」在问题侧成立,在需求侧不成立。

**二、合入即归档,删除归档的内部前置(修正 ADR-0034 的口径)。** 全部 MR 合入的有单会话自动归档时,不再要求「提交 MR·跑绿」阶段已收口、环境验证卡已答或挂着不可修卡——这些是平台内部账本的状态,而合入是人在平台上做的决定、代码已进主干,合入事实本身就是「交付完成没有」的答案。内部账本状态不再前置否决这个外部事实:没收口的阶段随归档一并收口,未答的卡作废(统计口径视为认可)。已全部合入时答「已在平台处理,重新监看」也不再看旧提交的流水线——直接归档。

**平台事实前提(两条决定共同的地基)**:只要 MR 合入,分支最新提交的流水线最终一定绿——哪怕平台走「屏蔽合入」放行,合入动作也会补一次通过的结果。「红着进主干」在这套平台上不存在,因此不设计「合入了但流水线是红的」的质量告警分支:检查目标跟到合入头,等到的必是绿灯,正常收口、归档。

**随迁面**:合入状态循环成为外部推送的唯一感知点(逐仓比对平台返回的源分支最新提交);重启自愈「监看账落后于推送账就补挂」对带平台外标记的检查账让路——落后的推送账不是正确目标,补挂会跟跟随机制打架;检查账新增 external_head 字段(上 wire,前端镜像同步);红灯材料新增「分支头是平台外提交」提示段(文案在 assets/issue-prompts 的 notices 模板)。

**曾考虑**:发现外部推送就暂停,等人确认再继续检查——否,分支按单号命名,外部推送也是本单的改动,停下来等人点一次只是把闭环速度换成仪式;外部头红灯时把「必须先拉代码」做成机械门禁(没拉取就不许派发修复回合)——否,拉没拉、差异看不看得懂只有 AI 当场知道,提示词说清利害即可,平台不核对过程。
