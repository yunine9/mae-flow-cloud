# 问题会话参考仓:公共组件仓目录注入、按需拉取、台账隔离只读(取消仓数量上限,修订 ADR-0023)

2026-09-23 拍板(grill-with-docs 会话;同日会话内二稿:注入范围由「全部启用行」收窄为「模块订阅条目」——不是每个模块都依赖公共组件,全量注入对无关会话是上下文污染)。背景:定位问题深入后常发现要参考公共组件/公共库的源码才能改对,而模块预绑的几个仓不够。拉取能力其实已有——pull_repo 本就收任意地址、中途随时可调(ADR-0001);真正缺的是三样:AI 不知道公共仓的地址;拉进来算什么身份(关联仓教义是彼此平等、可改可交付,公共组件是跨模块共享资产,不该被一纸问题单顺手改);以及人看不到会话里拉过哪些参考件(知识仓至今只活在过程记录里)。

**公共组件仓目录与模块订阅(地址发现)**:组件仓库表(组件知识研究线登记的公共构建块清单,`component-repositories.json`)是公共仓的唯一维护处:名称、代码仓地址、描述(写「何时需要读取」)都在这一张表。业务模块新增「参考组件仓」配置:从目录条目中**多选订阅**,存条目引用不抄地址——地址变更零跟进,这是它区别于被否决的「模块级自由清单」的根本点。开场组装只把**本模块订阅条目**的名称、地址、描述注入会话上下文(与 skill 描述同一机制:AI 天天看得见,据此自行决定拉不拉,地址照抄调 pull_repo);无订阅或无模块的会话整节省略。不做检索工具:订阅节直接注入,规模天然有界。订阅管 AI 看得见什么,目录管拉进来算什么——两件事分开。

**身份判定与台账隔离(只读的结构保证)**:pull_repo 时宿主归类——地址命中目录启用行、且不是模块绑定仓/已指派仓,记入参考仓台账(`public_repos`),不进 repo_urls;否则维持现状入登记清单为平等关联仓。命中即判参考仓,**与是否订阅无关**(用户口头给的未订阅条目地址同样入参考仓台账)——身份跟共享资产属性走,不跟模块视野走,否则同一仓在不同模块会话里身份漂移。用户意志(模块绑定/元信息页签指派)永远压过登记表。模块订阅解析在开场组装时刻快照,会话进行中改模块订阅不追溯(与环境快照同一纪律);模块保存拒绝引用不存在的条目,条目事后被删/停用时模块配置页标「已失效」、注入时跳过。参考仓的只读与知识仓同款结构保证(ADR-0033 先例):目录在 repo/ 平铺在场、AI 随便读,但不在登记清单——交付工具经 locateRepo 只认登记清单,推不了、交不了;容器内 git push 本就被禁用。能强保证的是「改了也交付不出去」,不是「一个字符改不了」:AI 有 shell,文件级锁(chmod)拦不住还碍事,不做。不设原地改身份的通道:参考仓身份全生命周期不变;真要改公共组件,用户把它按普通地址重新指派一次(ADR-0023 通道),重新拉取即转为平等关联仓——「改共享资产」这个跨团队决定天然过一道人,不新增第二种通道。remove_repo 可摘除参考仓台账行并物理删工作区目录(AI 拉错了的出路;删目录与登记仓同款账实一致,ADR-0023 磁盘治理)。模块绑定仓在身份裁决里同样算已知(extraKnown):发起时显式给了仓清单的边缘场景下绑定仓不在 repo_urls,不该被登记表卷成参考仓。

**可见性**:会话详情仓卡片按身份出四类徽标——模块绑定 / 用户指派 / 参考仓(只读)/ 知识仓(只读);参考仓与知识仓都有独立卡片,不再只躺在过程记录里。元信息页签同口径分组陈列。

**取消数量上限(修订 ADR-0023)**:MAX_ISSUE_REPOS(8) 及其三处同尺校验(工具门禁、`POST /issues/:id/repos` 端点、元信息页签前端预判)一并删除。8 是多仓落地时(`eedb26a6`)的防御性保险丝、#241 定为静态闸口,数字本身无论证(查证:无任何 ADR 论证过为什么是 8);2026-09-23 拍板取消,不设替代护栏。ADR-0023「上限与格式」节的合并计数条款(≤8 不抵扣)随之作废,该节其余校验(https 限定、归一去重、模块绑定仓拒删、终态守卫)保留。

**调试形态**:`--debug-issue` 启动播种为公共组件种子独立建 bare 镜像,登记表 repository 直接写镜像路径——订阅快照与身份归类读同一份本地文件,注入的地址就是镜像路径,本地即闭环(否则调试会话拉公共仓必失败,新机制无法自测);示例模块播种即订阅,存量 dataDir 幂等补订阅。

理由:等人工喂地址卡的是闭环速度(这是本仓的核心取舍);注入按模块订阅收窄,不依赖公共组件的会话零污染;共享资产的修改权与问题单交付解耦——读源码是刚需,改是例外且该过人。台账隔离让「不可交付」不依赖提示词自觉,而是交付通道结构上够不着,与知识仓同一套已验证机制,零新增门禁。

曾考虑:(a) 模块配置加自由文本「参考仓」清单——否,地址要在 N 个模块里重复维护,改地址要改 N 处;本 ADR 采纳的「模块订阅」是它的折中形态:模块存目录条目引用而非地址,清单仍全局一份;(b) AI 检索工具(按关键词查目录)——否,订阅节直接注入更简单,也更贴 skill 描述的既有心智;(c) 全部启用行无条件注入——否(会话内二稿推翻一稿),对不依赖公共组件的模块是上下文污染,还诱导 AI 拉不相干的仓;(d) 参考仓行内原地升级按钮——否,暂无需求,指派通道天然兜底,少一个机制;(e) 文件系统只读锁——否,shell 可绕,假保证;(f) 上限放宽为 16 或维持 8——否,数量上限被拍板为无意义的限制,直接取消。
