# 交付动作收敛「提交 MR·跑绿」独占:修复阶段不碰远端写操作

2026-09-22 拍板(#373)。问题单 issue-139 卡死:AI 在「问题修复」阶段直接调 `create_mr` 建 MR,回执又教它「结束本回合,等待流水线结果」,于是停下等绿;绿灯到达时平台没有唤醒分支,会话定格在「空闲+修复+流水线已绿」直到工作区被回收。

背景里有一条被部分收回的决策链:2026-08-28 拍板「作业自由,门只守流程出口与出厂动作」,2026-09-10 随任务宿主能力开放把 `push_branch`/`create_mr` 等对问题流**全阶段**开放(评审文档「问题流同步开放」一行)。阶段简报与门禁读同一列工具,修复阶段的简报于是亲口告诉 AI「可用工具含 create_mr」——引导层主动邀请错位调用,是卡死的第一推手;回执不分阶段地教等,是第二推手;当时绿灯落在修复阶段无唤醒分支,是第三推手(#357 已补)。

决定:`push_branch`/`create_mr` 收敛为「提交 MR·跑绿」阶段独占——注册表的全程可调循环摘除,修复阶段显式列同步摘除;fix 出口文案与阶段简报同步改写(「本阶段不推送,推进后交付」);门禁拒绝回执按注册表自动指路「提交 MR·跑绿」,零新机制。确立**交付类工具收敛的判定标准**:凡启动与阶段语义绑定的平台机器的工具(推送/建 MR 会启动流水线监看,验绿门以 MR 台账为收口半边),收敛到所属阶段独占;调查、取证、分诊类(lookup_modules/pull_repo/remove_repo/report_ut/respond_review/declare_review_rework)继续全程可调。「作业自由」对只读/记账/分诊类继续成立;对启动平台机器的交付类,机器的语义属于阶段,门禁就守在阶段上。无单路线不含「提交 MR·跑绿」,从此任何阶段都无交付工具,与「无单不交付代码」对齐。

`#357`(全绿+修复阶段→开回合指路)与催办词 nudge.fix_wait_pipeline **保留**:返工期间阶段回到修复且账上有在途监看(返工前建了 MR),绿灯仍打进唤醒分支——它是返工链路的常驻唤醒点,不是死代码;催办词兜部署时点的存量异常态。强制 AI 先 `complete_stage` 再交付,首轮与返工轮(验证打回、检视返工)的交付序列完全统一。

接受的代价:

1. 修复阶段中途搁置(等配置卡、等检视、跨天)期间已提交未推送的工作,遇工作区清扫需从会话历史重做——9-10 之前一直如此,且没有任何提示词教过修复阶段推送,该能力从未被当作备份机制使用;
2. 责任人在修复阶段中途要求「先推一下」的即时诉求,答复变为「先推进阶段」;
3. 唤醒兜底从「主防线」退为「返工与存量的兜底」,新会话的错位调用在源头不可能发生。

**曾考虑**:只摘 `create_mr` 留 `push_branch`(防停等即可)——否,修复阶段推送无教学、无正当场景,留着它简报就得解释「能推但别等」,不如「交付动作全在下一阶段」一句话干净;机械禁 + 删 #357/催办(门禁即一切)——否,返工期间账上旧 MR 的绿灯仍会落在修复阶段,唤醒分支删不得;任务流同步收敛——否,任务流的「阶段性交付」是责任人指令驱动的正当能力,问题流的教训不外溢。
