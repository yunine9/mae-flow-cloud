# 问题控制台元信息页签与用户指派仓:手填仓以"运行时补充通道"回归(修订 ADR-0003)+ Agent 主理原则

2026-09-11 拍板(grill-with-docs 会话,spec #238):问题控制台新增「元信息」首签——只读陈列登记元信息(标题/描述全文/业务模块/网管环境,凭据零出现)+ 关联仓清单;用户可在清单上增(HTTPS 链接)删(模块绑定仓除外)仓,点「确定」一次性提交。

**翻案记录(对 ADR-0003 的显式修订,不是悄悄改)**:ADR-0003(2026-08-29)裁定"手填仓废除,仓的唯一来源是模块绑定"。本 ADR 把手填仓以**收窄后的形态**请回来:登记页维持只读(登记口径不变),但会话运行中,用户经元信息页签可以指派仓——分析深入后发现缺仓/多仓,不该逼用户口头转告 Agent。手填是补充通道而非替代:模块绑定仍是仓的主来源,登记时的仓仍由模块带出。

**删除语义(产品语义,通知词与工具描述同源)**:用户移除一个仓 = 用户裁定该仓与本问题无关。Agent 收到的通知必须带上这句,并要求:此前与该仓相悖的分析思路或结论应重新审视,必要时修订;移除动作本身调 remove_repo 工具执行。平台不代执。

**Agent 主理原则(升格为项目原则,日后同此口径)**:不涉及安全风险的前提下,运行时状态变更一律由 Agent 经工具执行,UI 只做状态展示。落实为提交协议的三段式:端点只校验+留痕+经平台回合通道发送通知(不直改 repo_urls)→ Agent 收到通知执行(pull_repo 幂等入列 / remove_repo 摘除)→ 清单随执行结果经事件流自刷,前端不做乐观更新、提交后只显示"已通知 Agent 处理"。

**门禁口径(拍板:单一事实检查)**:一个仓能不能删,只看一件事——远端有没有该单的同名修复分支(master_<工号>_<单号>,ls-remote 现查不信缓存)。在=拒(提示用户先去代码平台删远端分支);网络不可判定=保守拒(宁误拦不误放);不存在=放行。MR 不单独查(远端分支不存在时 MR 自然不可合)。模块绑定仓在工具层机械拒删(前端连删除按钮都不渲染,但门禁不依赖 UI——防 API 直调的侥幸)。分支名固定这一前提若变,门禁口径随之复核。

**上限与格式**:页面指派只收 HTTPS(浏览器用户手输口径;file:// 是 Agent 工具的口径,不经页面);合并计数 ≤ MAX_ISSUE_REPOS(8),**移除不抵扣**——先拉后删的执行时序下抵扣不成立,current+新增 ≤ 8 是任何执行顺序都不越闸的唯一静态保证,前后端同尺预判。归一比对(trim/去尾斜杠/去 .git/小写)三处同源:前端绑定标、端点校验、工具门禁。

**终态**:archived/canceled/failed 会话元信息页签整页只读;服务层终态守卫打回仓变更(防死信——终态不可续聊,发送只会写成永不送达的便签)。

理由:仓清单登记即死锁是真实痛点(分析深入后发现缺仓只能口头转告,平台不感知不留痕不可审计);而"用户指派"与 ADR-0001 的"变更仓判定权归 AI"不冲突——用户指派是人的意志输入,执行与怎么用仍是 Agent 的裁决。把执行完全交给 Agent(平台不代执)让通知成为唯一的事实入口:留痕、语义(删除≠少个目录,是方向修正)、幂等(pull_repo 天然幂等)都在一条链上。门禁收敛为单一事实检查,是刻意对抗门禁清单膨胀——每多一道门就多一处前后端漂移面,#241 评审中"上限口径前后端相反"正前车之鉴。

曾考虑:(a) 平台直接改 repo_urls 并代为克隆——否,违背 ADR-0001"平台不自动克隆"与 Agent 主理原则,且丢掉 Agent 侧拉取回执(基线命中/分支创建)这层事实反馈;(b) 平台代删远端分支后再放行删除——否,删远端分支是不可逆外向动作,平台不做,用户自行操作后门禁自然放行;(c) 删除走"状态摘除+目录留给磁盘清扫"——否,账实分离(清单没有、盘上还在)正是磁盘治理要消灭的形状;(d) MR 状态单独门禁——否,与远端分支检查冗余,且多一道门多一处漂移。
