# 检视:人工意见触发整体回退,闭环靠分析确认卡不做逐条回执

2026-08-31 拍板:问题流新增检视能力——用户对分析报告悬停提意见(块级锚点:行尾 ✎ 按钮、原地输入框,交互照搬需求流 Annotatable;每条意见 = 源行号 + 原文快照 + 自由文本要求,「记下」即落服务端草稿),攒批一次「提交 N 条意见」,轻量确认层列明后果后提交:作废当前挂起的问答卡,走 env_verify 验证失败同一条整体回退(问题分析重做、其后各阶段标 redo、回退轮次 +1、UT/流水线/MR 申报账作废、分支与 MR 延用同分支追加修复)——检视只是给整体回退多加了一种人工触发源,与机器触发共用一套账。意见清单注入新一轮问题分析。边界:转正后的会话不可检视;检视回合进行中不可叠加(按钮置灰,等新一轮分析卡出来);自由模式无阶段机可退,检视降级为普通插话。闭环刻意从简:锚点复用 reanchor 四态检测,送出后原文还在 = 黄灯提醒"这条可能没被吸收",原文没了 = 「已被改动」徽标;加上修订后的新版报告,用户在分析确认卡上整体裁决,不做逐条回执、不做逐条裁决按钮。

理由:检视的典型场景是 fix 甚至 MR 都做完了、回头发现分析方向不对——只在分析确认卡上加"补充意见"够不着这个场景,常驻悬停入口才能随时回头;触发路径复用整体回退而非新写一套,是同一语义不许有两套账(round、redo、作废规则漂移起来就是两种回退)。任务流 MR 检视环的逐条回执闭环(receipt 文件、revision 校验、五站徽标、needs_clarification 阻断)曾考虑照搬,被否:那是为"代码改动难一眼看出、看不动全文"设计的重型机制;分析报告是人要通读的文档,新版报告加锚点徽标已足够支撑整体判断,机制成本买不回对应价值,留作后续增强。无单三节点流程(analyze 出口同为分析确认卡)同理适用。
