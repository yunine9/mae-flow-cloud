# MR 检视意见回复收敛 respond_review 单通道:删草稿文件协议,交办批次直达 CodeHub

2026-09-22 拍板(#383)。issue-131 现场:检视人在 CodeHub MR 讨论区提了 4 条代码意见,责任人批量交办后,AI 照着收到的 `review.triage` 通知(分析报告检视的话术)用 respond_review 把回复落了本地面板账,CodeHub 讨论区无人应答;平台为 CodeHub 同步预留的 `mr_review` 通知(指示 AI 写 mr-review-replies.json 草稿文件)是死代码,全源码零引用,AI 从未被告知这条路径。即便写了也送不出去:问题流出站信箱条目无 mr 字段、flush 不传,adapter resolve 处理器丢弃 body 里的 mr(确定性失败);生产 adapter.json 又未配置 token(296 次 {mr} 报错、25,712 次 401)。三层故障叠一个根因:交办复用 submitReviews 发送咽喉时,把分析报告检视的话术一并带给了代码意见——CONTEXT.md 明令不混称的两个概念(检视 vs MR 检视意见)在通知层被混了。

决定:

1. **通道合并**:AI 对 MR 检视意见的回复一律走 respond_review(面板账照落),平台在回合收口后由监看环扫描批注账,把「已 respond 未入箱」的外部意见自动装入出站信箱直达 CodeHub 讨论。SHA 绑定不变量不变:装箱时绑该仓当前推送收据,漂移即作废交人工。mr-review-replies.json 草稿协议、stageMrReviewReplies、死通知 mr_review 整体删除;notices 头部同步护栏②的五处清单相应改四处。
2. **交办通知分节**:批次含外部意见注入 `review.triage.mr` 专用文案(代码意见语义:能改的修码后同分支重推,纯澄清的直接作答,回复自动代发 CodeHub,正文自足、写明改动与提交号);含报告意见保留 review.triage。混合批次两节拼接,不拒绝交办。
3. **分诊边界护栏**:declare_review_rework 申报清单含外部意见即打回并指路——代码意见没有报告回退,验收闸在流水线与 MR 合入,不在分析报告确认卡;不护栏则误触发会把分析阶段标记重做,让责任人为一条代码意见重确认报告。
4. **信箱去重按次**:从「每讨论至多一条(非 failed)」改为「每次 respond 一条」——追问线程的后续回复照发,幂等键各一;按讨论去重会让 CodeHub 只见首条回复,检视人看到的是过时答案。
5. **存量自愈**:上线后「已 respond 未入箱」的历史回复自动补发(issue-131 的 4 条真实回复,迟到送达好过无声);SHA 绑定与幂等键兜底风险。
6. **机械修复与需求侧对齐**:信箱条目增加 mr(装箱时按 MR 台账固化,同 expected_sha 的「装箱绑事实」,flush 透传);adapter resolve 处理器改 `{...body}` 与 reply 同款;resolve 代点政策不动(部署开关,缺省检视人点解决为准);adapter 启动时 token 个人头与服务令牌两来源皆空打显眼警告(不拒启)。生产 adapter.json 的 token_file 指向既有 codehub-token 文件属运维动作,随修复说明交付。

与需求侧的关系:域语义一致(批注-交办-信箱-直达讨论),AI 回复入口各从其运行时形态——需求侧 review 循环写 review_replies.md 文件、问题侧 SDK 会话用类型化工具;SHA 漂移处置两侧政策各异(需求侧持票等匹配收据,问题侧漂移即作废)。差异是决策不是漂移(mrDiscussionReply.ts 头注既定立场),不许悄悄统一。问题侧不引入文件协议的理由:同一份回复内容,AI 本就必须经 respond_review 落面板账,再写一份草稿文件是第二套要伺候的协议——协议知识住在提示词里、无 schema 校验、写读有竞态、断了无声;issue-131 展示的正是多一套 AI 侧协议就多一类故障面。

接受的代价:

1. respond_review 工具描述改写:对带外部来源的意见,回复会外发 CodeHub——面板回复与对外发言合并为一次调用,不存在「面板说一套、CodeHub 发另一套」(这本来就是要求,不是损失)。
2. 存量补发可能把过时的回复送到检视人面前——迟到的真话好过无声,检视人可追问,追问走新通知与按次入箱的现成线。
3. 自愈扫描挂在监看环上,环不在场不扫描——交办既有守卫保证有 MR 才交办,监看环在场是常态;终态会话不可交办,不产生新回复。

**曾考虑**:

- 接通死代码(修 mr_review 通知,AI 写草稿文件,respond_review 保持本地):否——多养一套 AI 侧协议,正面撞上 issue-131 暴露的依从性故障面;SHA 绑定时机从平台装箱退到「指望 AI 按时机写文件」。
- 新开 respond_mr_review 专用工具:否——第三条路,扩大而非收敛 AI 的选择面。
- 混合批次拒绝交办:否——校验是给用户添步骤,分节拼接是给消息添一段话。
