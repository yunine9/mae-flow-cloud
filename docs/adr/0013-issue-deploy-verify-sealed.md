# 问题流固定流程收为五阶段:换库环境验证封存下线(流程终点=MR 跑绿)

2026-09-02 拍板:换库验证(deploy_verify 阶段 + env_verify 闸 + build_deploy 工具链)当前**极度不可靠且开发周期还很长**,决定不上线——固定有单流程从六阶段收为五阶段(`dts_info → prep_repo → analyze → fix → mr_green`),**流程终点 = 全部 MR 流水线跑绿**。三条收口路径(空清单即时、全绿即时、监看器滞后)统一落到「fixedComplete + idle + 小鲁班通知用户待归档」,归档仍是用户手动动作(与旧验证通过后的形态同形,归档结论自动推导:有 MR → 已提MR)。**收口不是终局**:归档前用户续聊 = 返工,平台重开 mr_green 阶段(reply 入口机械重开,转移账留痕),AI 继续修、同分支重推、重新申报,验绿门重新受理,可多轮;这不是回退——轮次账不动,分支与 MR 延用,现场记录连续。

封存纪律:**代码原地保留,流程不可达**。换库资产(build_deploy 工具与 ops-tools 执行体、env_verify 闸的 kind/码表/裁决分支、env_needed 的 deploy 用途、环境 vault 的部署凭据)一律不删;阶段注册表删掉 deploy_verify 行后,阶段门禁对 build_deploy 恒拒(拒绝文案自动落「本场景流程不含该工具」),env_verify 无举升路径永不举起,月光永不代答清单保留词条作封存期回归锚。web 端 deploy_verify 标签挪进 LEGACY_STAGE_TEXT(旧现场会话的阶段名照样示人,不猜不炸)。

理由:换库是六阶段里唯一被焊死的「特定验证形态」节点,它假设每个问题都有网管环境、都靠换库验证收口;它不可靠时整条有单流程被它堵死收不了口。先让「代码层绿」的闭环用起来,比等一个遥遥无期的真验证强——CONTEXT「一仓一 MR」词条写的闭环定义(MR 全部建好且流水线全绿)至此才与实际流程一致。配置开关与条件跳过被否:开关意味着两套流程形状长期共存、测试矩阵翻倍,而换库在任何站点都不可用,没有第二形状的真实用户;条件跳过要为「什么条件算可跳过」再造一套检测,还让用户看到一个永远走不完的阶段。表驱动注册表保证了重启换库的成本与今天摘掉它的成本同一量级:注册表加回阶段行(声明 goal/exit/tools/gate)、complete_stage 三条收口路径退回 fixedAdvance、提示词与 web 词表同步——一天内可完成,届时另立 ADR 撤销本条。

存量兼容明确不做(拍板):停留在 deploy_verify 的旧会话不迁移——fixedStageIndex 对它返回 -1,推进/收口/催办守卫全部安全空转,续聊降级为自由对话;旧会话的 6 节 stage_states 数组在新进度条上多出的一节不渲染(web 按 5 节词表取齐)。已知代价:这些会话收不了口,只能人工归档/取消;数量预期趋零,接受。

曾考虑:(a) 用「验证形态可配置」替代删除(注册表加验证维度)——方向正确但当下没有第二种可用验证形态,为不存在的形态先造抽象是过度设计,封存+ADR 记录重启路径是同一扩展性的更便宜实现;(b) 全绿自动归档(不等人)——被否,归档是用户对「修好了」的最终拍板,收口态的 idle 也是用户发现返工需求的窗口,自动归档会把返工变成重新开会话;(c) 收口后返工走整体回退拉回 fix——被否,回退语义锚在「分析报告错了」(轮次+1、各阶段 redo),返工锚在「修复没修干净」,硬套会把轮次账搞浑;续聊重开当前阶段零新机制,且是旧验证通过后已验证存在的形态。
