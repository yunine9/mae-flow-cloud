# 推送前基线同步:基线新变更先并进修复分支,冲突当场交回 Agent

2026-10-31 拍板(grill-with-docs 会话):有单会话的 `push_branch` 执行时,宿主先带凭据取回该仓基线分支的最新提交并与修复分支比对——基线无新提交照常推送;有新提交则合并进修复分支(允许 fast-forward,不用 rebase)再推送。合并撞冲突时本次推送拒绝,冲突文件清单与解决指引作为工具回执当场交回,Agent 在当前会话内解决冲突、按「提交格式」提交(宿主代为合并产生的提交同样必须合规,信息为 `[单号][fix] 同步基线 <基线> 至 <短SHA>`),再调 `push_branch` 重新探测,无冲突才真推。起因:问题单处理拖长(检视反复、合入排队)后基线前移,修复分支钉死在拉仓那一刻,MR 合入时冲突且流程内无人能解——Agent 容器里的克隆被加固(凭据只在宿主一次传输窗口在场),自己取不了基线;此前唯一出路是人工处理或重开会话。

**理由**:冲突要趁早、趁有人在现场时解决。MR 验绿等待期冒出冲突,现有机制只支持用户插话开回合,而 AI 手里没有把基线并进来的工具,插话也解不了;把同步前移到推送前,冲突出现在 Agent 正在干活的回合里,回执即现场,解决成本最低。取回基线失败按 fail-open 处理(照常推送、留痕):传输故障不该永久卡死交付,与需求侧外来提交探测同口径;正常路径下合并冲突都会走 Agent 解决路径,fetch 全失败的残余风险由平台合入门禁兜底。

**连带取舍(拍板)**:已跟踪文件有未提交改动即拒推(未跟踪的过程产物不拦——它们不改变推送内容,真与基线合并相撞时同步会如实报错让路)——`push_branch` 注释里「脏工作区熔断」写了却没做的承诺这次做实(2026-08-28 空 MR 事故面),也与合并的前置天然一致。同一会话连续 3 次推送前同步撞冲突,回执升级提示「基线持续变动,建议人工确认合并时机」,不硬停——循环若真实(基线真在频繁推进),循环信息本身就是事实,让人看得见即可,平台不替人叫停。不做配置开关,多一个旋钮就多一个没人知道的出错面。实现落在 issueFlow 内独立完成(fetch + merge + 冲突状态安全落盘,沿用代理 gitdir 生成、状态文件复制回真实 gitdir 的模式),不 import 需求侧 `taskBranchSync`——两条交付通道互不 import 的契约保持(issueGit 模块头所立),两边语义本就不同(需求侧 rebase 接续、问题侧 merge 同步),将来真要合并,以契约为准抽公共层。宿主合并后、交回容器前调用属主修复,保证 Agent 在容器里可写。同步账(提交数、基线 SHA 区间)进 `issue.json` 与转移账留痕。

**保留**:`push_branch` 其余语义不动(单号门禁、force 覆盖前现查远端、在途互斥、多仓逐仓串行);「分支最新提交」口径不动——平台上有人直接往修复分支推新提交是远端异动,由检查目标自动跟随管,基线同步管的是基线分支这一侧,两边不混;多仓会话逐仓同步各自的基线;无单形态没有修复分支与推送,天然不涉及。

曾考虑:(a) 复用 `taskBranchSync`——除双通道契约外,它防的「有人直接推了任务分支」与本次的「基线前移」是两类事实,机制各异。(b) rebase 接续(需求侧同款)——修复分支上是多提交合规账,重写历史没有收益。(c) 取不到基线就拒推(fail-closed)——网络抖动不该停交付。(d) 冲突时开专职修复会话(需求侧模式)——问题流是单会话持续形态,工具回执本就回到当前回合。(e) 合并提交独立设类型词(如 chore)——拍板定 `fix`。(f) 连续冲突硬熔断——见连带取舍。(g) 同步时机放到 MR 验绿等待期、发现冲突再同步——那时距拉仓更远、冲突更大,且回合已收口,不如推送前当场解决。
