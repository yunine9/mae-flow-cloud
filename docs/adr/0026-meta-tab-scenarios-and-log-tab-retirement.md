# 元信息页签场景化与拉取日志页签退役:标题/描述归无单场景,日志人读面收敛为下载

2026-09-14 拍板(grill-with-docs 会话)。修订 ADR-0023 立的元信息页签构成;Agent 主理原则第二例。

**元信息页签场景化**:无单场景(登记)有登记信息,有单场景(DTS)没有——标题与问题描述只在无单场景渲染,判定口径用 `detail.ticket`(与头部单号徽标、DTS 页签禁用同一条判定词);DTS 场景这两项不渲染,单据页签是标题/描述的唯一出处。压死骆驼的事实:DTS 发起时 wire 上的 description 存的是单据标题的抄本(发起调用 `description: ticket?.title`),元信息里陈列它 = 同一信息两处、且其中一处是错的。实现是条件渲染不是懒加载——数据同步就在 detail 上,代码分割只有复杂度没有收益。

**去壳**:「登记信息」section 壳整体删除,标题/问题描述/业务模块/网管环境一律 MetaField 平铺;登记场景四项全显,DTS 场景只显后两项。壳按场景改名(「基础信息」之类)被否——DTS 下模块来自单号预绑、环境来自运行中环境闸补配,本来就不是"登记"事实,两场景各是各的来源,不硬凑一个两场景都含糊的标题。

**网管环境空态**:DTS 发起不带环境,等运行中环境闸回填——未配置时显示「尚未配置」加一句引导(等 AI 举卡询问后回填),不设第二编辑入口(元信息页签只读陈列原则不破)。

**拉取日志页签退役**:页签连同日志树、逐文件在线查看器、在线解压整体退役。AI 读日志从来不走这个页签——链路是 Agent 在容器里跑 issue-ops 技能把日志拉到 local-logs、再用自己的文件工具读,页签从头到尾只是人看的橱窗,拆橱窗不动仓库;而人要日志的场合(转交网管、留档)要的是文件不是网页阅读器。人读面收敛为一枚「下载日志」钮:整包 zip,后端新增打包端点(复用过程文档打包先例)。在线解压随查看器陪葬——下载后本地处理的前提下失去意义。

**「拉取日志」按钮 = 意图递交(Agent 主理第二例)**:按钮不执行任何事,新端点照抄 POST /issues/:id/repos 骨架(终态/queued 守卫 + recordTransition/appendSessionEvent 留痕 + startPlatformTurn 投递),AI 经既有 issue-ops 技能执行拉取。忙时 steer 排队(当前工具调用做完即送达,不掐断不丢),空闲开新回合,缺环境走既有环境闸(举卡→回填→自动续跑),全链无新状态位、无新并发面、无新停点。服务端直跑 fetch-logs 被否:技能编排(凭据获取、虚拟化/K8s 双引擎分叉)复制进 TS、分钟级任务要新造后台状态机、与 AI 回合并发写 local-logs 零锁、绕一圈仍欠"通知 AI"的通道——执行者就是 AI,"执行完通知 AI"自然消解。清单刷新靠既有 updated_at 轮询,点击后的提示须管理时延预期(仿关联仓「已通知 Agent 处理」)。

**按钮状态机**:非终态常显「拉取日志」(环境未配置也显示,点了自然走到环境闸——空态引导由它承接);已拉取(materials.logs 清单非空,无独立状态位)显示「下载日志」;终态拉取钮消失、下载钮保留(终态只回收 repo/,local-logs 保留期内仍在,与「导出现场记录」终态可用同口径);不做「再拉一次」入口(想拉新的,对话现场一句话)。重复拉取不设门禁,提示词一句"已拉取过则向用户确认"兜住——排队语义下连点只是重复意图,无破坏性。

**契约钉同步**:七签逐字表改六签、`view === "logs"` 分支断言删、`--workspace-tab-color` 计数、issueMetaPaneSmoke fixture 补 source/ticket 两场景,随代码同 PR 改。

曾考虑:(a) 保留日志树+查看器迁往别处——否,无"在线翻日志"的高频证据,AI 分析在会话内,人要的是文件;(b) 页签不删只加下载钮——否,橱窗留一半不如不开;(c) 服务端直跑拉取——见上,四硬伤;(d) 「登记信息」壳场景化改名——否,去壳更统一。
