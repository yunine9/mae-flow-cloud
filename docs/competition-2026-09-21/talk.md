# 十分钟讲稿与演示路线

## 第 1 页：MAE Flow（35 秒）

今天我想分享 MAE Flow 里最核心的一部分：怎样把一个会写代码的 Agent，组织成团队日常能用的工程工具。

一个需求的工作不会在代码生成后结束。它还会经历需求澄清、设计检视、编译测试、推送，以及 MR 反馈。我们做的 Harness，就是把这些环节接起来，让 Agent 持续执行，让人能在关键地方作决定。

我会围绕可靠性、可维护性、高效和安全讲几个设计取舍，然后用 Cloud 里一个已经完成的需求展示落地效果。

## 第 2 页：核心 Harness 架构（75 秒）

这张图可以从中间看。Agent 负责理解问题、分析方案、编写代码，以及根据反馈修复。

围绕 Agent，我们补了两类支撑。第一类是工作方法，例如怎样做需求分析、怎样写测试、什么时候查知识，通过 Prompt 和 Skill 表达。第二类是执行协调，例如当前任务在哪里、人在什么时候作了什么决定、工具实际执行了什么，以及中断后怎样接着做。

下方是 Git、编译测试、MR 和流水线。Agent 可以解释结果，但是否推送成功、流水线是什么状态，仍然要读取真实工具结果。

上方是人。人明确目标、审视方案、提出修改意见，并作出交付取舍。Cloud 把这些交互和材料放在同一个工作台里。今天演示 Cloud，是为了让大家看到这套核心机制怎样被使用。

## 第 3 页：可靠与安全（90 秒）

这里最重要的是区分两种反馈。

如果流水线报告了可以定位的编译或扫描失败，系统把真实失败信息交给 Agent，继续修复和验证。遇到权限、审批或者需要业务判断的问题，就明确交给人。

如果 MR 上出现一条检视意见，我们不会直接认定它必须改。尤其是现在 AI 也会不断提检视报告，如果每条都自动改，很容易形成循环。我们的做法是先交给责任人判断，再把选中的意见交给 Agent。

可靠性体现在结果有依据、过程有记录，中断后能够恢复已保存的上下文。安全体现在人的回答不能由 Agent 代做，取消、接管和远端权限仍然有效，不能为了把流程走完就把失败写成通过。

这些机制降低风险，但代码质量仍需要测试和人的判断。我们保留这条边界。

## 第 4 页：易改与够快（80 秒）

我们也走过加很多检查的路。每个检查单看都像有道理，放在一起却可能让 Agent 不断补格式、补回执、重新确认，真正的工作没往前走。

现在我们先判断规则属于哪一层。工作方法，尽量写进 Prompt 和 Skill。执行状态与人工决定，由程序管理。不同代码平台的命令和返回差异，放在适配层。这样的划分让一个方法或者一个外部接口变化时，修改有明确落点。

效率上，我们优先减少无意义的等待和返工。例如已经确认的同样内容，不应该因为一次普通提交又让人确认。并行则以明确的职责和依赖为前提，不把同一个工作区交给多个写入者互相覆盖。

这也是我们一直坚持的取舍：流程不等于质量，却直接影响闭环速度。没有明显质量收益的流程，应当简化。

## 第 5 页：切到真实需求（20 秒）

下面不展开整个 Cloud。我只打开一个已完成的需求，看它的目标、一次人的介入，以及最终交付证据。用这一条链，验证刚才讲的设计。

## Cloud 演示（4 分钟）

演示前选好一条真实需求，固定标签页或截图，避免现场搜索。每一步只放大一个重点。

| 时间 | 打开什么 | 指给评委看什么 | 建议口述 |
| --- | --- | --- | --- |
| 5:00–5:35 | 已完成任务的需求原文 | 一句业务目标、责任人、任务 ID | “这是实际需求，先说明要解决什么问题。” |
| 5:35–6:20 | 产出文档或架构图 | 一个模块的职责与接口关系 | “Agent 把实现方案先整理成了可以讨论的材料。” |
| 6:20–7:25 | 批注与检视、对应代码改动 | 一条真实意见、补充要求、处理结果 | “责任人决定改什么。这里能看到意见怎样落实到具体改动。” |
| 7:25–8:30 | 测试记录、MR 链接与平台状态 | 真实执行结果、对应版本、已合入状态 | “完成有外部结果支撑。这里分别看测试和实际合入。” |
| 8:30–9:00 | 交付摘要（该任务有则展示） | 修改结构与测试范围的简短总结 | “这份材料帮助 Committer 快速定位重点，需要时仍可展开代码。” |

若任务没有交付摘要，最后半分钟停留在 MR 结果页，不补造文档。若没有合适的一条检视修改记录，换需求或者明确说明这个案例没有该环节，不拿别的任务拼成一次交付。

现场不演示等待编译、不临时派发新任务、不点击推送或关闭意见。演示用的已完成任务只读。预先截好同一任务的关键画面，网络异常时按同样顺序讲解。截图要让文字可读，去掉与展示无关的个人信息与敏感内容。

## 第 6 页：结束（1 分钟）

MAE Flow 最核心的工作，是给 Agent 一套能够持续执行、又允许人介入的工程支撑。

可靠，是结果有依据。易改，是规则有清楚的归属。够快，是少做无意义的等待和重复确认。安全，是关键权力仍然掌握在人和真实系统手里。

我们希望把少数人摸索出的 AI 开发方法，逐步变成团队都可以使用的工具。Cloud 是其中一个落地现场，今天展示的是背后的核心设计取舍。

## 答辩准备

**和一个 Skill 有什么不同？**

Skill 承载方法，是这套系统的重要组成。Harness 还承接会话和工具执行、状态保存、人工决定与交付反馈，让方法能够在持续的任务中被执行。两者职责不同，可以配合。

**流程越多，是不是越可靠？**

要看它核对什么。真实权限、人的回答和工具结果值得核对。文档多一个空行、同样内容重新提交，不应该成为反复返工的原因。我们的原则是优先删除没有明显质量收益的检查。

**为什么认为可维护？这么大的工程也会越来越难维护。**

我们用职责划分控制修改范围：方法、流程事实、平台适配、页面交互各有落点，也给关键行为配定向回归。当前仍有大的服务模块和历史耦合，需要继续拆解。可维护性是持续约束，不因为画了分层图就已经解决。

**Agent 仍然可能写错怎么办？**

工具不能消除模型错误。通过设计检视、真实测试、流水线反馈和人工取舍发现问题，把明确的问题交回原任务修复。平台不把“流程完成”当作代码正确的证明。

**有没有具体提效数字？**

没有完成统一口径统计，就只展示当前案例可核实的结果。代码首次成型比例、Token 消耗等可辅助分析，但不能直接当成人力节省比例，也不能单独代表代码质量。

**安全是否代表彻底隔离、凭据绝不进入模型？**

不作这种承诺。这里讲的是需求交付中的操作权限、人工决定、取消接管和真实结果核验。具体隔离与凭据暴露取决于部署和工具链，要按实际链路说明。

**断电和重启后能不能继续？**

已保存的会话和任务状态可以恢复。入口与执行服务分开部署时，重启入口不必打断执行。执行器本身退出仍可能中断在途命令，恢复时要核实结果，不能把上下文恢复解释成命令必然成功。

**为什么展示 Cloud，却说只讲核心？**

参赛讲解聚焦 MAE Flow 的核心执行与控制思路。Cloud 提供了团队交互、托管执行和平台集成，让这套思路更容易展示。不会把所有 Cloud 扩展功能都声称为单独一个 Skill 已经具备。
