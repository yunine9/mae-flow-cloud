# PI 会话上下文：请求前主动整理

## 现场与取舍

task-20 报告中的网关拒绝为 `current input length 179544 > max input length 169984`。
这证明当次请求超过实际容量；`end_turn` 或中断日志本身不能证明模型主动放弃，
也不能仅凭报告断定每次中断都是 token 上限造成的。

横向核对发现：宿主按事件数量压缩，Pi 按已用容量在回合边界压缩，Cloud 又在
超限后压缩并重发原消息。新输入、同轮工具输出、临时知识不受同一预算管理；
摘要请求本身可能过大；发生工具调用后，最后一次模型错误还可能被当成正常结束。

按 kernel-simplification 的顺序处理：删除事件数触发、问题流阶段强制压缩、
SDK 自动压缩与 Cloud 原消息重发的重复路径。真实模型容量不能删除，统一在
`sessionCompaction.ts` 管理。保留现有普通网络重试、用户审批和工具执行语义，
不增加审批、收据或内核步骤，不修改 mae-flow 内核。

## 现在如何运行

1. 主、子、Build-Fix、知识整理等会话都从 `CloudSession.openSession` 接入同一策略。
   每次模型请求前计算；连续调用工具的一轮也会检查，不必等整轮结束。
2. 容量先读 `model.contextWindow`。明确的网关容量反馈可向下校正，并以原生
   custom entry 随会话持久化；重启沿用，不改用户的模型配置文件。
3. 统计系统提示词、工具定义、有效历史、新消息和临时召回知识。
   中文使用保守估计，图片单独估计；真实 usage 的输入加缓存输入校准估算，
   不是精确 tokenizer，也不是模型自行判断。通常约 70% 触发；输出预算较大时
   提前触发，为响应和新增结果留空间。
4. 优先保留近期消息以及当前用户原话，旧历史整理成目标、约束、已完成、
   未完成和证据位置。沿用 Pi 的工具调用切点，保留成对的调用与结果。
   单个已完成工具批次或输入太大时，整批整理并留下续跑提示，不能保留巨量
   尾部导致“压完还爆”。短的当前用户需求另外保留原文。
5. 使用当前主模型整理。摘要输入也有预算，长历史分段更新摘要；不丢掉长日志
   的中段。最终摘要完整且确实减少上下文后才写 Pi compaction entry。
   原始消息仍在原生会话文件中，无第二套转储文件。
6. 工具正在运行、等待人工回答时不调用压缩或 abort；请求前是工具批次完成后的
   安全位置。主动取消会中止摘要请求，不提交半截/空白/截断摘要。
7. 网关第一次暴露更小容量时允许一次补救，从已完成工具结果继续，不追加原
   用户消息，不重新执行工具，不通过重启容器处理上下文。再次报错如实返回。
   新一轮后来积累的超限仍有一次机会。
8. 摘要失败保留原会话，避免每次工具调用都重复尝试；普通执行可继续。
   若模型仍拒绝超限且无法整理，报出真实原因，不假装已完成。

## 配置和观测

无需新增配置。旧 `compact-every`、`issue-compact-every-events` 和管理页事件阈值
不再决定策略，管理页移除事件阈值输入；接口保留旧字段兼容历史客户端。
原生自动压缩只在本会话用内存 override 关闭，不改其他 Pi CLI 的持久化设置。

日志记录会话名、触发原因、估算前后 token、当前容量、容量校正、失败/取消原因。
摘要模型的 token 计入该会话消耗。数字是估算；生产摘要质量和网关真实延迟
仍需部署后观察，不能用本机模拟网关的耗时替代。

## 本地验收

使用真实 Pi 0.84.1 SDK、原生会话落盘与可控 HTTP 模型端点测试：

- 200k 配置与 169984 网关容量量级的大输入，在执行请求前缩小。
- 中文、缓存 usage 校准、工具 schema、临时知识均参与预算。
- 多段摘要、单轮巨量工具日志、当前用户约束、原始历史与重启压缩边界。
- 网关容量反馈、恢复不重复用户消息、后来再次超限、重启沿用容量。
- 工具执行期间不打断；摘要失败、空摘要、取消不破坏历史。
- 主会话工具执行后的模型错误如实报告，子会话错误仍正确回传。
- 问题流切阶段保留报告与修改方案，小会话不因旧事件阈值多调用模型。
- 进程 SIGKILL 后续跑和已完成工具/子 Agent 结果恢复的已有回归。

这些测试验证策略和恢复行为；没有把模拟摘要当成真实模型语义质量的证明。
