# task-5 检视意见与推送接续修复

2026-09-11，根据内网现场补充报告修正诊断：两次推送确认都已被接收，
已有推送收据得到复用，Agent 收口后最终也创建了 MR 并进入流水线修复。
确认后约七分钟的处理主要花在清单登记及重确认，不能归因于确认丢失。

## 已修复的断点

- 旧 `sent/owner_pending` 表示意见到了责任人队列，并不表示已送给 Agent。
  它与新草稿使用同一个待处理判据，责任人选择按意见修改时随决定送出，
  不再按旧 route 过滤；已自行答复或已闭环的意见不混入。
  先持久化决定及意见版本，再更新送达展示；中断后按同一决定补投影。
- 工作区与交付清单记录的文件集合、内容指纹相同时保留原审批，
  仅登记清单、暂存、提交或调整比较基线不要求重答。
  文件集合或内容真实变化仍作废旧审批。
- 真实变化由内核登记 `approval_request`，Cloud 在已有工具结果通道中
  复用 AskUserQuestion 创建实际等待卡，按审批对象幂等。
  回答经现有内核 Hook 登记；`messages` 不再被描述成创建问题的途径。
- `--unchanged` 不是“已推送”的声明。指引要求优先复用准确的清单，
  否则用 `--file` 明确实际交付文件；不删除缓存来绕过检查。
  未归类残留报错只显示前 20 个路径及总数。
- Agent 在 `external_verify` 收口后，先持久化宿主交接状态再释放容器，
  避免容器清理和 MR 请求期间仍显示 Agent 在执行。无新使命、无人待答、
  无宿主操作待执行的旧 `running` 快照，恢复后直接接续宿主验证。
  责任人换了目标的 queued 任务保留新使命。
- 流水线触发使用公共客户端的 HTTP 状态校验与 30 秒请求预算，
  失败进入原交付恢复流程，不把失败响应当成触发成功。
- 推送成功立即同步内核发布 SHA，纯旧 CI 批次退出调度并保留历史；
  与它混在一起的人工意见继续处理，回执只要求仍有效的条目。
  自动生成的旧 CI 使命在修复版本发布后撤出，追加的人工目标保留；
  纯 CI 修复直接查新 SHA 的流水线，已有运行不重复触发。
- 当前流水线材料目录绑定 SHA 和请求批次，旧文件移至历史目录；
  404、断网、空响应、延迟返回都不能重新展示旧材料。
  MR 采集结果核对实际 SHA，版本不明时如实缺失，不能把请求参数当证据。

## 回归证据与边界

- 真实 Python 内核 + ScriptedModel + CloudSession + KernelHost：
  `done` 拒绝旧审批 → 实际 waiting → 用户答复 → 内核记账 → 下一次
  `done` 进入 push，重确认请求清除。
- 真实 Git + 主会话自然收口 + 本地 Git 平台替身：已有推送继续创建 MR、
  验证流水线；容器停止期间状态准确；旧 running 恢复不重复派会话、
  不重复触发已有流水线；新人工目标不被吞掉。
- 意见发送覆盖新草稿、旧责任人队列、不同作者/旧 route、暂缓、
  自行答复，以及决定落盘后投影中断恢复。
- 真实 Git 推送后的 running / success / failed 三种结果均验证：
  新失败只送新 SHA 证据；推送不伪造质量通过，人工意见不会一起被关闭。
- 采集器使用受控平台替身测试 MR 旧 SHA、缺失 SHA、按提交回查，
  镜像测试覆盖延迟响应、错误版本与超时；内核覆盖混合批次的回执登记。
