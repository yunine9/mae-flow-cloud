# 单仓拆分方案(2026-08-31 用户检视通过,已开工)

## 2026-09-03 勘误:拆分变成分析的产物,下单开关取消(用户拍板)

原方案让单仓下单时勾「大需求先分析再拆分」。这把"该不该拆"压给了信息
最少的人、放在了信息最少的时刻——那正是分析阶段应该产出的结论;判错两头
都贵(大需求没勾=巨型 MR,小需求勾了=白跑一轮分析加一次确认)。现在的
口径:

- **仓数不决定路线,开关也不决定。** 多仓仍天然先分析(客观事实);单仓
  一律按普通任务下单、照常填单号,不问"大不大"。
- **拆分由读完仓的 Agent 提议,人有最后一票。** 单仓直接开发的主任务多挂
  一个工具 `propose_split`(理由 + 建议切法)。Agent 在澄清需求/定规格盘出
  改动面后判断一个 MR 装不下就调它;宿主举一张决定卡,只有主责任人能答:
  选「先分析再拆分」才掐掉编码会话、按分析单重启,后面就是本文原有的澄清→
  盘点→划分方向卡→方案→确认→按单元建子任务;选「不拆,一个任务干完」会话
  原地继续,零成本,以后不再受理。上一位 Agent 的理由与切法进分析提示词当
  起点,不当结论。
- **同仓串行不变**;父单下单时的单号不下传,确认卡逐单元填。
- 人一开始就知道要拆,在需求原文里写一句"先拆分"即可,Agent 读到会直接
  提议;不再需要模式开关。

下文凡提到"勾了先分析拆分"的地方,按"Agent 提议后转成分析单"理解。

## 解决什么问题

特别大的需求只涉及一个仓时,现在拆不动——拆分只到"仓"粒度,单仓
就只能一个人一个任务扛到底。目标:单仓也能拆给多个人,每人认领
一块,每块一个任务一个 MR,检视面小到"一个人能负责任地看完"。

## 跑起来什么样(以"通知按用户偏好过滤"为例)

1. 下单选仓,照旧;
2. **澄清期(线上会议室,chain 的第一责任)**:Agent 读代码理解
   需求后逐题追问,直到**所有不确定事项每条都有结论**(人答了、或
   明确记"按 X 假设,责任人拍板")。责任人答题,协作者对问题清单
   随时批注插话(机制现成);全部 Q&A 沉淀为 CHAIN 文档必备章节
   「已确认事项清单」(问题→结论→谁拍板)。**方案里不许有待定项**
   ——模糊性留给下游=让 N 个 agent 分头猜,拆分方案出现 TBD 即
   不合格,打回澄清期;
3. 澄清收口后,盘出**改动面盘点 = 存量触点 + 新增规划**("要改
   14 处:偏好存储 3 个文件、过滤逻辑 5 个…"/需求全是新功能时则是
   "计划新建哪几个模块、接缝落在哪几个既有文件"——纯新增反而好拆:
   边界自定、冲突面趋零,接缝文件统一归契约块);
4. **划分方向卡(新增固定阶段)**:盘点清单摆给人看,问"怎么切,
   有什么讲究?"——人给方向("按这三块切,过滤给老李"),也可以答
   "你看着切";协作者在这张卡上都能批注插话;
5. Agent 出拆分方案:第一块永远是**契约骨架**(接口头文件+空实现,
   编译得过),后面是各业务块,排成**串行队列**;人确认方案时给每块
   定责任人和单号。
   **2026-09-01 勘误(用户拍板)**:原文"不填回落父单号"已废——
   "父单号"概念整个取消。勾了"先分析拆分"的需求**下单不填单号**,
   单号在拆分确认卡上逐单元填(一个交付分支一个单号,拆完知道有几个
   交付才填几个);同仓同责任人的单元不能同号(内核按
   {基线}_{工号}_{单号} 派生分支,同号即同名分支互相覆盖)。
   **拆得不合理就打回重拆**:选「需要修改」+ 批注圈问题,Agent 结合
   批注修订再举卡,循环到满意(现有方案修订机制原样)。**执行中**
   才发现切错:已合入的块不动,主责任人取消未开工的块、回主任务
   修订方案重新确认——建单可重入(已有 task_id 的块跳过),只补
   生成修订后的新块;
6. 逐块执行:契约块合入 → 单元 1 开工(基线里天然有接口骨架)→
   合入 → 单元 2 开工 → … 每块都走完整的现有流程(Build-Fix、
   流水线、push 确认、MR 检视、合入)。**串行队列按仓各排各的**:
   需求涉及多仓时,各仓的链并行往前跑,只有同一个仓内部逐块排队
   (实现=同仓单元间加 blockedBy 边);仓与仓之间只在分析出真实
   跨仓依赖边时才互相等,与现有跨仓语义一致;
7. 干活中某块要改接口?Agent 直接改(就是往已合入的契约文件上加
   新提交,普通 git 演进),被负责面拦下**自动举卡**,主责任人点
   "放行"即裁决,改动随该块 MR 一起检视——不开新任务。放行卡 +
   MR diff 即变更留痕。**方案文档不追改**:它是拆分时刻的设计快照,
   接口唯一真相是基线里的头文件(任务书写明"以代码为准")——两个
   真相源打架比文档旧更危险,与"投影不是第二状态机"同一纪律。
   例外:改动大到动摇拆分本身(职责挪块),主责任人在卡上拒绝,
   转而修订拆分方案。

### scope 与执行顺序

`scope.paths` 是单元允许修改的范围，不是文件永久所有权。按阶段拆分
时，契约骨架、逻辑实现和补测天然可能修改同一目录甚至同一文件；只要
任务存在明确先后顺序，方案确认应允许范围相同、父子包含或部分重叠。

当前同仓单元统一串行：上游 MR 合入基准分支后才算完成，下游随后启动，
启动时重新从远端最新基准分支克隆代码。因此同仓重叠范围不会造成并发
写冲突。若后续开放同仓并行，重叠单元必须增加先后依赖，或由人明确确认
并行修改风险；不能在没有顺序的情况下静默并发。

## 人参与的六个时点

1. **下单**:事先有成见写"执行补充"(可选);
2. **澄清期(线上会议室)**:责任人逐题拍板,协作者批注插话,结论落「已确认事项清单」;
3. **划分方向卡**:给切法方向,协作者可批注(最接近"开会讨论分工"的时刻);
4. **方案确认**:定每块的责任人和单号,拍板生成任务;
5. **越界/契约卡**:某块要动别人的面或契约文件时,主责任人一键裁决;
6. **每块的 push 确认 + MR 检视**:现有机制,谁的块谁签字。

## 第一版明确不做(路线图,真需求撞墙再做)

- **同仓并行**:第一版同仓全串行(跨仓照旧并行)。串行直接消灭
  并发冲突、契约广播、资源争抢、失败传播四类问题;agent 通宵干活,
  串行的日历代价可接受。实测跑通后再放开"无依赖边的单元并行"。
- 逐单元会签(先靠划分卡批注+方案确认兜);
- 边类型体系/OpenAPI 契约测试(灰度期同语言头文件为主,REST 按需);
- 集成收口专门机制(先用"最后一个单元=集成验证面"表达);
- 检视排队/关键路径调度。

## 输出件清单(作者产出只有两份,其余机械派生)

  1. `CHAIN-<单号>.md`——完整方案,必备章节:需求理解、已确认事项

     依赖图(Mermaid)、逐单元启动说明;

     责任人)+ 依赖边。与 md 同源,矛盾以人检视过的 md 为准。

  (方案复制进子任务工作区,现有机制)、单元任务书(建单时按节
  抽取一页内联)、划分方向卡上的盘点(CHAIN 章节内容上卡)。
