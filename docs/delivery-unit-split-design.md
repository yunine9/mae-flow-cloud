# 交付单元拆分:大需求单仓/跨仓统一分工设计(2026-08-31 对齐)

一句话:把需求拆分图的节点从「仓」泛化成「**交付单元 =(仓,文件面)**」,
跨仓拆分与同仓模块拆分坍缩成同一张平面 DAG,复用现有全部拆单机制。

背景与动机(用户提出的现实问题):特别大的需求只涉及一个仓时,现有
能力只会按仓拆单——单仓就拆不动,多个人无法分工。Agent 时代瓶颈从
"写"移到"审",拆分的第一目标是**把每个 MR 的检视面切到一个人能负责任
地看完的大小**,不是把写码并行化。

## 已对齐的决定

1. **节点泛化**:交付单元 =(仓 URL,可选 scope)。scope = 模块名 +
   负责路径面。跨仓依赖与仓内模块依赖是同一种边,拓扑机制不区分。
2. **两级只在分析层**:分析 Agent 先按仓划职责、再对大仓按模块划面;
   执行层就是一张平面 DAG,不引入两级任务树。
3. **契约先行 = DAG 第一节点**(不需要新机制):接口/骨架/共享文件
   注册占位作为 scope=契约层 的节点,同仓其余节点全部 blockedBy 它;
   契约节点 merged 后下游解锁,克隆基线天然包含契约,无需追赶。
4. **单号策略(用户拍板)**:每个交付单元可设自己的单号,同仓多 MR
   挂同一 REQ 或子单号**皆可**。现有机制已支持:图节点本有逐节点
   ticket 字段,建单时节点有单号用节点的、没有回落父单号
   (taskService.ts createRepositoryDeliveries:
   `ticket: repository.ticket ?? task.summary.ticket`)。
5. **灰度节奏**:先做**串行依赖链版**(契约节点 + 全链 blockedBy,
   零并发风险),真实大需求跑通一单后再放开同仓并行。

## 机制盘点(读码实测,均为现成积木)

- 拆分图来源:分析 Agent 按云端指引写
  `.mae-flow-work/<ticket>/requirement-graph.json`(节点+依赖边),
  指引全文在宿主 `requirementAnalysisPrompt`(taskService.ts:14337),
  **内核零涉及**——拆分是交付前置分析,不是流程判定,红线无涉。
- 拓扑排序 + 循环检测:`requirementGraphPlan`(taskService.ts:6488)。
- 逐节点建单(可重入、逐节点单号/责任人/blockedBy):
  `createRepositoryDeliveries`(taskService.ts:6705)。
- 依赖解锁:settleMergeState merged 时 pump「依赖任务解锁」。
- 契约变化回流:CrossRepositoryUpdate(子任务发现契约不够用 →
  回流主任务 → 复制给上下游子任务)。
- 同仓并行的冲突收敛:冲突门禁真实事实 + 自动冲突修复窄使命
  (2026-08-30 MFC-037 修复轮落地),后合节点由机器追赶目标分支。
- 文件面边界执行原语:交付白名单(delivery_selection)+ 宿主机械
  边界整理——现为排除清单,反向即负责面 allowlist。
- 同仓多在途任务闸门:重复下单 409 对内部拆单豁免;MR 幂等键是
  (源分支→目标分支),逐节点单号使分支名天然不撞。

## 要改的清单(全部宿主侧)

1. **图契约扩展**:节点加可选 `scope`(模块名+负责路径);校验从
   「节点 URL 与下单仓一一对应且数量相等」(taskService.ts:3017/3030)
   放宽为「每节点 URL ∈ 下单仓,每仓 ≥1 节点」。
2. **分析指引扩写**:requirementAnalysisPrompt 增加单仓模块拆分指导
   (何时拆、按检视面定粒度、契约节点先行、scope 路径面怎么写)。
3. **建单下传 scope**:子任务使命写明负责面;交付门禁按 allowlist
   校验越界——越界不硬拒,举卡让人裁决(可能是拆分方案漏了)。
4. **放宽两个闸门**:「单仓任务责任人必须是下单人」(taskService.ts:4899
   附近)与「协作者邀请要求 ≥2 仓」改按节点数判定。
5. **UI 适配**:需求图展示同仓多节点(仓名+scope),子任务卡带负责面。

暂不做:专门的集成收口机制(先用「最后一个节点=集成验证面」表达);
同仓最大并行度调度(灰度期串行链,不需要)。

## 已知边界

- 同仓并发任务的现场细节(每任务独立 clone,理论干净)未实测,
  这是灰度先串行的主因。
- 检视面粒度没有机器判据,依赖分析 Agent 判断 + 人工确认拆分方案
  ——与现有跨仓拆分同一信任模型。
