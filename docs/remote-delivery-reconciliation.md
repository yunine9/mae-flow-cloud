# 推送前与恢复时核对远端事实

2026-09-12：task-24 报告显示内核有 published，而宿主缺少交付投影。
仅凭报告不能断定投影被哪个写入覆盖，也不能从 delivery_watch 推断 MR
已合入。当前代码中 published 由可信宿主登记，普通 done 不产生推送收据。

修复将远端核验移到交付准备、推送确认之前。没有 MR 标识时按仓库及
源/目标分支查询全部生命周期，唯一匹配才关联；多个匹配由责任人选择。
先查 MR，已合入复用原可信 close，保留未推送本地改动的说明；无需远端
源分支仍存在。opened 再用隔离的宿主 Git 环境核验远端引用，只有与当前
HEAD 一致才补发布收据，查询期间 HEAD 换版或任务取消则不采纳旧结果。
空收据对象不能阻断有效收据恢复，也不能被当成真实发布事实。

恢复等待推送确认和无 MR 关联的 delivery_watch 时复用同一入口。
人工新目标、暂停任务不被自动启动。MR 合入可按原收口规则停止在途执行。
只撤销过期的推送卡，不代答其他检视或澄清问题，不制造流水线 PASS。

工作台任务标题下增加“刷新 MR 状态”，查询中禁用重复点击，失败在旁边
显示原因；多个候选展示 MR 链接及关联操作，不自动挑最新 MR。

## 部署

本次只修改 Cloud，内核无需新增版本。必须同时更新 Cloud 与适配器配置：
将 deploy/adapter-config/mr-pipeline.patch.json 合入现场配置，按同目录
README 的候选配置脚本操作，包含新 mr_discover 命令。只更新代码而不更新
已有适配器配置时会明确提示未配置，不能把不支持查询误当成没有 MR。

mr-discover.py 使用既有 CodeHub REST API 查询 state=all，分页有总预算，
过滤精确分支对及跨 fork 同名分支；失败不返回伪造的空列表，凭据不回显。

## 验证边界

真实 Git 裸仓、Python 内核与可控平台回归覆盖：投影全丢且本地有新提交、
已合入收口、重启恢复、过期卡撤销、同 HEAD 补账、不同 HEAD 不误记、多个
MR 不猜选、责任人权限；既有 CI 接续、MR 抢占与取消回归继续通过。
部署查询脚本通过本地 HTTP 替身验证全生命周期、分支/fork 过滤及故障。
内网 task-24 的数据没有现场修改，真实内网 API 仍需随部署验证。

## MR 监听连续性修复

既有讨论派修复并非缺失，原入口绑在 await_merge + 检视门禁失败 + 自动修复
开启之后；同时讨论/回复 HTTP 没有超时，监控单拍异常会使整环退出。
这些是代码中确认的风险；没有内网日志不能断言 task-5 究竟命中哪个分支。

现在 opened MR 每轮先观察讨论，running/verifying/paused 等状态也进入现有
FeedbackStore 索引，观察快照不覆盖在途 Agent 的原始材料。派单仍只在
await_merge 执行，遵守自动修复开关与唯一 writer。明细有未解决意见时，
滞后的绿灯不能核销它们；平台批注 verified 从不代表 CodeHub 已解决。
讨论请求及回复批次有 10 秒预算，单拍异常继续下一拍；合入检查优先执行。
配置缺失、HTTP 失败、返回体缺字段都视为查询失败，不冒充没有意见。
部署仍需配置既有 mr_discussions/discussion_reply（参考 mr-loop-adaptation.md），
本仓不能代替内网配置提供真实讨论；未配置时界面显示查询失败并持续重试。

新增回归覆盖暂停/运行中观察而不派单、await_merge 门禁绿灯但有两条讨论仍
派修复、单拍异常后恢复、响应正文挂起超时、观察幂等且不重置处理状态。
本地真实服务已在浏览器点击“刷新 MR 状态”，核验由暂停且缺 MR 投影恢复
到真实远端已合入并完成，按钮自动退场；未连接内网 task-5/task-24。
