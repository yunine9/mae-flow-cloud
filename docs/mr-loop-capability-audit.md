# MR 闭环能力自检问卷(给内网模型执行)

> **这份文档是一个任务书**:在内网,把下面每一项逐条核实,产出一份
> 固定格式的《能力核对报告》带回外网。报告的用途是回答一个问题:
> **现有平台能力够不够支撑 MR 闭环的完美集成;不够的话,缺哪几块、
> 各自有没有替代路。** 外网按报告迭代契约与代码——你(内网模型)
> **不写代码、不改代码**,只做核实与记录。
>
> 执行纪律:
> - 每一项都要**真调一次**拿到真实输出,"文档上说支持"不算数;
> - 输出样例脱敏后原样记录(保留字段名与取值形状,值可以打码);
> - 判定只有三档:**✅ 已具备 / ⚠️ 有替代路(写明) / ❌ 缺失**;
> - 拿不准就标 ⚠️ 并写下你看到的原始证据,不要替外网下结论。

---

## A. 逐项能力核对(闭环的最小充分集)

对照系统:CodeHub(或等价托管平台)、CI 平台、检视系统。
每项给出:判定、你用的调用(命令行/MCP 工具名+参数)、真实返回样例。

| # | 能力 | 闭环里谁消费 | 不具备时的后果 |
|---|---|---|---|
| A1 | 建 MR(源分支→目标分支,带标题) | 交付点 | 整条链没有入口 |
| A2 | 建 MR 幂等(重复建同分支对能识别已存在) | 恢复/重放 | 重启后 MR 翻倍 |
| A3 | 查 MR 生命周期(opened/merged/closed) | 合入监控 | 永远不知道赢没赢 |
| A4 | 查合并门禁(九项,名字+过/没过) | 失败分类 | 只能盲修 CI,检视/冲突/等审批全误判 |
| A5 | 按 SHA 查流水线结果(结果绑提交) | 流水线裁决 | 旧绿灯背书新代码(造假) |
| A6 | 拉流水线失败详情(失败 job、构建日志文本) | CI 修复的口粮 | 修复会话瞎修 |
| A7 | 拉未解决检视讨论(id/文件/行号/内容) | 检视修复 | 检视意见永远挂着 |
| A8 | 回复讨论并标记已解决(带讨论 id) | 检视闭环收尾 | 修了代码门禁还是红 |
| A9 | HTTPS push 到工作分支(个人或服务令牌) | 修复推送 | 修完推不上去 |
| A10 | 触发流水线 / 或 push 自动触发 | 交付点 | 有码没验证 |

**每项按此格式记录:**

```
A4 查合并门禁
判定: ✅/⚠️/❌
调用: codehub-cli mr view --project xxx --format json   (或 MCP 工具名+入参)
返回样例(脱敏):
  {"mergeable_state": {"conflict_passed": true, ...}}
备注: 九项的确切拼写是 ...;"未通过"的取值形状是布尔/字符串 "failed"/...
```

## C. 调用通道核对(CLI vs MCP vs REST)

外网适配层目前的形态是**argv 命令模板**:每个端点配一条命令行,
JSON/正则抽字段。所以每个能力都要回答"有没有一条命令行能拿到它":

- C1 逐项写明:走 codehub-cli 子命令?走 curl 打 REST?还是**只有 MCP
  一条路**?
- C2 若某能力只有 MCP:记录 MCP 网关的**传输形态**(stdio 进程?
  SSE?streamable HTTP?)、鉴权方式(X-Auth-Token/w3token 怎么带)、
  以及**一次完整调用的原始报文**(初始化+工具调用+返回)。外网拿到
  这个才能决定:给适配层加原生 MCP 客户端,还是包一个"MCP→命令行"
  的桥(比如一个 20 行的 python 脚本,stdin 进参数、stdout 出 JSON
  ——桥本身也是配置产物,不算改代码)。
- C3 SSE 日志网关(get_mr_pipeline_info / download_build_task_log):
  在试点机器上**能不能直连**?跑一次,把返回的 record_ids /
  x_auth_groups 形状记下来。

## D. 约束与红线核对

- D1 工作分支是谁建的?格式固定吗(如 `目标分支_用户_单号`)?
  别人会不会往上面推提交?(决定 force-push 永久禁用还是可放开)
- D2 CodeHub token 与 HTTPS push 凭据是同一个吗?(实测一次 push)
- D3 检视"回复"与"标记已解决"是一个调用还是两个?谁有权限 resolve
  (作者?任何人?token 对应人)?
- D4 SuperChecker 类"不可修工具失败"长什么样?(工具名?错误码?
  贴一条真实失败)
- D5 流水线是 push 自动触发还是要显式触发?同一 SHA 重复触发会怎样?
- D6 单仓还是多仓交付?多仓的话 MR 之间有没有依赖关系?

## E. 报告格式(最终产出,原样誊回外网)

```
# MR 闭环能力核对报告 <日期>
## 总判定: 可以完美集成 / 可以集成但有 N 处缺口 / 关键能力缺失
## A 逐项: (十行,每行 编号+判定+一句话)
## B 门禁表: (填完的表)
## C 通道: (每能力一行:CLI/REST/仅MCP;仅MCP 的附原始报文)
## D 约束: (六个问题的答案)
## 缺口清单: 每个缺口写三样——缺什么、平台上有没有替代路、
##            建议外网怎么改(加端点?改形状?降级?)
## 附件: 各调用的脱敏返回样例
```

## 附:你可以用来自检适配层的命令(填完 adapter.json 之后)

```bash
npm run adapter -- --config adapter.json --selftest \
  --repo <仓地址> --source-branch <工作分支> --target-branch <目标分支> \
  --sha <一次真实提交> --mr <MR iid>
```

它会打印每个端点解析出的命令(令牌打码)和只读端点的一次真实调用
结果、契约字段核对。这段输出也要进报告附件。
