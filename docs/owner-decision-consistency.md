# 用户改口后的文档一致性

task-21 报告的现象是“回执口径对、Spec/TC 和旧目标口径错”。没有内网现场不能
证明每次模型到底读取了哪份材料，但当前实现能确认三处传递问题：

- 插话进入宿主指令账，AskUserQuestion 答复只进入 waiting 账。原 task_context
  和恢复提示只读前者，旧 set_target 因而容易压过较新的澄清答复。
- Open 漏读 decisions；Build 明确要求以文档压过会话，前提却没有保证文档吸收
  新答复。Story 任务卡原本已有 decisions，但 Spec 排在前面，且未要求核对矛盾。
- Agent response、执行目标摘要、用户原话的作用没有讲清，容易把“已登记”
  误当成“用户批准”，又把“已写回执”误当成“所有产物已同步”。

## 平台与 Agent 的分工

平台从原有指令、waiting、annotations 台账组合阅读上下文，保留原始编号、时间、
操作者、提问语境、每题答复、附言和处置状态。供 Agent 的工具结果带答复来源编号；
`task_context(view=instructions, keyword=编号或文字)` 可查完整原文。主会话恢复时
附最近输入；`.mae-flow-work/owner-inputs.json` 是按原账重建的阅读副本，供子 Agent
任务卡读取，不是第二套决定注册表、审批或授权事实。副本不可写不阻断用户操作，
工具仍能读原账；未新增 UI、hook 或门禁。

| 输入 | 传递方式 |
| --- | --- |
| 初始需求 | 当前任务需求及原文材料 |
| 决策卡、澄清卡、自定义答复/附言 | 原 waiting 账，按回答时间整理，保留问题对应关系 |
| 责任人/协作者插话及显式知识引用 | 原宿主指令账，身份区分；完整固定版本内容保留 |
| 代码/文档批注、转交附言 | 原 annotations 账；只有已送达的当前意见进入执行上下文 |
| 责任人自行答复、逐条处置、再次处理 | 原 annotations 账；旧闭环不能代表新一轮已通过 |
| 接管会话内用户要求 | 用户消息落盘后同时登记原宿主指令账，交还后仍可查 |
| MR 外部讨论 | 原始讨论快照进入阅读上下文，既有 FeedbackStore 负责派发；不把状态更新时间当成用户发言时间，外部显示名不成为操作授权 |
| 全局 Story/跨仓更新 | 既有协作记录同时进入阅读上下文，不伪装成本任务责任人原话 |

平台只标出目标摘要之后有新输入，不猜哪些话已经被推翻，不自动删除无关目标。
Agent 先区分补充、推翻、疑问、建议和执行排序，再同步受影响的 decisions、BEH/TC、
Story/实施附录、代码、UT。决定表可用一行“来源及当前结论 → 对应 BEH/TC”，
不强制新版本格式；旧口径留作历史并说明取代关系。未送出的草稿仍等责任人处理，
协作者的话不取得责任人操作授权，机器 response 不作为用户决定输入。

现有设计/需求检视要对比原话、决定和对应行为/用例的含义，点名矛盾的两边及影响；
清楚的冲突直接原地改，真正歧义才合并询问。不会因为摘要、编号、文件时间变化而
重新开配置、重建任务/分支/MR，也不会再造“语义不通过→无限重试”的机械环。
local-spec validate 明示只检查结构，不给出“语义已正确”的假保证。

## 验证与边界

task-21 夹具保留旧“不执行脚本”和新“执行 queryENE.sh 获取等效数”的原话，验证
真实 waiting 落盘/重读、查询工具、子 Agent 输入顺序及旧目标降级显示，且流程状态
不被展示逻辑改写；覆盖草稿/待送批注隔离、附言/人工处置、权限和阅读副本故障。
结构检查不能证明任意自然语言语义正确，因此没有用字符串匹配冒充模型理解测试。
内网 task-21 的 Spec、代码和会话未现场修改，部署后仍应让 Agent 按最新原话核对。

部署需 Cloud 与随仓 kernel 快照一起更新；独立内核源仍维护在
mae-flow 的 cloud/workflow-customization 分支，本次同步该来源，不手改快照。
