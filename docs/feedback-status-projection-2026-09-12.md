# 机器反馈结束后仍显示处理中

## 根因与行为

内核的 `superseded`（新推送替代旧流水线）和 `superseded_by_merge`
（随真实 MR 合入结束）此前未进入 Cloud 反馈状态映射，索引继续保留
`repairing`。混合批次也把仍在处理人工意见的批次状态套给已退出调度的旧 CI。
发布、合入与重启没有完整补齐这份展示索引，刷新页面只能读到旧状态。

Cloud 现在消费这两个既有内核状态，并依据已签名的发布事实逐条投影混合批次。
发布成功、可信合入结束和服务恢复时同步索引；这三个展示对账入口失败只记录
原因，不倒退推送或合入事实，不重派 Agent。核销权限仍由原有收据校验负责。

面板、会话流与 Agent 的反馈查询统一保留历史失败：

| 事实 | 展示 | 自动调度 |
| --- | --- | --- |
| 旧流水线已被新推送替代 | 已被新版本替代 | 历史记录 |
| 机器告警随真实合入停止 | 随合入结束 | 历史记录 |
| 责任人暂缓 | 已暂缓，未解决 | 暂缓 |
| 真正验证通过 | 已完成 | 已关闭 |

统计使用“待闭环”，不再把暂缓和已结束条目统称“进行中”。没有新增按钮、
人工确认流程或运行门禁。人工批注/MR 讨论仍由各自来源方裁决，新推送不
替人工验收；同 SHA、无法确定 SHA 和 Build-Fix 告警不因新推送被猜成过时。

`annotations.jsonl` 的 `drop` 是撤回批注，与机器反馈索引不是同一条状态。
有明确 `source=workspace` 与 `source_id` 关联的撤回会闭环对应记录；删除
“转自流水线”的批注副本不会把原始流水线失败改成通过，也不按文案猜关联。

## 验证与部署

- 65 项专项回归通过：逐条状态、索引重建、幂等、4 条批注已 drop、实际
  Git/内核的推送与合入、重启恢复、宿主工具、来源回执和内核故障恢复。
- 同一 MR 经人工意见与流水线反馈两轮后合入的独立端到端用例通过。
  Git 与内核真实执行，模型和远端平台使用测试替身。
- `npm run gate` 包含类型检查、web 构建与契约测试；133 项通过，1 项因
  未配置真实 Docker 构建镜像而明确跳过。
- 真组件静态渲染的 1200/600 宽截图已目视检查，证据位于
  `.pilot/feedback-state-diagnosis/`。
- 扩展 MR 回归的合并提交标题断言在未修改的 `da5055c` 同样失败：夹具最新
  提交是 `[REQ9][feat]测试交付提交`，断言要求 HEAD 为 merge 标题。本次未改
  该提交机制，保留对照日志 `baseline-conflict.log`，不能宣称全量测试全绿。

仅改 Cloud，内核已具备上述状态。部署并重启 Cloud 后，仍保留内核现场且有
可信宿主收据的任务会自动对账，不需要手改 task.json 或重新派修复。
无法访问内网现场，尚未核对内网所指四条具体记录的 ID 与原始账本。
