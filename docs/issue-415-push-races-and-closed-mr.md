# Issue 415：并发推送与 MR 关闭后的重复执行

## 定位

[Issue 415](https://github.com/yunine9/mae-flow-cloud/issues/415) 的正文报告：任务 15 多次遭遇远端分支领先，之后 MR 关闭，宿主持续返回笼统的“当前 MR 或推送授权不允许发布”，Agent 又重复发起推送。问题单没有附加评论。

核对当前代码后，确认并非完全没有推送前同步：工具推送已有 `prepareHostPush`，自动交付也会同步源分支和目标分支。实际漏洞有四处：

1. `absorbForeignBranchCommits` 在 `ls-remote` 后 fetch，却仍按较早查询的 SHA 接续；查询与拉取之间新增的提交可能遗漏。
2. 同步完成后，远端仍可能继续前进。Git 正确拒绝非快进推送，但宿主没有在同一次操作中重新同步，而是让 Agent 或交付恢复再尝试。
3. `allowPush=false` 原本会抛出笼统错误，再走普通工具失败的会话续接，覆盖关闭 MR 后的等待状态。后台监听也只在 `await_merge` 状态处理关闭，运行和修复期间会漏掉。
4. 推送成功后，远端头若立即被别人继续推进，严格要求远端头等于本次 SHA 会误报失败；实际上本次提交可能已经在远端历史里。

本机用真实 bare Git 仓、两个提交者和 HTTP 平台夹具复现这些窗口。没有直接修改生产任务、分支或 MR。

## 修复

- 同步使用本次实际 fetch 到的远端头。
- 工具推送和自动交付共用有限重试：只有 Git porcelain 明确报告非快进拒绝时，重新同步、核对既有授权后再推送；同一次操作最多发送三次。持续并发写入则停止自动重试，提示协调同分支提交者。网络、权限和仓库规则错误不冒充并发推进。
- 保留现有文件范围确认和真实冲突处理；不自动扩大授权、不强推覆盖别人的提交。重试只触发最终成功提交对应的流水线。
- MR 关闭在运行、排队、验证及推送确认期间均可识别：停止自动执行、保留本地代码与原目标，继续监听重开/合入。拒绝结果直接展示 MR 关闭原因，不再交给 Agent 猜文件权限。
- MR 重开后接续因关闭而停下的原工作；用户主动暂停的任务不会被自动恢复。关闭等待也能跨服务重启保留。
- 推送后的反查允许远端头已经是本次提交的后继，但必须实际拉取并验证祖先关系；收据仍只记录本次发送的 SHA。若历史不包含本次提交，仍报告失败。
- MR 状态变化与传输结果交错时，保留真实推送收据，旧执行不再继续安排流水线或恢复 Agent。

本机锁无法阻止远端其他提交者，所以没有把 fetch、同步、push 宣称为跨服务原子操作，也没有增加新的审批流程。需求交付的宿主逻辑仍在 TS，未修改内核快照或问题单处理流程。

## 验证与边界

定向测试覆盖：查询与 fetch 间新增提交、同步后再次推送、持续并发三次停止、成功后远端追加、自动交付只触发最终 SHA、MR 关闭零传输和零会话重试、重开接续、重启恢复、用户暂停、单号纠正、检视回复与凭据隔离。最后一轮相关回归 122 项通过，类型检查通过。

扩大到相关 MR/CI 回归时，有一条既有测试“流水线绿后仍持续监听：同一 MR 后续转红会自动修复并重验”失败。保存的任务现场显示它在下一次推送之前停于反馈回执 JSON 读取：`Unexpected end of JSON input`，对应未修改的反馈回执读取路径。依仓库规则，记录该 CI 反馈域失败，不在本问题中扩展修复或重跑全量套件。

生产仍需部署本次版本。原 MR 如果仍关闭，任务应明确等待责任人重新打开或主动停止；系统不会擅自新建或重开 MR。没有绕过真实代码冲突和原有文件范围决定。
