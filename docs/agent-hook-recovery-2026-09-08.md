# 子 Agent 证据登记与标准按钮修复

## 已证实的问题

task-3 的现场描述提示 Critic 观察缺失。本机没有内网原始现场，不能仅凭描述断言是哪次部署首次丢失。代码和真实 Hook 联测确认了以下缺陷：

- `KernelHost.postTool` 未传子会话标识和生命周期；Python 默认把缺少 status 的结果当作 returned，未检查 is_error。
- 启动、完成观察写入异常在内核内部被吞掉。Cloud 虽然会记录 Promise rejection，但收不到这类“返回成功”的异常。
- Cloud 调用的分发器仍可能因看门狗、内部异常或 CLI 失败而 exit 0；被信号终止且退出码为 null 也可能被宿主当成功。
- agent_finished 已写入、内核尚未完成登记时重启，旧恢复逻辑会跳过已 finished 的子任务。
- 文件范围检视引用了未导入的 started_observation；以前异常被吞掉，真实链路测试才将其暴露。
- Agent 观察文件损坏时可被静默重建，导致历史观察丢失。

## 修复后的协议

1. 启动派发先经内核授权并登记 started。Cloud 严格模式下登记失败返回故障。
2. 子 Agent 返回、模型失败、中断、初始化失败均写入真实生命周期事件；完成载荷携带 call_id、child_session_id、状态、原始事件时间。
3. 报告先持久化，再等待内核登记，最后追加 agent_observed 确认事件。该事件表示内核已处理投递，不代替内核质量判定；纠偏反馈随确认记录留存。
4. 重启只补投未确认的完成事件；按原调用 ID 幂等登记，保留原完成时间。尚未完成的子 Agent 如实登记为 interrupted。
5. IO、进程、分发器故障有界重试，仍失败则阻止后续工具并如实结束本任务。没有新增 Agent 执行时限。
6. 真正缺少 started 的历史报告不伪造观察，也不匹配到另一位 Critic；内核返回明确纠偏，要求按 current 重新派发本步所需子 Agent。

严格故障协议由 KernelHost 自动设置 `MAE_FLOW_HOOK_STRICT=1`，不要求部署者新增 serve 参数。内核普通插件模式的分发器故障策略保持原状。`Task` 与 `Agent` 以及各类内核子 Agent 共用同一协议；普通工具也在前次登记失败后停止执行。

## AskUserQuestion 标点

确认答案、choice 映射、展示选项和独立任务确认的归一化规则遗漏了半角逗号。现统一兼容 `,` / `，`；只改匹配时的格式处理，不改写用户原话。否定、审批主题版本、步骤归属和选项映射仍照常校验。
