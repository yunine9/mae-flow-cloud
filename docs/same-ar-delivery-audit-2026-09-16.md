# 同仓同 AR 交付与记忆召回排查（2026-09-16）

## 结论

AR 是业务单号，不是 MR 的唯一标识。同仓串行单元允许共用 AR；同仓并行单元必须使用不同 AR。分支通常按目标分支、责任人、AR 命名，因此相同责任人的串行单元会复用远端分支，但必须各自交付、各自创建 MR，不能继承前一轮的完成结果。

串行复用仍有 Git 边界：普通合并/快进保留上一轮源提交历史时可继续快进；源分支被删除后可以重新创建。若 squash/rebase 改写合入历史且保留旧源分支，下一轮可能无法快进，当前外来提交处理会停止推送并保留现场。这种情况下不能承诺同 AR 自动接力，也不能用强推覆盖旧分支来消除阻塞。需要先确认分支处理方式，或为下一单元使用不同 AR。

## 本次处理

- 删除“同分支唯一历史 MR 即本任务 MR”的推断。发现候选先查生命周期；只有当前任务已有该版本的推送记录、且本地仍在该版本，才允许自动恢复已结束的 MR。打开的 MR 仍保留原有找回能力，多候选不猜选。
- 普通刷新、自动交付、重启恢复继续共用远端对账入口。
- 所有 MR 合入收口入口统一停止在途 writer，然后确认合入源版本包含本地 HEAD。外部追加提交可以正常合入；缺对象时只获取 Git 对象，不改写分支或工作区。旧合入不能把本地新提交标成完成。
- 修正假平台按分支取第一条 MR、忽略请求 MR 标识的问题，避免同 AR 多轮验证使用错误门禁结果。
- 记忆 sidecar 默认检索预算由 1500ms 调整为 3000ms；上下文预算为 sidecar 实际预算加 500ms，替代固定 200ms。仍有超时降级、预热、单会话单在途检索和缓存，不让检索故障阻塞任务。

## 横向检查

| 环节 | 结果 |
| --- | --- |
| 普通下单 | 同仓同 AR 在途任务冲突检查；不同仓可以同 AR |
| 拆分确认 | 按依赖可达关系判断串行；同仓无依赖不能同 AR |
| 提前开始、调度、恢复 | 复用调度冲突检查，不能借提前开始制造同 AR 并行 |
| 推送 | 每任务独立推送记录；拒绝无依据覆盖外来历史，不强推 |
| MR 创建 | CodeHub 配置的 mr_lookup 只查询 opened；上一轮 merged 不应作为新建结果 |
| MR 发现 | 全生命周期查询不能直接认领历史记录，本次修复 |
| 合入完成 | 公共 settle 入口核对本地未交付提交，本次修复 |

## 验收场景

1. 正常秒级记忆查询进入模型上下文；真正超时仍可继续任务。
2. 本任务推送记录存在、MR 投影丢失：主动刷新/重启仍可恢复合入。
3. 同分支历史 MR 已合入，但当前任务有新代码：不认领、不完成。
4. 旧版本已经误绑 MR：刷新不能把本地新提交标完成。
5. 修复 writer 工作时旧版本被合入：停净 writer、保留提交、不标完成。
6. 外部在当前 MR 追加提交后合入：可完成，不伪造新版本流水线通过记录。
7. 同仓同 AR 两轮真实 Git 交付：第二轮新提交、新 MR、独立合入。

已经误标 completed 并落下内核 close 的生产任务不会被本补丁自动重开。应保留工作区，先核对本地独有提交及实际远端包含关系，再处理后续交付；不能仅凭本地提交数断言代码永久丢失，也不能直接擦除历史收据。
