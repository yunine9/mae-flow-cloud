# 基础组件知识萃取

## 使用

配置中心 → 基础组件仓：团队成员维护组件名称、HTTP/HTTPS 仓库地址、分支、组件目录、适用语言（可多选）及说明。每个条目表示一个可研究的源码范围，同仓多个组件可分别配置。配置保存留有操作者及前后值。

团队资产 → 知识文档 → 萃取知识：选择组件、**单个语言**和具体主题，例如“文件句柄归属、异常清理及 UT Mock”。配置中心的“萃取知识”也进入这里。语言不同分别研究，避免不同语言 API 混用。

研究在后台执行，最多并行两份。同一操作者、组件配置、语言、主题复用已有进行中或完成记录。需要检查源码更新时点击“重新萃取”；普通查询和重复发起不会重新拉仓。失败记录可直接重试。

记录保留范围、固定源码版本、工具调用、返回片段（最多 4000 字符）、错误与 Markdown 草稿。研究使用少量有代表性的真实调用，明确事实、推断、单一样例与版本未知。不是编译或测试通过证明。

审查时可编辑草稿，选择平台通用、业务模块或代码仓范围；确认采纳后才调用现有知识文档保存及索引链路。草稿不参与正式知识检索。知识阅读页可回到原萃取记录；采纳操作在文档历史留痕。重新萃取不会覆盖已经采纳的知识。

## Agent 调用

沿用统一 `knowledge` 工具，不新增阶段或审批：

1. `knowledge(action="search", query="C++ 文件写入 句柄释放")`，已有适用知识直接复用。
2. 缺少内部组件用法时，`knowledge(action="components")` 查看配置。
3. `knowledge(action="research", component_id="返回的组件 ID", language="cpp", query="文件句柄归属和异常清理")` 返回研究 ID、状态及界面链接。
4. 继续独立工作。需要结果时 `knowledge(action="research_status", id="研究 ID")`，不循环轮询。草稿仅作有待核实的证据，不能当作已采纳规范。

组件分析子 Agent 继承相同工具。提示词要求在 implementation 计划中记录知识缺口和研究链接，不因为旁路研究阻塞整个任务。

## 内网运行条件

- 使用平台当前主模型，无须专门配置萃取模型。
- **平台服务宿主**安装 `ec`，服务运行账户可执行并可访问 Sourcegraph。自动查找 `~/.local/bin/ec` 或 PATH，也可设置 `MAE_FLOW_EC_BIN=/absolute/path/ec`。
- 只在内网 PI 所在电脑安装 ec 不够；若 Cloud 在另一台服务器运行，需要该 Cloud 服务宿主也具备 ec。工具由宿主调用，不要求业务编译容器安装 ec。
- 使用已确认的接口：`ec tools`、`ec repos QUERY`、`ec kw QUERY`、`ec nls QUERY`、`ec read REPO PATH --start:=1 --end:=160`。不依赖 Lua 或任意 `ec call`。
- 同步组件源码使用发起人的个人 Git 凭据。缓存按账户、凭据、仓库和分支隔离；首次浅抓取，后续 fetch，研究固定到本次 commit 读取；同一缓存的准备操作串行。
- 研究模型只有 `component_source` 和 `code_search` 两个只读工具，无 Bash、写文件、推送或子任务工具。源码缓存为 bare Git，不加载其仓库指令作为研究指令。
- 模型阶段十分钟上限，单次 ec 调用三十秒上限。停止服务会终止会话，意外重启会将旧的未完成记录标为中断，不能假装完成。
- 记录：`<data>/component-research/<id>/record.json`；执行事件、会话文本保存在同目录。源码缓存：`<data>/component-source-cache/`。这些是本部署内部资料，沿用团队成员可信的访问范围。

## 已验证与内网验收

本机自动测试覆盖：配置与语言、复用与并发、重启中断、普通 knowledge 检索不可用时独立发起研究、真实 Git 缓存与固定版本读取、真实 PI 会话调用 ec 替身、无写入工具、HTTP 发起/查看/采纳、草稿不入索引与采纳留痕。

本机没有内网 ec/Sourcegraph，**替身验证不能证明真实检索效果**。内网部署后用一个已知组件主题验证：源码同步成功；搜索返回真实调用仓库；read 能展开上下文；草稿引用与源码一致；语言和适用范围正确；确认采纳后能通过“试搜知识”及任务 knowledge 工具召回。无结果时应显示证据不足，不能为了产出而虚构用法。
