# 运行中交办与等待反馈

责任人可以在 Agent 工作期间继续交办修改意见，不用等一个阶段或上一批意见全部结束。相关要求结合处理；等待远端流水线时可继续不依赖其结果的工作。独立调查和只读检查可并行，具体安排通过 Cloud 实际注入的 `concurrentWorkPrompt.ts` 传达给 Agent。

## 已接入的行为

- 需求侧的普通插话、批注、MR 修复交办共用处理指引。MR 会话启动空档直接持久化补充要求，去掉提交接口最多十秒的等待。
- 问题侧的报告批注支持运行中提交、连续提交。每次只发送当次草稿快照，不默认回退分析、不清空验证登记、不额外启动执行者。
- 空闲时继续当前会话；排队时随启动送达；正在等人回答时保留问题卡，意见完整保存，随答复送达。接管期间不启动 Agent。
- 启动空档、发送失败和回合收口时，原有恢复通道接续尚未送达的消息。停靠消息不再截断到 2,000 字，也不再超过八条就丢最早一条。
- 界面区分接收与读取，保留批量交办的接收说明；完成仍以实际修改、逐条回应及验证结果为准。不能用“已读取”代替“已落实”。

## 并行的实际边界

这次没有增加自动分叉的多 writer 执行器。同一工作目录仍由一个执行者负责修改；不需要重新起一轮才能交办。子 Agent 的独立调查可以并行，若分头改代码，必须先隔离工作目录，再由主 Agent 汇总并验证。

当前工具执行期间，PI 的 steer 会在工具结束后消费，不会在模型尚未读到时宣称已开始处理。现有 Build-Fix 是专项写入者，切换到人工功能修改时仍须先释放旧执行权；不会放开两个执行者同时改共享目录。

流水线结果仍绑定实际验证的代码版本。收到了新要求不等于旧验证失效，但出现新代码也不能把旧提交的绿色结果当作新代码通过。

## 验证

`concurrentReviewDispatch.test.ts` 覆盖运行中两批交办、待启动、等待人答复、长消息及十批恢复、发送失败、接管/终态边界、MR 启动空档。`issueConversation.test.ts` 覆盖读取状态和原话展示；`mrLoop.part4.test.ts` 覆盖 CI 与人工意见合并以及单 writer 的竞态。
