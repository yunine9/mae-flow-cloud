# 统一知识检索本机穿刺验证（2026-09-16）

## 结论与边界

继续使用 memsearch 可行，但不能将现有 corpus_search 简单改名后当作完整方案交付。先修正统一候选排序、模块知识接入、版本适用信息和检索分数解释，再做工具、提示词与治理 UI 的完整实现。

第一轮穿刺只增加可复现诊断脚本和报告，没有修改生产检索路径、知识库或部署；后续核心实现和复测见文末。不是完整功能验收，也没有验证 Agent 是否实际遵守检索提示词。

## 环境与复现

本机已有 `.local/memsearch-venv`：memsearch 0.4.19、milvus-lite 3.2.1、pymilvus 3.0.1，缓存模型 `gpahal/bge-m3-onnx-int8`，未启用额外模型重排。

```bash
NO_PROXY=localhost,127.0.0.1 no_proxy=localhost,127.0.0.1 HF_HUB_OFFLINE=1 \
  .local/memsearch-venv/bin/python harness/knowledge-search-probe.py \
  --output .local/knowledge-probe/result.json
```

脚本创建独立临时语料和数据库，结束后删除；不打开现有知识库。首次启动受到本机代理影响，gRPC 把回环连接送到代理端口；本命令仅对本进程排除回环代理后正常运行，不改系统代理设置。

语料包括 12 条根据讨论构造的对抗样例（10 条已采纳、1 条草稿、1 条停用），以及仓库真实的 kernel-simplification、task-patrol 两份 SKILL.md。样例不是生产数据，不能把小样本命中率当成生产准确率。模块样例放在单独目录用于验证现有仓库限定的遗漏，不代表现有业务模块存储格式。

## 实测结果

| 场景 | 结果 | 对实现的影响 |
| --- | --- | --- |
| `-DDT_test=UT generate-sources`、`ResolveFmaFileKey` | 正确经验排第一 | 底座能处理本次测试的技术字符串；不等于所有符号均支持精确匹配 |
| 中文回调生命周期换说法 | 全库搜索正确经验第一；现有 sidecar 合并后第二，第一是无关版本配置 | 本仓与全局分开检索后按 RRF 分数直接合并会扭曲排序 |
| 中文 YAML 换说法 | 正确经验被召回，但不是第一 | 不能把首条结果直接视为适用规范 |
| 纯中文的两个诊断查询 | BM25 返回空，语义仍有结果 | 本机默认分词并未提供有效的中文关键词补充，需另测中文分词支持 |
| 2.6B / 2.7B 相似配置 | 正确版本第一，但错误版本仍紧随其后（约 0.984） | 排名不能代替版本适用性判断 |
| repo-b 的 UT 构建 | 现有 sidecar 返回 repo-b 说明，不带 repo-a UT 说明 | 仓库限定在此样例有效 |
| 跨仓告警模块经验 | 全库能找到；现有 sidecar 查询 repo-a 时漏掉 | 需统一模块、仓库、全局候选，不能只查本仓与平台目录 |
| 盆栽浇水、缺失的 Rust Tokio 规范 | 无对应知识仍返回若干候选 | 检索必须允许表达“只是候选”；不能宣称命中即有答案 |
| 真实技能文档 | 两个问题均召回对应文档，前几项包含同文档多片段 | memsearch 能索引非经验 Markdown；统一工具还需按资产合并片段 |
| 草稿 | 未进入向量索引 | 当前候选排除生效 |
| 修订接口名后重新索引 | 搜索结果包含新名字，不含旧正文 | 此次更新路径生效 |
| 已采纳经验改成 rejected，不重建索引 | 当前 sidecar 不再返回该经验 | 读取当前正本状态过滤能挡住残留索引；非所有停用 API 的端到端验收 |

冷启动约 2.4 秒，20 个初始片段索引约 0.37 秒；本轮每个问题的全库搜索加 sidecar 搜索合计为几十毫秒。仅代表小型暖缓存本机样例，不是大语料性能承诺。

## 为何不能用融合分数当置信度

本机 memsearch 将两路 RRF 分数归一化：两路都第一趋近 1；只有语义一路有结果时，第一名约 0.5。

实测：

- 相关的中文回调问题：语义余弦第一名约 0.632，关键词无结果，融合分数 0.5。
- 无关的盆栽问题：语义余弦第一名约 0.379，关键词无结果，融合分数同样 0.5。

因此，用融合分数阈值 0.5/0.6 筛选会同时放进噪声或丢掉正确经验。余弦分数也不是概率，不能用这两个样例直接定一个生产阈值。

本仓与平台各自搜索，两个集合各自产生“第一名”；直接把这些排名分数混排，不能表示它们对同一问题的相对相关性。

## 对完整实现的修正建议

1. 复用 memsearch，统一资产 ID、来源、启用状态、范围和版本信息；经验、模块知识和团队文档不再依赖经验文件名规则统一识别。
2. 在同一适用候选集合中排序。优先验证后端过滤能力；不能先全库取极少量再过滤，以免无关仓的内容挤掉相关结果。不要维持多个分区分数直接比较的旧路径。
3. 先保留原始查询的符号和版本，检索结果携带完整适用条件、例外和正文入口。片段按资产合并，避免同一长文档占满结果。
4. 针对中文、中英文混合、技术字符串补充分词诊断；需要时调整底座配置，不先自建第二套关键词引擎。
5. 工具将结果表达为候选，不把 RRF 分数暴露成可信度。Agent 根据适用条件决定使用或不使用。自动补充更应克制，不能把所有 top-k 正文强塞进上下文。
6. 不立即加重排模型或固定阈值；用更多带人工相关性标注的真实问题比较后再决定。
7. 统一工具和行动前检索提示词仍需端到端验证：中途出现新问题能否调用、展开、正确使用；检索不可用时能否继续任务。不得新增“未检索不准行动”的阻塞机制。

## 后续核心优化与复测（同日）

已实现统一 `knowledge` 工具，接入当前已发布工程资料、当前仓库关联模块资料和已采纳经验。取代新会话的两个旧检索工具；保留经验写入入口，自动记忆补充也使用修正后的候选集合与底层排序。

实测中新增发现：memsearch 默认会丢弃只有标题的段落，经验的“适用场景”标题因此可能没有进入向量。已改为短经验完整索引（含适用场景和例外），长文片段携带主题，且剔除审计 frontmatter。真实统一工具测试先抓到“回调问题排出告警资料”的失败，修正后在原样例通过，没有降低预期排名。

本地第二批新增不同问法和无答案问题，总计 21 个查询：17 个相关问题的正确资料均在前五条，其中 16 个首位命中；4 个无答案问题均返回空。含糊的“流水线配置不一致”仍不是首位命中，不能声称完全消除误召回。两份仓库真实技能文档经优化后的侧车首位命中，并按文档去重。

本轮版本与模块测试通过 Cloud 提供明确候选清单；不是 memsearch 自动理解并确认了版本。实际 TypeScript → sidecar → 模型 → 工具回包另有真件测试，覆盖自动发现关联模块、产品版本排除、经验搜索、停用与离线全文读取。

默认 BGE-M3 模型使用余弦 0.50 作为保守噪声下限，代码标识符的准确命中可以保留；此值是小样本初步校准，不是生产准确率保证，其他模型不能照搬。中文 BM25 分词尚未改变；中文能力由本机语义模型承担。本轮没有更换模型、增加重排模型，也没有修改生产部署。
