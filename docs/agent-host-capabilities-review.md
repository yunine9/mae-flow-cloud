# Agent 宿主能力：实现与审查记录

2026-09-10。核心原则：Agent 在任务授权内自主推进；平台协调执行、保存真实结果、承接人的决定。阶段负责组织工作，不作为通用工具的禁令。不新增质量 Hook、REST/MST 或部署验证。

## 本次接通的能力

| 能力 | Agent 入口 | 行为 |
| --- | --- | --- |
| 任务现场 | `task_context` | 当前状态、等待原因、真实交付结果、责任人原始消息编号、宿主操作结果 |
| 平台与反馈 | `task_context feedback/platform/reviews`、`task_pipeline status` | 反馈来源和精确 ID、MR 门禁与讨论、绑定提交的流水线状态及日志 |
| 知识 | `task_context knowledge`、`task_knowledge` | 发布模块、关联仓、知识正文及版本；沿用已有记忆检索，不要求退回分析或重新圈选 |
| 关联仓 | `task_control pull_repo` | 拉取本任务、发布模块目录或责任人提供的关联仓，用于调查；不暗改当前交付仓 |
| 设计材料 | `task_document` | 按行读取当前及父/子/同父模块的 Story、Spec 等产物；其他任务不可读 |
| 代码和 UT | 现有文件/Bash 工具 | 编辑、提交、运行 UT，更新 Story、测试设计和架构材料；不新增模板、注释数量或测试通过率门禁 |
| 验证控制 | `task_control retry_verification/stop_verification`、`task_pipeline trigger` | 有配置时单次执行 Build-Fix，独立停止在途验证，或触发已推送提交的流水线；停止不隐含跳过或推送 |
| 当前任务诊断与恢复 | `task_diagnostics`、`task_control restart_session` | 读取本任务 Git、事件、内核和宿主持有的容器信息；重建当前会话和容器，保留仓库、历史和工作目标 |
| 目标调整 | `task_control set_target/defer_feedback` | 引用真实责任人消息；调整优先级，或逐条暂缓明确不再处理的事项；原失败事实保留 |
| 反馈回执 | `task_feedback_reply`、`task_feedback_result` | 工作台意见和机器反馈逐条结构化记录；避免拼错 ID、把摘要带入 ID；沿既有核验链消费，不代签责任人验收 |
| 阶段性交付 | `task_control push/create_mr` | 固定任务仓、分支、SHA 和 MR 目标分支，真实推送、创建 MR；不要求先修完全部旧问题，不伪造 PASS |
| 模块协作 | `task_context related`、`task_collaborate`、已有拆分工具 | 查询关联任务进度和设计，按责任人已有协作指令同步接口/设计信息；不修改别人的分工 |

问题流同步开放 `lookup_modules`、`pull_repo`、`report_ut`、`push_branch`、`create_mr` 的阶段限制。单号、已登记仓库、任务分支、真实推送等前置条件仍在各工具执行处核对；用户主动开启的推送过目设置保留。未提交的在途文件可以留在工作区，推送只包含已提交历史并明确告知未包含部分。

新工具挂在需求主会话；问题流继续使用其原有工具工厂。验证子会话和人工接手会话不另起第二个任务控制者。Build-Fix 运行期间用户插话，会停止旧验证并把新要求送回主 Agent，无需等旧问题修完。

## 规则为何更少

- 复用 `extraTools`、Git/MR/流水线客户端、知识库和现有任务协作通道，不做第二套平台适配器。
- 内核继续是反馈生命周期的唯一写入者。目标调整通过原有签名 `feedback-open` 命令登记，Cloud 只做投影和执行。
- 宿主操作账本只记录调用与结果，不替代流程状态。模型排队后交还回合，宿主释放旧执行者再做有副作用的操作，结果送回同一任务。
- UT 失败、格式、注释、材料不足如实披露；不因此新增禁止推送的质量门禁。实际取消/接管、交付对象和责任人最终裁定仍有效。

## 目标与质量事实分开

`set_target` 是“先做 B”，不代表 A 已被取消。责任人明确“这轮不修 A/延期 A”，Agent 才逐条调用 `defer_feedback`。每条记录保留原始消息编号、责任人、理由及反馈版本；新的意见版本仍正常进入任务。

部分暂缓时，Cloud 与内核 `current` 都只要求剩余条目的回执，并单独展示已暂缓事项。整个批次暂缓后提升后续批次；没有后续批次时回到当前目标的编码现场，不宣告完成或验证通过。

流水线暂缓精确绑定原 SHA 的反馈，新提交失败不会被一概屏蔽。MR 暂缓绑定讨论及其修订版本，不因重复轮询复活；讨论改变后重新处理。

推送记录 `git_push` 的真实结果，旧 `delivery.sha` 和旧流水线结论保持各自身份。阶段性推送、MR 创建、流水线变绿都不自动等于整个任务完成。

## 专项审查发现及修复

| 实际问题 | 修复与证据 |
| --- | --- |
| 交接更新 epoch 后异常回到旧 catch，被丢弃，任务无 Agent 却仍 running | 宿主操作统一异常出口，由当前执行权落 failed 并通知；真实 TaskService.settle 故障注入覆盖容器停止失败和账本写失败 |
| 推送/MR 成功后任务状态写失败，可能丢失结果或重复操作 | 先保存远端收据，再更新任务投影；恢复只补状态。真实裸 Git 仓与本地 MR 适配器覆盖 |
| 验证重试沿旧路径另派修复，同时工具也恢复主 Agent | 单次验证模式只回传事实，既有正常交付仍沿原派修路径，避免双重入队 |
| 真正 Build-Fix 用 running 且持有 driver/container，插话仍被挡 | 以在途验证事实识别，撤销旧回调、停止验证、确认释放后接续；新消息先保存 |
| 可写 config 把宿主基线误作任务分支，MR 排队后目标分支漂移 | 核对宿主已有基线与分支，排队固定 MR 目标分支；执行不重读可变目标 |
| 控制字段被篡改后，通过其他正常签名入口“洗白” | 统一在宿主验签入口核对控制字段摘要及序号，覆盖正常反馈、流水线、close 等入口；兼容合法阶段推进和无控制字段的历史任务 |
| 内核仍把部分暂缓的条目列在必写回执中 | 当前目标与已暂缓摘要单列，只渲染仍需处理的条目 |
| 预创建的空白回执首次写入失败，atomic rename 使容器 bind mount 留在旧 inode | 接受空白初始文件，逐条保留其他回执，原位写入保持 inode；错误 ID 当场指出 |
| 人工诊断采集器会执行仓内 fsmonitor，且可跟随软链读宿主文件 | Agent 使用独立的任务范围采集器：safeGit、固定文件名、NOFOLLOW、真实路径校验；无害 marker/假秘密回归证明不执行、不泄漏 |
| 关联文档根目录被换成指向任务外的软链 | 在读取产物前核对任务目录与材料根，保留既有文件级路径边界，兼容 Windows 分隔符 |

## 必要的实际边界

宿主提供任务能力，不开放任意宿主 Shell、账号凭据、全局策略或其他任务的运行控制。合并、强推、删除、生产部署不从普通推送权限推导；跨模块发消息仍须对应既有责任人协作指令。工具已有授权不重复询问。

未配置的宿主验证/MR/流水线接口会如实返回缺项。远端流水线取消和 MR 描述修改未有当前适配器接口，本次不伪造这两项；Build-Fix 的独立停止与现有任务暂停/接管可用。MR 对外回复继续使用已有逐条草稿与授权发送链。

暂停、取消和接管后旧执行者不能自行恢复。已开始的远端操作若刚好完成，保留其真实结果，不把“用户已取消”写成“远端未发生”。

## 用户如何使用

责任人可以直接说：“A 这轮先不修，先解决 B，相关 UT 验证后把当前提交推上去。”Agent 读取真实反馈和原消息，逐条登记 A 的暂缓理由，接续 B，再请求宿主推送。无需人为切回指定阶段，也不要求把 A 伪装为已解决。

“先推当前提交”“重新跑一次验证”“换个会话继续排查”“看看关联模块的 Story”分别复用已开放的任务工具。工具返回 `queued` 只是排队；交接后的操作记录和远端收据才代表结果。部署后新建或重建的主会话会装载这些工具。

- `721a116` 引用了尚未导出的 `looksLikeBusyCollision`，导致问题流模块无法加载。补齐与当前 Pi 实际错误一致的分类函数，并验证普通工具/服务忙错误不会被吞掉。

- 主任务、CI、MR、工作台反馈和冲突修复的提示词统一采用“当前目标，新责任人要求可调整”；删除禁止阶段性推送的旧指令。真实模型请求中的开场有回归断言。
