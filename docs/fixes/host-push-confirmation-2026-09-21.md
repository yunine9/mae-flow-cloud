# 修复推送入口重复确认

## 实际原因

task-27、task-43 的现场报告显示本地提交尚未发布，并停在 `host_push_confirm`。
沿当前代码核对，`delivery.sha` 是已发布事实，不是推送许可：传输使用准备后的
`operation.sha` 和任务的仓库地址，成功验证远端后才更新 `delivery.sha`。
不能提前改成 HEAD 来假装代码已推送。现场报告缺少最后一次宿主操作的失败结果，
不能仅凭三个 SHA 不同断定具体 Git 失败原因。

确认规则确实有两套：普通交付按已确认文件范围复用决定，工具推送只继承同 SHA
的旧操作确认，且确认结果未进入普通交付的清单。每轮修复新提交因此可能重新询问。
另外，操作排队后提交发生变化会在准备阶段被拒绝，无法继续准备当前交付。

## 简化

- 工具推送复用现有 `delivery_selection`；人工确认也写回同一清单。删除同范围
  新 SHA 必须重新确认的规则及提示词。兼容旧操作和旧卡片。
- 排队操作取得执行权后读取当前分支和 HEAD，完成同步、范围整理，再核对实际
  文件范围。范围不变时沿用决定；新增范围或明确“先调整”仍须确认。
- 同一待办恢复不重复通知；范围变化另建待办，避免复用已回答的卡片。
- 保留真实分支、传输期间并发改写、远端推送结果的检查。网络失败不覆盖发布
  记录，重新推送不因 SHA 相同或不同另加审批。

task-43 的旧 MR 关闭 502 是独立问题；既有换号恢复逻辑在新交付已建立后只补旧
MR/分支清理，不重复建 MR 或推送。本次验证该逻辑，不把它归因到旧 delivery.sha。

## 验证

`tests/pushBaselineSync.test.ts` 使用真实本地 bare 远端和真实内核：一次人工
确认（含小鲁班备注）后连续修复、重建提交、同步上游均能实际发布；旧发布 SHA
在成功前保持不变；重复恢复同一卡不通知；跨入口复用确认；新增文件、明确打回、
网络失败重试、切换分支分别验证。另运行推送策略和单号纠正回归测试。

只修改 Cloud TS，不修改内核源码。内网需部署后再确认现场操作结果；没有远程
修改生产任务状态，也没有强推或将本地 SHA 冒充已发布 SHA。
