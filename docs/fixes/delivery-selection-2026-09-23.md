# 交付文件选择简化（#432）

用户可能漏看或漏勾文件，清单不能因此成为后续修复的永久限制。
需求交付中的文件选择改为“整理当次提交”，任务目标和责任人最新意见决定后续修复。

## 原因与证据

#432 报告 task-20 的清单从 12 个文件扩展至 15、16、19 个时反复阻塞。
这些具体轮次来自问题报告；本次没有直接读取生产任务的完整执行日志。
对当前代码的核对确认了四个会相互放大的机制：

- 自动交付和工具推送都把后续文件集合与历史清单精确比较，增减文件即重新要求确认。
- `restore_delivery_paths` 只能恢复旧清单已知路径，并把已确认状态改回待调整。
- 同步后的提交整理会自动移除旧清单排除的业务文件，可能撤掉必要修复。
- 未勾选文件曾被永久加入 `.git/info/exclude`，Agent 后续查看 Git 状态可能看不到它们。

给清单增加依赖扫描或更多恢复步骤，仍会保留“必须事先把所有文件选对”的前提。
本次直接删除这个前提。

## 当前行为

1. 推送卡默认选择当前已经提交的改动。用户可剔除或补选文件，宿主只整理当次提交。
   新卡和未显式传文件选择的确认不再套用旧的待调整清单。
2. 确认推送后，必要的实现、依赖、配置、测试可直接新增、删除、重命名或补回。
   文件增减、同步和新提交不会另开范围审批，也不需要先调用恢复清单工具。
3. 清单和当时的 HEAD 保留为历史记录。未勾选本身不等于永久禁改；用户明确要求
   不改或不提交的内容，仍由主 Agent 和 Build-Fix 的实际提示词要求遵守。
4. 首次推送确认偏好、明确“先调整”、工作台人工检视复检继续使用原有流程。
   分支身份、推送期间并发改写、远端实际发布 SHA 以及平台注入目录检查保留。
5. 不再自动按旧清单撤销业务修复，也不再为文件勾选增加永久 ignore。
   旧任务启动和推送时清理 Cloud 标记区内、可由任务选择记录确认的旧 ignore 条目，
   保留用户自行维护的规则及平台目录规则。
6. 旧会话的 `restore_delivery_paths` 继续可用：接受当前任务实际业务文件，更新记录时
   保留原推送决定，不要求排队时 SHA 不变，也不停止容器或丢弃模型上下文。

只修改需求侧 Cloud TS、实际提示词和文件选择的默认值，不修改问题单流程或内核源码。
没有增加新的审批状态、质量检查 Hook 或依赖识别器。

## 验证与部署边界

`tests/pushBaselineSync.test.ts` 使用真实本地裸 Git 远端和真实内核：确认 12 个文件后，
分三轮补到 15、16、19 个，期间更新远端目标分支并重启服务；每轮全部必要文件都实际
到达远端，没有重新要求确认。另覆盖旧恢复操作、无文件快照的旧推送确认、明确调整、
首次人工选择、并发同步、网络失败、错误分支以及真实发布 SHA。

`tests/deliverySelection.test.ts` 覆盖平台目录清理、业务暂存和未暂存内容保留、旧 ignore
迁移、中文及引号路径。`tests/hostSessionContinuity.test.ts` 验证更新旧选择记录保留
容器和模型会话。人工意见处理与文件选择草稿也按改动域做回归。

本次九个定向测试文件共 132 项，129 项通过。`workspaceExecutionPanel.test.ts`
有 3 条存量源码断言失败：两条仍要求旧的 `readDiffReview(task.id)` 调用形态，
一条要求旧的 `localGroupOpen` 组件状态；基线代码已改变这些结构，本次没有修改这些
调用或组件。按仓库约定报告后停止追查。随后补充的旧推送确认兼容回归单独通过。

生产仍需部署新版后继续原任务；本次没有远程改写生产状态或代答尚未处理的人工待办。
旧清单若已在以前实际删掉业务代码，需要 Agent 按最新需求补回，不能凭文件名重建内容。
