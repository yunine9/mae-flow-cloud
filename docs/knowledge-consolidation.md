# 定时知识整理

入口：**团队资产 → 知识库 → 知识整理**。创建、查看进度、失败重试、停止以及审查草稿都在这里。所有团队成员可维护，保存设置、编辑、采纳和撤回都会记录操作人。

## 日常使用

- 默认每天 **03:00（Asia/Shanghai）** 检查资料变化，可修改时间、时区或暂停，也可立即运行。服务不在线时不执行，恢复后当天到点会补检查；一次只运行一轮。
- 只处理已采纳经验、启用的正式文档和已发布模块资料，Skill 继续走原生技能加载，不参加整理。没有变化不调用模型。
- 使用平台主模型后台生成专题草稿，不阻塞需求任务，不自动采纳。新草稿通过已部署的小鲁班通知发起人；定时运行通知最后保存设置的人。未配置通知渠道时，从页面查看待审列表。
- 打开草稿可阅读来源、对比现有版本与新草稿、查看矛盾提示、编辑 Markdown，然后采纳。完整覆盖的来源由审查人确认；部分覆盖的原文继续参与检索。
- 采纳后的专题和上传、源码萃取的文档放在**同一个知识库**，支持原有试搜、阅读、导出。原文保留为来源证据，没有被删除。

## 增量与适用范围

宿主先按显式语言、模块、仓库、产品版本和局部路径分组。Agent 再查找相关资料，阅读原文，按主题组织章节与例子；没有明确语言的旧经验不会被程序推断为某种语言。语义搜索暂不可用时，可继续用关键词与原文阅读。

同主题使用稳定标识更新，不每天生成新文档。已有待审草稿不会被后台覆盖，其他新专题仍可生成；针对待审专题的新变化，在本次审查后继续整理。丢弃的草稿不会在来源完全没变化时天天重提。

来源修改、撤回或模块停用后，引用它的旧专题立即退出统一知识检索；有效原文继续可用。待更新专题需重新审查。判断在读取实时资料目录时进行，不依赖旧向量索引是否已经清理。

这是有意保守的范围隔离：第一版不自动合并不同适用范围的知识，也不会自动把模块经验升级为平台规范。模型会提出组织方式，人仍需判断归纳是否准确、前提是否保留。

## 数据与可移植性

以部署的 `dataDir` 为根：

- `knowledge-consolidation/state.json`：日程、任务状态、专题草稿、发布内容、来源版本和操作记录，原子保存。
- `knowledge-consolidation/published/kg-….md`：已采纳专题的独立 Markdown，含适用范围与来源清单，可直接拷贝。
- `knowledge-consolidation/runs/<任务>/<范围>/sources.json`：本轮读取的固定资料快照；同目录的事件、会话记录可排查实际阅读过程。

`published` 也保留历史采纳内容，不因撤回来源而删除文件；需要当前仍有效的知识，请使用页面“导出知识”，不要把历史备份目录直接当作实时检索库。

向量索引仍是可重建的检索副本。原始 Markdown 不变，专题是额外的可移植成果。公开仓备份/自动推送未在本次接入；现有“导出知识”可以选中专题下载 Markdown ZIP。

## 验证

`tests/knowledgeConsolidation.test.ts` 覆盖合并、编辑、增量、同名不同模块/语言/版本、全文/部分覆盖、来源失效回退、并发发起、重启中断、定时去重、通知重试和只读主模型会话。与现有知识文档、检索、导出测试一起运行。

本机 GLM 实测用三份明确标注为验证样例的 C++ SampleFile v2 文档：合并成一个句柄生命周期专题，保留同步接口/v2/借用所有权边界；含独立日志脱敏规则的原文被标为部分覆盖，继续可检索。该样例不代表内部 CBB 规范。
