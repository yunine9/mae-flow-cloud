# 交付报告：测试结果与改动点 4+1

代码已推送且 MR 创建成功后，Cloud 在后台使用任务主模型生成 `交付报告.md`。新提交、最终流水线结果和合入状态变化后自动更新，未结束的验证明确标注为阶段性结果。报告生成不阻塞编码、推送、修复或合入，也不增加审批步骤。

## 报告内容

测试报告逐项对应设计用例、条件/操作/预期、测试代码位置、实际结果、执行证据与版本，区分通过、失败、跳过、未执行和未确认。MST 就是模块 UT，统一称为“模块 UT（MST）”，与函数 UT 分开呈现，不另加一层测试或重复计数。新补的用例不能冒充编码前设计。

报告先展示改动点 4+1，再展示测试报告。逻辑、开发、进程、物理、场景五个视角以图说明变化：职责关系图、组件依赖图、时序图、部署图、场景活动图。每个变化视角给出实际 PlantUML 图，通常 3～5 张小图；进程与场景完全相同时可明确引用同一张图。沿用或不涉及只写一句具体依据，源码已确认的调用可以画时序图，缺运行日志另在验证结论中说明。

图中用标签和颜色标明新增、修改、删除及必要的既有部分。每图只配一句变化结论和最多两条代码依据/设计偏离说明，4+1 图外说明以 600 字内为目标，省去重复的覆盖表和逐文件解读。测试用例仍完整列出，用证据编号引用表后的统一索引，减少命令、版本和限制的重复。

## 编码前设计及报告依据

以 Story 为主要展示位置，在现有测试设计表中用“用例级别”区分函数 UT 与模块 UT（MST），不新增章节。Spec 保留用例依据；主任务按模块展示可检视的设计，子任务承接并细化。已有实现需要继续修改时，只补充受影响场景，不重新走设计审批。历史用例可能位于 `implementation.md`，应保留来源、按场景核对，不能因文档位置不同遗漏。

报告子会话通过 `delivery_source` 分页读取固定 base/head 之间的改动和源码，通过 `delivery_evidence` 读取生成时冻结的 Spec、Story、实施附录及真实工具记录。它没有 Bash、写业务文件、人工提问或派发子 Agent 的权限。活动 MR 使用共同祖先；合入后保留原始改动起点，补生成时读取建分支记录；没有可靠起点时说明失败，不伪造空改动。

执行证据包括当前版本的流水线结果、平台已保存且版本匹配的原始材料、已有独立验证结果、编码会话和最近三轮独立验证的命令输出。流水线材料总量最多 8 MiB、单文件最多 1 MiB，读取期间版本变化则放弃该次材料；绿灯任务没有保存逐项结果时明确说明。每份事件日志最多读取末尾 8 MiB，保留最近 250 条命令/修改记录；长命令输出保留开头与末尾，裁剪边界交给报告注明。主 Agent 自述不作为测试通过证据。未绑定提交版本的执行记录必须写“执行版本未确认”；旧版本结果、基线预热和套件整体通过不能替代当前版本的逐项验证。

## 生成、恢复与查看

同一任务串行生成，仅处理最新变化，迟到报告不能覆盖新版本。相同提交和验证结果不重复调用模型。每次最多运行 10 分钟；失败保留上一份报告，等待新结果或人工重试。服务关闭中断的报告重启后补跑一次。已完成的历史任务不批量补跑；责任人或管理员可在任务页点击“生成报告”“更新报告”或“重试生成”（`POST /tasks/:id/delivery-report`）。代码现场已回收时仍可阅读已有报告，不能补生成。

成功后原子发布任务根目录的报告，沿用产出文档入口与下载能力，不写业务仓。补生成、更新、重试和生成状态收在“产出文档 → 报告”菜单中，不另占顶部提示条；更新失败时仍可查看上一份报告。小鲁班通知责任人，`deliverySummary=1` 链接直接打开文档；通知失败不撤回报告。继续交付时归档上一份材料，空间清理保留已发布文档。交付经验复盘仍使用真正的首次提交，不能因报告更新而丢失首次到最终版本的差异。

实际生成指令与图渲染检查位于 `src/deliverySummaryAgent.ts`，生成时直接注入报告会话，无需另行调用 Skill。4+1 章节缺图或 PlantUML 语法错误有一次修正机会，其他章节的图或外层代码块内的图不能代替；图数、节点数和文字篇幅由提示词指导，不增加主任务的质量门禁。测试覆盖版本更新、迟到结果、恢复和取消、失败保留、已完成任务补生成及权限、固定版本读码、历史设计读取、Pi 工具调用、真实图渲染与桌面浏览器操作。模型的实际分析质量仍需用真实任务核对；测试中的脚本模型不等于生产报告验收。
