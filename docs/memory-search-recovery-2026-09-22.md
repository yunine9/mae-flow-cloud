# 记忆检索超时修复与验收（#387 / #389）

内网补充证据没有证明 GOAWAY 是搜索超时的主因，也没有用当前检索样本证明服务完全恢复。本次修复针对已确认的代码问题，保留默认 3 秒搜索预算，不修改知识原文、采纳状态、适用范围和检索排序。

## 改动

- 宿主发送请求 ID、发出时间和绝对截止时间。Python 在开始执行、生成查询向量后及后续查询前检查截止时间；过期请求不再执行后续步骤。宿主和 Python 队列均限制在 128 条，繁忙时明确返回不可用，不无限堆积。
- 搜索不再顺便给候选文档生成向量。缺失或已编辑的文档按路径合并为后台索引；先搜索当前已就绪的资料，全部未就绪时明确返回索引准备中，部分就绪时统一知识查询保留范围不完整提示。
- 单个数据库仍只有原来的 sidecar 持有；stdin 由独立读取线程接收，数据库与模型操作仍串行。搜索、健康检查和正文读取优先；长文索引每 8 个片段之间、全库重建每篇文档之间处理等待中的读请求。不通过另起数据库进程解决排队。
- 数据库 RPC 使用剩余请求预算，单次最多 10 秒。不能强行中断正在执行的 ONNX 原生计算；当前小批次完成后检查截止时间，不再开始后续批次，已写入的索引片段可在后续重试复用。
- pymilvus 客户端禁用空闲保活 ping，保活周期为 5 分钟。memsearch 0.4.19 没有暴露连接选项，因此只在独立 sidecar 初始化期间临时包装客户端工厂，并在接收请求前恢复。不编辑 site-packages，不使用未经支持的环境变量，不改变服务端处罚参数。
- 健康检查实际查询数据库。日志记录请求 ID、操作、结果、排队、文档检查、索引批次、查询向量、向量搜索、关键词搜索和数据库调用耗时；不记录查询正文、知识内容或凭据。数据库耗时包含在相关操作耗时中，各字段不能简单相加。

## 本机验证

使用与报告相同的依赖：memsearch 0.4.19、milvus-lite 3.2.1、pymilvus 3.0.1、grpcio 1.83.1，bge-m3 ONNX 离线模型。所有真实测试创建独立临时数据库，不访问生产数据库。

- 默认 3 秒预算连续搜索五次，均命中合成知识；一轮实测 14 / 11 / 11 / 10 / 11 ms。这只是本机小样本，不代表生产 318 篇资料的性能。
- 首次未索引时报告准备中，后台准备完成后可检索；文档更新时不返回旧正文，重新索引后返回新版本。
- 已过期请求不执行，后续有效请求仍可执行；索引批次之间优先处理搜索；队列有界、后台索引去重、请求上下文与截止时间不会互相覆盖。
- 健康检查反映数据库故障，日志不包含查询正文，连接选项仅在初始化阶段生效。
- 原有模块、版本、采纳状态、停用和相关性筛选测试保持通过。

## 内网部署后验证

重启对应服务以加载新 sidecar；不删除数据库或锁文件，不要求重建全部索引。进程首次接触旧索引时会后台检查文档，缺失的片段才重新生成。

登录后在「团队资产 → 试搜知识」连续搜索同一问题五次，或使用现有认证调用 `POST /knowledge-documents/search`，请求体为 `{"query":"具体问题"}`。记录 available、hits 数量、warnings 和总耗时。该入口与任务记忆的候选范围不同，但使用同一个 sidecar。

若仍超时，通过宿主日志的 `id` 对齐 sidecar 的 `memory_request`，区分 `queue_ms`、`index_batch_ms`、`embed_ms`、`dense_ms`、`keyword_ms`、`database_ms`。另外观察长时间运行后的 GOAWAY 频次；本机短时测试不作为生产长时稳定性证明。
