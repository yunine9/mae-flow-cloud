# 执行连续性：入口重启与 Pi 会话恢复

Web 入口与执行服务可以独立运行。重启入口只断开浏览器连接，Pi、子 Agent、运行中的命令、任务容器、流水线与 MR 监听仍由原执行进程持有。

执行服务自身需要升级或异常退出时，需求流和问题流会打开原 Pi 会话文件，带回已落盘的消息、工具结果、子 Agent 报告及压缩摘要。内核 `current` 用于核对流程事实，不再是恢复时仅有的上下文。

## 进程与状态归属

```text
浏览器 / 回调
    │ 原有 HTTP、Cookie、SSE
    ▼
serve.ts：Web 静态页面 + API 转发
    │ runtime-url，写请求不自动重试
    ▼
executionRuntime.ts：原业务 API、鉴权、TaskService、IssueFlowService
    │ 唯一 dataDir 锁与任务状态写入者
    ├─ Pi / 子 Agent / 任务容器
    └─ 宿主操作、内核、流水线与 MR 监听
```

这次没有复制 TaskService 状态，也没有让两个进程同时恢复任务。执行服务仍持有原有鉴权和全部业务 API；入口负责页面与传输。业务 API 或执行逻辑的代码升级仍需更新执行服务，不能只换入口就声称后端修复已生效。页面展示的部署版本来自执行服务。

## 启用独立部署

首次切换需要停止旧单进程服务一次。同一数据目录不能同时运行旧服务与新执行服务。保留原数据，不使用 `--fresh`。

1. 将原完整服务配置复制到部署侧的 `runtime.json`，保留 `data`、鉴权、模型、内核、隔离镜像、平台适配器、回调与所有业务参数。执行服务的监听改为 `127.0.0.1:8786`。对外的 `public-url` 仍指向原入口地址。
2. 独立启动执行服务：`node --import tsx src/executionRuntime.ts --config /etc/mae-flow-cloud/runtime.json`。也提供 `npm run runtime -- --config ...` 供手工启动。
3. Web 入口配置只需要下面这些值，使用原端口：

```json
{
  "host": "127.0.0.1",
  "port": 8787,
  "runtime-url": "http://127.0.0.1:8786"
}
```

4. 使用 `node --import tsx src/serve.ts --config /etc/mae-flow-cloud/web.json` 启动入口。构建后的页面默认读当前版本的 `web/dist`，也可通过 `web-root` 指定。

生产中两个进程必须由独立服务单元守护，不能放在重启时一起清理的进程组或 systemd unit 中；不要配置让执行服务随 Web unit 的重启一起停止。直接用 Node 启动，避免 npm/tsx 包装进程的信号转发差异。反向代理、浏览器、小鲁班回调仍访问原 Web 端口，SSE 继续使用原协议。

**发布目录也要独立且不可变。** 执行服务运行在它自己的固定 release 目录里，更新页面入口不能原地覆盖该目录、其依赖、内核或脚本。否则长会话可能执行到一半新一半旧的文件。更新执行逻辑时另外准备新 release，再计划重启执行服务；本次不热替换运行中的 Pi 代码。

没有配置 `runtime-url` 时，`npm run serve` 保持单进程模式并打印提示：重启仍会中断执行，只能利用原生会话恢复。仅拉代码、不调整部署方式，不会自动获得不中断执行的能力。

## 会话保存与恢复

- Pi 原生 JSONL 位于任务的 `pi-agent/sessions/<身份摘要>/`，绑定任务 ID、会话角色、transcript 路径和真实工作目录。只打开明确绑定的文件，不扫描“最近一次会话”猜测归属。
- 主需求 Agent 与问题会话可恢复；新任务、不同角色和新的专项分析保持独立上下文。已经返回到主会话的子 Agent 报告可复用；执行器中断时尚未完成的子 Agent 如实登记中断，不伪造完成。
- 文件权限为 `0600`、会话目录为 `0700`，沿用 `pi-agent` 的宿主保护边界；不要将其归档到业务代码仓或当成普通文档接口暴露。
- SDK 原生恢复压缩树。保存到首条用户消息，不必等模型完成第一轮。异常断写只修复末尾半行并保留断写原件；中间损坏保留原文件，明确记录恢复失败原因。
- 最新人工答复、插话、批注和执行事实继续由已有宿主恢复路径递交。恢复提示要求按最新决定同步文档、测试、实现；历史目标不能推翻新决定。会话文件是模型上下文，不是审批、推送或流水线事实的权威来源。
- 调用已经有原生结果或事件回执时，带回原结果。确实没有可靠返回的调用标为待核实，要求先查文件、执行日志或远端收据；宿主不会为了填补上下文自动执行它。

## 如实说明的边界

- 入口重启不终止执行服务中的命令；执行器自身重启仍可能中断命令、容器和未完成的模型流。保存上下文不能保证远端副作用恰好执行一次，原有宿主操作收据与幂等核验仍然必需。
- 模型已经返回并落盘的内容可恢复；尚在流式生成、尚未落盘的思考无法跨进程复活。
- 升级前使用内存会话的老任务，没有原生文件，无法恢复已经丢失的对话。平台明确显示“依据现场重建会话”；建立文件后的后续恢复才显示“恢复原会话上下文”。
- SSE 重连可能短暂中断显示；提交请求断线时不自动重发 POST。用户应先查询操作是否已经生效，避免重复决定或重复创建。

## 验证

`tests/executionContinuity.test.ts` 用真实 Node 子进程、实际 Pi SDK、真实 Bash 命令及脚本模型验证：入口进程重启时长命令只执行一次；执行器 SIGKILL 后原工具结果和新决定进入恢复请求；压缩记录与断写恢复；正式执行入口的唯一锁、登录和待确认卡；代理鉴权、SSE、故障 503 与禁止自动重发写请求。

`tests/recovery.test.ts`、问题流、Hook 与压缩用例覆盖待回答卡、用户插话、批注和完成回执的继续处理。这里的模型为可检查请求体的脚本模型；未将内网 GLM、Docker 容器或生产 systemd 部署称为已经完成的实测。
