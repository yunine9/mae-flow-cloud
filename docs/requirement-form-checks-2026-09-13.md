# 需求流文档形式检查清理

本轮只处理需求流第一优先级：减少文件存在、占位词和章节结构检查造成的重复工作。问题流、收据核验、检视交接状态机未改动。

## 最终行为

- `done` 不再执行文档形式检查；旧 flow 定义仍能读取，显式诊断仍可使用。执行方案不再把这些检查列为机器证据要求，原有产物指引保留。
- 写入文档后不再运行模板章节比对，相关比对实现已删除。Hook 仍登记文件写入、用户回答、Agent 生命周期和实际命令执行。
- `current` 不再重放旧任务中的同类形式提示，不改写旧任务数据；实际质量诊断继续展示。
- Spec 步骤改为内容自查，`local-spec validate` 保留为按需结构诊断。Cloud 的 TS 启动指引要求按用户原话核对范围、行为、验收条件和真实未决事项，新建及恢复会话均接入。

保留真实用户决定、路径权限、分支与推送核验、编译/UT 记录、流水线版本关联及现有质量诊断。没有把“未检查格式”记成“质量通过”。

## 验证

内核定向回归覆盖：不执行旧定义中的形式检查、真实流水线失败仍拒绝、缺少人工确认仍拒绝、手动 Spec 诊断、写入登记、旧提示恢复、质量提示保留及执行方案。

Cloud 定向回归 37 项通过，覆盖真实需求会话、跨进程审批恢复、Git 重定向、检视决定，以及新建和恢复后的模型请求确实包含自查指引。同步快照后类型检查、Web 构建和契约测试通过（134 通过、1 项真实容器用例因环境条件跳过）。

内核完整自检有既存行数限制失败：`delivery_commands.py` 为 572 行，超过 500 行。修改前后该文件相同，本轮不通过放宽限制或无关拆分消除该项。

本地验证不代表内网已部署，也没有测量生产耗时改善比例。发布使用随 Cloud 同步的内核快照，无新增 adapter 配置或部署脚本。
